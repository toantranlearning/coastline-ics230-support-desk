2Design flaws and implementation flaws

Most security fixes change code that does the wrong thing. This module is about code that does exactly what it was designed to do, where the design itself was wrong. The difference decides who can find the problem and how it gets fixed.

Picture a small billing site. A signed-in customer opens a page to read one of their invoices. The page picks the invoice from the number in the URL.

GET /invoice.php?id=1043 HTTP/1.1
Host: billing.example.com
Cookie: PHPSESSID=b7e2c1a9f04d5e6f

Here is the code behind it. Read it looking for a coding mistake.

✕PHPVulnerable
<?php
// WHY: A prepared query controls SQL syntax but does not enforce ownership when the required owner condition is absent.
require 'auth.php';
require_login();

// The invoice id comes straight from the URL and is the only thing that selects the row.
$invoiceId = $_GET['id'] ?? '';

$statement = $pdo->prepare('SELECT * FROM invoices WHERE id = :id');
$statement->execute(['id' => $invoiceId]);
$invoice = $statement->fetch(PDO::FETCH_ASSOC);

render_invoice($invoice);

Vulnerable. Why: A prepared query controls SQL syntax but does not enforce ownership when the required owner condition is absent.

The query is parameterized, so there is no SQL injection. The request needed a valid session, so a stranger cannot reach it. Every line is careful. Now change the number in the URL to 1044, an invoice that belongs to a different customer. The page hands it over.

Response
HTTP/1.1 200 OK
Content-Type: text/html

Invoice 1044   Customer: Dana Okafor   Amount due: $2,150.00

The code never asked the question that mattered: may this customer read this invoice? The design said, in effect, that any signed-in customer may ask for any invoice by number. The code did that perfectly. This is an authorization bypass through a user-controlled key (CWE-639). The key is the id in the URL.

★A design flaw can be implemented perfectly

A control that was never specified cannot be added by writing more careful code. The code is already doing what it was told. The rule "this invoice belongs to this customer" lives in a policy, not in any line of PHP. Until someone writes it down as a requirement, every developer who touches the feature will leave it out, and each of them will be right to.

◆Implementation flaw, design flaw

An implementation flaw is code that fails to do what the design intended. You fix it by changing the code, and a tool that reads the source can often spot it. A design flaw is code that does exactly what the design intended, where the intent was missing or wrong. You fix it by changing the design, which usually means adding a rule nobody wrote down. No tool can find it, because the rule it would check for is not there to be read.

OWASP A06 Insecure Design is the category for the second kind. Its text draws the same line. A secure design can still have implementation bugs. An insecure design cannot be fixed by a perfect implementation, because the control was never created. Threat modeling is the discipline that finds such rules before they are scattered, inconsistently, through twenty PHP pages.

CWE-639: Authorization Bypass Through User-Controlled Key (opens in a new tab) is the formal entry. It describes a system that "does not prevent one user from gaining access to another user's data or record by modifying the key value identifying the data." The A06 page in section 1 is the source for the design-versus-implementation distinction.

3The four questions of threat modeling

Threat modeling has collected a lot of ceremony over the years. Underneath it are four questions. You would ask the same four about a bridge, a checkout counter, or a login form.

  1. What are we working on?
  2. What can go wrong?
  3. What are we going to do about it?
  4. Did we do a good enough job?

Question 1 is answered by a diagram of one feature, which is section 4. Question 2 is answered by walking a checklist across that diagram, which is STRIDE in section 5. Question 3 maps a control to each threat worth acting on, which is sections 6 to 9. Question 4 is the one teams skip. It turns an opinion into engineering. "Use authorization" is not an answer to question 4. It becomes one when the team names which people may take which actions on which records, then writes a test for an allowed case and a denied case.

iWhy question 2 needs structure

Asked cold, "what can go wrong?" produces whatever the loudest person in the room fears that day. The diagram and the checklist exist so the question is asked about a specific flow and a specific security property. That is what lets someone other than the author repeat the exercise and reach the same list.

The four questions come from the Threat Modeling Manifesto (opens in a new tab), which states them in exactly these words. It defines threat modeling as "analyzing representations of a system to highlight concerns about security and privacy characteristics." The OWASP cheat sheet in section 1 builds its whole structure on the same four.

4Decompose the feature into a data-flow diagram

You cannot reason about "the application." You can reason about one feature. Take the invoice page from section 2 and write down how a request moves through it.

Browser  ->  GET /invoice.php  ->  session check  ->  invoices table  ->  invoice PDF store

A data-flow diagram names five kinds of thing and draws the lines where trust changes. Here is that inventory for the invoice feature.

4. Decompose the feature into a data-flow diagram. Columns: Element, What it is, In the invoice feature.
ElementWhat it isIn the invoice feature
Actorswho or what starts a flow, inside or outside your controlanonymous visitor, signed-in customer, billing administrator, the payment provider
Assetswhat has value, and so what an attacker wantsinvoice contents, customer identity, the amount owed, session integrity, the billing page staying up
Entry pointsevery place data can arrivethe id in the URL, the session cookie, request headers, any posted form field
Processescode that transforms or decidesthe PHP route, the session handler, the authorization check, the database layer
Data storeswhere state persiststhe invoices table, session storage, the PDF file store, the access log

◆Data-flow diagram

A data-flow diagram is a picture of one feature. Boxes stand for the processes and stores. Arrows show the data moving between them, each with a label for what it carries. A dashed line marks each trust boundary. Anything crossing a boundary must be checked on the far side, because a boundary is exactly where your ability to enforce a rule stops.

iThe vocabulary you already have

Module 01 section 4 drew the first trust boundary, browser to server, and section 5 gave you source, sink, and flow. A data-flow diagram is that same analysis drawn for a whole feature instead of one line. The browser-to-server line is the obvious boundary. PHP trusting what the database returns is also one. PHP trusting its file store, its log service, or the payment provider are boundaries too. Draw every line where you stop being able to enforce something.

Where do the lines go? Everywhere data passes from a place you control to a place you do not, or back.

A data-flow diagram does not need artistic detail. Boxes, arrows, labels, and boundary lines are enough when they make the assumptions visible. The diagram is not the deliverable. The argument the team has while drawing it, about which arrow is really checked, is the deliverable.

OWASP: Threat Modeling Process (opens in a new tab), now marked historical, is the source for the element names. It says entry points "define the interfaces through which potential attackers can interact with the application." It says a data-flow diagram highlights "the privilege or trust boundaries." The cheat sheet in section 1 names the same elements: trust boundaries, data flows, data stores, processes, and external entities.

5Apply STRIDE to the flow

STRIDE is a checklist of six things that can go wrong. Each one is the opposite of one security property. Walk it across every element and every arrow in your diagram. It prompts questions you would not otherwise think to ask.

5. Apply STRIDE to the flow. Columns: Category, Property it violates, Invoice-feature example.
CategoryProperty it violatesInvoice-feature example
SpoofingAuthenticationa stolen session cookie is accepted as the customer, because holding the cookie is treated as identity
TamperingIntegritythe customer edits the id in the URL to another customer's invoice (CWE-639)
RepudiationAccountabilityan invoice is downloaded and nothing records who asked for it or when
Information disclosureConfidentialitya verbose PHP error shows a file path, or a refusal confirms that an invoice number exists
Denial of serviceAvailabilitya script asks for thousands of PDF renders and exhausts the server
Elevation of privilegeAuthorizationthe request body carries role=admin and the server honors it, which is improper privilege management (CWE-269)

Take the single arrow from the browser to GET /invoice.php and ask all six questions of that one arrow.

▸Six questions against one arrow

  1. Spoofing: can a request arrive with someone else's session cookie, and what makes a stolen cookie hard to replay?
  2. Tampering: can the id name an invoice this customer does not own, and what rejects it?
  3. Repudiation: if the invoice is downloaded, does anything record who downloaded it and when?
  4. Information disclosure: does a failed lookup ever show the query, a file path, or the fact that the invoice exists?
  5. Denial of service: is there a rate limit on the route and a ceiling on how many renders one session can trigger?
  6. Elevation of privilege: is there a field in the request that raises the caller's authority, and does the server ignore it?

Six prompts against one arrow produced six requirements. None of them needed you to already know what the vulnerability was. That is what the technique buys you.

!STRIDE is a prompt, not a proof

Work through the six letters for each box and arrow. Then add the threats that fit no letter. Business-logic abuse usually needs plain reasoning rather than a mnemonic. An invoice that can be refunded twice. A discount that stacks with itself. An order that can be edited after approval. None of those is a STRIDE category, and each is a real incident someone has had. A list of STRIDE hits with no diagram, no ranking, and no verification is a brainstorm, not a threat model.

Microsoft: STRIDE model (opens in a new tab) is the original vendor's description of the six categories, from the team that introduced them. The OWASP cheat sheet in section 1 gives the property each one violates, and names repudiation's property "accounting."

6From a threat to a security requirement

A threat written as a worry cannot be closed. A threat written as an abuse case can be tested, assigned, and argued with.

◆Abuse case

An abuse case is a threat described from the attacker's side, in enough detail that someone can build against it and test it. It records the attacker's goal, what they need first, the steps, the asset affected, the control expected, and how to verify the control.

Here is the abuse case for the invoice feature. A signed-in customer changes id in /invoice.php?id=1043 to another customer's number. The route fetches the invoice without checking ownership, so one customer reads another's billing data. The asset is invoice confidentiality. The expected control: the lookup selects an invoice only when it belongs to the current session. The verification: two accounts; the owner succeeds, and the other customer is refused without learning whether the invoice number exists.

Notice how much more specific that is than "add authorization." The test names two accounts and two outcomes. It also carries one subtle requirement: the refused customer must not learn whether the invoice exists. That is a design decision someone had to make on purpose. A uniform 404 response can avoid explicitly confirming that an inaccessible record exists; other response differences still need review.

◆Security requirement

A security requirement is a sentence about what the system must do, or must refuse to do, that someone else can verify. It is written like any other requirement, with "must," and it traces back to the threat it answers. "The application must be secure against broken access control" is a wish. Here is a requirement: "A request for an invoice whose customer does not match the signed-in session must return 404. Its response should minimize observable differences between a missing and an unauthorized record. It must be logged with the requesting account." If two engineers could disagree about whether the code meets it, keep rewriting until they cannot.

How does a threat turn into something that can pass or fail? Each step below is more specific than the one before it.

The requirement drives the fix. The lookup carries the ownership rule. The type of the id is checked before use. A request for an invoice the customer does not own gets the same 404 a missing invoice would, so the status and body do not confirm whether the row exists. This alone does not establish timing equivalence.

✓PHPSecure
<?php
// WHY: Placeholders keep bound values separate from the SQL statement structure.
require 'auth.php';
$currentUser = require_login();

$invoiceId = filter_input(INPUT_GET, 'id', FILTER_VALIDATE_INT);

if ($invoiceId === false || $invoiceId === null) {
    http_response_code(400);
    exit('Invalid request');
}

// Ownership is part of the lookup, so a row for another customer is never selected.
$statement = $pdo->prepare(
    'SELECT * FROM invoices WHERE id = :id AND customer_id = :customer'
);
$statement->execute([
    'id'       => $invoiceId,
    'customer' => $currentUser['id'],
]);
$invoice = $statement->fetch(PDO::FETCH_ASSOC);

if ($invoice === false) {
    http_response_code(404);
    exit('Not found');
}

render_invoice($invoice);

Secure. Why: Placeholders keep bound values separate from the SQL statement structure.

▸Tracing the two accounts through the code

  1. Dana owns invoice 1044 and asks for it. The query matches on both id and customer_id, returns the row, and the page renders.
  2. Rae asks for 1044. The query matches on id and fails on customer_id, so fetch returns false. The route answers 404 with Not found.
  3. Rae asks for 9999, which does not exist. The query returns no row. The route answers the same 404 with the same text.
  4. Rae cannot tell case 2 from case 3, so the refusal reveals nothing about which invoice numbers exist.

A requirement is closed by a test that runs and passes, not by a sentence in a document that asserts it. The OWASP Application Security Verification Standard (opens in a new tab) is where professional teams get requirements phrased this way. It describes itself as "a list of requirements for secure development." The A06 page in section 1 says the same from the other direction: "Add security language and controls to user stories."

The functions in the code have their own pages. PHP Manual: PDOStatement::execute (opens in a new tab) documents passing the array of named values. PHP Manual: http_response_code (opens in a new tab) sets the status. MDN: 403 Forbidden (opens in a new tab) confirms the 404 choice. A server "may decide to send a 404 response instead of a 403 if acknowledging the existence of a resource to clients with insufficient privileges is not desired." The OWASP Abuse Case Cheat Sheet (opens in a new tab), now archived, has the record format behind the abuse-case definition.

7Secure software architecture

Requirements say what must be true. Architecture decides where each rule lives so that it is true everywhere.

◆Secure software architecture

Software architecture is the arrangement of an application's parts and the rules about which part talks to which. The parts are the pages, the shared code they include, the data stores, and the web server in front of them. A secure software architecture places each security control in one spot that every request has to pass through. It places data where nothing can reach it except that spot. It is decided before the code, because it is the one thing the code cannot fix later.

Three architecture decisions decide most of what a PHP application can be made to do.

  • Where a control lives. A check written inside each page is written twenty times and forgotten once. A check in one shared function, which every page calls first, is written once and reviewed once. The portal's own design document names three shared includes, db.php, auth.php, and layout.php, that every page requires. That is the spot where a shared check belongs.
  • Where data lives. A web server hands out any file under its published folder, and no PHP runs when it does. The portal's router.php says so in a comment: anything that exists in the project folder is served as it is. Data that sits there is reachable by anyone who knows or guesses its address.
  • What each part is allowed to do. The database account a page uses, the folders PHP can write, the routes the server exposes. Each one is a ceiling on damage.

Where a file lives decides whether any check runs at all. Here is the invoice PDF stored under the published folder, with the page linking straight to it.

✕PHPVulnerable
<?php
// WHY: A predictable public file URL can bypass the application route that was supposed to enforce access.

require 'auth.php';
require_login();

// The PDF sits in webroot/files/, which the server publishes.
// This link works for anyone who has it, signed in or not.
$id = (int) ($_GET['id'] ?? 0);
echo '<a href="/files/invoice-' . $id . '.pdf">Download PDF</a>';

Vulnerable. Why: A predictable public file URL can bypass the application route that was supposed to enforce access.

Response
GET /files/invoice-1044.pdf HTTP/1.1

HTTP/1.1 200 OK
Content-Type: application/pdf

No PHP ran for that second request. The server found a file and sent it. Here is the same feature with the PDFs in a folder the server never publishes, and the page as the only way in.

✓PHPSecure
<?php
// WHY: Placeholders keep bound values separate from the SQL statement structure.
require 'auth.php';
$currentUser = require_login();

$invoiceId = filter_input(INPUT_GET, 'id', FILTER_VALIDATE_INT);
if ($invoiceId === false || $invoiceId === null) {
    http_response_code(400);
    exit('Invalid request');
}

// The ownership rule runs here, on every request, because there is no other path to the file.
$statement = $pdo->prepare(
    'SELECT pdf_name FROM invoices WHERE id = :id AND customer_id = :customer'
);
$statement->execute(['id' => $invoiceId, 'customer' => $currentUser['id']]);
$row = $statement->fetch(PDO::FETCH_ASSOC);

if ($row === false) {
    http_response_code(404);
    exit('Not found');
}

// storage/ is beside the published folder, not inside it.
header('Content-Type: application/pdf');
readfile(__DIR__ . '/../storage/invoices/' . $row['pdf_name']);

Secure. Why: Placeholders keep bound values separate from the SQL statement structure.

✓The pattern to copy

Put every control in one shared place that every request passes through. Put every data file outside the folder the server publishes, so the only way to it is through your code. Give each part of the application the least it needs: the database account, the writable folders, the exposed routes. Decide these three things before writing pages, and write them down in the design document.

iThe module's own incident is an architecture decision

The incident behind this module is an unauthenticated actor downloading the portal's database through a data directory the web server was handing out. The portal's db.php builds data/portal.sqlite inside the project folder, from data/seed.sql beside it, and router.php serves any file that exists in that folder. That is storage of a file with sensitive data under the web root (CWE-219), and the related weakness is files or directories accessible to external parties (CWE-552). Neither is a typo in a function. Both are decisions about where data lives and what the server exposes.

OWASP Proactive Controls, C4: Address Security from the Start (opens in a new tab) is the source for the first paragraph. It says "creating a secure architecture prevents vulnerabilities before they even become part of the application." It calls a secure architecture pattern "a standard solution that has been reviewed and hardened against known security threats." PHP Manual: readfile (opens in a new tab) documents the function that sends the file, and W3Schools: PHP readfile() Function (opens in a new tab) has a runnable example.

8Secure-design principles

The choice of control is not invented fresh each time. A short list of principles guides it. Saltzer and Schroeder wrote them down in 1975, and they have survived every change of platform since. That is a fair sign they describe something structural.

Least privilege

Give PHP, its database account, and each user only what the job needs. A page that reads invoices does not need a database account that can drop tables. A customer role does not need the actions a billing administrator has. When something goes wrong, the privileges in force are the ceiling on the damage. A request that carries its own elevated role and is believed is the opposite of this principle, and it is improper privilege management (CWE-269).

Fail-safe defaults

Start from denial. If a role is missing, a policy lookup fails, or a session is invalid, the protected action does not run. Write the gate so that the allow path is the only path that reaches the action.

✓PHPSecure
<?php
// WHY: The rejection branch must stop or exclude further processing so denied input cannot reach the protected operation.
// Deny by default: the allow branch is the only path that reaches the action.
if (!$policy->allows($currentUser, 'read', $invoice)) {
    http_response_code(404);
    exit('Not found');
}

stream_invoice_pdf($invoice);

Secure. Why: The rejection branch must stop or exclude further processing so denied input cannot reach the protected operation.

The inverted version looks the same and is not.

✕PHPVulnerable
<?php
// WHY: A response status alone does not prevent subsequent protected statements from running.
// If the policy call returns null, this rejection condition is false and execution continues. An uncaught exception stops execution.
if ($policy->denies($currentUser, 'read', $invoice)) {
    http_response_code(404);
    exit('Not found');
}

stream_invoice_pdf($invoice);

Vulnerable. Why: A response status alone does not prevent subsequent protected statements from running.

What happens to each gate when the policy lookup fails? Run both against a policy that returns null, which is what a failed lookup often returns.

PHP
<?php
// A policy object whose lookup failed. It returns null instead of true or false.
class Policy
{
    public function denies(string $user, string $action, int $invoice): ?bool
    {
        return null;   // the lookup failed; nobody decided
    }

    public function allows(string $user, string $action, int $invoice): ?bool
    {
        return null;   // the same failed lookup
    }
}

$policy = new Policy();

// Deny-first gate: the action runs unless the policy says "denied".
if ($policy->denies('rae', 'read', 1044)) {
    echo "Deny-first gate: refused\n";
} else {
    echo "Deny-first gate: invoice streamed\n";
}

// Allow-first gate: the action runs only when the policy says "allowed".
if (!$policy->allows('rae', 'read', 1044)) {
    echo "Allow-first gate: refused\n";
} else {
    echo "Allow-first gate: invoice streamed\n";
}
Output
Deny-first gate: invoice streamed
Allow-first gate: refused

✕An inverted gate fails open, and it fails silently

When the policy returns null, the deny-first gate treats "nobody decided" as "not denied" and streams the invoice. There is no error in the log and no symptom in testing, because the happy path still works. The failure shows up only when the policy layer has a bad day, which is the worst time to learn that refusal was never the default.

✓Refusal is the default, and the allow path is explicit

The action runs only after an affirmative yes from the policy. Anything else, including an error or a missing answer, lands on refusal. This is the shape to copy for every protected operation.

Complete mediation

Check authorization on every protected request, on the server. Hiding a button in the page is a user-interface choice, not a control. Module 01 section 4 explained why: the browser is the attacker's computer, and a request can be typed by hand without your page ever loading. The same reasoning rejects any authority the client claims about itself.

✕PHPVulnerable
<?php
// WHY: A role chosen by the requester is a claim, not an authoritative permission decision.

// The request states its own role, and the server believes it.
$role = $_POST['role'] ?? 'customer';

if ($role === 'admin') {
    delete_invoice($_POST['id']);
}

Vulnerable. Why: A role chosen by the requester is a claim, not an authoritative permission decision.

✓PHPSecure
<?php
// WHY: The rejection branch must stop or exclude further processing so denied input cannot reach the protected operation.
$currentUser = require_login();

// The role is read from the server's session record, never from the request body.
if ($currentUser['role'] !== 'admin') {
    http_response_code(403);
    exit('Request denied');
}

delete_invoice($_POST['id']);

Secure. Why: The rejection branch must stop or exclude further processing so denied input cannot reach the protected operation.

A protected action reached with no server-side authorization check at all is missing authorization (CWE-862). It is one of the most common design gaps in real applications.

Separation of privilege

The highest-impact actions may require two independent conditions: an administrator role together with a recent second factor, or a requester plus a separate approver. One stolen credential should not be enough for the worst thing the system can do. Many teams call this separation of duties.

Defense in depth

No single control is trusted to be perfect. The invoice fix in section 6 carries ownership in the query. The gate above adds an explicit policy check. Least privilege on the database account caps what a slip could reach. Each layer is chosen so that a failure in one does not expose the asset on its own.

Minimize the attack surface

Every entry point, parameter, and served file is something an attacker can reach and you must defend. Remove the ones the feature does not need. A debug parameter, an unused admin route, or a data file in a web-served directory each widen the surface for no benefit.

Secure defaults

The safe configuration is the one that ships. Cookies carry HttpOnly and Secure out of the box, error display to the browser is off in production, and a new account starts with the least authority rather than the most. Security that depends on someone remembering to turn it on is security that is off.

Open design

The security of a system should not depend on hiding the PHP filename, the database schema, or the algorithm. Keys and credentials are secret. The design should stay safe when its operation is fully known. Obscurity can raise an attacker's effort, but it must never be the thing holding the door shut.

Economy of mechanism

Keep the design as small and simple as it can be. A control nobody can explain in a sentence is a control nobody can review.

Saltzer and Schroeder, The Protection of Information in Computer Systems, section I.A.3 (opens in a new tab) is the 1975 source. Its wording for fail-safe defaults is "base access decisions on permission rather than exclusion." For complete mediation it says "every access to every object must be checked for authority." CWE-862: Missing Authorization (opens in a new tab) and CWE-269: Improper Privilege Management (opens in a new tab) are the formal entries for the two code examples.

9Rank and treat the threats you find

A real pass produces more threats than a team can address at once. Ranking turns the list into a plan. For each threat, record the fields below.

9. Rank and treat the threats you find. Columns: Field, Why it is there.
FieldWhy it is there
Likelihood, with reasoningthe reasoning is what survives review; the label on its own is not evidence
Impact, on which asset and on which of confidentiality, integrity, availabilitynames what is actually lost, which is what a non-specialist asks first

Risk is likelihood multiplied by impact. OWASP's rating method scores each from 0 to 9 and calls the result low below 3, medium from 3 to 6, and high from 6 to 9. Numbers do not create truth. A plain high, medium, or low with a clear reason is more useful than a precise-looking score built from guesses, because the reason is the part a reviewer can disagree with.

◆Residual risk

Residual risk is the portion of risk that remains after a control has been applied. A control shrinks a risk; it rarely removes it. The ownership rule in section 6 stops one customer reading another's invoice. It does nothing about a billing administrator whose account may read every invoice. That leftover is the residual risk, and it gets its own line, its own treatment, and its own owner.

What is left once the control is in place, and who decides what to do with it?

The four treatments are the cheat sheet's. Mitigate adds a control that lowers likelihood or impact. Eliminate removes the feature or the data so the threat has nothing to act on. Transfer moves the cost to someone else, such as an insurer or a vendor. Accept records that the risk stays, with a reason and a name. A threat you have identified, priced, and consciously accepted is in better shape than one you mitigated by reflex without asking what it cost. What is never acceptable is silent acceptance, where nobody decided and nobody can say who would have.

Here is one row from a threat register, written so that it can be checked.

Threat:        a signed-in customer reads another customer's invoice by changing id
Likelihood:    high; the id is visible in the URL and sequential
Impact:        high; confidentiality of every invoice
Priority:      1
Treatment:     mitigate
Control:       lookup by id AND customer_id; uniform 404; log the account
Residual risk: a staff account that may read all invoices can still be misused
Owner, date:   billing team, end of sprint 21
Test:          two accounts; owner gets 200, other customer gets 404 and a log line

▸The strongest treatment is a control with an owner and a test

Compare two treatments for the same threat. The weak one reads "use authorization." The strong one is the register row above: a named control, a residual risk stated, an owner, a date, and a test someone who was not in the room can run. Only the second can be built, checked, and re-run.

OWASP Risk Rating Methodology (opens in a new tab) is the source for likelihood times impact, the 0 to 9 scale, and the three bands. It also says "not all risks are worth fixing." NIST glossary: residual risk (opens in a new tab) gives the definition used above, "portion of risk remaining after security measures have been applied." NIST traces it to SP 800-30 Rev. 1. The cheat sheet in section 1 names the four responses: mitigate, eliminate, transfer, accept.

10Incident-response basics

Threat modeling is what you do before the worst day. Incident response is what you do on it. The two share one idea: a plan written down and tested is worth more than a plan improvised under pressure. The words below are the ones the TC-IR-01 form and TechCorp's runbook use, and every incident report in this course is written with them.

What an incident is

◆Event, security incident, Discovery

An event is anything observable that happens on a system: a sign-in, a request for a page, a firewall blocking a connection. A security incident is a violation, or an imminent threat of violation, of a security policy, an acceptable-use policy, or standard security practice. TechCorp's runbook narrows it to its own case. There, an incident is any actual or reasonably suspected unauthorized access to, taking of, change to, or destruction of customer data or the systems that hold it. Discovery is the earliest moment anyone at the company knew, or reasonably should have known, that an incident had happened. Discovery starts the clock on every deadline that follows.

Slow pages, one PHP error, a forgotten password, and a scanner alert on its own are events. None of them is an incident until someone shows unauthorized access or change. A scanner alert is a claim, and a claim is verified before anything is declared.

◆Carrier, Breach Response Unit, panel counsel

The carrier is the company's cyber insurance company. Its policy pays for the expensive parts of a breach, such as forensics, lawyers, and customer notification. It pays on one condition: the company follows the carrier's playbook. That starts with telling the carrier within a fixed window after Discovery. The carrier's Breach Response Unit is the desk you call. Panel counsel are the lawyers the carrier supplies; privacy counsel decides whether customers must be notified. No public statement goes out without the carrier's written consent, because a wrong statement can void the coverage.

A runbook and a playbook

◆Playbook, runbook

A playbook is the broad plan for a kind of incident. It says who holds which role, what the phases are, who may decide to take a system offline, and who may speak outside the company. It is written for a whole team and for a class of situation. A runbook is the step-by-step procedure for one task on one system, written for the person at the keyboard. How to take the preservation copy. How to clear the session store. How to rotate every credential in the database. A playbook points at runbooks. The two words are not standardized, and some teams swap them, so a company defines them for itself.

In this course the carrier's Incident Response Playbook sets the minimum any insured company must meet. TechCorp's runbook turns that minimum into steps for three people, one server, and a support desk that opens at seven. The runbook carries roles too, so it borrows from both shapes. That is normal for a small team with one document.

Who does what

An incident needs a few jobs done at once, and each job needs one named person. The names vary by company. The jobs do not.

◆Incident Commander, IC log, holding statement

The Incident Commander (IC) is the single person directing the response. There is exactly one at any time. The IC decides, including whether the system goes offline, and delegates every repair action rather than doing it. The IC log is the running record the IC keeps: one line per action, with the time and the person, written as it happens rather than from memory afterward. A holding statement is the short, approved text the support desk may read to callers while the facts are still being established. The desk may repeat it; it may not add to it.

On a three-person team the IC and the person doing system actions may briefly be the same person. The second person joins as soon as they are reachable, because the IC should be deciding, not typing. A named alternate takes over the IC role if the first person cannot be reached within a set time.

Severity tiers

A severity is a label chosen at Discovery that sets the commitment: who is called, how fast, and whether people are woken up. It is a decision about response, not a measurement of the attacker. The IC assigns it with one sentence of justification, and revises it as the facts change.

Severity tiers. Columns: Tier, What it usually means, What it commits the team to.
TierWhat it usually meansWhat it commits the team to

NIST names three things that decide where an incident lands. The functional impact is what the business can no longer do. The information impact is what data was read, changed, or taken. Recoverability is how much effort it takes to get back. A tier definition that leaves a real finding fitting two rows is itself a defect in the runbook.

!When you are unsure, choose the higher tier

Argue the tier at the review afterward, not during the incident. A tier chosen too low delays the carrier call and the containment. A tier chosen too high costs a few hours of attention. The costs are not symmetric.

The lifecycle

NIST SP 800-61 Revision 2 described four phases: preparation; detection and analysis; containment, eradication, and recovery; and post-incident activity. Revision 3, published in April 2025, supersedes Revision 2 and integrates incident response with the NIST Cybersecurity Framework 2.0. TechCorp's fictional runbook retains the historical Revision 2 phase names. The Orientation incident-reporting guide explains how this course relates to the current guidance.

Which section of the incident report belongs to which phase?

Preparation is everything that exists before the incident. The roles, the contact card, the runbook, and the blank report form. Logging that records enough to reconstruct what happened. Backups that have been restored at least once. All of it is cheap before an incident and impossible to create during one.

Detection and analysis starts at Discovery. Someone reports what they saw and writes down the time. The IC is designated, a severity is assigned, and evidence is preserved before anything is changed. An analyst establishes what happened and what condition allowed it. The analysis also records what it could not determine and why.

Containment limits ongoing harm without yet removing the cause: a deny rule in front of the affected path, the portal taken offline, every session invalidated, every credential rotated. NIST's own words: containment "provides time for developing a tailored remediation strategy." It happens before the analyst's determination is in, because it cannot wait for it.

Eradication removes the cause. NIST describes it as eliminating the components of the incident and identifying and mitigating the vulnerabilities that were exploited. The fix is written as pseudocode first, so that what moves, what changes, and what fails closed is the decision that gets reviewed. Then the code. A second person reviews both before anything is deployed. Then the fix is verified by checks that are annotated with what each one proves and what it does not.

Recovery restores service in a controlled order and applies heightened monitoring for a set period, so that a recurrence is seen. At the end of the period the remediation is confirmed still to hold under test. Only the IC declares the incident closed, and only when the written report is finished.

Post-incident activity is the lessons-learned meeting, held within days of closure. It is blameless: its subject is the system conditions that permitted the incident, never the individuals involved. Every corrective action leaves the meeting with a named owner and a target date. The gaps that slowed the investigation are findings too, and they feed the next round of preparation.

◆Blameless review, corrective action, root cause

A blameless review is the post-incident meeting whose subject is what condition permitted the incident, not which person. A corrective action is one change that comes out of it, with a named owner, a target date, and a status. The root cause is the condition that, had it been different, would have prevented the incident. It is stated in one plain sentence. A report that cannot state it is not ready to close.

Mitigation and remediation

◆Mitigation, remediation

A mitigation is a temporary reduction of a vulnerability's impact or of the chance it is exploited. The cause is still there. A remediation removes the vulnerability itself. A deny rule in front of an exposed folder is a mitigation. Moving the folder out of the server's reach is a remediation. Containment is built from mitigations. Eradication is the remediation.

Here is a mitigation for the billing site's exposed PDF folder from section 7, placed in the router that the built-in server runs for every request. It buys time. It removes nothing.

✓PHPSecure
<?php
// WHY: The rejection branch must stop or exclude further processing so denied input cannot reach the protected operation.
// Stopgap: refuse any request whose path starts with the exposed folder.
// This is a MITIGATION. The files are still under the published folder.
$path = parse_url($_SERVER['REQUEST_URI'] ?? '/', PHP_URL_PATH) ?: '/';

if (str_starts_with($path, '/files/')) {
    error_log('deny rule: ' . $path);
    http_response_code(403);
    exit("Forbidden\n");
}

Bash
mv webroot/files app-root/storage/invoices

What does each one change, and what does each one leave behind?

✕A mitigation recorded as a fix closes a finding that is still open

The deny rule depends on one line of configuration surviving every future deployment. Delete the line, and the incident is back, with no error and no symptom until the next download. Write every stopgap down as a mitigation, say what it does not protect against, and keep the finding open until the cause is removed and verified. The way to tell the two apart is a test: switch the mitigation off and run the attack again. If it still fails, you have a remediation.

Keep the mitigation in place after the remediation. It is now a second layer, which is defense in depth from section 8, rather than the defense.

Preserve the evidence first

Before anyone changes anything, copy what is there. NIST's guidance is to acquire evidence from a system as soon as one suspects an incident. Keep a log of each item. The log records what the item is and where it came from, who collected it, the time and date with the time zone, and where it is stored. A rebuild that feels decisive destroys the answers to the only questions that matter: how the actor got in, what they reached, and whether they are still there.

Bash
# Preservation copy: keep the original timestamps, then record a hash of the copy.
cp -p webroot/data/seed.sql incident/seed.sql.2026-08-24T0920
sha256sum incident/seed.sql.2026-08-24T0920 | tee incident/hashes.txt
Output
c8b067e1671583177155c17517dc85450e213e9c188a7d2a483005d38671a702  incident/seed.sql.2026-08-24T0920

cp -p keeps the file's original modification time, which is itself evidence of when it last changed. The hash lets anyone later prove the copy is the one taken that morning. The matching line in the IC log reads like this.

2026-08-24 09:20 PT  team lead  preservation copies of the application directory and
                                data/portal.sqlite taken into the incident folder;
                                hashes recorded in incident/hashes.txt

!Cleaning up first is the mistake people make

The instinct on a bad morning is to delete the strange file, restart the server, and change the password. Each of those destroys a record. Preserve, then contain, then change. If in doubt, isolate the machine rather than power it off.

◆Earliest established activity, the determination, exfiltration

The earliest established activity is the earliest moment the analyst could prove the actor was present. It is not the same as the earliest moment the actor was present, and a report says "earliest established" for that reason. The determination is the analyst's written statement of what happened and what condition allowed it. The report restates it in the writer's own words. A writer who cannot restate it does not yet understand the fix. Exfiltration means data was copied out of the system. Repairing the flaw does not un-take copies already made, which is why credentials are rotated even after the files are moved.

◆Change record, second-person review, annotated confirmation, closure

A change record is the written entry for one change to the system: what changed, who made it, when, and who reviewed it. Second-person review means someone other than the author read the pseudocode and the code before deployment. An annotated confirmation is a verification check with a sentence stating what it proves and what it does not, so a reader can trust it without re-running it. Closure is the IC's declaration that the incident is over, made only when recovery is complete and the report is finished. The incident file is kept for years afterward, because the carrier and the law may ask for it.

What OWASP A09 names

The incident report's section 5.3, what the analysis could not determine, is usually long on a system that records little. OWASP has a category for that condition. Auditable events such as sign-ins, failed sign-ins, and high-value transactions are not logged, or are logged inconsistently. Logs are not monitored for suspicious activity. The application cannot detect, escalate, or alert in near real time. Alerts cannot be handled because "the playbook for the use case is incomplete, out of date, or missing." No incident response and recovery plan has been established or adopted. When a runbook limit is a recording gap, that is the category to cite by name.

11Common misconceptions

  • ✕"STRIDE is the threat model."

    STRIDE is one prompt inside a larger process. A list of STRIDE hits with no diagram, no ranking, and no verification is a brainstorm, not a model.

  • ✕"We threat-model once, at the start."

    Update the model when the data flows, roles, dependencies, or deployment change. A model that describes a system you no longer run is worse than none, because it is trusted.

  • ✕"Authentication solves access control."

    Identity is an input to authorization, not a blanket permission. Knowing who is asking says nothing about whether they may have this record.

  • ✕"A high risk score proves the flaw is exploitable."

    A risk ranking supports a decision about where to spend effort. Evidence supports a conclusion about exploitability. Do not let a number stand in for a test.

  • ✕"A parameterized query means the request is authorized."

    Parameterization decides how the database reads a value. It says nothing about whether this user may see the row that comes back. Those are separate defects with separate fixes.

  • ✕"A control removes the risk."

    A control shrinks the risk. What remains is the residual risk, and it needs its own owner and decision.

  • ✕"The deny rule fixed it."

    A deny rule is a mitigation. The cause is still there, and one deleted line brings the incident back. The finding stays open until the cause is removed and verified with the rule switched off.

  • ✕"Restart the server, then figure out what happened."

    Restarting destroys the evidence that would tell you. Preserve first, then contain, then change.

  • ✕"Threat modeling requires a security team."

    It requires a diagram, six prompts, and an hour. The version you actually do is worth more than the formal one you defer.
