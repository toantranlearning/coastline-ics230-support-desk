Requests, responses, and code excerpts below describe a fictional training snapshot. Cite them as supplied simulated evidence, not as tests you performed or proof of the current state of your lab.

1Scope and snapshot

The fictional target is the TechCorp portal at https://portal.training.invalid. The .invalid domain is a documentation example, not a target to visit. The snapshot is independent of the changes you have made in your own course copy.

The permitted investigation in this assignment is reading and analyzing this packet. No automated scanner runs in Cloud Shell. Any separate manual lab check must follow the course Rules Of Engagement and be identified as your own observation.

2Candidate A: Input reflected into HTML

Candidate claim: a stored equipment label is interpreted as markup when the results page displays it. Priority suggested by the fictional analyst: investigate promptly. The priority is a starting judgment, not a score from a tool.

Evidence A1, supplied source excerpt

✕PHPVulnerable
<?php
// WHY: Raw output allows a stored label to contribute HTML structure to the response.
echo '<td>' . $equipment['label'] . '</td>';

Vulnerable. Why: Raw output allows a stored label to contribute HTML structure to the response.

Evidence A2, supplied fixture value

Equipment id: 12
Stored label: <b>Loan kit</b>

Evidence A3, supplied HTML response excerpt

HTML
<td><b>Loan kit</b></td>

Evidence A4, supplied rendering note: the text Loan kit appeared bold. Its surrounding <b> tags were not displayed as literal text. This note is part of the simulated packet.

Explain what these excerpts establish and what they leave unknown. Distinguish markup interpretation from demonstrated script execution or data theft. Name an earlier module's control that addresses the identified output behavior.

3Candidate B: Missing anti-CSRF protection

Candidate claim: a staff preference-changing endpoint has no anti-CSRF protection. The initial lead was the absence of a hidden token in the rendered form.

Evidence B1, supplied form

HTML
<form action="/preferences.php" method="post">
  <input name="theme" value="blue">
  <button type="submit">Save theme</button>
</form>

Evidence B2, supplied handler description: the handler requires the staff member's session cookie and accepts the submitted theme. The supplied source review found no synchronizer token check and no Origin or Referer validation in this endpoint or its shared handler.

Evidence B3, supplied anonymous control observation: the endpoint redirected an anonymous request to sign-in. This shows authentication enforcement, not whether a signed-in browser can be induced to send a preference change.

Evidence B4, supplied cookie metadata: the session cookie has HttpOnly and Secure; this snapshot does not show an explicit SameSite attribute. Cookie behavior can also depend on browser defaults and request circumstances.

Evaluate whether B1 alone would be enough to conclude that the control is absent. Then explain what B2 adds, which facts still affect exploitability, and why B3 does not answer the intent question. Use the CSRF control taught in Module 06 rather than treating cookie flags as equivalent to a request-specific token.

4Candidate C: Possible database injection

Candidate claim: a punctuation character in an equipment-search query caused a server error, suggesting injection.

Evidence C1, supplied request

GET /equipment.php?q=%27 HTTP/1.1
Host: portal.training.invalid

Evidence C2, supplied response

HTTP/1.1 500 Internal Server Error
Content-Type: text/plain; charset=UTF-8

Request could not be completed. Reference: training-C2

Evidence C3, supplied query code

✓PHPSecure
<?php
// WHY: Binding the value preserves it as a query parameter rather than SQL syntax.
$stmt = $pdo->prepare('SELECT id, label FROM equipment WHERE label LIKE ?');
$stmt->execute(['%' . $term . '%']);

Secure. Why: Binding the value preserves it as a query parameter rather than SQL syntax.

Evidence C4, supplied internal log explanation: the query completed successfully. A later attempt to open a missing template file failed, producing the response in C2. The log associates that failure with training-C2.

Judge the injection claim for this specific path and snapshot. A server error is a lead requiring analysis; it does not identify its cause by itself. Explain whether the evidence supports the proposed cause and whether there is a separate availability or configuration problem worth recording. Do not extend the conclusion to every query in the application.

5Candidate D: Session cookie missing a protection flag

Candidate claim: the session cookie lacks HttpOnly.

Evidence D1, supplied response header

Set-Cookie: techcorp_session=REDACTED; Path=/; Secure; SameSite=Lax

Evidence D2, supplied configuration note: the session identifies the signed-in rep. The header is from the simulated HTTPS response; the identifier was redacted for the teaching packet.

Explain which flag is absent and what risk the absent flag relates to. Do not claim an existing XSS exploit or a stolen session merely from this header. Name the configuration change to investigate and a response check that could confirm the changed header.

Evidence E1, supplied object-access design description: /customer.php?id=... requires a signed-in rep and queries a row by id. In the supplied training snapshot, that query has no rep/partner ownership restriction, and there is no separate ownership decision before the row is returned. This description is included for the coverage analysis; it is not a finding that one of the simulated alerts raised.

An ordinary authenticated crawl could request its own customer's page and observe a successful response. Without knowing which records belong to which caller and comparing the required access policy, that success does not reveal the missing owner rule. Explain how the absence of an alert differs from evidence that access control works.

7Interpret the packet

For each alert you choose, record:

  • The candidate claim and evidence identifiers so the reader can trace your reasoning.
  • The supporting or contradicting facts, including the role and path represented.
  • Your verdict: supported, contradicted, or unresolved, with a reason.
  • The established behavior and potential impact separately so a possibility is not reported as an event.
  • A proposed control and a proposed verification check, labeled as proposals because you have not performed them in this packet.

Prioritize using the confirmed behavior, affected assets, likely exposure, and uncertainty. No numerical score is required. Use the assignment's requested report length and deliverables.

✓Preserve the source of a claim

Cite A3 as supplied simulated HTML, not as a capture from your own portal. If you perform an authorized manual check separately, label that evidence with your own lab state and result because the teaching snapshot and your repaired application may behave differently.
