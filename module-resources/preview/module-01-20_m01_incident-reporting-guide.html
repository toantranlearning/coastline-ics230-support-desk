A developer fixes a defect. The next person needs to know what failed, what changed, and why the evidence supports calling it repaired. Your incident report connects those pieces. In this course, the code demonstrates your secure coding decisions; the report explains and tests them.

★A report is a supported account of the work

Every important conclusion should connect to an observation, supplied case fact, or cited source. The reader should be able to distinguish what you know, what you infer, and what remains unknown.

Use this standing reference for each incident-report assignment. The assignment names the incident, required sections, tests, and deliverables. This guide explains how to write those sections. The TC-IR-01 Form and Worked Example supplies the form and a completed fictional case.

1What incident reporting means in this course

TechCorp is the fictional organization whose portal you repair. Its incidents provide a setting for practicing secure coding and design. You work in your own authorized lab copy, investigate the assigned behavior, implement the assigned control, and document the outcome.

TC-IR-01 is the name of the reusable form. TC-IR-001, TC-IR-002, and similar identifiers name individual cases. Reuse the form's structure while writing a new report for the incident assigned.

◆Finding, event, and incident

A vulnerability is a weakness that could permit harm. A finding documents a discovered condition, such as an unsafe output expression. An event is an observed occurrence, such as a request or failed sign-in. An incident involves circumstances that meet the organization's incident criteria. Finding a vulnerability does not establish that someone exploited it or that data was stolen.

When an assignment calls its case an incident, use that case identifier. State which facts the case supplies and which behaviors you reproduced. A classroom reproduction is evidence of that behavior in your lab; it does not establish a production breach.

The security lecture teaches why a control is needed and how it works. The lesson's PHP Companion page explains language constructs used to implement it. Your report assesses the security decision and evidence, rather than retelling syntax or setup instructions.

iThe assignment sets the scope

Complete the sections and checks the assignment requests. A full organizational report may be much longer. If the form asks for five to eight summary sentences but the assignment asks for two or three, follow the assignment. Do not invent an Incident Commander, carrier notification, second reviewer, or monitoring period to fill a field.

2How the course relates to NIST and industry

NIST Special Publication 800-61 Revision 3, published April 2025, places incident response within the Cybersecurity Framework (CSF) 2.0. Govern, Identify, and Protect support preparation; Detect, Respond, and Recover address incidents. Improvement draws on lessons learned throughout the work. Revision 3 supersedes Revision 2.

Our form is a course adaptation, not an official NIST form or a certification of compliance. The following mapping explains the connection; it is not a NIST requirement to use these headings.

In an organization, developers contribute technical analysis and repairs while incident leadership coordinates scope, priorities, communications, and recovery. Other participants may include operations, privacy, legal, and business owners. The report helps these readers make decisions without requiring everyone to inspect the source code.

!Fictional policies are case facts

TechCorp's carrier clock, seven-year retention period, and approval rules belong to the fictional case and runbook. They are not universal NIST requirements. In a real organization, notification and retention follow applicable obligations and organizational procedures. In this course, record what the case establishes; mark an unavailable determination as unavailable.

3Begin with authorization and the assignment

Read the Rules Of Engagement before any security testing because permission, targets, methods, and stop conditions determine which actions you may take. Use the TechCorp Lab Guide for environment and account details so your report can concentrate on the investigation.

Before changing code, identify the assigned case, affected file or feature, required sections, and required checks. Capture the starting behavior while it is still reproducible because changing the code can remove evidence of the original condition. Use only the authorized methods for your own course environment.

If a step would affect an unapproved system or expose someone else's information, stop that step and ask the instructor for direction. Describe the uncertainty without attempting to confirm it on the unapproved target.

4Separate facts, observations, and conclusions

A useful report makes its basis visible. Use these distinctions while drafting.

4. Separate facts, observations, and conclusions. Columns: Type, Example, How to support it.

✕Do not turn a possibility into a result

Write “the supplied markup changed the display” when that is what you observed. Writing “an attacker stole customer records” adds an event your evidence does not establish. The difference affects scope, severity, and response decisions.

Severity expresses how urgently the organization should act based on impact and circumstances. Use the assignment's or runbook's scale and justify the selected level with known facts. A weakness category or scanner score alone does not describe the actual impact on this application.

5Write the required report sections

Complete the sections required by the assignment, using the form's headings so the instructor can locate the required analysis. When a section is required but information is unavailable, explain the gap. “Not determined: no historical access logs were supplied” is more informative than a blank cell.

Section 1: Administrative details

Identify the case, author, report date, scope, and current status. Record supplied roles and dates as supplied facts. Distinguish discovery time from earliest established activity: finding a problem today does not prove it began today. State the time zone for actual timestamps; use relative times when the assignment requests them.

Section 2: Executive summary

Explain the affected feature, observed problem, root cause, response, and current status in the assignment's requested length. Write this section after the analysis because the summary should reflect your evidence. A manager should understand the result without reading PHP code.

Section 3: Systems and data affected

Name the file, endpoint, feature, and data values involved. Distinguish data that could be exposed from data confirmed to have been read, changed, or taken. Limit the scope to supported facts so the reader can judge impact accurately.

Section 4: Timeline

Separate supplied historical events from your investigation and repair actions. Each entry needs a source, such as the case packet, test capture, or change record. Preserve ordering and time-zone information because mixing clocks can create a false sequence. If the case gives no date, use “reported in the assignment; time not supplied.”

Section 5: Detection and analysis

Explain the symptom, how it was found, the relevant code or design path, and the failed control. Where the lesson calls for it, identify the source, trust boundary, sink, and interpreter. Include the module's relevant OWASP category or CWE only when you can explain why it applies.

A symptom is what you saw. A root cause is the condition that made it possible. “The page looked wrong” is a symptom; “untrusted text reached an HTML output expression without encoding” identifies a failed control. Describe broader process failures only when the case supports them.

Record the limits of the investigation. Missing logs, an untested endpoint, or an unavailable production configuration can restrict a conclusion. Connect a meaningful gap to a proposed follow-up instead of filling it with a guess.

Section 6: Response actions

Distinguish the actions you performed from actions you recommend:

  • Containment limits ongoing harm, such as temporarily disabling an affected feature.
  • Mitigation reduces exposure while a weakness may remain.
  • Remediation corrects the underlying weakness, such as replacing an unsafe data-handling pattern.
  • Eradication addresses the incident's causes and persistence, as applicable to the case.
  • Recovery restores and verifies the required operation.

Name the control, changed location, and intended security effect. Explain why the change addresses the cause established in section 5. A proposed credential rotation or second-person review must remain labeled as proposed until it actually occurs.

Section 7: Confirmation of remediation

Record what you tested, what happened, and what the result establishes. Include both the previously unsafe behavior and legitimate behavior because a repair must enforce the security requirement while preserving the feature's intended use. Boundary and rejection checks should follow the assignment.

If a temporary mitigation blocks the feature, its blocked response cannot prove the underlying code is repaired. Use an authorized check that exercises the repaired path independently of the stopgap; if that is unavailable, record the limitation and avoid claiming confirmation.

Section 8: Notification determination

Record the authorized decision-maker and determination when the case supplies them. Otherwise state what is unknown and which role would need to decide. Students report through the course submission process; they do not contact fictional customers, insurers, regulators, or other parties.

Section 9: Post-incident actions

Propose a specific improvement tied to the root cause or an investigation gap. Include an owner or responsible role, target, and status where required. “Improve security” is too vague to verify. “Application maintainer: review other HTML output expressions for the same missing control; proposed” names reviewable work.

Section 10: Closure and attestation

State what was verified and what remains open. Completing a lab repair does not establish that every organizational closure condition has been met. Record your own completion honestly; do not sign as a fictional official or assert that an unperformed review occurred.

6Build evidence the reader can follow

For each check, use four elements: performed, expected, observed, and interpretation. An expected result describes the requirement; an observed result records what your test actually produced. The interpretation states what that comparison supports and its limits.

The example below uses an imaginary equipment-label feature, not an assignment solution. Its observations are illustrative and must not be copied as your own results.

▸Write a bounded conclusion

“The repeated markup case now displays as literal text, and the ordinary name remains unchanged. These results support the repaired label output path. Other output paths were outside this check.” This connects the conclusion to the checks without claiming the whole application is secure.

Use text for requests, responses, logs, and small code changes because the reader can inspect and search it. Use a screenshot when appearance is the evidence. Give each capture an identifier such as E1 and describe the relevant detail so a reader does not have to infer what the image demonstrates.

For each evidence item, record the source, capture time or sequence, relevant account role, and whether it represents the state before or after your change. Include enough detail to reproduce the authorized check. File paths and nearby function names are useful alongside line numbers, which can shift after edits.

✓Keep evidence traceable and private

Keep original captures and label redacted copies because editing evidence without explanation can change its meaning. Remove live tokens, credentials, and unrelated personal data from submission copies because the report does not need to expose them. Describe each redaction, and use fictional lab data for the assigned tests.

For this course, the submitted report and evidence provide the preservation record. Keep working files together and submit the required items to Canvas. A formal forensic chain of custody is not an added assignment requirement. In an organization, evidence handling and retention follow established procedures; our classroom record practices prepare you to understand that responsibility.

7Use sources and AI responsibly

Distinguish your test evidence from a reference explaining the control. An OWASP or NIST citation supports the reasoning; it cannot prove what happened in your lab. Place citations near the statements they support and follow any source requirements on the assignment.

AI may help explain concepts, propose or refactor code, suggest tests, and plan or edit a report when the assessment permits it. You remain responsible for understanding the code and verifying claims. Report only results you observed because a generated test transcript is not evidence.

A useful disclosure names the tool, assistance requested, material used or changed, and checks you performed. For example: “Gemini suggested boundary cases and revised my summary for clarity. I selected the applicable cases, performed them in my lab, and checked the revised summary against evidence E1–E4.” Use this wording only if it describes your actual work. Unaided assessments follow their own instructions.

8Review and submit

Use the assignment's submission list as the final checklist because deliverables differ by incident. Before submitting, confirm:

  • The report has the correct incident ID and required sections so it can be assessed against the assigned case.
  • Claims distinguish supplied facts, observed behavior, analysis, and unknowns so the reader can judge their support.
  • The repair addresses the root cause and stays within scope so an unrelated change does not substitute for the assigned control.
  • Evidence includes the required unsafe, legitimate, and rejection cases so both protection and preserved behavior can be assessed.
  • Each check states the actual result and its limits so a passing observation is not overstated.
  • Evidence files, citations, and permitted AI assistance are identified so the work remains traceable.
  • The submitted Markdown report and required attachments open correctly so the instructor can read the preserved record.

You do not need a polished story in which every test passes on the first attempt. Record failures, corrections, and remaining limits honestly. A clear report of an unresolved problem supports a better decision than an unsupported claim that it is fixed.
