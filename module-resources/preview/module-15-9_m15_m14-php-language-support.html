A failed lookup produces two outputs: a message for the person using the application and a record for the responder investigating the failure. PHP needs to keep those destinations separate. Detailed diagnostics can help the responder while disclosing information if they reach the browser.

This companion supports the M14 security lecture. It explains exception flow, callbacks, output buffering, structured records, and write-result checks. Standalone examples use local practice values and temporary files; they do not change the portal's logging configuration or provide the incident assignment's completed repair.

★Follow both the data and the execution path

Ask what the caller sees, what the log receives, and whether the operation continues after a failure. A logging function can write a valid record while describing an event that has not yet happened.

1Read runtime error settings without confusing suppression and repair

ini_set changes a supported PHP configuration setting for the current execution. The lecture uses ini_set('display_errors', '0') to keep automatically displayed diagnostics out of the response. error_reporting(E_ALL) selects the error levels PHP reports.

PHP
<?php
$settings = ['display_errors' => '0', 'reported_levels' => 'E_ALL'];
echo 'Display errors: ' . $settings['display_errors'] . "\n";
echo 'Reported levels: ' . $settings['reported_levels'] . "\n";
Output
Display errors: 0
Reported levels: E_ALL

This practice displays intended settings as data, rather than changing the runtime. Hiding automatic error output does not correct a vulnerable query, ensure that diagnostics are logged, or catch a failure before the settings execute. Deployment configuration and a deliberate handler remain relevant.

!A quieter response is not evidence that the cause disappeared

Verify the underlying repair and the logging path because disabling display changes disclosure behavior while leaving the failing operation in place.

Source: PHP ini_set (opens in a new tab) documents runtime settings; PHP error_reporting (opens in a new tab) describes level selection.

2Distinguish Exception, Error, and Throwable

Throwable is the interface implemented by both Exception and Error. Some runtime failures are Error objects, so catching only Exception does not catch every throwable failure.

PHP
<?php
try {
    strlen();
} catch (Throwable $failure) {
    echo get_class($failure) . "\n";
}
Output
ArgumentCountError

try encloses the operation. Calling strlen without its required argument causes an ArgumentCountError. PHP skips the remaining ordinary path in that block and enters a compatible catch. $failure receives the thrown object. get_class returns its class name.

This is a local demonstration, not a production error response. The object's getMessage, getFile, and getLine methods provide diagnostic details that can include sensitive context. Their availability does not mean they belong in a browser response.

Source: PHP Throwable (opens in a new tab) describes the shared interface and methods; the same interface applies to caught exceptions.

3Read an uncaught-exception callback

set_exception_handler registers a callback for an uncaught throwable. A callback is a function supplied for another operation to invoke later. The handler receives the thrown object; execution stops after the handler finishes.

PHP
<?php
$reference = 'practice-42';
set_exception_handler(function (Throwable $failure) use ($reference): void {
    echo 'Operation failed. Reference: ' . $reference . "\n";
});
throw new RuntimeException('Internal practice detail');
echo "This line is not reached.\n";
Output
Operation failed. Reference: practice-42

function (...) { ... } defines an anonymous function. use ($reference) captures that outside variable by value so the callback can access it. : void declares that the function returns no value. It does not mean “never returns”; a handler can finish its body, after which PHP stops the failed execution.

throw raises the exception. The final echo does not run. A local catch would handle the failure before it reached this global handler.

✕A handler needs its own failure plan

Handle failures in its encoding and logging operations because a new uncaught failure inside the handler is not automatically routed back through the same handler. A successful registration does not prove that every error path returns the intended generic response.

Source: PHP set_exception_handler (opens in a new tab) documents the callback and termination behavior; PHP anonymous functions (opens in a new tab) explains captured variables.

4Buffer output and discard a partial page

ob_start starts an output buffer. Subsequent ordinary output accumulates there instead of immediately being sent onward. ob_end_clean discards and closes the active buffer.

PHP
<?php
ob_start();
echo "Partial page with internal detail.\n";
ob_end_clean();
echo "Generic failure message.\n";
Output
Generic failure message.

The first message entered the buffer and was discarded. The second is written after that buffer ends. The lecture uses buffering to avoid leaking a half-built page when a handler responds to a failure.

This example has exactly one active buffer. Real applications can have nested buffers or output already transmitted. Cleaning one buffer cannot retract bytes already sent. Response status and headers must be set while headers are still available to modify.

iTrace where output becomes committed

Review early output and buffer ownership because a handler's generic message is only part of the response if earlier content already escaped. Output buffering supports the response design; it does not establish every deployment's behavior by itself.

Source: PHP ob_start (opens in a new tab) and PHP ob_end_clean (opens in a new tab) explain buffer creation and removal.

5Build a structured record with explicit defaults

The lecture's logger combines default fields with caller-supplied fields using array union, +. For duplicate keys, the left array's value wins. This differs from arithmetic addition and from some array-merging operations.

PHP
<?php
$defaults = ['app' => 'equipment', 'time' => 'practice-time'];
$fields = ['app' => 'other', 'event' => 'access_refused'];
$entry = $defaults + $fields;
echo $entry['app'] . "\n";
echo $entry['event'] . "\n";
Output
equipment
access_refused

The caller's app value does not replace the left-hand default. The new event field is retained. That behavior should be an intentional logger contract, because callers need to know which fields they can supply.

gmdate('c') produces an ISO 8601-style timestamp using UTC. A timestamp can help order records, but ordering still depends on clocks and collection behavior. A correlation identifier connects related records; it is not a user credential and should not carry a session token.

Source: PHP array operators (opens in a new tab) explains union; PHP gmdate (opens in a new tab) documents UTC formatting.

6Encode a record rather than concatenate untrusted lines

json_encode serializes an array into a JSON string. With JSON_THROW_ON_ERROR, an encoding failure throws JsonException instead of returning false.

✓PHPSecure
<?php
// WHY: JSON escaping keeps a supplied newline inside its field rather than creating an apparent second record.
$entry = ['event' => 'login_attempt', 'actor' => "avery\nforged entry"];
$line = json_encode($entry, JSON_THROW_ON_ERROR);
echo $line . "\n";

Secure. Why: JSON escaping keeps a supplied newline inside its field rather than creating an apparent second record.

Output
{"event":"login_attempt","actor":"avery\nforged entry"}

The source uses a double-quoted string, so the actor value contains an actual newline. JSON represents that newline as the characters \n inside the string. Appending one newline after the encoded record then creates one record line.

Structured encoding preserves field boundaries. It does not ensure that a log viewer uses those fields safely, that the record is authentic, or that the payload contains no secret. Those are separate design decisions.

PHP
<?php
try {
    json_encode(['detail' => "\xB1"], JSON_THROW_ON_ERROR);
} catch (JsonException $failure) {
    echo "Encoding failed.\n";
}
Output
Encoding failed.

The byte in this example is not valid UTF-8 text. The exception branch makes the failure visible. A production logger needs a defined fallback that avoids exposing the sensitive record or silently pretending it was recorded.

Source: PHP json_encode (opens in a new tab) documents serialization and error flags.

7Select permitted fields instead of dumping the request

A request can contain a password, session token, or unrelated private text. Logging its whole array copies those values. A deliberate event schema selects what the investigation needs.

✓PHPSecure
<?php
// WHY: Selecting named event fields avoids copying the request's password into the record.
$request = ['username' => 'avery', 'password' => 'practice-secret'];
$entry = [
    'event' => 'authn_login_fail',
    'actor_id' => $request['username'],
    'outcome' => 'invalid_credentials',
];
echo json_encode($entry, JSON_THROW_ON_ERROR) . "\n";

Secure. Why: Selecting named event fields avoids copying the request's password into the record.

Output
{"event":"authn_login_fail","actor_id":"avery","outcome":"invalid_credentials"}

The password remains absent because the code never selects it. This is stronger than copying everything and hoping a later display masks it. Actor identifiers can still be personal information, so the actual schema and retention policy should reflect the investigation's purpose.

✓Choose the record's fields before writing it

Record the action, relevant actor and object identifiers, outcome, and correlation reference that the event needs because collecting unrelated data increases exposure without necessarily helping the responder.

Source: OWASP Logging Cheat Sheet (opens in a new tab) discusses event attributes, excluded data, and log injection defenses.

8Check a write result strictly

file_put_contents returns the number of bytes written or false on failure. With FILE_APPEND, it appends instead of replacing existing contents. A zero-byte write and failure are different results.

PHP
<?php
$path = tempnam(sys_get_temp_dir(), 'course-log-');
if ($path === false) {
    exit("Temporary file unavailable.\n");
}
$record = "practice event\n";
$written = file_put_contents($path, $record, FILE_APPEND);
if ($written === false) {
    echo "Write failed.\n";
} else {
    echo 'Bytes written: ' . $written . "\n";
    echo file_get_contents($path);
}
unlink($path);
Output
Bytes written: 15
practice event

This practice creates and removes a temporary file; it does not write the portal's log. sys_get_temp_dir identifies the temporary directory, tempnam creates a unique file, and unlink removes it. The reported byte count includes the trailing newline.

The lecture instead uses error_log($line, 3, $destination). Message type 3 appends to the named file and returns a Boolean. It does not automatically add a newline, so the logger supplies one. Neither return value proves durable remote collection, monitoring, retention, or immunity to disk loss.

Source: PHP file_put_contents (opens in a new tab) documents bytes and append behavior; PHP error_log (opens in a new tab) documents message type 3.

9Do not describe a planned action as already completed

A log-write check can gate a sensitive action, but the event name and outcome need to match the stage being recorded.

PHP
<?php
$recorded = false;
if (!$recorded) {
    echo "Action not performed: required record unavailable.\n";
} else {
    echo "Proceed to the action.\n";
}
Output
Action not performed: required record unavailable.

!$recorded negates the Boolean. The program selects the refusal branch for failure. A record written before a database change should describe intent or an attempt, rather than asserting success before the change completes. A later success or failure event can record the actual result, according to the chosen audit design.

!Two successful calls do not automatically make one atomic operation

Evaluate the failure interval between the log write and data change because the action might fail after the first record succeeds. The report should state the verified behavior and residual gap rather than claim that a Boolean return solves every consistency problem.
