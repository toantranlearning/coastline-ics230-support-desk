A staff member keeps the portal open while visiting another page. A request arriving with a valid session cookie may identify that browser without proving the staff member intended a change. This module adds the missing intent check to state-changing requests.

★A signed-in browser can send a request its user never intended.

The security decision and the evidence for it are the focus of this lesson. Use the PHP companion for the language expressions used to implement the controls.

2The browser sends your session cookie by destination

After you sign in, the portal knows you by a session cookie. Module 01 section 6 called this ambient authority: the browser attaches the cookie to every request bound for the portal, and it decides to attach it from where the request is going, never from what caused the request. A page on evil.example can make your browser send a request to portal.example, and the cookie rides along.

That is the whole mechanism behind cross-site request forgery (CWE-352). MITRE's definition: the application does not, or cannot, sufficiently verify whether a request was intentionally provided by the user who sent it.

★A valid session proves the sender, not the intent

Every request that carries your session cookie is authentic. The browser really did send it on your behalf. Authentication answers who is signed in. Authorization answers whether that account may act on the object. Neither one answers whether the person at the keyboard meant to send this request, and that missing answer is CSRF.

The attacker never learns the cookie's value. They do not need to. The browser's same-origin policy lets a page on one origin send a request to another origin (a link, a redirect, a form submission). What it stops is reading the response. MDN puts it as cross-origin writes are typically allowed and cross-origin reads are typically disallowed.

◆Origin, same-origin policy

An origin is the scheme, host, and port of a URL, so https://portal.example and https://evil.example are different origins. The same-origin policy is the browser rule that restricts how a page from one origin can interact with a resource from another. It lets the page cause a request to another origin. It does not let the page read what came back.

So the attacker can cause the request to be sent, fully authenticated, with any body they choose, and cannot see the answer. That is why CSRF goes after actions that change state. The attacker does not need to read the response when the action itself was the goal.

2. The browser sends your session cookie by destination. Columns: Question, Answered by, How.

3A request that is authenticated, authorized, and still forged

Suppose the portal had a page that lets a signed-in rep change their own home office. It reuses the real helpers from the portal's auth.php and db.php.

✕PHPVulnerable
<?php
// WHY: A prepared query controls SQL syntax but does not enforce ownership when the required owner condition is absent.
require_once __DIR__ . '/db.php';
require_once __DIR__ . '/auth.php';

auth_require_login();

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $office = $_POST['home_office'] ?? '';

    $stmt = db()->prepare('UPDATE users SET home_office = ? WHERE username = ?');
    $stmt->execute([$office, auth_username()]);

    header('Location: profile.php');
    exit;
}

Vulnerable. Why: A prepared query controls SQL syntax but does not enforce ownership when the required owner condition is absent.

Read what is right about this before what is wrong. It requires a login. The query is a prepared statement, so there is no injection (Module 04). It updates only the signed-in rep's own row, so there is no object-level authorization defect. It would pass a review that asked whether the route is authenticated and touches the correct row.

What it has no way to check is whether the request came from the portal's own form. An attacker writes a page with a form that posts to the route.

HTML
<form action="https://portal.example/office.php" method="POST">
  <input type="hidden" name="home_office" value="Nowhere">
  <button>Claim your prize</button>
</form>

When a signed-in rep opens that page and clicks the button, the browser assembles this request.

POST /office.php HTTP/1.1
Host: portal.example
Origin: https://evil.example
Content-Type: application/x-www-form-urlencoded
Cookie: PHPSESSID=2ec651cbaff77ef42200c50194e79c5d

home_office=Nowhere

▸What the server sees when the forged form submits

  1. The rep, already signed in to the portal, opens the attacker's page and clicks the button. A script on the page could submit the form with no click at all.
  2. The browser prepares the POST to portal.example. Because the request is bound for that site, it attaches the portal session cookie on its own. The attacker's page never reads or sets that cookie.
  3. The server receives a POST with a valid session, so auth_require_login() passes. The row being updated belongs to the session's own user, so an ownership check would pass too.
  4. The UPDATE runs. The rep's home office is now Nowhere, and the rep did nothing but click a button on another site.

Compare that forged request with the one the portal's own form sends. The two differ in the Origin header and in nothing else that the server checks. Both carry the cookie. Neither carries anything that could only have come from a page the portal served. The Network panel of your browser's developer tools shows two requests side by side; the Orientation page Requests and Developer Tools covers how to open it and read a request's headers and body.

When CSRF does not apply. CSRF depends on a credential the browser attaches by itself. An API that authenticates with an Authorization header, which client code adds to each request on purpose, is not open to this attack in the same way, because a cross-site page has no way to make the browser add that header. This is not a general exemption. A cookie used anywhere in the flow brings the exposure back.

The CSRF cheat sheet names the same three facts: the attack needs cookie-based session handling, a request the attacker can predict, and an action worth forging. PortSwigger: What is CSRF (opens in a new tab) lists those three conditions in the same words and is the independent second source.

4Safe and unsafe HTTP methods

The HTTP standard says which methods are read-only. RFC 9110 defines GET, HEAD, OPTIONS, and TRACE as safe, meaning their semantics are essentially read-only. It draws the line so that automated retrieval (spiders) and prefetching can run safely, with no human deciding to send each request.

◆Safe method, state-changing request

A safe method is one the standard defines as read-only: GET, HEAD, OPTIONS, and TRACE must not change anything on the server. A state-changing request creates, updates, or deletes something, and it belongs on POST, PUT, PATCH, or DELETE. The word safe here is the protocol's term for read-only. It is not a claim about security.

Here is what happens when a state change sits on a GET route and someone puts this tag on any page in the world.

HTML
<img src="https://portal.example/close-account.php">

Every visitor's browser fetches that image with GET, carrying their portal cookie, before anyone decides to click anything.

✕A state-changing GET fires with no human and no error

Put a state change on a GET route and it can run without anyone intending it and without leaving a sign that anything unusual happened. A prefetcher warming links, a crawler indexing a page, a chat application building a link preview, or an <img> tag pointing at the route triggers it silently, with the victim's session, and the response looks ordinary. There is no warning and no failed request to investigate. Use an unsafe method for every state change.

Choosing an unsafe method is necessary. It is not sufficient.

!Changing GET to POST is not the fix

The forged form in section 3 already uses POST. An attacker can submit a cross-site POST with a script and no click. The right method is a prerequisite for the defense that follows, and the cheat sheet says it in one line: do not use GET requests for state changing operations.

RFC 9110, section 9.2.1 Safe Methods (opens in a new tab) is the standard quoted above, including the rule that the resource owner must disable an action when it is reached by a safe method.

5The synchronizer token pattern

The defense is to require a value in the request that the attacker's page cannot obtain and cannot guess. The cheat sheet calls this the synchronizer token pattern and lists it as the primary defense for an application that keeps server-side sessions, which the portal does.

◆Synchronizer token, CSPRNG

A synchronizer token is a random value the server stores in the user's session and also places in every form that changes state. A genuine request carries the value back, and the server compares the returned value with the stored one before acting. A CSPRNG, a cryptographically secure pseudo-random number generator, is the only acceptable source for the value, because its output cannot be predicted from earlier output. In PHP that source is random_bytes().

Three steps carry the pattern. First, mint the token once per session and keep it in the session, where only the server can read it.

✓PHPSecure
<?php
// WHY: Cryptographic random bytes avoid predictable values for security-sensitive identifiers.
session_start();

if (!isset($_SESSION['csrf_token'])) {
    // 32 random bytes from the CSPRNG, written as 64 hex characters.
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}
echo $_SESSION['csrf_token'], "\n";

Secure. Why: Cryptographic random bytes avoid predictable values for security-sensitive identifiers.

Output
d277a38afc85329164c4be770e938a1670137fa5fc295bf320290e64f7c96ab3

random_bytes() returns raw bytes, which the manual warns may be unprintable or invalid UTF-8. bin2hex() writes each byte as two hexadecimal characters, so the value is safe to put in a form.

Second, place the token in the form as a hidden field, encoded for the attribute it lands in (Module 03 section 6).

✓PHPSecure
<?php
// WHY: HTML encoding represents special characters as data at the HTML output location. $token = htmlspecialchars($_SESSION['csrf_token'], ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'); ?>
<input type="hidden" name="csrf_token" value="<?= $token ?>">

Secure. Why: HTML encoding represents special characters as data at the HTML output location. $token = htmlspecialchars($_SESSION['csrf_token'], ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8'); ?>

Third, on submission, compare the returned value with the session's, before any state change.

✓PHPSecure
<?php
// WHY: The string comparison avoids numeric-string coercion in the secret check.
$sent     = $_POST['csrf_token'] ?? null;
$expected = $_SESSION['csrf_token'] ?? null;

if (!is_string($sent) || !is_string($expected) || !hash_equals($expected, $sent)) {
    http_response_code(403);
    exit('Request denied');
}

// Only past this point is the state change allowed to run.

Secure. Why: The string comparison avoids numeric-string coercion in the secret check.

A request whose token is missing, malformed, or wrong never reaches the code that changes state. It gets a short denial and stops.

Response
HTTP/1.1 403 Forbidden

Request denied

▸Reading the comparison line

  1. $_POST['csrf_token'] ?? null reads the posted field, or null when the field is absent. The is_string test rejects a missing field and rejects an array, which a request such as csrf_token[]=x would produce (Module 03 section 8).
  2. $_SESSION['csrf_token'] ?? null reads the stored value. If the session has no token, for example a session that was never shown a form, the request is refused rather than compared against nothing.
  3. hash_equals($expected, $sent) takes the secret first and the user's value second, which is the order the manual requires. It returns true only when the two strings are identical.
  4. On any failure the handler sends 403 and exits. The code that changes state is never reached.

hash_equals() is the comparison for a secret, not == and not ===. Module 03 section 8 showed that == converts both sides first, so "1e3" == "1000" is true. hash_equals("1e3", "1000") is false. The manual adds the second reason: a plain comparison stops at the first byte that differs, so the time it takes leaks how much of the secret was right. hash_equals() takes the same time either way.

Three properties carry the whole defense. Drop any one and the defense is gone.

  1. Unpredictable. It comes from a CSPRNG, never from rand(), mt_rand(), uniqid(), or a timestamp, so it cannot be guessed or derived.
  2. Bound to the authenticated session. It lives in the session, so a token minted for one session is rejected when it is replayed against another.
  3. Checked on the server, before the change. The comparison runs on the server and fails closed on a missing or malformed value. A check the client could skip is no check at all.

Why the attacker cannot win this. The token sits in the session and in a page your origin served. The attacker's page can cause a request, and the same-origin policy keeps it from reading your page to learn the token. Thirty-two random bytes are not guessable in any useful time. The defense holds because the browser's own isolation denies the attacker the one value the request must contain.

iLifetime, and one rule that does not change

A per-session token is the common choice. A high-impact operation may use a short-lived or single-use token, at the cost of breaking a user who has two tabs open, so test that case on purpose. Whatever the lifetime, never use the session ID itself as the token. That copies the session identifier into form fields, page source, and anything that logs a request body. A leaked token should cost one form submission, not the account. The cheat sheet adds that a token must never travel in a URL, where browser history and server logs would keep it.

PHP Manual: random_bytes (opens in a new tab) documents the CSPRNG sources and the exception thrown when none is available. PHP Manual: bin2hex (opens in a new tab) and PHP Manual: hash_equals (opens in a new tab) document the two helpers, including the argument order and the timing note.

6One shared check that every POST handler calls

Section 5 gave the three steps as separate snippets. Pasting them into each page is how one page gets missed. The portal's lib/ folder already holds shared helpers for passwords, signing, and queries, each with a header stating what it does. A token check belongs in the same style: one file, three small functions, called by every page that changes state.

✓PHPSecure
<?php
// WHY: HTML encoding represents special characters as data at the HTML output location.
/**
 * One anti-forgery check for every POST handler in the portal.
 *
 * csrf_token()   returns this session's token, minting it on first use.
 * csrf_field()   returns the hidden input to place inside every POST form.
 * csrf_require() stops the request with 403 unless the posted token matches.
 */

function csrf_token(): string
{
    if (session_status() === PHP_SESSION_NONE) {
        session_start();
    }
    if (!isset($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf_token'];
}

function csrf_field(): string
{
    return '<input type="hidden" name="csrf_token" value="'
        . htmlspecialchars(csrf_token(), ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8')
        . '">';
}

function csrf_require(): void
{
    $sent     = $_POST['csrf_token'] ?? null;
    $expected = $_SESSION['csrf_token'] ?? null;

    if (!is_string($sent) || !is_string($expected) || !hash_equals($expected, $sent)) {
        http_response_code(403);
        exit('Request denied');
    }
}

Secure. Why: HTML encoding represents special characters as data at the HTML output location.

A page uses it in two places: once in the form, once on the first line of its POST branch. Here is the home-office page from section 3, repaired.

✓PHPSecure
<?php
// WHY: Placeholders keep bound values separate from the SQL statement structure.
require_once __DIR__ . '/db.php';
require_once __DIR__ . '/auth.php';
require_once __DIR__ . '/csrf.php';

auth_require_login();

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    csrf_require();   // nothing below runs without a matching token

    $office = $_POST['home_office'] ?? '';
    $stmt = db()->prepare('UPDATE users SET home_office = ? WHERE username = ?');
    $stmt->execute([$office, auth_username()]);

    header('Location: profile.php', true, 303);
    exit;
}
?>
<form method="post" action="office.php">
  <?= csrf_field() ?>
  <label>Home office <input name="home_office"></label>
  <button type="submit">Save</button>
</form>

Secure. Why: Placeholders keep bound values separate from the SQL statement structure.

✓The pattern to copy

Keep the token logic in one file. Mint one token per session from random_bytes(), place it in every form that changes state with csrf_field(), and call csrf_require() on the first line of every POST branch, before any database work. Reject a missing or mismatched token with a short denial. A new page gets the same protection by calling the same two functions.

iWhat lib/hmac.php is for, and why the token does not need it

The portal's lib/hmac.php signs a value the server hands to the client and later trusts back, and its header says it proves the value was issued by this server and not altered. That is the tool for the cheat sheet's other pattern, a signed double-submit cookie, which suits an application with no server-side session. The portal keeps sessions, so the token lives in the session and the server already knows the real value. No signature is needed.

The OWASP CSRF Prevention Cheat Sheet, synchronizer token pattern (opens in a new tab) is the source for the pattern, its token requirements, and the stateful versus stateless split. W3Schools: PHP Sessions (opens in a new tab) has runnable examples of session_start() and $_SESSION, which the helper relies on.

7SameSite and the session cookie

The SameSite cookie attribute tells the browser whether to attach a cookie to a cross-site request at all. Setting it is defense in depth behind the token. Here is what MDN says each value does.

7. SameSite and the session cookie. Columns: Value, What the browser does.
ValueWhat the browser does
Strictsends the cookie only for requests that originate from the same site that set it
Laxsends it for same-site requests, and for a cross-site request only when the request is both a top-level navigation and uses a safe method
Nonesends it with every request, cross-site included; the cookie must also carry Secure

◆Site, as SameSite uses it

A site is the scheme plus the registrable domain, such as https://example.com. Every host under that domain is the same site, so shop.example.com and blog.example.com are same-site to each other even though they are different origins. SameSite compares sites, not origins.

What Lax withholds the cookie from, exactly:

  • any cross-site request that is not a top-level navigation: a fetch() call, an <img> or <script> load, or a navigation inside an <iframe>;
  • any cross-site top-level navigation that uses POST, PUT, or DELETE, which includes the forged form in section 3.

What Lax still sends the cookie with: a cross-site top-level navigation using a safe method. That is a link you click from another site, an assignment to document.location, or a GET form submission. So a route that changes state on GET is still exposed under Lax, which is one more reason for section 4.

Set the attributes before the session starts, because a cookie that has already been sent cannot be re-flagged. The manual says the call lasts for one request, so it runs before session_start() on every page.

✓PHPSecure
<?php
// WHY: The SameSite and HttpOnly attributes reduce particular cookie exposures; they complement the request-specific intent check.

session_set_cookie_params([
    'samesite' => 'Lax',
    'httponly' => true,
]);
session_start();

Secure. Why: The SameSite and HttpOnly attributes reduce particular cookie exposures; they complement the request-specific intent check.

Response
Set-Cookie: PHPSESSID=2ec651cbaff77ef42200c50194e79c5d; path=/; HttpOnly; SameSite=Lax

!The portal's cookie has no SameSite attribute until you add one

PHP's session.cookie_samesite setting defaults to an empty string, and the manual says an empty value sets no SameSite attribute at all. The portal's auth.php calls session_start() with no cookie parameters, so its session cookie goes out with no attribute. What happens next is up to the browser. MDN says some browsers use Lax as the default when the attribute is missing, and that this default form is more permissive: the cookie is also included in POST requests set no more than two minutes earlier. Two reps with different browsers can get different results from the same forged form. Do not rely on a browser default. Write the attribute.

Lax blocks the cross-site POST from section 3 in a browser that honors the attribute, which is real protection. Treat it as strong defense in depth rather than the whole control, for three reasons the cheat sheet gives. It depends on browser behavior you do not control. It is scoped to the registrable domain, so a page on a sibling subdomain can still send the cookie. And it does nothing for a route that changes state on GET.

HttpOnly is the second attribute to set, and it covers a different threat. MDN says it forbids JavaScript from accessing the cookie through document.cookie, which limits what a cross-site scripting bug can steal (Module 05 section 9). It does not stop CSRF, because the browser still attaches the cookie on its own.

Secure tells the browser to send the cookie only over https:, with an exception MDN notes for localhost. A cookie marked SameSite=None must carry it. Whether to set it on your portal depends on how the portal is reached, which is out of scope for this module.

The MDN Set-Cookie reference (opens in a new tab) is the source for every browser behavior in this section. PHP Manual: session_set_cookie_params (opens in a new tab) documents the array form and the rule that it runs before session_start(), and PHP Manual: session configuration (opens in a new tab) gives the empty default for session.cookie_samesite. The OWASP Session Management Cheat Sheet (opens in a new tab) says session cookies must set SameSite explicitly rather than rely on the browser default.

8Checking the request origin

For a state-changing request the server can also ask where the request came from. The browser answers in headers that page script cannot set.

◆Origin header, Fetch Metadata

The Origin header carries the scheme, host, and port of the page that caused the request, with no path. Browsers add it to every cross-origin request and to same-origin requests that are not GET or HEAD. Fetch Metadata is a family of Sec-Fetch-* request headers; Sec-Fetch-Site says whether the request came from the same origin, the same site, a different site, or a user action such as typing a URL. Both are forbidden request headers, which means a script on a page cannot set or change them.

The cheat sheet's order: if Origin is present, compare it with the origin you expect; if it is absent, fall back to the origin part of Referer; and treat a missing header or Origin: null as no evidence of a same-origin request.

✓PHPSecure
<?php
// WHY: Comparing parsed origin components avoids accepting a different host merely because its text resembles the expected origin.

function origin_matches(string $expected): bool
{
    $origin = $_SERVER['HTTP_ORIGIN'] ?? null;

    if ($origin === null && isset($_SERVER['HTTP_REFERER'])) {
        $p = parse_url($_SERVER['HTTP_REFERER']);
        if (isset($p['scheme'], $p['host'])) {
            $origin = $p['scheme'] . '://' . $p['host'] . (isset($p['port']) ? ':' . $p['port'] : '');
        }
    }

    return $origin !== null && $origin === $expected;
}

Secure. Why: Comparing parsed origin components avoids accepting a different host merely because its text resembles the expected origin.

Run with five request shapes against an expected origin of https://portal.example, it answers:

Output
{"HTTP_ORIGIN":"https://portal.example"}                 true
{"HTTP_ORIGIN":"https://portal.example.evil.net"}        false
{"HTTP_ORIGIN":"null"}                                   false
{"HTTP_REFERER":"https://portal.example/office.php"}     true
{}                                                       false

!Compare whole origins, never substrings

The mistake that keeps reaching production is a substring check. A test that asks whether Origin contains portal.example accepts portal.example.evil.net and notportal.example as readily. Build the full scheme://host:port string and compare the whole thing against the value you expect, as the function above does. Referer has a further limit: a referrer policy can strip it, so a rule that requires it rejects real users unless you define the fallback.

Sec-Fetch-Site: cross-site on an unsafe method is a signal the server can reject on, and MDN reports the header as available across browsers since March 2023. Older or unusual clients omit it. The cheat sheet makes a fallback to the Origin and Referer check a mandatory part of any Fetch Metadata policy, so write down which clients you expect and what happens when the headers are absent. An origin check of either kind supplements the token. It does not replace it.

MDN: Origin (opens in a new tab) lists when the header is sent and the cases where it is null, which include a page opened from a file: URL. MDN: Sec-Fetch-Site (opens in a new tab) defines the four values. MDN: Referer (opens in a new tab) documents what the referrer policy allows into that header.

9When a token is not enough

A valid token proves a request came from a page your origin served. It does not prove that a human weighed the action, and it does not decide whether this user may perform it at all.

High-impact actions need more than a token. For a password change, a new payment destination, MFA removal, or account deletion, add a check that a person is present and paying attention. The cheat sheet names re-authentication and one-time tokens as the user-interaction defenses, and says not to use a CAPTCHA for this, because a CAPTCHA is built to stop bots, not forged requests. Reserve re-authentication for these costly actions. Loading a page or viewing help text does not call for it.

A token is not authorization. A user can hold a valid token for their own session and still have no right to the object they are acting on. CSRF defense verifies that the request came from your form. A separate authorization check decides permission. Neither substitutes for the other.

Cross-site scripting defeats CSRF defenses. The cheat sheet says it plainly: XSS can defeat all CSRF mitigation techniques. If an attacker can run script on your origin, that script reads the token out of the page and sends the request through your own site. Every signal in the sections above then looks correct, because it is correct. The request came from your page.

iTwo controls, two boundaries

A token stops a different origin from causing a request. Output encoding at every sink (Module 05) keeps hostile script out of your origin in the first place. The two guard different boundaries, and neither backs up the other. The cheat sheet draws the same conclusion: tokens stay essential for cookie-based authentication even though XSS can bypass them.

The OWASP CSRF Prevention Cheat Sheet, user interaction based defenses (opens in a new tab) is the source for the re-authentication guidance and the XSS statement.

11Common misconceptions

  • ✕"POST prevents CSRF."

    A cross-site form submits POST with a script and no click. The method is a prerequisite for the defense, not the defense.

  • ✕"The request has a valid session cookie, so it is legitimate."

    The browser attaches the cookie by destination. That gap is the entire vulnerability.

  • ✕"A confirmation dialog stops it."

    A client-side "are you sure?" runs only on your own page. The forged request never renders it, so the dialog stops nobody.

  • ✕"SameSite solves it."

    It is strong and incomplete. Sibling subdomains, state-changing GET routes, SameSite=None integrations, a cookie with no attribute, and browsers that do not honor it all sit outside it.

  • ✕"The token should be the session ID."

    That leaks the session identifier into markup and logs, so a stolen token costs the whole account instead of one request.

  • ✕"CSRF tokens authorize the action."

    They show the request came from your form. An authorization check decides permission.

  • ✕"We have tokens, so XSS is less urgent."

    It is more urgent, because script inside your origin reads the token and uses it.

  • ✕"Checking the Referer is enough."

    A referrer policy can strip the header, and a substring check accepts look-alike hosts. Compare whole origins, define the fallback, and keep the token.

12Check your understanding

Work these before you look at the answers.

  1. An attacker never learns the value of your session cookie. Why can they still cause an authenticated request to be sent on your behalf?
  2. Given that an attacker can send a cross-site POST anyway, why must a password change never happen on GET?
  3. Name the three properties a synchronizer token must have, and say what fails if each is missing.
  4. A request arrives with a valid, session-bound CSRF token. Name two things it still does not prove.
  5. Why does the token comparison use hash_equals() rather than ==?
  6. Your application sets SameSite=Lax and uses no tokens. Describe a route that is still exploitable, and say why Lax does not cover it.
  7. What does HttpOnly protect against, and why does it not stop CSRF?
  8. A cookie is sent with SameSite=None. What other attribute must it carry?
  9. An API authenticates with a bearer token in an Authorization header and uses no cookies. Why is it not open to classic CSRF, and what would bring the risk back?
  10. Why does a cross-site scripting bug defeat an otherwise correct CSRF token?
  11. Why does the portal need one shared csrf_require() rather than a check pasted into each page?

Answers: (1) the browser attaches the cookie by destination on its own, and the same-origin policy only blocks reading the response, so causing the request is enough. (2) safe methods are sent by prefetchers, crawlers, previews, and <img> tags with no human involved, so a state-changing GET runs with the victim's session and no click; Lax still sends the cookie on it. (3) unpredictable, session-bound, and server-checked, failing respectively to guessing, to replay across sessions, and to a client-side check that never runs. (4) that a human considered the action, and that the user is authorized for the object. (5) == converts both sides first, so unrelated strings can compare equal, and a plain comparison stops at the first differing byte, which leaks how much of the secret was right; hash_equals() compares the whole string in constant time. (6) any state-changing GET, since Lax still attaches the cookie to a cross-site top-level navigation with a safe method; a sibling subdomain is another answer. (7) HttpOnly keeps script from reading the cookie through document.cookie, which limits cross-site scripting theft, and the browser still attaches the cookie itself, so CSRF is unaffected. (8) Secure. (9) the browser does not add an Authorization header on its own, so a cross-site page cannot make the request carry the credential; a cookie used anywhere in the flow brings the risk back. (10) script inside your origin reads the token out of the page and sends the request through your origin, so every origin and token signal is genuinely correct. (11) a check pasted into each page is a check one page forgets; one function called on the first line of every POST branch gives every page, including the next one written, the same protection.
