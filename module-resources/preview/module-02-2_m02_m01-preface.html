What this module is for

This module gives you the words the course is written in, and it puts the code you will work on in front of you.

Correct and secure are different properties. Correct means the code does what its specification says. Secure means it holds up against someone trying to abuse it. When a specification never says what the feature must refuse to do, code can pass every test and still be exploitable. The lecture shows that gap in a few lines of PHP. Then it names what security protects (confidentiality, integrity, availability), where checks belong (the trust boundary), and how an attack travels (source, sink, flow). It explains what a session cookie really is (a bearer credential), and it lists the eight habits a secure developer carries into every feature.

You also reach your own copy of the TechCorp customer portal, a small PHP application that runs in Google Cloud Shell in your browser. There is nothing to install. You sign in to it, change a line, watch the change appear, undo it, and write a short report on what you did. That is the whole edit loop, and the report is the first Markdown file you submit.

The question this module answers

How can code that does everything it was asked to do still be exploited, and what does a developer look at to find out?

What you will be able to do

After Module 01 you can:

  1. Tell correct from secure, and say why a passing functional test does not show the code is safe.
  2. Name the three security objectives and say which one an incident broke.
  3. Locate the trust boundary in a web request and explain why a check in the browser stops no attacker.
  4. Trace a value from its source to its sink and state what injection is.
  5. Explain why a session identifier is a bearer credential, and what ambient authority is.
  6. State the eight principles of the secure developer, and recognize the fail-open and hardcoded-secret code shapes.
  7. Read a CWE number and an OWASP Top 10 category, and tell a vulnerability from a scanner alert.
  8. Launch your course environment, sign in to the portal, change a file, reset it, and write a short Markdown report with evidence.

Before you start

  • Read the syllabus and the authorized-use rule on the Course Materials, Software & Technology Requirements page in the Course Orientation module.
  • Sign in to a Google account in your browser, then launch your environment from the Launch Course Environment page, the last page of this module, and work through its tutorial panel. The lecture asks you to type its examples into a PHP file there, so have it open before you read.
  • Read the Writing in Markdown page in the Course Orientation module. Your lab report is a Markdown file.

Materials

  • The lecture page, which teaches everything the quiz needs.
  • The three required readings named in lecture section 1: OWASP Top 10:2025, the OWASP Secure Product Design Cheat Sheet, and CLARK: Software Security Basics.
  • Your course environment, running the TechCorp customer portal, with its editor and terminal.
  • The Working in Google Cloud Shell and Writing in Markdown pages in the Course Orientation module.

Where you may run this

You change two lines of display text in your own course environment this module and put them back. Nothing is scanned or attacked. Your own environment is the only system you are authorized to test; the Working in Google Cloud Shell page states the rule.

When you are done

Module 01 is complete when you have posted and replied in the introductions forum, submitted the quiz, and submitted the lab report. The report is reports/m01-setup.md, with the NAME / AI DISCLOSURE / REFLECTION block at the top and the three captures: the signed-in customer list, the portal with your change, and the portal after the reset.

If your environment will not launch or you cannot sign in, report what you tried, what you saw, and what you plan to do next, in the same report. A documented blocker with a next step is a complete answer to a setup problem.
