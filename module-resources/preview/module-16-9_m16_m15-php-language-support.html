The main lecture teaches breach analysis, dependency decisions, and secure refactoring. This page explains the PHP used to make a change reviewable: functions and return values, explicit test checks, file hashing, field rules, output representation, and controlled failures. The examples use equipment categories and labels rather than implementing the date-filter assignment.

A PHP test establishes the behavior it actually exercised. It does not prove that a CDN artifact is safe, that a repair is deployed, or that every library call is covered. Those conclusions need the evidence described in the main lecture.

1Extract a function without hiding its result

A refactor changes organization while preserving the behavior that should remain. A function gives a piece of behavior a name and an explicit result.

PHP
<?php
function categoryForPicker(string $raw): string
{
    return $raw;
}

echo categoryForPicker('camera') . "\n";
echo '[' . categoryForPicker('') . "]\n";
Output
camera
[]

string $raw declares the argument type. : string declares the normal return type. return hands the value back to the caller. Calling the function does not change its argument automatically. The caller decides where to store or display the result.

The brackets in the second output are added by the echo expression so you can see the empty-string result. They are not returned by the function. The function currently returns every string unchanged, including strings the feature should reject.

◆Characterization test

A characterization test records behavior that already exists and should continue to work. A security negative test checks behavior the application should refuse. Keeping both distinguishes a complete repair from code that rejects everything.

Source: PHP returning values (opens in a new tab) describes function returns.

2Use explicit checks that actually run

The lecture demonstrates assert. PHP's assertion configuration can disable evaluation, so an apparent successful execution may have checked nothing. A learning test can instead use explicit conditions and a failing exit status.

This standalone program uses a deliberately incomplete category function. It prints both test results before reporting failure.

PHP
<?php
function categoryForPicker(string $raw): string
{
    return $raw;
}

$ordinaryPass = categoryForPicker('camera') === 'camera'
    && categoryForPicker('') === '';
$negativePass = categoryForPicker('<b>camera</b>') === '';
echo $ordinaryPass ? "Characterization: PASS\n" : "Characterization: FAIL\n";
echo $negativePass ? "Negative: PASS\n" : "Negative: FAIL\n";
if (!$ordinaryPass || !$negativePass) {
    exit(1);
}
Output
Characterization: PASS
Negative: FAIL

The process exits with status 1, signaling failure to a runner. === checks exact type and value. && requires both ordinary cases to pass. ! reverses a Boolean, and || means either failed test is enough for the final failure branch.

!Confirm the test was evaluated

Use the explicit checks here or deliberately enable assertion evaluation for a test harness, because assertions can be disabled by runtime configuration. Do not rely on assert as a production input-validation control.

zend.assertions=1 enables generation and execution of assertions. Zero skips execution, and minus one avoids generating assertion code. assert.exception historically affected how failure was reported and is deprecated in modern PHP; explicit exceptions or test-runner checks avoid relying on that setting.

Source: PHP assert (opens in a new tab) describes runtime configuration and why assertions are unsuitable for normal runtime checks.

3Apply a field rule and repeat the same tests

The fictional category feature permits either an empty selection or one of two named categories. The repaired function maps accepted values to themselves and returns empty text for others.

✓PHPSecure
<?php
// WHY: Named choices prevent markup or unrelated strings from becoming a category supplied to a renderer.
function categoryForPicker(string $raw): string
{
    $allowed = ['camera', 'microphone'];
    return in_array($raw, $allowed, true) ? $raw : '';
}

$ordinaryPass = categoryForPicker('camera') === 'camera'
    && categoryForPicker('') === '';
$negativePass = categoryForPicker('<b>camera</b>') === '';
echo $ordinaryPass ? "Characterization: PASS\n" : "Characterization: FAIL\n";
echo $negativePass ? "Negative: PASS\n" : "Negative: FAIL\n";
if (!$ordinaryPass || !$negativePass) {
    exit(1);
}

Secure. Why: Named choices prevent markup or unrelated strings from becoming a category supplied to a renderer.

Output
Characterization: PASS
Negative: PASS

in_array($raw, $allowed, true) checks membership with strict type/value matching. The conditional operator condition ? value_if_true : value_if_false returns the chosen value. The empty selection remains empty because it follows the fallback path.

This function expects a string supplied under an established caller contract. A web handler must check request shape before calling it. A library can still contain a flaw after this caller limits its inputs; the test confirms this local rule, not the library's overall safety.

Source: PHP in_array (opens in a new tab) documents its strict argument.

4Read output helpers separately from validation

A helper can make an output operation consistent across callers. Its return still has a particular destination.

✓PHPSecure
<?php
// WHY: The returned string represents a label as HTML text without deleting its punctuation.
function labelParagraph(string $label): string
{
    $safe = htmlspecialchars($label, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
    return '<p>' . $safe . '</p>';
}

echo labelParagraph('Loan & return') . "\n";
echo labelParagraph('<b>Camera</b>') . "\n";

Secure. Why: The returned string represents a label as HTML text without deleting its punctuation.

Output
<p>Loan &amp; return</p>
<p>&lt;b&gt;Camera&lt;/b&gt;</p>

The local $safe variable holds a new encoded string. The original label is not rewritten. Concatenation adds fixed paragraph tags around the encoded content. This helper produces HTML text content; its name does not make it appropriate for JavaScript, SQL, or a full requester-controlled URL.

A map such as ['daily' => 'daily.pdf', 'annual' => 'annual.pdf'] can likewise keep a caller's choice separate from a filesystem path. array_key_exists($choice, $map) checks whether that key exists. The server retrieves the selected fixed filename; it does not concatenate an arbitrary requester filename into storage paths.

Source: PHP htmlspecialchars (opens in a new tab) documents representation; PHP array_key_exists (opens in a new tab) documents map-key checks.

5Read file hashing and raw-byte representation

Subresource Integrity represents a digest of particular resource bytes. A version number names what you requested; the hash checks which bytes you received. Neither declares those bytes free of vulnerabilities.

This standalone program creates a temporary learning file, hashes it, and removes it. It prints only predictable properties, so the expected output does not require a particular temporary path.

✓PHPSecure
<?php
// WHY: Checking file and hash results prevents a failed read from being presented as a valid integrity value.
$path = tempnam(sys_get_temp_dir(), 'ics230-hash-');
if ($path === false) {
    throw new RuntimeException('Temporary file unavailable');
}
try {
    if (file_put_contents($path, 'Loan kit') === false) {
        throw new RuntimeException('Learning file write failed');
    }
    $digest = hash_file('sha384', $path, true);
    if ($digest === false) {
        throw new RuntimeException('Learning file hash failed');
    }
    echo strlen($digest) . "\n";
    echo strlen(base64_encode($digest)) . "\n";
    $integrity = 'sha384-' . base64_encode($digest);
    $expectedIntegrity = 'sha384-' . base64_encode(hash('sha384', 'Loan kit', true));
    echo $integrity === $expectedIntegrity
        ? "Digest matches learning bytes.\n"
        : "Digest differs.\n";
} finally {
    unlink($path);
}

Secure. Why: Checking file and hash results prevents a failed read from being presented as a valid integrity value.

Output
48
64
Digest matches learning bytes.

hash_file('sha384', $path, true) hashes file contents. The third argument requests 48 raw digest bytes rather than hexadecimal text. Base64 represents those bytes with 64 printable characters. hash applies the same algorithm to the supplied string instead of a file. The comparison checks that the file actually contains the intended learning bytes.

try contains the operation; finally runs cleanup whether the operation succeeds or throws. The example's file is temporary and invented, not a downloaded dependency. In real integrity evidence, record the exact resource URL, version, retrieval source, and digest that were reviewed.

Source: PHP hash_file (opens in a new tab) documents raw output and failure; PHP tempnam (opens in a new tab) documents temporary file creation.

6Read date rules without confusing shape and meaning

A regular expression such as /\A\d{4}-\d{2}-\d{2}\z/ checks a representation: four digits, hyphen, two digits, hyphen, two digits. preg_match returns 1, 0, or false. Comparing !== 1 rejects both a nonmatch and a matching-operation failure.

That shape accepts 2026-99-99. Calendar validation is a separate rule. A date parser may normalize impossible dates or report warnings, so using a parser alone does not establish a valid original value. Check parsing errors and the intended date policy, including permitted range, when the application requires calendar correctness.

A JSON serialization call represents the date as JavaScript-readable data. HTML attribute encoding represents it inside the field. The two outputs still need review at their separate destinations. Server-side field validation prevents an unintended value reaching the library, but a library's later rendering can still create another sink.

Source: PHP preg_match (opens in a new tab) documents match outcomes; PHP DateTimeImmutable createFromFormat (opens in a new tab) describes parsing and normalization.

7Read dependency configuration without inventing a library

Composer's composer.json declares requirements and allowed version constraints. composer.lock records the selected dependency versions and metadata for a resolved build. Composer configuration is JSON data, not executable PHP source. Neither file guarantees that every deployed file matches the intended dependency set or that all dependencies are safe.

For browser resources, a pinned CDN URL and an integrity attribute serve different functions. An SRI digest must represent the actual bytes; hashing a filename, version string, or hexadecimal digest as if it were raw bytes produces a different value. PHP's third hash_file argument is therefore part of the evidence, not a cosmetic choice.

✓Explain what each change proves

Separate version selection, byte verification, caller validation, and regression checks in your report, because they address different questions. A passing field test does not establish integrity of the CDN response.

Source: Composer basic usage (opens in a new tab) describes the manifest and lock file.
