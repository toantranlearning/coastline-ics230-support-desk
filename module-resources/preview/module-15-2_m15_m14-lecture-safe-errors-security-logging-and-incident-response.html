A request fails. The caller needs a controlled response, while the maintainer needs enough information to investigate. This module connects safe error handling, security logs, and response decisions without exposing secrets in either channel.

★A useful error report tells the right reader the right detail.

The security decision and the evidence for it are the focus of this lesson. Use the PHP companion for the language expressions used to implement the controls.

Read this page with your course environment open, so you can type each example into a small PHP file and watch what it does. Red code blocks show a shape to recognize and never ship. Green code blocks show the pattern to copy.

2When prevention fails: fail closed, and record why

The earlier modules stopped attacks before they landed. This module assumes one got through, because in a running system one eventually does. Two questions then decide how bad it gets. Did the software fail into a safe state? And did it leave a record someone can trust?

Code is usually reviewed along the path where everything works. An attacker works the other path: a value of the wrong type, a database that refuses a query, a log file that cannot be written, a condition the designer thought could never happen. That path gets less testing, so it is where the attacker looks first.

★Fail closed, and record why

When the program cannot make a trustworthy decision, it keeps the safest state instead of going ahead. That does not mean every request crashes. It can mean refusing one action, undoing one database change, or taking one feature offline while the rest keeps serving. Whatever it does, it writes down enough that someone can later work out what happened and why.

The opposite is failing open: the check breaks, and the action goes ahead as if the check had passed. The weakness catalog calls it not failing securely (CWE-636). OWASP's category for the whole family of mishandled failures is A10:2025 Mishandling of Exceptional Conditions. Its own words for a transaction that breaks part way through: roll back every part and start again, which it calls failing closed.

The right response depends on which kind of failure it is. The reply that is correct for a mistyped form field is wrong for a crash, and the reverse.

MDN defines the codes. A 400 is a client error such as malformed syntax. A 401 means the client must authenticate. A 403 means the client's identity is known and access is refused. A 409 means the request conflicts with the server's current state. A 500 is the generic code for a situation the server does not know how to handle. A 503 means the server is not ready, as when it is down or overloaded.

The first four rows are conditions you expected, and you can name them to the user without giving anything away. The last row is the dangerous one, and the next section shows why.

OWASP A10:2025 Mishandling of Exceptional Conditions (opens in a new tab) names the category and the roll-back rule. MDN: HTTP response status codes (opens in a new tab) defines each code in the table. CWE-636: Not Failing Securely (opens in a new tab) is the formal entry for failing open.

3What a verbose error tells an attacker

A verbose error is reconnaissance the application performs on the attacker's behalf. The weakness catalog calls it generation of an error message containing sensitive information (CWE-209).

The portal does this today. db.php turns error display on for every page. Its comment says the setting is there so problems show up on the page while the portal is new. The connection is also set to throw an exception on any database error. Together, those two settings mean any failing query prints its exception to the browser.

✕PHPVulnerable
<?php
// WHY: Displaying server error details can disclose queries, paths, and configuration to callers.

// db.php, as shipped
ini_set('display_errors', '1');
error_reporting(E_ALL);
// ...
$pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

Vulnerable. Why: Displaying server error details can disclose queries, paths, and configuration to callers.

Here is what the portal answers when a customer page is asked for a record whose id is not a number. The query is built by concatenation, so the word abc lands inside the SQL.

Response
HTTP/1.1 200 OK
Content-type: text/html; charset=UTF-8

<h2>Customer lookup</h2>
...
<b>Fatal error</b>:  Uncaught PDOException: SQLSTATE[HY000]: General error: 1 no such column: abc

Stack trace:

#1 {main}
  thrown in /home/you/cloudshell_open/coastline-ics230-support-desk/customer.php on line 58

The path is the folder where your portal runs. Everything else is exactly what the page sends.

▸Read the message the way an attacker does

  1. SQLSTATE[HY000] and no such column: abc say the store is SQL, name the engine's error format, and confirm the input reached a live query unchanged. That is the first thing an injection attempt wants to know.
  2. SELECT * FROM c... shows the start of the real statement, so the attacker knows the shape of the query they are feeding.
  3. customer.php:58 names the file and the line that runs the query, which is a target for later attacks and a map of the code.
  4. The absolute path gives away the install folder and the operating system layout.
  5. The status is 200 OK. The page had already started sending HTML before the query ran, so the status could no longer change. Nothing in the response says that anything failed, except the text.

The PHP manual is direct about the setting: error display is a development feature and "should never be used on production systems." The bundled php.ini-production sets it off, and the manual advises error logging in place of error display on production sites. Turning display off is necessary. Section 4 shows why it is not the fix on its own.

CWE-209: Generation of Error Message Containing Sensitive Information (opens in a new tab) is the formal entry, and its examples include a caught SQL exception printed to a web user. PHP Manual: Error handling runtime configuration (opens in a new tab) documents display_errors, log_errors, and error_log and carries the production warning quoted above.

4Safe error handling: one boundary, two messages

The fix splits one failure into two messages for two audiences. The user gets a short reply that says a failure happened and nothing about why. The server log gets the whole record. One random id appears in both, so support can find the record from the reply.

◆Correlation id

A correlation id is a random, meaningless string made for one request and written into both the user's reply and the server's record of what happened. It carries no secret and no internal detail, so it is safe to show. A user quotes it to support, and support finds the full record with it. The same id on every event a request writes is what lets an investigator line those events up later.

How does one failure become a reply the user can see and a record the user cannot?

Handle the failure once, at the edge of the application, so no single page can forget. In PHP without a framework, that edge is set_exception_handler: it registers one function that runs for any exception no try block caught, and the script stops after it runs. Put it in a file every page includes before it writes any output.

✓PHPSecure
<?php
// WHY: Cryptographic random bytes avoid predictable values for security-sensitive identifiers.
// errors.php: included by every page before any output.
ini_set('display_errors', '0');            // backstop, not the fix
ob_start();                                // hold the page until it is complete
$correlationId = bin2hex(random_bytes(8));

set_exception_handler(function (Throwable $e) use ($correlationId): void {
    error_log(json_encode([
        'time'           => gmdate('c'),
        'event'          => 'sys_exception',
        'correlation_id' => $correlationId,
        'class'          => get_class($e),
        'message'        => $e->getMessage(),
        'file'           => $e->getFile(),
        'line'           => $e->getLine(),
    ], JSON_THROW_ON_ERROR) . "\n", 3, __DIR__ . '/../portal-security.log');

    ob_end_clean();                        // throw away the half-built page
    http_response_code(500);
    header('Content-Type: text/plain; charset=utf-8');
    echo "Something went wrong. Quote reference $correlationId to support.\n";
});

Secure. Why: Cryptographic random bytes avoid predictable values for security-sensitive identifiers.

Here is a page that includes it and then fails the same way the customer page did.

✓PHPSecure
<?php
// WHY: One controlled error handler returns a generic response while keeping investigation detail in the designated log.

// orders.php
require_once __DIR__ . '/errors.php';
require_once __DIR__ . '/db.php';

echo "<h2>Order lookup</h2>\n";
$ref = $_GET['ref'] ?? '';
$row = db()->query("SELECT * FROM orders WHERE ref = $ref")->fetch();

Secure. Why: One controlled error handler returns a generic response while keeping investigation detail in the designated log.

The user sees this, and only this.

Response
HTTP/1.1 500 Internal Server Error
Content-Type: text/plain; charset=utf-8

Something went wrong. Quote reference d02854efd559d792 to support.

The log holds the rest, under the same id.

Log entry
{"time":"2026-10-08T16:37:26+00:00","event":"sys_exception","correlation_id":"d02854efd559d792","class":"PDOException","message":"SQLSTATE[HY000]: General error: 1 no such table: orders","file":"\/home\/you\/cloudshell_open\/coastline-ics230-support-desk\/orders.php","line":7}

▸What happens, step by step

  1. errors.php runs first. It turns display off, starts an output buffer, makes an id from eight random bytes written as sixteen hex characters, and registers the handler.
  2. orders.php prints a heading. Because of the buffer, nothing has reached the browser yet.
  3. The query fails. PDO throws a PDOException. No try block catches it, so PHP calls the registered handler with the exception.
  4. The handler writes one JSON line to the log: the time, the id, the exception's class, message, file, and line.
  5. ob_end_clean discards the buffered heading, so the half-built page never goes out. The status becomes 500 and the generic text is sent.
  6. The script stops. The browser has the id. The log has everything else.

The buffer is why the status code works. Without it, the heading would already have been sent, the headers with it, and the status would stay 200 the way it did in section 3.

!Catch Throwable, not Exception

PHP has two separate trees of things that can be thrown. Exception is one. Error is the other, and it covers the type errors and argument errors that hostile input provokes. Error does not extend Exception, so a handler that accepts only Exception never sees those. Throwable is the interface both trees implement, and the manual says it is the base interface for any object that can be thrown, "including Error and Exception." A boundary handler accepts Throwable.

✕PHPVulnerable
<?php
// WHY: Catching Exception alone misses Error objects such as ArgumentCountError in PHP.

try {
    strlen();                      // an ArgumentCountError, which is an Error, not an Exception
} catch (Exception $e) {
    echo "caught\n";
}

Vulnerable. Why: Catching Exception alone misses Error objects such as ArgumentCountError in PHP.

Output
Fatal error: Uncaught ArgumentCountError: strlen() expects exactly 1 argument, 0 given
✓PHPSecure
<?php
// WHY: Catching Throwable covers both Exception and Error objects; the printed detail here is a local teaching demonstration.

try {
    strlen();
} catch (Throwable $e) {
    echo get_class($e), ': ', $e->getMessage(), "\n";
}

Secure. Why: Catching Throwable covers both Exception and Error objects; the printed detail here is a local teaching demonstration.

Output
ArgumentCountError: strlen() expects exactly 1 argument, 0 given

iConfiguration is a backstop, not the fix

display_errors = Off hides the output of failures you never handled. One misconfigured environment, a debug tool left on, or a different server's defaults brings the disclosure back, with no change to your code. Handle the failure in code first. Then turn display off as well, so an unhandled case still stays off the page. Warnings and notices do not throw, so they do not reach the exception handler; set_error_handler is the companion function for those.

iRequest and result are separate evidence

This example records the request before allowing the change. A production implementation must also record the actual success or failure of the update and handle failures between the two writes. An intent record alone does not prove the account was disabled.

✓The pattern to copy

One handler at the boundary, registered before any output. It writes the full detail to the server log under a correlation id, discards any partial page, sets a status that matches the failure, and sends a short generic body with the same id. The user can report the failure. The log can explain it. Nobody has to choose between a system that can be debugged and one that does not leak.

PHP Manual: set_exception_handler (opens in a new tab) documents the handler's Throwable parameter and that execution stops after it runs. PHP Manual: Throwable (opens in a new tab) and PHP Manual: Error (opens in a new tab) confirm that Error implements Throwable and does not extend Exception. PHP Manual: random_bytes (opens in a new tab) documents the cryptographically secure bytes behind the id and the bin2hex example. OWASP Error Handling Cheat Sheet (opens in a new tab) states the rule in one sentence: a generic response is returned by the application, and the error details are logged server side and not returned to the user. W3Schools: PHP Exception Handling (opens in a new tab) has a live editor for try, catch, and throw.

5Logging is the input to detection

An application that fails safely but records nothing has solved half the problem. The weakness catalog calls the other half insufficient logging (CWE-778): when a security-critical event occurs, the product does not record it or leaves out important details. NIST puts the reason plainly: logs are particularly important for recording and preserving information that is vital to incident detection, response, and recovery.

Start with what the portal keeps today, because the gap is the incident. The built-in server writes one line per request to its own log, which scripts/start.sh sends to /tmp/techcorp-portal.log. Here is the line for an administrator disabling a staff account.

Log entry
[Thu Oct  8 09:30:10 2026] 127.0.0.1:56364 [302]: POST /admin.php

What does that line answer, and what does it leave out?

The line says a POST reached admin.php and was answered with a redirect. It cannot say who sent it, which account was changed, whether it was enabled or disabled, or whether the change succeeded. admin.php itself reads a username and an action from the form, runs one UPDATE on the users table, and redirects back to the page. It writes nothing else. The same is true of sign-in: auth_login returns false on a bad password and the page shows a message, and no record of the attempt exists anywhere. The login_failures table is in the schema, and nothing writes to it or reads it yet. The upload page records uploaded_by and uploaded_at on the documents row, which is a business record of the file, not an audit record of the action.

The OWASP cheat sheet says to log these where possible. Input validation failures. Authentication successes and failures. Authorization failures. Session management failures. Application errors. Higher-risk functions such as user administration, administrator actions, sensitive data access, and data export. Put against the portal, that list is the module's job.

  • sign-in success and failure, so a spray of failed attempts across many accounts becomes visible;
  • authorization denials, because a refused action is a control firing and often the first sign of probing;
  • validation failures, which show malformed or hostile input arriving;
  • administrator actions, which carry the most authority and so the most risk;
  • reads of sensitive records, so access to customer data can be reconstructed.

A useful event answers a fixed set of questions. The cheat sheet groups them as when, where, who, and what. When is the time of the event. Where is the application and the part of it that emitted the event. Who is the source address and the user identity. What is the type of event, its severity, and a description. Add the outcome, the reason, and the correlation id from section 4. Write each value into its own field.

✓PHPSecure
<?php
// WHY: Serialization represents structured values as data rather than hand-built executable syntax.
function log_security_event(array $fields): bool
{
    $entry = ['time' => gmdate('c'), 'app' => 'portal'] + $fields;
    $line  = json_encode($entry, JSON_THROW_ON_ERROR) . "\n";
    return error_log($line, 3, __DIR__ . '/../portal-security.log');
}

$ok = log_security_event([
    'event'          => 'authz_fail',
    'actor_id'       => 'rmarsh',
    'action'         => 'customer.read',
    'object_type'    => 'customer',
    'object_id'      => '7',
    'outcome'        => 'denied',
    'reason'         => 'not_assigned_rep',
    'source_ip'      => '203.0.113.7',
    'correlation_id' => '3f9a2c7e5b1d0a84',
]);

Secure. Why: Serialization represents structured values as data rather than hand-built executable syntax.

Log entry
{"time":"2026-10-08T16:32:24+00:00","app":"portal","event":"authz_fail","actor_id":"rmarsh","action":"customer.read","object_type":"customer","object_id":"7","outcome":"denied","reason":"not_assigned_rep","source_ip":"203.0.113.7","correlation_id":"3f9a2c7e5b1d0a84"}

▸Reading the helper

  1. gmdate('c') writes the current time in UTC in the ISO 8601 form, with its offset, so lines from different machines can be put in order. The vocabulary cheat sheet asks for that exact form.
  2. The + merges the two fixed fields with whatever the caller passed. Every line starts the same way.
  3. json_encode turns the array into one line of JSON. JSON_THROW_ON_ERROR makes a bad value throw instead of returning false, so a failure cannot slide into the log as the word false.
  4. error_log with type 3 appends the string to the named file. The manual notes it adds no newline, so the helper adds one, and that a relative path depends on the working directory, so the helper builds an absolute one.
  5. The path is one folder above the project. The portal's router serves any file that exists inside the project folder, so a log kept there would be downloadable, which is the Module 02 incident again.
  6. The function returns what error_log returns: true when the line was written, false when it was not. Section 7 uses that.

The OWASP Logging Vocabulary Cheat Sheet gives standard event names, so events from different parts of a system line up: authn_login_success, authn_login_fail, authz_fail, sys_crash, and others in the same shape. Use its names where one fits, and its shape where none does.

Each security decision writes one line as it happens. What do the lines look like across one administrator's session?

◆Security event

A security event is a structured record of one security-relevant thing that happened, carrying the fields an investigator needs and nothing else. Note what the example above does not contain: the customer record's contents, the rep's name or email, and the request body. It stores object_type and object_id rather than the object, and actor_id rather than the person. That is enough to rebuild a timeline without hoarding personal data.

OWASP Logging Vocabulary Cheat Sheet (opens in a new tab) gives the event names and the ISO 8601 rule. 6What must never enter a log

A log that captures too much is its own breach. The usual way a secret lands in a log is not malice. It is a well-meaning dump of the whole request.

✕PHPVulnerable
<?php
// WHY: Building structured output from unchecked text can change the output structure.
// "Log everything, we might need it." The password goes with it.
error_log('login attempt: ' . json_encode($_POST));

Vulnerable. Why: Building structured output from unchecked text can change the output structure.

Log entry
login attempt: {"username":"rmarsh","password":"hunter2"}

That line is a fresh compromise. Anyone who can read the log now holds a working credential, and nothing errored to warn you. The weakness catalog calls it insertion of sensitive information into a log file (CWE-532).

✕A secret in a log is a new breach, and it is silent

Never write a password to a log, including a failed one. The same goes for a session id, a reset or access token, a full payment card or tax number, an API key, a private key, and a database connection string. Nothing fails when you do. The application keeps working. The secret sits in a readable file, often copied to a central collector and into backups, until someone reads it. Log the fact. Never log the secret.

The repair records that the event happened and who it involved, using identifiers that are not secrets.

✓PHPSecure
<?php
// WHY: Structured event fields preserve the meaning of an action without depending on ambiguous prose.

log_security_event([
    'event'     => 'authn_login_fail',
    'actor_id'  => $username,       // an identifier, not a secret
    'outcome'   => 'invalid_credentials',
    'source_ip' => $sourceIp,
]);

Secure. Why: Structured event fields preserve the meaning of an action without depending on ambiguous prose.

The OWASP cheat sheet's exclusion list is longer than the critical block above. It also names application source code, sensitive personal data, data a user did not consent to provide, and anything above the logging system's own classification. Such data is removed, masked, hashed, or encrypted before it is written. A hashed session id may be kept where one is needed. A failed password is still a secret. It is often a real password typed into the wrong field.

OWASP Logging Cheat Sheet, data to exclude (opens in a new tab) is the list. CWE-532: Insertion of Sensitive Information into Log File (opens in a new tab) is the formal entry. OWASP Proactive Controls C9: Implement Security Logging and Monitoring (opens in a new tab) states the same rule for passwords, session ids, card numbers, and social security numbers.

7Keeping the log trustworthy

A log is evidence only if it can be trusted. Two different problems undermine that: an attacker who writes into it, and an attacker who reaches it.

Recall the words from Module 01: a source is where untrusted data enters, and a sink is the operation that hands data to another reader. A log is a sink. Its reader is the investigator, and the grammar they read is "one line is one record." Untrusted text written straight into that grammar is injection aimed at your own evidence. The weakness catalog calls it improper output neutralization for logs (CWE-117).

✕PHPVulnerable
<?php
// WHY: Concatenating untrusted text into a line allows newline characters to forge additional log entries.

// Plain text, the value pasted straight into the line.
file_put_contents(
    '/var/log/portal/app.log',
    date('c') . " login user=$username\n",
    FILE_APPEND
);

Vulnerable. Why: Concatenating untrusted text into a line allows newline characters to forge additional log entries.

A username is untrusted input. Suppose someone submits alice, then a newline, then 2026-07-26T20:15:00+00:00 login user=admin. The newline ends the real line and a forged one follows it.

Log entry
2026-07-26T20:14:13+00:00 login user=alice
2026-07-26T20:15:00+00:00 login user=admin

The second line looks exactly like a genuine event. How does a structured record stop that?

iThe same defense as a parameterized query

Module 04 removed SQL injection by keeping the value out of the command's grammar. Structured logging does the same at this sink. json_encode writes a newline inside a string as the two characters \n, so the hostile value stays inside one field no matter what it contains, and it can never start a new record. The attempt is also visible: one username with a fake log line inside it is itself a security event.

Log entry
{"event":"authn_login_fail","actor_id":"alice\n2026-07-26T20:15:00+00:00 login user=admin","outcome":"invalid_credentials"}

The other problem is the log as a target. The OWASP cheat sheet and Proactive Control C9 give the rules for protecting it. Here they are, with what each one defends against:

  • restrict who can write and who can read, and record every access to the log itself, so the record outlives the person it describes;
  • build in tamper detection, so a changed or deleted record can be noticed;
  • copy logs off the host that writes them, and to read-only storage as soon as possible, so a compromised host cannot edit its own history;
  • synchronize time across every machine, because a timeline built from clocks that disagree is fiction;
  • notice when logging stops, since an attacker who can force a logged error can repeat it until the disk fills;
  • set retention by legal, regulatory, and contractual need, and keep logs no longer than that, because a log is also personal data.

The last rule has a second half people skip. The cheat sheet says logs must not be destroyed before the required retention period and must not be kept beyond it. Retention is a decision, not a default.

What should happen when the log cannot be written? The cheat sheet says a logging failure must not stop the application or leak information. For an action whose requirement includes being recorded, failing closed from section 2 means refusing that one action with a safe message while everything else keeps serving. OWASP A09's own prevention list ends the point with two words: always fail closed.

✓PHPSecure
<?php
// WHY: The rejection branch must stop or exclude further processing so denied input cannot reach the protected operation.
// Record the request first. It is not yet evidence of a successful update.
$written = log_security_event([
    'event'       => 'account_disable',
    'actor_id'    => $actorId,
    'object_type' => 'user',
    'object_id'   => $username,
    'outcome'     => 'requested',
]);

if (!$written) {
    http_response_code(503);
    exit("This action could not be recorded, so it was not performed. Try again later.\n");
}

q('UPDATE users SET disabled = 1 WHERE username = ?', [$username]);
// A completed implementation also records the actual update result.

Secure. Why: The rejection branch must stop or exclude further processing so denied input cannot reach the protected operation.

Response
HTTP/1.1 503 Service Unavailable

This action could not be recorded, so it was not performed. Try again later.

iRequest and result are separate evidence

This example records the request before allowing the change. A production implementation must also record the actual success or failure of the update and handle failures between the two writes. An intent record alone does not prove the account was disabled.

✓The pattern to copy

Write untrusted values into fields, never into the line. Keep the log outside the published folder. Restrict and record access to it. Copy it off the host. Keep clocks in step. Watch for the log going quiet. Set a retention period on purpose. When an action must be auditable and the record cannot be written, refuse the action and say so in plain words.

8From a log line to a response

Having a log is routinely mistaken for being able to detect an attack. Four separate functions stand between an event and a person acting on it, and each one can be missing on its own.

Loggingwrites down that an event happenednothing to investigate afterward
Monitoringcompares events and system state against expectationsdata nobody looks at
Alertingtells a named owner when a condition is metdetection with no reaction
Responsea person investigates and actsan alert everyone has learned to ignore

Which of the four is the portal missing today, and what is lost at each break?

A log sitting unread on a host supports a later reconstruction and detects nothing in the moment. OWASP A09 lists both failures by name: logs of applications and APIs that are not monitored for suspicious activity, and alerts that are not received or reviewed within a reasonable time. It also names the two things an alert needs that teams forget: a threshold, and a playbook for the person who receives it.

◆Alert, threshold

An alert is a message to a named owner that a defined condition has been met. A threshold is the line that defines the condition: how many of which events, in what time window, from what source. Ten failed sign-ins on one account inside five minutes is a threshold. A usable alert names its signal and threshold, the asset affected, a priority, an owner, who to escalate to, and the playbook to run. An alert path that has never fired is an assumption, so fire it on purpose and confirm a person received it.

Module 02 section 10 defined the playbook and the runbook, and the lifecycle a response follows: preparation, detection and analysis, containment, eradication, recovery, and lessons learned. This module adds the input side of detection. The carrier's own playbook, which TechCorp's runbook was adapted from, makes the link concrete. Its preparation step P-2 requires centralized logging of security-relevant events, kept twelve months with ninety days available for immediate query. Its detection step D-6 applies once an incident is suspected. It says to retrieve all authentication events, privilege changes, and administrative actions for the affected systems, covering the thirty days before the earliest suspected activity. Every one of those is an event the portal did not write. A playbook step that asks for records that do not exist cannot be run.

NIST's current guidance says the same from the other direction. Its detection outcomes call for continuously monitoring log events for known malicious and suspicious activity, for transferring log data to a small number of log servers, and for correlating events from multiple sources. Correlation needs a shared key, which is what the correlation id and a synchronized clock provide.

iTwo incident-response ideas from Module 02 that this module relies on

After detection comes analysis and containment, before eradication and recovery; acting out of order destroys evidence. And before any destructive cleanup, a responder preserves the evidence and establishes scope, because a rebuild answers none of the questions that matter. Both come from the lifecycle in Module 02. Here, the log lines are the evidence being preserved.

Cyber Incident Response Playbook, Kestrel Specialty Insurance Group is the carrier document; its sections 4 and 5 hold steps P-2 and D-6. The NIST detection outcomes (DE.AE) are in SP 800-61 Rev. 3, linked in section 5. The alert conditions are from the A09 entry in section 1.

!Silence in a log is not evidence of absence

A log that was never written cannot show that something did not happen. "No failed sign-ins were recorded" is a statement about the logging, not about the sign-ins. Write the two apart. The carrier's playbook, step D-9, puts it as a rule: where scope cannot be established, state so explicitly rather than estimating. Its step D-4 adds that the initial severity is not binding and may be revised as understanding improves.

The 72-hour clock that section 1 records starts at Discovery, whatever the records show. The carrier requires notice within seventy-two hours of Discovery for any incident reasonably likely to result in a claim. A thin timeline does not pause it.

Section 8, the notification determination, asks who decided whether anyone must be told, on what basis, and the outcome. The form says that when regulated data categories are involved, counsel makes this call, not the technical team, and that the carrier's involvement is recorded. The basis is the data categories in section 3. That is why section 3 names a tax identifier rather than "customer data." The technical team's part is to state, with its confidence, what the records establish and what they cannot rule out. When the records cannot show whether data was reached, the determination says that in those words. The worked example from Module 01 did exactly this. Counsel directed that distribution of the data be assumed rather than argued, because nothing inside the company could answer the question.

What does each path look like from the records to the two judgments?

◆Notification determination, confidence

The notification determination is the recorded decision on whether affected people, the carrier, or a regulator must be told, with who decided it, the basis, and the outcome. Confidence is the writer's honest statement of how well the records support a conclusion: established by a named record, inferred from partial records, or not determinable. A determination written with its confidence can be revisited when new records arrive. One written as a bare yes or no cannot.

12Common misconceptions

  • ✕"Hide the error with a friendly page or some CSS."

    If the detail was sent to the browser, it was disclosed. What the page chose to display is not the question. The response body is.

  • ✕"Turn display_errors off and the leak is fixed."

    That hides output from failures you never handled. One misconfigured environment or debug tool brings it back. Handle the failure in code, then turn display off as a backstop.

  • ✕"Catch Exception and you have caught everything."

    PHP's Error tree, including the type and argument errors hostile input provokes, does not extend Exception. The boundary accepts Throwable.

  • ✕"Log everything, so nothing is missed."

    Excess data creates privacy exposure, storage cost, and noise that buries the real event. Record what answers an investigator's questions and nothing more.

  • ✕"A failed password is fine to log, since it was wrong anyway."

    It is still a secret, and often a real password typed into the wrong account. Log the attempt and the actor, never the password.

  • ✕"We have logs, so we would detect an attack."

    Logging is one function. Monitoring, alerting, and response are three more, and each can be absent on its own.

  • ✕"Nothing was logged, so nothing happened."

    A log that was never written cannot show absence. Say what the records establish and what they cannot, and choose the severity on reasonable suspicion.

  • ✕"Failing closed means taking the whole site down."

    It means keeping the safest state for the affected action, which is usually one request refused while the rest keeps serving.

13Check your understanding

Work these before you look at the answers.

  1. A page throws an unexpected exception. What should the user see, and what should the server keep?
  2. What is a correlation id, and why is it safe to show a user?
  3. Name four categories of security-relevant event a log should record.
  4. Which weakness is it when the application records none of them, and how did that leave gaps in the earlier incident timelines?
  5. List four things that must never be written to a log.
  6. How does an untrusted value forge a second line in a plain-text log, and what removes the problem?
  7. Why is turning display_errors off necessary but not the fix?
  8. Why does the boundary handler accept Throwable rather than Exception?
  9. A log exists but no attack was detected. Which three functions beyond logging were missing?
  10. A sensitive action must be auditable, and the log cannot be written. What should happen, and why?
  11. The portal wrote no sign-in records. What does "no failed sign-ins were recorded" establish about the sign-ins, and what word does the severity rest on instead?
  12. What decides log retention?

Answers: (1) a generic message and a correlation id, with the exception class, message, file, line, and trace kept only in the server log. (2) a random, meaningless string written into both the reply and the server record; it carries no secret or internal detail, so the user can quote it and support can find the record. (3) any four of sign-in successes and failures, authorization denials, validation failures, administrator actions, and reads of sensitive records. (4) insufficient logging (CWE-778); the events were never written, so who did what and when could not be reconstructed. (5) any four of passwords including failed ones, session ids, reset or access tokens, full card or tax numbers, API or private keys, connection strings. (6) a newline in the value ends the real line and starts a forged one; structured logging keeps the value inside one field, because json_encode writes the newline as \n. (7) it hides unhandled output, but one misconfiguration or debug tool brings the disclosure back, so the failure is handled in code and display is turned off as a backstop. (8) PHP's Error types do not extend Exception, and Throwable is the interface both implement. (9) monitoring, alerting, and response. (10) the action is refused with a safe message, because an action that must be recorded has not met its requirement if it cannot be, which is failing closed. (11) nothing about the sign-ins, only that the logging was absent; the severity rests on "reasonably suspected." (12) legal, regulatory, and contractual need, and the risk of holding the data; logs are kept no shorter and no longer than that.
