What you will do

The problem: a visitor who has not signed in can download sensitive files directly. Requesting /data/seed.sql or /data/portal.sqlite returns the file, including the portal's fictional customer and staff-account data. The visitor never needs to open a PHP page, so the sign-in checks on those pages do not protect the files.

Ticket PORTAL-118 asks you to investigate this direct-access flaw. Reproduce it on the original site, change fixed/router.php to refuse /data/ requests, and prove that the requests are blocked while signed-in customer use still works. Plan about 60–75 minutes.

Design lesson — OWASP A06 Insecure Design: sensitive data files were placed inside the directory the web server serves. Your deny rule is a mitigation for that design decision; it blocks the assigned URLs but leaves the files in that directory. Moving sensitive storage outside the served directory would address the file-placement flaw. This lab asks you to apply and explain the mitigation.

This early report is a short worksheet: three claim rows, one flow, one threat, and a before/after table. Brief answers are enough. The full threat-modeling method remains in the lecture for practice; an exhaustive audit, diagram, STRIDE register, and ranked backlog are not required for this submission.

Step 3: Download the files without signing in

These terminal requests do not send a portal login cookie. They show what someone can download without signing in, even if your browser tab is signed in.

  1. In the file list on the left, click the arrow beside site, then click DESIGN.md. Read the Authorization and Deployment sections. They claim visitors cannot reach application data and supporting files are not served.
  2. Click inside the terminal at the bottom of Cloud Shell. Paste this command and press Enter:
Bash
curl -sS -i http://127.0.0.1:8080/data/seed.sql
  1. Look for HTTP/1.1 200 OK near the top, followed by SQL text. 200 means the server sent the file. Copy that status line and two or three lines of SQL into the report's evidence block.
  2. Now paste this command and press Enter. It saves the database to a file rather than filling the terminal with unreadable binary data:
Bash
curl -sS -D reports/m02-before-headers.txt -o reports/m02-before.sqlite http://127.0.0.1:8080/data/portal.sqlite
  1. Paste this command and press Enter to display the response information:
Bash
cat reports/m02-before-headers.txt
  1. Find its status line. It should also say 200 OK. Copy the actual line into your report.
  2. Paste this command and press Enter to identify the downloaded file:
Bash
file reports/m02-before.sqlite
  1. The output should identify a SQLite database. Copy that output into your report. You have now downloaded both files without signing in. Keep the downloaded database in Cloud Shell; do not submit it.
  2. In your report's first two claim rows, mark each claim supported or contradicted by these results. Add the status or file-identification evidence beside your answer.
  3. Open the original portal's 8080 browser tab. Sign in as rmarsh if needed. Click Customers, then click one customer's account link. In the third claim row, record whether those pages opened.
  4. In the editor, open site/router.php. Press Ctrl+F (Cmd+F on a Mac), search for file_exists, and read the block containing return false. That branch lets the server send an existing file directly. In the worksheet, explain in one sentence why a sign-in check on a different PHP page did not stop the downloads.

Fill in the three short design prompts

  1. In the worksheet's Flow line, put /data/seed.sql on the request arrow and the downloaded SQL on the return arrow. Name the browser-to-server boundary: the request came from outside the server. No drawing is required.
  2. In Threat and STRIDE category, write one sentence saying who could download what data. Compare that threat with the six STRIDE categories in lecture section 5, choose one, and state why it fits.
  3. In Requirement, finish “The portal must…” with a rule describing who must be refused access to these files and what response should show the refusal. You will test that rule next.

Step 4: Add the blocking rule to fixed

  1. In the editor's file list, expand fixed, then click router.php. Check the editor tab's path: it must be fixed/router.php, not site/router.php.
  2. Press Ctrl+F (Cmd+F on a Mac). Search for $path =. Close the Find box. You should see this existing line:
PHP
$path = parse_url($_SERVER['REQUEST_URI'] ?? '/', PHP_URL_PATH) ?: '/';
  1. Click at the end of that line and press Enter. Paste the following code on the new line, before the existing // The site root comment. Do not add another <?php tag.
PHP
// Block direct requests for the data folder.
if (str_starts_with($path, '/data/')) {
    http_response_code(403);
    exit("Forbidden\n");
}
  1. Read the three actions: str_starts_with checks the requested path, http_response_code(403) sets the refusal status, and exit stops the router before it can serve the file. This rule blocks all /data/ requests, including unsigned-in requests.
  2. Save with Ctrl+S (Cmd+S on a Mac). Leave site/router.php unchanged.
  3. Click inside the terminal. Paste this command and press Enter:
Bash
php -l fixed/router.php
  1. Look for No syntax errors detected in fixed/router.php. Copy the actual output into your report. If PHP reports an error, compare your pasted block with the example above, check its braces and semicolons, save, and run the command again. A clean syntax check means the file can be read by PHP; the next step checks whether it blocks the downloads.

Actual Cloud Shell IDE: fixed is expanded on the left and router.php is selected. Insert the supplied rule on the blank line after $path is set, before the site-root branch. The exact code above remains selectable text.

Step 5: Check that the rule works

  1. In the terminal, paste this command and press Enter. Notice 8081: this request goes to your changed copy.
Bash
curl -sS -i http://127.0.0.1:8081/data/seed.sql
  1. Look for 403 Forbidden and a body saying Forbidden, instead of the SQL file. 403 means access was refused. Put the actual status in the report table's Fixed 8081 column for /data/seed.sql.
  2. Run this command for the database:
Bash
curl -sS -i http://127.0.0.1:8081/data/portal.sqlite
  1. Check for 403 Forbidden again. Put the actual status in the table's Fixed 8081 column for /data/portal.sqlite. Copy both status lines into the evidence block.
  2. Repeat the port-8080 commands from Step 3, actions 2, 4, and 5. The original should still send both files with 200 OK. Enter those actual statuses in the table's Original site 8080 column.
  3. Open the 8081 portal tab. Sign in as rmarsh if needed, click Customers, then click one customer's account link. Both pages should still open. Record what you saw in the table's legitimate-use row. Also record the original site's result from Step 3.
  4. If 8081 still sends a file, check that you edited and saved fixed/router.php, placed the new block immediately after $path is set, and tested port 8081. Run the syntax check again after correcting an edit.
  5. In the report's explanation, answer these two questions in one sentence each: Are the data files still inside the served folder? What would happen if this blocking rule were absent? This explains why the rule is a temporary control, or mitigation, rather than removal of the file-placement flaw.
  6. Leave the rule in fixed/router.php. You will keep this repair for later course work.
