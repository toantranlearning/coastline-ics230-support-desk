What you will do

Ticket PORTAL-118 asks whether the design document's claim that supporting files are not served is true. Read that claim, observe two exposed data files, add one routing stopgap, and prove that ordinary customer use still works. Plan about 60–75 minutes.

This early report is a short worksheet: three claim rows, one flow, one threat, and a before/after table. Brief answers are enough. The full threat-modeling method remains in the lecture for practice; an exhaustive audit, diagram, STRIDE register, and ranked backlog are not required for this submission.

Step 1: Open both portals

  1. Launch Google Cloud Shell (opens in a new tab) with the Google account used for setup. Open your existing course folder containing site, fixed, reports, and scripts.
  2. Select Open Editor if needed. Right-click the course folder and choose Open in Integrated Terminal.
  3. Run this command and press Enter:
Bash
bash scripts/start.sh
  1. Wait for both startup messages. Open Web Preview → Preview on port 8080 for site, then Web Preview → Change port → 8081 for fixed.
  2. Sign in separately with fictional username rmarsh and password password. Check the port before each test. Leave site/ unchanged and keep earlier repairs in fixed/.

Use the Cloud Shell Guide for first setup or startup problems. Test only your own copies under the course Rules Of Engagement.

Step 2: Start the supplied report

  1. In the editor, open assignments/early-reports/m02-design-audit-starter.md.
  2. Copy it into the workspace-level reports/ folder and name the copy m02-design-audit.md. From the workspace-root terminal you can use:
Bash
cp assignments/early-reports/m02-design-audit-starter.md reports/m02-design-audit.md
  1. Fill in your name and disclosure. Complete its prompts as you work. You can also download the report starter from this page.

Step 3: Read and observe

  1. Open site/DESIGN.md. Read its Authorization and Deployment sections.
  2. In your report, use the three supplied rows to assess these claims: supporting files are not served; unsigned-in visitors cannot reach application data; a representative can open the Customers page after signing in. Use observed evidence, not the design document alone.
  3. From the workspace terminal, request both files without sending a sign-in cookie. Save the binary database to a file rather than printing it:
Bash
curl -sS -i http://127.0.0.1:8080/data/seed.sql
curl -sS -D reports/m02-before-headers.txt -o reports/m02-before.sqlite http://127.0.0.1:8080/data/portal.sqlite
cat reports/m02-before-headers.txt
file reports/m02-before.sqlite
  1. Record actual status lines, a short SQL excerpt, and the database file identification. The starting site is expected to return 200 for both. Keep the downloaded database local; do not submit it.
  2. Open site/router.php and locate $path and the branch that serves existing files. Explain in one sentence why signing in on a PHP page does not protect these file requests.
  3. Complete the starter's one-line flow: visitor → web server/router → data file. Label the requested path and returned data; name the browser-to-server trust boundary. No separate diagram is required.
  4. In the starter's Threat and STRIDE category line, name who could misuse the observed flow, what they could obtain, and which asset is affected. Open this module's lecture section 5, compare your threat with the six STRIDE definitions, and choose the best-matching category. Add a short reason; you only need one threat.
  5. In the Requirement line, finish “The portal must…” with the access rule your test should demonstrate. Include the protected path, who should be refused, and an observable outcome. Use lecture section 6 to check that another person could test your sentence.
  6. For each claim row, write supported or contradicted and add the exact status or page observation that led to that decision. For the sign-in claim, use the original 8080 preview: open Customers and one account, then record what loaded.

Step 4: Apply the stopgap in fixed

  1. Open fixed/router.php. Find the statement that sets $path.
  2. Open lecture section 10 beside the editor and find the PHP example that blocks /files/. Read the condition and its rejection branch before using it.
  3. In fixed/router.php, use Ctrl+F (Cmd+F on a Mac) to find $path =. Place the new rule immediately after that statement and before any routing branch.
  4. Adapt the lecture's rule so its condition uses str_starts_with($path, '/data/'), its rejection branch calls http_response_code(403), and processing stops with exit. The rule should reject the path before the existing-file branch can serve it. Preserve the surrounding PHP syntax.
  5. Change only this routing rule. Leave the original site/router.php unchanged.
  6. Save with Ctrl+S (Cmd+S on a Mac), then check syntax from the workspace root:
Bash
php -l fixed/router.php
  1. Resolve syntax errors before continuing. No syntax errors detected establishes parsing; the next step checks behavior.

Step 5: Prove the result

  1. Run both requests against fixed, port 8081:
Bash
curl -sS -i http://127.0.0.1:8081/data/seed.sql
curl -sS -i http://127.0.0.1:8081/data/portal.sqlite
  1. Record actual status lines. Both should return 403. Repeat the original port-8080 requests to confirm the comparison copy still returns 200.
  2. In the 8081 preview, sign in as rmarsh, open Customers, and open one customer's account. Record the actual result so you show legitimate use still works.
  3. In the worksheet's results table, enter each actual port-8080 status under Original site and each port-8081 status under Fixed. For the legitimate-use row, describe whether Customers and one account opened in each copy. Do not replace a failed result with the expected value.
  4. In the supplied fenced text block, replace the bracketed prompt with the actual syntax-check output, request status lines, and database file identification. Keep the opening and closing triple backticks so Markdown preserves the evidence.
  5. Explain in two sentences why the rule is a mitigation: where do the files still live, and what would happen without the rule? Retain the stopgap in fixed/ for later work.

If a result differs, record the exact error and copy/port, inspect the rule's position, and rerun the syntax check. Ask for help with that evidence; do not reset unrelated repairs or invent a passing result.

Step 6: Report and submit

  1. Finish the supplied prompts with short answers. Keep your name, disclosure, and a two-sentence reflection. No full TC-IR-01 report is required yet.
  2. Save and use Markdown: Open Preview from the command palette to check the worksheet.
  3. Download reports/m02-design-audit.md and the complete changed fixed/router.php by right-clicking each file and choosing Download.
  4. In this lab's Canvas assignment, choose Start Assignment, upload both files, and select Submit Assignment. Check the confirmation and filenames. Screenshots are optional if text evidence is sufficient; upload any you reference.

What to submit

  • m02-design-audit.md: completed short worksheet with three claims, one flow/threat/requirement, test results, brief explanation, and disclosure/reflection.
  • router.php: your complete changed file from fixed/.
  • Any optional image evidence referenced in your report.

Keep the working change in your portal. Do not submit the database, original site, or a full application archive. The separate readiness review follows this lab.

Open notes and open book are both fine. Respond in your own words; do not copy from other sources.
