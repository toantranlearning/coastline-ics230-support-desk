Your team has made decisions about identity, ownership, responses, and failure. PHP is how your individual build expresses those decisions. This page helps you follow the language statements and explain where each decision takes effect. The main lecture teaches secure design and verification; this support page introduces no additional graded syntax requirements.

The examples use a fictional equipment-reservation API, separate from the partner API you build. The first program runs without HTTP, a database, or the portal helpers. It models an already authenticated identity rather than implementing authentication. Later fragments explain how the same PHP constructs appear in a web handler.

iKeep predicted output separate from evidence

Output shown here is the expected result of a learning example. Your build report needs actual requests and responses from your own implementation, because an example cannot establish what your handler did.

1Read one complete function

A function groups statements and gives that group a name. A caller supplies arguments, and return hands a result back to that caller. Here, reservationView selects the public fields of a reservation when its owner matches the authenticated member.

✓PHPSecure
<?php
// WHY: Explicit types and an ownership comparison make the accepted inputs and returned data visible for review.
declare(strict_types=1);

function reservationView(array $reservation, int $memberId): ?array
{
    if ($reservation['member_id'] !== $memberId) {
        return null;
    }
    return [
        'id' => $reservation['id'],
        'label' => $reservation['label'],
    ];
}

$reservation = ['id' => 7, 'member_id' => 12, 'label' => 'Loan kit'];
$authenticatedMemberId = 12;
$result = reservationView($reservation, $authenticatedMemberId);
if ($result === null) {
    echo "Not found.\n";
} else {
    echo json_encode($result, JSON_THROW_ON_ERROR) . "\n";
}

Secure. Why: Explicit types and an ownership comparison make the accepted inputs and returned data visible for review.

Output
{"id":7,"label":"Loan kit"}

The reservation array has three entries. The response array has two. Creating a new response array selects the permitted fields; it does not alter the original reservation. The owner's identity is intentionally omitted from the public response.

declare(strict_types=1) affects scalar type handling for calls made from this file. It does not validate the contents of an array, establish authentication, or check a business rule. The example assumes the reservation comes from trusted test data with an integer member_id. A real handler must establish its input contracts and normalize database types deliberately.

★A type declaration describes a value, not its authority

An integer can still be a caller's invented identity. The value used for ownership must come from authentication, because the PHP type alone cannot establish who the caller is.

▸Follow the non-owner branch

With integer 13, PHP evaluates 12 !== 13 as true. It executes return null, leaves the function, and assigns null to $result. The caller's $result === null condition is true, so Not found. is printed. The response-array construction is never reached.

3Distinguish return, echo, and exit

return ends the current function and supplies its result. echo writes output and continues. exit ends the script. These operations have different consequences for a handler.

PHP
<?php
function describeMethod(string $method): string
{
    if ($method !== 'GET') {
        return 'Unsupported method';
    }
    return 'Read request';
}

echo describeMethod('POST') . "\n";
echo "Caller continued.\n";
Output
Unsupported method
Caller continued.

The return skipped the function's remaining statements, but the caller continued. A helper returning an error value does not automatically stop the endpoint. The caller has to handle that value before it queries or writes data.

Source: PHP return (opens in a new tab) explains the difference between returning inside a function and returning from a file.

4Read a prepared query and its parameter array

This fragment requires a configured PDO connection called $pdo. It is not a standalone exercise.

✓PHPSecure
<?php
// WHY: The fixed query separates bound values from SQL structure and restricts the selected row to the authenticated owner.
$stmt = $pdo->prepare(
    'SELECT id, label FROM reservations WHERE id = ? AND member_id = ?'
);
$stmt->execute([$reservationId, $authenticatedMemberId]);
$row = $stmt->fetch(PDO::FETCH_ASSOC);
$result = $row === false ? null : $row;

Secure. Why: The fixed query separates bound values from SQL structure and restricts the selected row to the authenticated owner.

-> calls a method on an object. $pdo->prepare(...) returns a statement object, stored in $stmt. The statement's execute method receives an indexed array of values. The first value fills the first ?; the second fills the second ?. Parameter order is significant.

PDO::FETCH_ASSOC is a named class constant requesting an associative array: column names become array keys. fetch returns false when there is no next row. The last line uses the conditional operator condition ? first_value : second_value to normalize that outcome to null.

The course helper q_one($sql, $params) performs preparation, execution, and fetching, and returns one associative array or null. q_all returns an array of rows, possibly empty. A helper that returns null has not decided which HTTP response to send; that decision belongs to the handler.

!Binding does not supply an ownership rule

Keep both the object condition and the authenticated owner condition in the query for this design, because binding only separates values from SQL syntax. A perfectly bound query selecting by object id alone can still return another user's record.

A placeholder represents a value. It cannot stand for an arbitrary table name, column name, or SQL keyword. Where a design permits selectable sorting, its code must map permitted choices to fixed SQL fragments rather than bind a keyword.

Source: PHP PDO prepare (opens in a new tab) documents placeholders and prepared statements.

5Read HTTP status and JSON output

This is a web-handler fragment. It needs HTTP to demonstrate the status and headers.

✓PHPSecure
<?php
// WHY: A controlled rejection sends the chosen status and stops execution before later work.
if (($_SERVER['REQUEST_METHOD'] ?? '') !== 'GET') {
    http_response_code(405);
    header('Allow: GET');
    header('Content-Type: application/json');
    echo json_encode(['error' => 'method_not_allowed'], JSON_THROW_ON_ERROR);
    exit;
}

Secure. Why: A controlled rejection sends the chosen status and stops execution before later work.

$_SERVER is a PHP-provided array containing request and server information. ?? '' supplies an empty string when the key is absent or null. It is a default, not authentication or validation.

http_response_code(405) sets the response status. header sets a header. json_encode returns a string representing the array as JSON. echo writes that string. exit prevents subsequent handler statements from running.

For a POST request, the intended response is status 405 with Allow: GET, JSON content type, and body {"error":"method_not_allowed"}. For a GET request this fragment writes nothing; execution continues to the next control. Headers and status must be set before output commits the response, because later header changes may fail once output is sent.

◆JSON serialization

Serialization represents PHP values as text another program can parse. It does not decide which fields that program is permitted to receive. Construct the permitted response fields first, then serialize them.

Source: PHP HTTP response codes (opens in a new tab) and PHP header (opens in a new tab) describe the response operations.

6Read exceptions without exposing their details

An exception interrupts the normal path. A matching catch receives the thrown object. The following standalone example deliberately fails JSON encoding with an invalid UTF-8 byte so you can see the controlled branch.

✓PHPSecure
<?php
// WHY: Throwing on serialization failure reaches a controlled error path instead of treating failure as a successful empty response.
try {
    $payload = ['label' => "\xFF"];
    echo json_encode($payload, JSON_THROW_ON_ERROR) . "\n";
} catch (Throwable $error) {
    echo "Controlled error branch.\n";
}

Secure. Why: Throwing on serialization failure reaches a controlled error path instead of treating failure as a successful empty response.

Output
Controlled error branch.

JSON_THROW_ON_ERROR changes serialization failure into a JsonException. Throwable covers PHP exceptions and errors, including TypeError. $error holds the thrown object. The program does not print its message or trace.

Replace "\xFF" with 'Loan kit'. The expected output becomes {"label":"Loan kit"}, because that valid string can be encoded and the catch block is skipped.

A production handler additionally needs its chosen generic error status/body and a controlled operational record. A correlation id connects that response to the relevant server-side event. Logging an exception's raw message can expose credentials, SQL values, or personal data, so a generic event category and permitted metadata are safer than unrestricted logging of every exception detail.

Source: PHP json_encode (opens in a new tab) defines serialization failure and flags; PHP Throwable (opens in a new tab) explains the shared error/exception interface.

7Explain the course helpers and control handoffs

require loads and evaluates another PHP file. __DIR__ names the directory containing the current file, allowing a fixed path to a helper. A helper name such as q_one is course application code, not a built-in PHP function. Its contract matters: arguments, return values, exceptions, and side effects determine how the next statement can use its result.

The API lecture also uses hash('sha256', $key) to represent a key by its hash and hash_equals to compare known and supplied strings deliberately. random_bytes supplies random bytes; bin2hex represents those bytes with hexadecimal characters for a correlation id. A correlation id identifies an event, not a user and not an authorization grant.

When reviewing an AI-proposed helper call, compare its name and contract with the actual helper file, because a plausible function name can be invented and a real function can still be called with incorrect arguments. Your explanation should identify which prior control produced the value and which later control trusts it.

✓Explain a concrete handoff

Trace the authenticated identity into the ownership query and then trace the selected fields into JSON, because those are two separate decisions. Saying that an endpoint “uses secure helpers” does not show where either decision is enforced.

Source: PHP require (opens in a new tab) documents file loading; the helper contracts are defined in your portal's lib/ files.
