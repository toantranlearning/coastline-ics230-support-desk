A customer enters the name Jordan & Lee. The application accepts it, stores it, and later displays it on a page. At each step, the name should remain meaningful data. Accepting the name and displaying it safely require two different controls: input validation and output encoding.

Check the value. Match the destination. Validation asks whether the value meets the field's rules. Output encoding writes it for the interpreter that will read it. A value can pass validation and still need encoding when it reaches the page.

What should happen to the ampersand in that name? The application should preserve it. When it displays the name in HTML, it writes Jordan &amp; Lee; the browser shows Jordan & Lee. The stored name, the HTML source, and the visible page are different representations of the same meaningful data.

Now consider <b>Loan kit</b>. If a free-text field permits these characters, accepting them does not grant permission to create HTML elements. Encoding at the HTML output keeps the brackets visible as text. A field with tighter business rules may reject that input instead. The field determines acceptance; the destination determines the output control.

★Two questions to carry into every example

At input: Does this value meet this field's rules? At output: Will the destination read this as data? Identify both before choosing a function, because a field rule and an output context can require different controls.

Why this matters to your work

A fix can block hostile markup and still damage legitimate names, quotes, or punctuation. Your evidence needs both results: the unwanted interpretation stops, and ordinary use still works. You will practice tracing the value, choosing the control, and proving what changed.

Before sending a test request, apply the course's Rules Of Engagement. Work in your own authorized portal copy and use the permitted manual methods. ROE precedes testing, including tests of a repair, because permission covers the target and method, and the activity can affect other people and their information.

Open your course environment as you work through the examples so you can compare the explanation with actual behavior. Code blocks labeled Vulnerable show the flaw; blocks labeled Secure show a repair pattern. If you use AI to propose a change, ask it to explain both decisions, then verify the results in your own copy. Generated code and predicted results can be wrong; your tests establish what the change actually does.

2Where this module starts

Module 01 gave you three words and one idea. A source is where untrusted data enters your program. A sink is the operation that hands data to another interpreter, such as echo into a page or a database query. Injection is what happens when data reaches an interpreter that reads part of it as a command. This module is about the two controls that sit on that path, one at each end.

In PHP, the sources you expect are the request superglobals.

PHP
<?php
$_GET;                             // the query string
$_POST;                            // the request body
$_COOKIE;                          // values you handed out and no longer control
$_FILES;                           // a client-supplied filename, type, and size
$_SERVER['HTTP_USER_AGENT'];       // any HTTP_* entry is a header the client set
file_get_contents('php://input');  // the raw body, for JSON and other formats

iStored data still needs review

There is a source people miss: the database. A value a user typed last month and that has sat in a table since is still a value a user typed. Reading it back does not make it safe. Treat a row you read from storage the same way you treat a request.

★Validation and encoding are two jobs, done at two different times

Validation happens on the way in. It answers a business question: is this value acceptable for this field, in this workflow? Encoding happens on the way out. It answers an interpreter question: how must this value be written so that the thing reading it treats it as data and not as instructions? Doing one well never does the other's job.

The word "sanitize" hides both jobs behind one verb. When someone says a value was sanitized, you cannot tell which check ran or which interpreter the output was written for. Say which one you did.

MDN: Website security (opens in a new tab) describes the same attacks from the browser's side. It uses the one word "sanitization" for the two jobs named above.

3Validation answers a business question

Validation asks whether a value is acceptable for this field in this workflow. Failing to ask is improper input validation (CWE-20), and it sits under a large share of the weaknesses this course covers.

Three different checks hide under the one word "validation."

3. Validation answers a business question. Columns: Check, The question it answers, A value that passes the row above and fails this one.
CheckThe question it answersA value that passes the row above and fails this one
SyntacticIs the value shaped correctly?2026-02-31 is a well-formed date string
SemanticDoes the value make sense here?a delivery date that is already in the past
AuthorizationMay this person use this value?account 47 is a valid number that belongs to someone else

Each row is a defect that survives the row above it. A review that stops at "we validate the input" has usually checked only the first row. The OWASP cheat sheet draws the same line: validate both syntax, the expected type and format, and semantics, whether the value makes sense for the operation. The third row is authorization, which is its own control and is out of scope for this module.

Here is a syntactic check followed by a semantic one, on a quantity field.

✓PHPSecure
<?php
// WHY: Strict failure checks distinguish missing or invalid input from integers; the separate range check enforces the allowed quantity.
$quantity = filter_input(INPUT_POST, 'quantity', FILTER_VALIDATE_INT);

// Syntactic: is it an integer at all?
if ($quantity === false || $quantity === null) {
    http_response_code(400);
    exit('Invalid quantity');
}

// Semantic: is it a quantity this business accepts?
if ($quantity < 1 || $quantity > 25) {
    http_response_code(400);
    exit('Quantity must be between 1 and 25');
}

Secure. Why: Strict failure checks distinguish missing or invalid input from integers; the separate range check enforces the allowed quantity.

▸What filter_input returns, case by case

  1. The form sends 12. The filter reads it as the integer 12. It passes both checks, and the code goes on.
  2. The form sends abc. The filter fails and returns false. The first check rejects it.
  3. The form has no quantity field at all. filter_input returns null. The first check rejects that too.
  4. The form sends 40. The filter reads it as an integer, so the first check passes. The range check fails, and the value is rejected with the out-of-range message.

The strict comparisons distinguish the integer zero from the failure values.

!Check the return value explicitly

filter_input returns false when the filter fails and null when the field is missing. PHP treats false, null, 0, and '' as the same thing in a plain if (!$quantity) test. Write it that way and you can no longer tell a missing field from an invalid one, so you cannot give the two different messages, and a legitimate 0 on a field that allows zero takes the failure branch. Compare with === and handle each case.

Reject an invalid security-sensitive value with a short message that gives nothing away. Do not try to repair it. A repaired value is a value you invented, and now two systems disagree about what the user sent.

4Prefer allow-lists over deny-lists

The tempting way to constrain a text field is to strip the characters you fear.

✕PHPVulnerable
<?php
// WHY: Removing one known tag misses variants and does not check the permitted colors.
$color = $_POST['color'] ?? '';
$color = str_replace('<script>', '', $color);

Vulnerable. Why: Removing one known tag misses variants and does not check the permitted colors.

This is a deny-list: a list of what is forbidden. It is only as complete as the author's imagination on the day they wrote it. The attacker picks a form the author did not list.

Removing the exact string <script> leaves <SCRIPT> unchanged. One pass over <scr<script>ipt> removes the inner tag and leaves <script> behind. None of those operations establishes that the submitted color is red, green, or blue.

◆Allow-list

An allow-list names what is permitted and refuses everything else. An allow-list defines the rules the field needs: its type, length, range, permitted choices, or whole-value pattern. A fixed-choice field needs exact membership; a name field needs rules that preserve legitimate names.

When the field is a fixed set, state the set and reject anything outside it.

✓PHPSecure
<?php
// WHY: The type check and strict membership test accept only the listed color strings without loose type conversion.
$allowedColors = ['red', 'green', 'blue'];
$color = $_POST['color'] ?? null;

// Establish a string before checking membership in the permitted set.
if (!is_string($color) || !in_array($color, $allowedColors, true)) {
    http_response_code(400);
    exit('Invalid color');
}

Secure. Why: The type check and strict membership test accept only the listed color strings without loose type conversion.

The third argument to in_array is the strict flag. Without it, PHP compares loosely, and section 8 shows what loose comparison does to a security check.

When the field is free text, the character set is still an allow-list. Fix the type, trim, bound the length, and require the value to match a pattern of permitted characters.

✓PHPSecure
<?php
// WHY: The type, character-count, and whole-value pattern checks enforce the username rules on the normalized value.
$username = $_POST['username'] ?? null;

if (!is_string($username)) {
    http_response_code(400);
    exit('Invalid username');
}

$username = trim($username);

if (mb_strlen($username, 'UTF-8') < 3 || mb_strlen($username, 'UTF-8') > 20) {
    http_response_code(400);
    exit('Username must be 3 to 20 characters');
}

if (preg_match('/\A[a-z0-9_]+\z/', $username) !== 1) {
    http_response_code(400);
    exit('Username may use lowercase letters, digits, and underscore');
}

Secure. Why: The type, character-count, and whole-value pattern checks enforce the username rules on the normalized value.

▸Reading the pattern

preg_match tests the value against a regular expression. \A anchors the match at the very start of the string and \z at the very end, so the whole value has to match, not a piece of it. [a-z0-9_] is the set of permitted characters, and + means one or more of them. A value such as rae_marsh matches. A value such as rae marsh fails on the space, and Rae fails on the capital letter. Use \A and \z rather than ^ and $, because $ lets a trailing newline through.

mb_strlen counts characters, where strlen counts bytes. An accented letter such as é occupies more than one UTF-8 byte. A byte limit and a character limit therefore accept different strings. Name the encoding explicitly when using mb_strlen.

▸Field rules should fit real names

An allow-list for free text does not have to be letters and digits. The OWASP cheat sheet says an allow-list can permit broad Unicode text while limiting its length. A display-name field accepts apostrophes, accents, and spaces, because real names have them. The point is that you decided what is permitted, and everything else is refused.

✓Apply the control at its enforcement point

Describe the permitted set positively and reject everything else. For a set, check membership with the strict flag. For free text, establish the type, apply the agreed trimming, bound the length, and check the permitted characters.

Why: these checks enforce the field's actual contract. Rejecting a value preserves that decision; silently changing it can make the application act on something the requester did not intend. Keep the rejection message generic so it does not disclose internal details.

5Normalize before you validate

A check must run on the value the operation will actually use. If one layer checks a value and another decodes it again, those layers can see different characters.

◆Normalization establishes one agreed representation

Normalization puts a value in the form the operation will use. Trimming permitted outer spaces and parsing a date are examples. Define the transformation first, perform it before validation, and keep that same representation through the operation. Otherwise, the value used can differ from the value that passed the check.

▸One request, two possible representations

PHP already decodes query-string values when it fills $_GET. A request containing tag=%252F produces %2F in $_GET['tag']. A further call to urldecode produces /. That extra step changes the character the validation rule needs to check.

✕PHPVulnerable
<?php
// WHY: Repeated decoding can change a previously checked value: %2F becomes /. Validation must check the representation that will be used.
$value = $_GET['tag'] ?? '';
while ($value !== urldecode($value)) {
    $value = urldecode($value);
}

Vulnerable. Why: Repeated decoding can change a previously checked value: %2F becomes /. Validation must check the representation that will be used.

✕Do not decode until a string stops changing

Repeated decoding lets the request choose how many transformations occur. A later transformation can create syntax absent from the checked value. Establish the representation once, then validate and use it without another decoding step.

An equipment tag permits lowercase ASCII letters, digits, underscore, and hyphen. This workflow needs no further decoding after PHP parses the request.

✓PHPSecure
<?php
// WHY: The rule checks the value PHP already parsed and rejects every character outside the permitted tag pattern; there is no extra decoding step.
$tag = $_GET['tag'] ?? null;
if (!is_string($tag) || strlen($tag) > 30
    || preg_match('/\A[a-z0-9_-]+\z/', $tag) !== 1) {
    http_response_code(400);
    exit('Invalid tag');
}

Secure. Why: The rule checks the value PHP already parsed and rejects every character outside the permitted tag pattern; there is no extra decoding step.

Response
Parsed value: kit_12 -> field check passes
Parsed value: %2F   -> 400 Invalid tag
Parsed value: /     -> 400 Invalid tag

The allowed pattern decides both rejections. No downstream layer changes the accepted value into a new one.

The request is parsed, its value is checked, and the operation uses that same value. Additional decoding is not part of this field's contract.

PHP Manual: urldecode (opens in a new tab) warns that $_GET and $_REQUEST are already decoded. The required input-validation reading explains why the checked representation must match the representation used downstream.

6Output encoding answers an interpreter question

▸Choose the control from the destination

A display name goes into a paragraph: use HTML text encoding. The same name becomes a URL query value: encode the query value, then encode the complete URL for its quoted HTML attribute. If it goes into a database query, use a bound parameter. The original value can stay the same; the destination changes the control.

Validation decided the value was acceptable. It said nothing about how the value must be written where it is about to land. That is the encoding question, and getting it wrong is improper encoding or escaping of output (CWE-116).

★The destination decides the encoding, not the value

Encoding writes a value so that the destination reads it as data rather than as syntax. The rule comes from the interpreter that is about to read the value: the HTML parser, the JavaScript engine, the URL parser. It does not come from the value, the field it arrived in, or your habit. The same stored value can need a different representation at each kind of sink.

Here is a value written straight into a page. Assume it holds <script>alert(document.cookie)</script>.

✕PHPVulnerable
<?php
// WHY: The value is inserted as raw HTML, so supplied tags can create elements or scripts instead of displaying as text.
$displayName = $_GET['name'] ?? '';
echo '<p>Welcome back, ' . $displayName . '</p>';

Vulnerable. Why: The value is inserted as raw HTML, so supplied tags can create elements or scripts instead of displaying as text.

Output
<p>Welcome back, <script>alert(document.cookie)</script></p>

The browser reads that response as HTML. The angle brackets open a real <script> element, and the browser runs what is inside. Nothing checked the value at the moment it was written, so the value chose the markup.

◆Output encoding

Output encoding replaces the characters that carry meaning in the destination language with a form the destination shows as literal text. For HTML text, htmlspecialchars turns & into &amp;, < into &lt;, > into &gt;, " into &quot;, and, with ENT_QUOTES, ' into &#039;. The browser prints those as the characters they stand for instead of acting on them.

✓PHPSecure
<?php
// WHY: HTML encoding writes special characters as entities, allowing the browser to display the accepted value as text.
$displayName = $_GET['name'] ?? '';

echo '<p>Welcome back, ' . htmlspecialchars(
    $displayName,
    ENT_QUOTES | ENT_SUBSTITUTE,   // encode both quote styles; replace invalid bytes
    'UTF-8'                        // never rely on the default charset
) . '</p>';

Secure. Why: HTML encoding writes special characters as entities, allowing the browser to display the accepted value as text.

Output
<p>Welcome back, &lt;script&gt;alert(document.cookie)&lt;/script&gt;</p>

All three arguments matter, and the manual is the source for each.

  • ENT_QUOTES encodes the single quote as well as the double quote. That is what makes the output safe inside a single-quoted attribute.
  • ENT_SUBSTITUTE replaces a malformed byte sequence with the Unicode replacement character. Without it, the manual says the function returns an empty string for a string with an invalid code unit sequence, which silently blanks the value.
  • 'UTF-8' names the character set. Left out, the function uses the default_charset setting of whatever server runs the code.

iThe defaults changed in PHP 8.1

Since PHP 8.1, htmlspecialchars with no flags behaves as if you passed ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML401. Before 8.1 the default was ENT_COMPAT, which leaves the single quote alone. Write the flags out anyway. Code gets copied between servers, and a reader should not have to know the PHP version to know what the call does.

That pattern is correct for HTML text and for a quoted HTML attribute. It is not automatically correct for a URL, for JavaScript, or for a SQL query, because each of those is a different interpreter with a different grammar.

A URL that goes into an HTML attribute crosses two interpreters, so it needs the encoding for each, in the order the interpreters will see them: URL-encode the parameter value first, then HTML-encode the finished URL for the attribute. The OWASP cheat sheet gives the same order.

✓PHPSecure
<?php
// WHY: The query builder encodes the query values; HTML encoding then protects the complete URL inside its quoted attribute.
$query = http_build_query(['topic' => $topic]);   // percent-encodes the value
$url   = '/threads.php?' . $query;

echo '<a href="' . htmlspecialchars($url, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') . '">Open thread</a>';

Secure. Why: The query builder encodes the query values; HTML encoding then protects the complete URL inside its quoted attribute.

When data must cross into JavaScript, serialize it instead of building code from it. Serialize it with json_encode and the hardening flags, and put it where the page reads it as data.

✓PHPSecure
<?php
// WHY: JSON serialization preserves data structure; the HEX flags prevent supplied characters from terminating the HTML script element.
$payload = json_encode(
    ['name' => $displayName],
    JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_THROW_ON_ERROR
);
?>
<script type="application/json" id="app-data"><?= $payload ?></script>

Secure. Why: JSON serialization preserves data structure; the HEX flags prevent supplied characters from terminating the HTML script element.

▸What each JSON flag does

JSON_HEX_TAG writes < and > as \u003C and \u003E, so a </script> inside a string cannot close the element early. JSON_HEX_AMP writes & as \u0026. JSON_HEX_APOS and JSON_HEX_QUOT write the two quote characters as \u0027 and \u0022. JSON_THROW_ON_ERROR makes a bad value raise an exception instead of returning false, so the application can handle the failure instead of silently emitting an empty data block.

For a SQL query no HTML function helps at all. SQL values travel as bound parameters, which is out of scope for this module, and the destination diagram shows the distinction.

!One encoder does not fit every sink

htmlspecialchars applied to a URL parameter, a JavaScript string, or a SQL value is the wrong tool used with confidence. Each context has its own dangerous characters and its own encoding. The OWASP cheat sheet says it in one sentence: browsers parse HTML, JS, URLs, and CSS differently, so the wrong encoding method may introduce weaknesses or harm the functionality of your application.

✓Apply the control at its enforcement point

Encode when you write the value, using the control required at that destination. Start from the accepted value for each output context; do not reuse one encoded form everywhere.

Why: HTML, URL, and JavaScript contexts interpret characters differently. A representation made for one destination may be incorrect or ineffective at another.

PHP Manual: htmlspecialchars (opens in a new tab) documents the flags, the empty-string behavior, and the 8.1 default. OWASP Cross Site Scripting Prevention Cheat Sheet (opens in a new tab) is the context-by-context guide. PHP Manual: JSON constants (opens in a new tab) defines each JSON_HEX_* flag.

7Finding every sink on a page

✓Make an output checklist before editing

Before editing, create a sink register: one row for each output expression, with its source, context, chosen control, and test. A value appearing twice creates two review obligations, even when both places use HTML.

A change that protects one output expression leaves the others to review. Trace each expression before editing.

Read the output statements and identify what surrounds each variable. The surrounding HTML determines whether the value becomes text, an attribute, or another context, which determines the control:

iEncoding at the sink is why you do not encode on the way in

If you HTML-encode a value as it arrives and store the encoded form, a later page that writes the value into a URL or into JavaScript receives the wrong encoding, and a page that shows it as text shows &amp; where the user typed &. Store the accepted value in its agreed normal form. Encode at each sink, for that sink.

8PHP type confusion

◆Check the type before using the value

Check that a submitted value is a string before passing it to a string function.

Why: a requester can send array-shaped input, such as quantity[]=1. A string function may then raise a type error instead of running the intended validation.

POST /order.php
quantity[]=1&quantity[]=2

With that body, $_POST['quantity'] is an array, not a string. Code that assumed a string now hands an array to a string function. Depending on the PHP version and the function, that is a warning, a fatal error, or a comparison that quietly gives the wrong answer. Establish the type before you rely on it.

✓PHPSecure
<?php
// WHY: The string check rejects array-shaped or missing input before a string operation can raise a type error.
$name = $_POST['display_name'] ?? null;

if (!is_string($name)) {
    http_response_code(400);
    exit('Invalid display name');
}

Secure. Why: The string check rejects array-shaped or missing input before a string operation can raise a type error.

The other trap is a loose comparison in a decision that must be exact.

✕PHPVulnerable
<?php
// WHY: Loose equality can accept a different numeric-looking string: "10" and "1e1" compare equal even though they are not the same token.
$token = $_GET['token'] ?? '';
if ($token == $expected) {
    grant_access();
}

Vulnerable. Why: Loose equality can accept a different numeric-looking string: "10" and "1e1" compare equal even though they are not the same token.

✕Loose comparison in a security decision can grant access and raise no error

== may apply type conversion before comparing. The manual's own examples: "1" == "01" is true, "10" == "1e1" is true, and 100 == "1e2" is true, because PHP reads both sides as numbers when they look numeric. A token check written with == can return true for a value that is not the token at all, with no error and a test suite that passes. Establish the expected types first. Use === for exact equality, in_array(..., true) for strict membership, and hash_equals when comparing a submitted secret with the known value. These comparisons support a policy check; they do not replace the policy itself.

✓PHPSecure
<?php
// WHY: The submitted value must be a string, and hash_equals compares it with the known secret without numeric-string coercion.
$token = $_GET['token'] ?? '';
if (is_string($token) && hash_equals($expected, $token)) {
    grant_access();
}

Secure. Why: The submitted value must be a string, and hash_equals compares it with the known secret without numeric-string coercion.

hash_equals avoids a comparison that stops at the first unequal character. Check that the submitted value is a string, and pass the expected secret as the first argument. A length mismatch returns false immediately, so the function does not conceal the length of the expected value.

iPHP 8 closed one door and left the rest open

Before PHP 8.0, 0 == "a" was true, because the string was converted to a number first. Since 8.0 it is false. The numeric-string cases above are still true in PHP 8, so the rule has not changed: a security decision is written with a strict comparison.

PHP Manual: Comparison operators (opens in a new tab) has the conversion table and the PHP 8 examples quoted above. PHP Manual: hash_equals (opens in a new tab) documents the function.

9Validation and encoding are both necessary

A shipping label accepts a display name under the field rules. That accepted value may still include characters with meaning in HTML:

Jordan & Lee

The value is valid, and it contains &, which has meaning in HTML. Validation should accept it, because the business accepts it. Encoding then writes it safely at the point it is used, as Jordan &amp; Lee. Neither control could have done the other's job. Rejecting the ampersand would have broken a real name. Encoding without validation would happily store a 4,000-character name that fails no output rule at all.

The reverse also holds. Encoding account 47 makes it safe to write into a page. It says nothing about whether the current user may see account 47. That is the third row of the table in section 3, and it is a separate decision.

✓Apply the control at its enforcement point

Validate on the way in, against the business rules for the field. Encode on the way out, for the interpreter at each sink. Run both. A value the business accepts can still carry characters that mean something to an interpreter, and a value that is safe for one interpreter can be wrong for the person who asked for it.

The OWASP Input Validation Cheat Sheet states the same division: use parameterized queries for SQL and context-aware output encoding to prevent cross-site scripting, and removing suspicious characters can change meaning and still does not provide either.

10How you prove the control works

✓Build evidence another person can review

Keep the request, the observed result, and one sentence explaining what the result proves. Put text evidence in fenced blocks; use a screenshot when the distinction is visible rendering.

Why: the input and result let another person evaluate your claim. A screenshot can distinguish literal tags from rendered HTML, while a code block preserves exact response text.

The markup case must display as text. The legitimate case must retain its apostrophe or accented letter. Either result alone leaves a gap in the proof.

Test a validation rule at its boundaries before claiming it works. Boundary cases reveal incorrect comparisons, while missing and wrong-type values reveal assumptions about the request. Choose the applicable cases below for each rule.

!Keep legitimate data in the verification set

Removing characters may stop one example without preserving the accepted value. Test punctuation and expected Unicode as well as markup. A value disappearing or changing is different from that value being displayed safely.

iA check that runs in the browser is a convenience, not a control

Module 01 showed that the client composes every request and can skip your page entirely. A browser-side check gives fast feedback. The server runs every rule on this page again, where the requester cannot reach it. The OWASP cheat sheet says it the same way: validate on the server even when the browser checks the same fields.

OWASP Web Security Testing Guide: Testing for Reflected Cross Site Scripting (opens in a new tab) explains how to investigate reflected output and its interpretation. Pair the security probe with legitimate-use checks to verify that your change preserves the field's intended behavior.

11Common misconceptions

iSanitize the input and you are done.

"Sanitize" names no business rule and no output context, so nobody can review it or test it. Say which of the three checks in section 3 you ran on the way in, and which interpreter you encoded for on the way out.

iValidation prevents injection.

Validation narrows the input and is worth doing. A valid name still contains an apostrophe, and a valid comment still contains angle brackets. Bound parameters are the query defense and encoding is the output defense.

iValidated data never needs encoding.

The two controls answer different questions. A value the business accepts can still carry characters that mean something to the interpreter at the sink.

iOne encoder is safe everywhere.

HTML text, HTML attributes, URLs, JavaScript, and SQL each have different syntax and different dangerous characters. The right encoder is the one the destination needs.

iStored data is trusted.

A value may have entered through another path, an import, or before the fix was deployed. Storing it did not check it. Treat a row you read back as a source.

iRejecting input is unfriendly.

Rejecting a bad value with a short, non-leaking message is better than silently changing what the user sent. Silent repair produces bugs nobody can reproduce.

iEncode on the way in and the whole site is safe.

Stored encoded text is wrong for every sink except the one it was encoded for, and it shows &amp; to the user who typed &. Store what was sent, encode where it lands.

12Check your understanding

Try these questions before reading the answers. Explaining the decision yourself reveals gaps that rereading a completed explanation can hide.

  1. State the question validation answers and the question encoding answers, and say why neither can replace the other.
  2. Where in the flow does validation run, and where does encoding run?
  3. What decides which encoding a value needs at a given sink?
  4. Give an allow-list rule and a deny-list rule for a color field. Which defines the complete accepted set, and why does either rule still need an output control?
  5. Why must you normalize before you validate? Give an input that gets through if you reverse the order.
  6. Which of the three checks in section 3 decides whether a user may act on a valid record ID?
  7. A request arrives as quantity[]=1&quantity[]=2. What does $_POST['quantity'] hold, and what should the code check first?
  8. Why can == accept a different numeric-looking token string, and what checks should replace that comparison?
  9. In an HTML text context, what two outcomes must an encoding test show, and what does it mean if only the first passes?
  10. What do the explicit flags and encoding in the lecture's htmlspecialchars call establish?

Compare your reasoning

  1. validation asks whether the value is acceptable to the business; encoding asks how the destination must read the value; one decides acceptability on the way in and the other decides representation on the way out.
  2. validation on the way in, encoding on the way out, at each sink.
  3. the interpreter about to read the output, not the value or the field it came from.
  4. an allow-list accepts only red, green, or blue; a deny-list removes a known string such as <script>. The allow-list defines the accepted set. Both still need the control appropriate to the output destination.
  5. validate the representation the operation uses; PHP parses tag=%252F into %2F, and another decode would change that checked value into /.
  6. authorization.
  7. an array, so the code checks is_string before using it as a string.
  8. loose equality can compare numeric-looking strings as numbers, so "10" == "1e1" is true; use ===, in_array(..., true), or hash_equals.
  9. hostile markup renders as literal text and a legitimate special character still displays; passing only the first suggests the code strips characters instead of encoding them.
  10. ENT_QUOTES covers the single quote, ENT_SUBSTITUTE stops an invalid byte sequence from returning an empty string, and 'UTF-8' keeps the result from depending on a server setting.
