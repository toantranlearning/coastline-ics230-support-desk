What this module is for

Module 10 protected data at rest. This module protects data in transit, between the browser and the server, and teaches where that protection stops. TLS makes the connection private and tamper-evident and proves the server's identity. It says nothing about what is inside the connection, and nothing about what the server does after it decrypts the request.

Available is not enforced. A host can answer HTTPS while the session cookie it sets would still ride on a plain http:// request. The browser may also have no standing rule to refuse http:// at all. The incident this module answers is that gap. Your portal is reached over HTTPS, auth.php starts the session with nothing set on the session cookie, and no page sends a Strict-Transport-Security header.

You will also learn exactly what your course environment can show you about TLS. Cloud Shell's proxy holds the certificate and runs the handshake. Your php -S process speaks plain HTTP behind it. Your code can set the headers and cookie attributes an HTTPS site must send, and you will evidence those. It cannot show a certificate or a protocol version, and you will say so rather than claim them.

The question this module answers

What does TLS protect in transit, what does certificate validation establish, and what does the application still have to do to keep the session on the encrypted channel?

What you will be able to do

After Module 11 you can:

  1. State the three properties TLS provides for the bytes on the wire, and name what it does not do.
  2. Explain the relationship between SSL and TLS, which versions a web application may offer, and the shape of the TLS 1.3 handshake.
  3. Describe the chain of trust and the four checks a client runs on a certificate, and read a curl failure for each.
  4. Explain why certificate expiry fails closed, and name the renewal and monitoring controls that prevent an outage.
  5. Keep certificate validation on in outbound PHP calls, and say what turning it off throws away.
  6. Set Secure, HttpOnly, and SameSite on PHP's session cookie where its attributes are set, and send a Strict-Transport-Security header with a max-age you can live with.
  7. Say which TLS facts your portal can evidence and which the proxy owns.

Before you start

  • Reread Module 01 lecture sections 4 and 6 if the trust boundary and the bearer credential are not yet automatic. TLS does not move that boundary, and the session identifier rides on every request after sign-in.
  • Reread Module 05 lecture section 9 for HttpOnly and Module 06 lecture section 7 for SameSite. This module adds Secure and shows where PHP's session cookie gets all three.
  • Sign in to your course environment as rmarsh and request login.php from the terminal with the headers shown. You will read the Set-Cookie line before you change anything.

Where you may run this

You change code this module, in your own course environment, in auth.php and layout.php. There is no scanning and no exploitation beyond requesting your own sign-in page and reading what your own browser stored and received. Treat the session identifier in your captures as a credential and redact it. Your own environment is the only target you are authorized to test.

When you are done

Module 11 is complete when you have posted and replied in the forum, submitted the quiz, and submitted the incident report for TC-IR-010: the completed TC-IR-01 form with the available-versus-enforced analysis in section 5, the fixed auth.php and layout.php, and before-and-after evidence in section 7 showing the session cookie carrying Secure, HttpOnly, and SameSite, the response carrying Strict-Transport-Security, and sign-in still working on the Web Preview.
