One real incident whose root cause is this module's topic. Say what went wrong and how it could have been stopped, then engage a classmate. The deep analysis belongs in your incident report.

The incident

In January 2025, Zimbra, which makes the Zimbra Collaboration mail and calendar server, fixed a stored cross-site scripting flaw in its Classic Web Client, CVE-2025-27915. The attack was one email with a calendar file attached. The web client wrote the HTML inside a calendar (.ics) entry into the page without making it safe. A <details> element in that entry carried an ontoggle event handler. When the recipient viewed the email, the handler's JavaScript ran in the recipient's signed-in session. No <script> tag was needed. The script could act as the user: the CVE record names setting mail filters that send messages to an address the attacker controls.

The facts, from the CVE record, the vendor's release notes, and two reports:

  • Affected: Zimbra Collaboration 9.0, 10.0, and 10.1. Fixed in 9.0.0 Patch 44, 10.0.13, and 10.1.5, released January 27, 2025.
  • Weakness: CWE-79, improper neutralization of input during web page generation.
  • Zimbra's release notes call it a critical stored cross-site scripting flaw in the Classic Web Client and say the fix strengthens input sanitization.
  • StrikeReady, a security firm, reported on September 30, 2025 that the flaw had been used earlier that year against the Brazilian military. The emails pretended to come from the Libyan Navy's Office of Protocol. By its account the script stole passwords, mail, contacts, and shared folders, and added a mail-forwarding rule. Zimbra told The Hacker News it found no evidence of those attacks; the claim is StrikeReady's.
  • CISA added the CVE to its Known Exploited Vulnerabilities catalog on October 7, 2025.

Sources: the CVE record for CVE-2025-27915 (opens in a new tab), Zimbra's 10.1.5 release notes (opens in a new tab), The Hacker News report (opens in a new tab), and Security Affairs' report (opens in a new tab).

Nobody bypassed a login or guessed a password. The server stored what the attacker sent, then wrote it into a page for a different user. That user's browser ran it with that user's session. That is the shape the lecture calls stored XSS.

Initial post

Write 150 to 250 words answering both questions about the Zimbra incident, in this module's vocabulary:

  1. What did they do wrong? Trace the failure as a flow. Name the source the attacker controlled, the trust boundary the calendar entry crossed, the sink where the web client wrote it into the page, the context it landed in, and the interpreter on the far side. Say whose session that interpreter was holding. Say why this is stored XSS rather than reflected, and why "the server was never breached" did not help the people who opened the email.
  2. How could it have been prevented? Name at least one specific control at a specific point in that flow, and say why it stops this exact attack rather than attacks in general. Encoding at the sink, an allow-list sanitizer where markup is a real requirement, and a Content Security Policy that refuses an inline event handler are all fair game. The lecture says which of them is the fix and which are depth.

A strong post commits to the mechanism. "They should have sanitized the input" is where the answer starts, not where it ends: sanitized where, for which context, and against what policy?

Peer reply

Reply directly to at least one classmate, in at least 75 words. Open with their name and sign yours. Stress-test their prevention: would their control have stopped this exact payload, an ontoggle handler with no <script> tag in sight, or only the attacks they thought of? Then add one control at a different point in the flow, so the two of you have sketched defense in depth. Post early enough in the module for a real exchange.

Expectations

Full sentences, proper grammar and punctuation, no text-message shorthand. "I agree" is not a reply.
