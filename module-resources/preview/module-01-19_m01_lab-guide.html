Use this page whenever an assignment asks you to work in the lab. It collects the setup, demo accounts, working routine, and submission guidance used throughout the course. Each assignment supplies its own incident, files to change, required tests, and deliverables.

What you are working on

The TechCorp customer portal is a fictional company's customer-service application. You will read and repair its PHP code in your own Google Cloud Shell workspace. The portal uses a SQLite database and contains intentional defects for the course exercises.

Cloud Shell is your browser-based workspace: its editor changes the files, and its terminal runs commands. Web Preview opens the running portal so you can sign in and test its behavior. Your Google account opens the workspace; the fictional accounts below sign in to the portal. Those are separate sign-ins.

Open your lab

Use the Cloud Shell Guide for first-time launch and return visits. From the workspace root containing site/, fixed/, reports/, and scripts/, run:

Bash
bash scripts/start.sh

Open Web Preview → Preview on port 8080 for the original site. Use Web Preview → Change port → 8081 for fixed, where you make repairs. Sign in separately to each. Check the port before every test.

Read and reproduce in site/; edit in fixed/; prove the hostile request fails on 8081 and legitimate use still works. Both copies start with identical source and maintain independent databases. Keep earlier repairs in fixed/. Saved command evidence remains in the workspace-level reports/, outside both web roots. Download the report from Canvas and edit it separately in Word or Word Online.

Apply ROE before testing

Read Rules Of Engagement before your first exercise. Check authorization and scope before every security-testing activity, including a test of your repair.

  • Test your own assigned portal copy using the assignment's allowed methods.
  • Use the browser or individual curl requests. Do not run scanners or attack tools in Cloud Shell.
  • Use demo data and respect privacy, consent, and the agreed reporting process.
  • Pause and ask the instructor if the target, method, or scope is unclear.

Find the files you need

The assignment names the files involved. Open the original under site/ and the working version under fixed/ in the editor. Paths below are relative to the selected portal copy. These locations recur across the course:

  • index.php: the customer-list page.
  • customer.php: customer search and account details.
  • lib/: shared PHP helper functions. Read the function headers before using them.
  • data/: the starting database records and the working SQLite database.
  • reports/: saved command output, notes, and working evidence; this folder is at the workspace root, outside both portal copies.

A filename identifies code to inspect; it is not a terminal command. For example, open customer.php in the editor to read its code, and open the customer search in the running portal to observe its behavior.

Use the same working routine

  1. Read the task. Identify the incident, repair scope, permitted methods, and required evidence.
  2. Observe the starting behavior. Run the specified manual test in your own portal and record what happens before changing code.
  3. Inspect and change the code. Find the relevant statements, explain their behavior, and make a focused repair. Leave unrelated exercise defects within their assigned scope.
  4. Check syntax and behavior. Run a PHP syntax check on each changed PHP file, repeat the original test, and test the legitimate behavior the assignment requires.
  5. Explain and submit. Connect your change to the security principle, record actual results, and complete Revision History and upload the Word report, supplied assignment.md, and complete changed source files from fixed/ to Canvas. Embed screenshots in the report unless the assignment requires separate images.

For example, to check the syntax of customer.php from the workspace root:

Bash
php -l fixed/customer.php

No syntax errors detected in customer.php means PHP can parse the file. It does not prove the repair works. The browser or request tests establish the behavior; your explanation states what the evidence supports.

Use AI as a learning aid

The Gemini Learning Coach supplies instructions for the assistant already available to you. On permitted practice work and project builds, AI may generate or refactor code, explain errors, and propose tests.

Read the proposal, understand its effects, and test it yourself. Disclose the assistance and report only results you observed. The syllabus and each assessment specify when assistance is allowed; unaided assessments remain unaided.

Complete the supplied corporate report

Download the Word report from the Canvas assignment. Read its supplied executive narrative, case facts, risk assessment, response decisions, and closure criteria. Use the Incident Reporting Guide to connect the technical work to the business decision.

Complete only the marked [STUDENT] entries. Each has an EXAMPLE and an Answer: space. Keep the supplied text; add your actual observations below the example, paste the requested screenshots with captions and alt text, and record your contribution in Revision History at the bottom. The early modules ask for brief additions; the full corporate narrative is supplied to model professional reporting.

Use Word Reports and Assignment Files for exact download, editing, accessibility, and Canvas-upload steps. The IDE is for code and command evidence, and the report is edited in Word or Word Online. Submit assignment.md and all required complete changed source files with the report. Screenshots embedded in the Word file do not need a second upload unless the assignment says otherwise.

Canvas submissions are the lasting record of finished work. Keep a separate saved copy. A saved editor or Word file is not a submitted assignment.

Reset or get help

The Working in Google Cloud Shell page explains the reset options and what they discard. Submit or download work you need before a reset. Read the command and understand its effects before running it.

If the portal does not open, run the startup command again from the workspace root. If the problem remains, contact the instructor through Canvas Inbox or the course Q&A discussion. Include the command or action you tried, the exact error, and what you expected. Remove secrets and private information from anything you share.
