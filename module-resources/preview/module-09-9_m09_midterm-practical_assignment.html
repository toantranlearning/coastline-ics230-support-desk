What this is

The midterm has two parts. This is the timed practical. One flaw from the Modules 03 to 06 lectures is placed in one file of your own portal copy. You find it, repair it, prove the repair with requests you type yourself, and write a short report, all inside the time limit. The written companion is a separate assignment in this module.

The conditions

  • Timed, in Canvas. The time limit and the window are stated on the practical's Canvas assignment. The timer starts when you open it and does not pause.
  • Unaided. You work alone. No AI tools on the practical; the syllabus policy applies.
  • Open environment. Your own portal copy, the lecture pages, the Course Orientation tool pages, and your own earlier incident reports stay open.
  • Your own copy only. The only requests you send are ones you type by hand at your own portal: in the address bar, in a form, or with curl. No scanner and no attack tool. The rule is on the Working in Google Cloud Shell page.

Before the window opens

  1. Open Cloud Shell and start the portal, as the Working in Google Cloud Shell page shows.
  2. Sign in as rmarsh and confirm the customer list loads.
  3. Open a new file in your reports/ folder for the report, as the Writing in Markdown page shows.
  4. Sign in once with curl and save the cookie to a jar, as the Requests and Developer Tools page shows, so a typed request is one command away.

What you receive when it opens

The Canvas assignment shows two things:

  • The ticket. The symptom, written the way the support desk reports one. It does not say what the flaw is or how to fix it.
  • The file. The name of the one file in your portal copy that holds the flaw.

The flaw is one class the Modules 03 to 06 lectures teach, placed on a code path your earlier assignments did not repair.

What you do

  1. Reproduce the symptom. Sign in and do what the ticket describes, on your own copy.
    • Keep the request you sent and the response you got, as text. This is your before evidence.
  2. Trace the flow in the named file. Find, by line number:
    • the source, where the value enters;
    • the trust boundary it crosses;
    • the sink, where the value is used or written;
    • the interpreter that reads it there.
    • Name the class of weakness with its CWE, in the lecture's words.
  3. Repair it in the lecture's pattern. Change the named file. Where the lecture's pattern calls a shared helper you already built, call it.
    • Do not strip characters, repair values, or delete the feature. A legitimate case must still work.
  4. Prove it with two tests. Type each request yourself and keep the request and the response as text.
    • The hostile case from the ticket now fails or arrives inert.
    • A legitimate case still works.
  5. Write the report and submit it before the timer ends.

Fix only what the ticket names. If you notice another weakness in the file, say so in one sentence at the end of section 5 and leave it alone.

What to submit

One Markdown (.md) file, written as the Writing in Markdown page shows. Put text evidence in fenced blocks. Where a piece of evidence is a screenshot, upload the image with the report.

At the top of the report, include this block, completed. The AI DISCLOSURE line reads None.

NAME: First Last
AI DISCLOSURE: None.
REFLECTION: Two or three sentences: what the flaw was, what you
changed, and how you know the change holds.

Then three sections, named as the TC-IR-01 form names them. The worked example on the TC-IR-01 Form and Worked Example page shows the length and tone.

How it is graded

The Midterm Practical Rubric is attached and marked for grading: diagnosis, repair, negative tests, legitimate behavior, and explanation within scope.

  • Report completeness. The three sections are present, accurate, and scoped to the ticket.
  • Verified fix. After the change, the hostile case fails on your own copy and the legitimate case still works. A fix the ticket did not ask for does not count here.
  • Principle and mitigation named. Both named precisely, and tied to the OWASP control by name.
  • Justification. Why the principle applies to this flaw, in your own words, against your own evidence. Naming alone does not earn full credit.
  • Clarity and professionalism. A reader who does not open the code can follow it. Evidence is labeled.

How to prepare

The ticket is answered by one of these sections. Reread them before the window.

  • Module 01 lecture, sections 4 and 5. Trust boundaries, and source, sink, and flow. The trace uses these words.
  • Module 02 lecture, section 10. Preserve the evidence first, and mitigation versus remediation.
  • Module 03 lecture, sections 3, 4, 6, 7, 8, and 10. The three kinds of check, allow-lists, encoding for the interpreter, finding every sink on a page, strict comparison, and the two-test rule.
  • Module 04 lecture, sections 5, 6, 7, and 14. Prepared statements, positional placeholders, wildcards in the value, and the before-and-after table.
  • Module 05 lecture, sections 4, 5, and 10. Stored versus reflected, where a value lands on a page, and the second-viewer test.
  • Module 06 lecture, sections 3, 5, 6, and 10. The forged request, the synchronizer token, one shared check, and the proof table.
  • Module 07 lecture, sections 2 and 4. A testable claim, and what turns an alert into a finding. Your report is a finding.
  • Your own reports for TC-IR-002 to TC-IR-005. The trace and the proof are the same work on different code.

To practice, pick one page of your portal copy, write the trace for one value on it, and time yourself.

Troubleshooting

  • The portal is not running when the window opens. Start it as the Working in Google Cloud Shell page shows. The timer does not pause.
  • The symptom does not appear. Read the ticket again and send the request as it describes, on the named file, signed in as the account it names.
  • Your fix breaks the legitimate case. That is a regression. Undo it and apply the lecture's pattern: encode at the sink, bind the value, validate on an allow-list, or check the token, depending on the class.
  • The timer is about to end. Submit what you have. The trace and the before evidence are graded even when the fix is not finished.
