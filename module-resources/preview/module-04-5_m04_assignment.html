What you are doing, and why

An incident came in against the customer search feature, and you are the person who answers it. The assignment has two parts. First you write the report on the TechCorp incident form: what happened, how, and what you did about it. Then you make the report true by fixing the code in your own course environment and proving the fix holds.

It practices the two controls from the lecture: server-side validation on an allow-list, and output encoding at every sink for the interpreter that reads it. Plan about two hours for the initial repair and report, followed by about two hours for verification and revision. Testing boundary cases and correcting the code or report are part of completing the assignment.

The incident: TC-IR-002

Here is the ticket the desk filed, and the analyst's determination on top of it.

iNote

Incident TC-IR-002 - Customer search renders a name as markup A support rep reported that a customer account named <b>Test Account</b> shows up in the search results in bold, not as the literal name. A second rep reported that searching for the customer O'Brien returns an error page instead of results.

Analyst determination. These are two symptoms of one root cause: the search page takes the term the rep types and the names it finds, and writes them into the page and into a database query without treating them as data. The bold rendering is the browser reading a stored value as HTML. The error on the apostrophe is the database reading the search term as part of a query. This assignment closes the rendering half. The query half is out of scope for this module and is expected to remain open at the end of it.

Use the Incident Reporting Guide for evidence and writing practices. Your model is TC-IR-001, the fictional worked example on the TC-IR-01 Form and Worked Example page in Course Orientation. The section requirements below govern this assignment.

Part 2 - The hands-on fix

Do this on customer.php in your course environment. Each step produces evidence that goes into the report.

  1. Reproduce it. Sign in and open the customer search. Search for Test.
    • The account named <b>Test Account</b> appears in bold instead of showing its literal name.
    • Capture the screen. This is your before evidence for section 7.
  2. Find the same data shown safely elsewhere. Open Customers from the top navigation.
    • The same account displays as plain text there. Two pages, one database row, two outcomes.
    • Open customer.php and index.php side by side and find the line in each that writes the name into the page.
    • Write one sentence on what the list page does that the search page does not.
  3. Trace the flow. In customer.php, find by line number:
    • where the search term enters;
    • the trust boundary it crosses;
    • any validation that is present;
    • every place an untrusted value is written into the page, and the interpreter beyond each.
    • There is more than one sink. The term is written back into the search box and into the results heading, and each matched name is written into the results table. Use the sink table in lecture section 7 to name the context of each.
  4. Validate the term. Add server-side rules before the term is used, in this order:
    • it must be a string;
    • trim it;
    • it must be 1 to 40 characters after trimming;
    • it must match an allow-list pattern of permitted characters. Letters, digits, spaces, apostrophes, hyphens, and periods are enough for a name search. Decide and write the pattern down.
    • On failure, reject with a short generic message and no detail. A check in the browser is a convenience; the requester controls the browser.
  5. Encode at every sink. At each place an untrusted value is written into HTML, apply htmlspecialchars with ENT_QUOTES | ENT_SUBSTITUTE and 'UTF-8'.
    • Encode at the moment of writing, for the place it is written. Do not encode once at the top and reuse the result.
    • The search box is an attribute, and the heading and matched names are HTML text. The results link writes the row's id into a quoted href; record that expression separately. The same HTML encoder can protect ordinary quoted text attributes and HTML text. A URL parameter has its own representation rules.
  6. Prove it. Capture, side by side with your before evidence:
    • the same search for Test, now showing the literal name with its angle brackets;
    • a search for Brien, confirming a legitimate punctuated name still displays in the results;
    • an invalid search, such as 41 characters, refused with your generic message.
    • A fix that breaks O'Brien or an accented name is a regression, not a fix.

The apostrophe error on a full search for O'Brien is still present at the end of this assignment. That is expected. It is a different interpreter and is out of scope for this module.

Expected output

Your captures will differ in cosmetic detail; the behavior must not. The assignment passes when the report is complete and the fix holds:

  • The account with markup in its name displays as literal text in the search results.
  • An invalid search term is rejected with a generic message and no verbose error.
  • A legitimate punctuated or accented name still displays correctly.
  • The search feature still works for ordinary terms.
  • Section 5 names the source, the trust boundary, every sink, and the interpreter; section 7 shows the before and after.
