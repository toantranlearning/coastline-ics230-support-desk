What this module is for

The earlier modules stopped attacks before they landed. This module assumes one got through, and asks two questions that decide how bad it gets: did the software fail into a safe state, and did it leave a record someone can trust?

Failing safely and recording the failure are two separate controls. A verbose error hands a stranger a map of the system. A sign-in, an admin action, or a record read that leaves no record cannot be reconstructed later. You add both controls to real code in your own course environment: the portal's error path, and its sign-in, admin, and customer record pages.

The desk found a call note nobody wrote, and the portal cannot say who signed in that weekend. One page also prints its database error to the screen. You answer both on the full TC-IR-01 form. The section that matters most is 5.3, what the analysis could not determine.

The question this module answers

How should software fail safely, and what must it record so that abuse can be noticed and investigated?

What you will be able to do

After Module 14 you can:

  1. Tell failing closed from failing open, and choose the response each class of failure needs.
  2. Read a leaked PHP error the way an attacker does, and say what it gives away.
  3. Handle an unexpected failure once, at the boundary, with a generic reply and a correlation id, and the full detail in the server log.
  4. Write structured security events for sign-ins, failed sign-ins, admin actions, and sensitive reads, with no secret in any of them.
  5. Keep a hostile value inside one log record, and refuse an action that must be audited when the record cannot be written.
  6. State what the records establish and what they cannot, and choose a severity and a notification determination on that basis.
  7. Complete all ten sections of TC-IR-01, including 5.3, for an incident whose evidence was never recorded.

Before you start

  • Reread Module 01 lecture sections 4 and 5 if trust boundary, source, and sink are not yet automatic. A log is a sink, and this module treats it as one.
  • Reread Module 02 lecture section 10, incident-response basics: the severity tiers, the lifecycle, mitigation versus remediation, and how the form follows them. The Incident Response Runbook page in Module 02 holds the tiers in its section 4.
  • Sign in to your course environment as rmarsh. Sign in once more with the wrong password, then open a customer record. Now look for the record of those three actions. The gap you find is the incident.

Materials

  • The lecture page, which teaches everything the quiz and the assignment need.
  • The three required readings: OWASP Top 10:2025 A09 Security Logging & Alerting Failures, the OWASP Logging Cheat Sheet, and the CLARK slides on post-deployment evolution and patching.
  • auth.php, admin.php, customer.php, and db.php in your course environment: the sign-in check, the admin console, the customer record page, and the connection file that turns error display on.
  • The TC-IR-01 Form and Worked Example page in the Course Orientation module.
  • Three handouts in this module, linked where the assignment uses them: the carrier's Cyber Incident Response Playbook, an excerpt of the server log, and the SQL file that puts your copy in the state the desk found.

Where you may run this

You change code this module, in your own course environment. There is no scanning and no exploitation beyond typing values into the portal's own pages and sending requests to it by hand. Your own environment is the only target you are authorized to test.

When you are done

Module 14 is complete when you have submitted the quiz and the incident report for TC-IR-012. The report is the completed TC-IR-01 form on all ten sections, with a section 5.3 that names each question the missing records cannot answer. Its section 7 holds the before-and-after evidence: each security event written without a secret, the admin action refused when it cannot be recorded, and the leaking page now answering with a generic message and a correlation id.
