Every lab and assignment in this course is graded against professional coding standards. Formatting is not decoration: the person reading your code next (a grader, a teammate, you in six weeks) spends their attention either on your logic or on decoding your layout, and only one of those is worth paying for. In a security course the stakes are higher still: most of the vulnerabilities you will study this term survive in code because a reader could not see what the code actually did.

Rather than restate a style guide here, this page points you at the standards industry actually uses, then specifies the handful of things particular to this course. Learn to work from a published standard now; that is the skill, and it transfers to whatever language your first job uses.

The standards we follow

Read the first one. Keep it open while you write your first labs. The rest are references you will return to over a career.

  • PER Coding Style (opens in a new tab). Start here. The PHP community's current coding-style standard from the PHP Framework Interop Group: naming, braces, indentation, line length, and file layout. Where it and any other source disagree, follow this one.
  • PSR-12 (opens in a new tab). The predecessor standard PER Coding Style evolved from; you will still see it named in tooling and job postings.
  • The PHP Manual (opens in a new tab). The language and library reference. Look a function up here before assuming what it does: several infamous vulnerabilities began as a wrong assumption about a standard function's behavior.
  • W3Schools PHP tutorial (opens in a new tab). The gentler reference when the manual is too dense; good for syntax reminders.
  • OWASP PHP Configuration Cheat Sheet (opens in a new tab). Where style becomes security: the settings and habits that keep a PHP deployment defensible.

iNote

You are not expected to memorize any of these. You are expected to work from them, the way a practicing engineer does: when you are unsure how something should be named, laid out, or called, look it up rather than guess. Professionals do not carry the whole standard in their heads either.

What this means in practice, and what a grader will look for:

  • Names say what the thing is. Functions are verbs, variables are nouns, constants are ALL_CAPS, and single letters are for loop counters only.
  • Indentation is consistent, braces are always used, and the layout makes the structure obvious at a glance.
  • Comments explain why, not what. A comment that contradicts the code beneath it is worse than no comment, because a reader believes it.
  • No commented-out scratch code, and no unexplained numbers or strings sitting in the middle of a line.
  • The code runs, and the evidence on the page shows it doing what the module asked.

The security standards this course enforces

These are graded as correctness, not style. Each one is taught in a lecture, and once taught it is required in everything you submit.

The security standards this course enforces. Columns: Rule, Why.
RuleWhy
Strict comparison (===, in_array(..., true)) in any security decisionLoose comparison type-juggles, and two different strings can compare equal
Validation is server-side, allow-list, length-after-normalizationA client-side check is a usability feature; a deny-list is a list of the attacks you thought of
Encoding at the sink, with explicit flags and an explicit character encodingDefaults changed between PHP versions; the sink's interpreter chooses the encoding

No error suppression (@) and no verbose errors to the userSuppression hides failures from you; verbose errors disclose internals to attackers

What this course requires

The rest of this page is specific to ICS C230.

The submission block

Every lab and assignment report opens with this block, completed, at the top of the file. It identifies the work as yours, carries the AI disclosure the syllabus requires, and keeps your reflection welded to the work it reflects on.

NAME: First Last
AI DISCLOSURE: What you asked an AI and what you used, or "None."
REFLECTION: Two or three sentences: what you built, what was
difficult, and what you learned.

!Watch out

A submission without the block is incomplete, no matter how correct the work is. It is the first thing checked.

How work is submitted

Submissions are Markdown files, written as the Writing in Markdown page shows: your code in fenced blocks, your evidence (requests and responses, test tables) in fenced blocks, screenshots uploaded with the report, in the order the assignment page lists.

Comment your reasoning at the security decisions

Where your code makes a security decision (a validation rule, an encoding call, a prepared statement, a rejected edge case), a one-line comment states the reason if it is not obvious. "What" comments are noise; "why" comments at trust boundaries are what a security reviewer reads first.

Before you submit

  1. The submission block is present and completed, disclosure line included.
  2. Layout follows PER Coding Style (linked above): consistent indentation, braces on every block, readable line lengths.
  3. Every security decision follows the table above, or your comment says why it deviates.
  4. Comments are accurate, and no commented-out scratch code remains.
  5. The evidence in your report matches what the assignment page's expected output describes.
