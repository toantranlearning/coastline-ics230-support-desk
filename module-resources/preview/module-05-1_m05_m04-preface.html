What this module is for

Module 01 gave you the word injection: untrusted data reaching an interpreter that reads part of it as a command. Module 03 put two controls on the path from source to sink, validation on the way in and encoding at the sink. This module is about the sink that reads SQL, and the one control that settles the question for it.

The incident this module answers is a sign-in bypass. Someone typed a few characters into the username box on the portal's sign-in page and was signed in as an administrator without a password. You will reproduce that bypass yourself before you remove it.

The same flaw sits at the customer lookup on customer.php: the name search and the account-id lookup both build their SQL from what the user typed. You fix all three.

"Fix" has a specific meaning this module. Parameterization is the fix. Validation, escaping, and least privilege are supporting controls, and telling the difference is one of the things you are assessed on. A change that strips or escapes characters makes the error page go away and leaves the hole open for the next crafted value.

The question this module answers

How does an application stop untrusted data from becoming executable instruction at the database?

What you will be able to do

After Module 04 you can:

  1. Reproduce SQL injection against your own portal and say precisely what the payload changed.
  2. Write out the exact statement the database was handed for a given input, and say how the parser read it.
  3. Trace request input into a concatenated query and name the line where data became syntax.
  4. Replace string-built SQL with a prepared statement and bound values, wildcards included.
  5. Explain why parameterization works structurally, rather than by filtering.
  6. Name the query components parameterization cannot protect, and say what does.
  7. Prove the original payload is now inert while legitimate lookups still succeed.

Before you start

  • Reread Module 01 lecture sections 4 and 5 if trust boundary, source, sink, and injection are not yet automatic. This module assumes all four.
  • Reread Module 03 lecture sections 3 and 6 if validation and encoding still blur together. This module adds a third control, parameterization, and the distinction between the three is the assessed idea.
  • Sign in to your course environment as rmarsh, open the customer search and an account's detail view on customer.php, and open the sign-in page. You will watch a typed value reach the database before you write anything.

Materials

  • The lecture page, which teaches everything the quiz and the assignment need.
  • OWASP Top 10:2025 A05 Injection, the OWASP SQL Injection Prevention Cheat Sheet, and the CLARK Secure Coding Guidelines, the three required readings.
  • auth.php, which runs the sign-in query, and customer.php, which runs the name search and the account-id lookup. index.php shows the same customer data read safely.
  • The TC-IR-01 Form and Worked Example page in the Course Orientation module.

Where you may run this

You change code this module, in your own course environment. There is no scanning and no exploitation beyond typing values into the application's own sign-in form and lookups. Your own instance is the only target you are authorized to test.

Module 04 is complete when you have submitted the quiz and the incident report for TC-IR-003: the completed TC-IR-01 form with a source-to-sink trace in section 5, the parameterized auth.php and customer.php, and before-and-after evidence in section 7 showing the ' OR 1=1 -- username no longer signing anyone in, a crafted customer lookup no longer returning records that were not searched for, and real accounts still signing in and still being found.
