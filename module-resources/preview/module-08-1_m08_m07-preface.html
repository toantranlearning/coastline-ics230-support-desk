What this module is for

Every scan example you have met so far was a confirmation of something you had already found by hand. This module is different. The supplied simulated packet represents candidate alerts, source review, response observations, and coverage gaps. No tool execution or complete application coverage is claimed. You do not know in advance what is real, and your job is to turn a pile of noisy tool output into a short list of defensible findings.

That is the actual work of a security engineer, and it is mostly judgment rather than tooling. Anyone can run a scanner. The skill is deciding which alerts are real, which are noise, which duplicate each other, and which five of forty matter enough to fix first.

This module writes no code and repairs nothing, which is the hardest thing about it: you will confirm real vulnerabilities, including both halves of this sprint's ticket, and then leave them in place with an owner written against each. The deliverable is a triage report, which is the document your findings actually travel in once you leave a classroom, plus the first real revision of the incident-response playbook you began in Module 02.

A scanner produces alerts. A person produces findings.

The question this module answers

How do you turn noisy tool output into defensible findings and verified remediation?

What you will be able to do

After Module 07 you can:

  1. State clearly what SAST, DAST, and manual review each can and cannot see.
  2. Read a scoped simulated security-testing evidence packet, and explain what a static taint analysis such as Psalm adds, without running either tool yourself.
  3. Validate an alert into a finding, or dismiss it as a false positive, with evidence either way.
  4. Tag every confirmed finding with an origin: baseline, shipped this term, or introduced by your own change.
  5. Deduplicate and prioritize findings by real risk rather than by tool severity.
  6. Burn a backlog down against a baseline and report counts a manager can act on.
  7. Write a triage report someone downstream could act on, with an owner against every deferred item.
  8. Interpret a clean result without overstating what it proves.

Before you start

  • Read the assigned CLARK Code Review material and OWASP testing guidance.
  • Re-read the correlation steps of Modules 04 and 05. This module is that habit applied to the whole application at once.
  • Open the Simulated Evidence Packet and read its scope before analyzing alerts. No scanner is run in this activity; the supplied observations are fictional teaching evidence.
  • Have your Module 02 backlog to hand. This module measures against it.

Materials

  • CLARK: Code Review (Sharevski)
  • OWASP Web Security Testing Guide · OWASP Secure Code Review Cheat Sheet · OWASP Proactive Controls (this module verifies C1 through C10)
  • The simulated packet, and references for OWASP ZAP, Nessus, Burp, and Psalm
  • The full portal source and your running portal, including this sprint's customer record release
  • Your Module 02 findings backlog, and the incident-response strategy you drafted alongside it

Scope, formalized

Scoping is the professional habit this module names, even though you are not running the scanner yourself. A scan without a written scope (targets, tools and versions, the authenticated role, exclusions, and a start time) is how authorized testing becomes unauthorized testing, and it is why you never point a scanner at a host you do not own. Reading a scan well starts with knowing what it was allowed to touch.

No authorization, no scan. And the scope is in writing before the first scan runs.

When you are done

Module 07 is complete when you have posted and replied in the intro forum, submitted the quiz, and submitted the scanning assignment: your reading of three findings from the simulated packet with a supported, contradicted, or unresolved verdict on each, the one vulnerability the scanner missed and why, the comparison of Nessus, ZAP, and Burp by the question each answers, and the tie-in naming which tool could help investigate one of your term's incidents.

This is a consolidation module. Your Module 02 backlog should look meaningfully different by the end of it, some items closed with evidence and some newly found, and every defect you confirmed is still in the application, deferred on purpose and written down with an owner.
