What this module is for

Module 01 named the session identifier a bearer credential: whoever presents it is treated as the user. This module is about the moment that credential is issued, and about everything the sign-in has to get right before and after that moment.

A sign-in is not one check. It is a chain of stages: store the password, check it, issue a session, carry it across requests, end it, and offer a way back in. Each stage can be attacked on its own, and the weakest one sets the strength of the whole chain. A correct password check is worth little if the identifier that follows it was planted before sign-in, or if the stored passwords give themselves up the moment the table is copied.

The desk filed one ticket against the sign-in with three weaknesses in it. A rep's account was reached by someone who guessed a password the rep had reused elsewhere; nothing counted the failed attempts. The identifier the attacker held before the sign-in was still valid after it. And the passwords in the users table are MD5 digests, so the database copy taken in the pre-term breach gives up every staff password quickly. You write the report for that incident, TC-IR-008, and you make all three fixes on auth.php and data/seed.sql in your own course environment.

The question this module answers

How does an application prove who is asking, and keep that proof safe across every request that follows?

What you will be able to do

After Module 09 you can:

  1. Treat a sign-in as a chain of stages, each with its own attack.
  2. Explain why a fast hash turns a stolen table into a list of passwords, and store passwords with password_hash, password_verify, and password_needs_rehash, moving old rows over at their next sign-in.
  3. State when a password is changed and when it is not, and name credential stuffing.
  4. Return one answer on every failed sign-in, and count failures on the server with a threshold, a window, and a recovery.
  5. Regenerate the session identifier at sign-in, and end a session on the server as well as in the browser.
  6. Say what makes two factors independent, and how a TOTP code proves possession.
  7. Prove the fixes with before-and-after evidence: a guessing run refused, a new identifier at sign-in, and a $2y$ hash where a digest was.

Before you start

  • Reread Module 01 lecture section 6 on sessions and the bearer credential. Every control in this module protects that one string.
  • Reread Module 04 lecture section 6 on ? placeholders and the portal's q and q_one helpers. The lockout and the password store both go through them.
  • Reread Module 08 lecture section 2, authentication is not authorization. This module is the other half of that line.
  • Sign in to your course environment as the rep account from Module 01 and open auth.php. You will watch a run of failed sign-ins meet nothing before you change anything.

Materials

  • The lecture page, which teaches everything the quiz and the assignment need.
  • OWASP Top 10:2025 A07, the OWASP Authentication Cheat Sheet, and CLARK's Session-based Vulnerabilities, the three required readings.
  • auth.php, the sign-in and session helpers; login.php, the page that calls them; data/seed.sql, the users and login_failures tables; lib/passwords.php and lib/query.php, the helpers you call.
  • The Requests and Developer Tools page and the TC-IR-01 Form and Worked Example page in the Course Orientation module.

Where you may run this

You change code this module, in your own course environment. The only guessing you run is a short set of wrong passwords against your own rep account in your own environment, typed by hand or sent with curl. Your own environment is the only target you are authorized to test. Do not reuse any password you test, and do not put a real password or session identifier into your submission.

When you are done

Module 09 is complete when you have posted and replied in the forum, submitted the quiz, and submitted the incident report for TC-IR-008: the completed TC-IR-01 form with the three weaknesses traced in section 5, the fixes on auth.php and data/seed.sql, and before-and-after evidence in section 7 showing a guessing run refused at your threshold while a correct sign-in still works, receives a new session identifier, and leaves a password_hash value where the MD5 digest was.
