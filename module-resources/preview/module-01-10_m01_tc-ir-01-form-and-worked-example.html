You complete a TC-IR-01 incident report in nearly every module of this course. This page is your standing reference: the blank form, and a completed example to model your reports on. Keep it open while you write.

The form's section structure never changes; each module's assignment tells you which sections that incident needs. The worked example below, TC-IR-001, is the pre-term breach filled in on this form, and it is the standard every report you write is held to. Its section 7 shows the annotation standard. Read it before your first report.

The terms the form uses (incident, Discovery, Incident Commander, severity, containment, eradication, recovery, mitigation and remediation) are defined in the Module 02 lecture, section 10, which also maps the form's ten sections to the response lifecycle.

iCourse adaptation and fictional case

Start with the Incident Reporting Guide for definitions, evidence practices, assignment scope, and the NIST connection. TC-IR-01 is a course form, not a NIST form. The carrier deadlines, retention period, and approval rules below are fictional TechCorp policies. Follow each assignment's required sections and length; do not invent events, approvals, reviewers, or notification decisions to complete the template. TC-IR-001 is a supplied fictional worked example, not a record of your lab results.

2Executive summary

Five to eight sentences a non-technical reader can follow: what happened, what was taken or changed, the root cause in one plain sentence, what was done about it, and where things stand. Write it last. If the summary cannot state the root cause, the incident is not ready to close.

3Systems and data affected

Every asset touched, what it holds, and what happened to it: read, taken, modified, or exposed but unaffected. Name data categories precisely; "customer data" hides the difference between a name and a tax identifier, and the notification decision in §8 turns on that difference.

3. Systems and data affected. Columns: Asset, Contents, Impact.
AssetContentsImpact

4Timeline of events

Every event with a date, a time, and the source that proves it: the senior analyst’s determination, a change record, the IC log, a person’s report. Distinguish what the attacker did from what responders did. An event with no source is an assumption; keep it out of the table or label it as one.

5Detection and analysis

5.1 How the incident was found

The actual channel, not the intended one. If a person found it by accident, say so; the gap between how it should have been detected and how it was detected is a corrective action in §9. Record who performed the analysis and when, and reference the analyst’s determination in the incident file rather than reproducing raw material here.

5.2 The vulnerability identified

The senior analyst delivers the determination; this section restates it in the writer’s own words. If you cannot restate it, you do not understand it yet, and the fix in §6.2 will show that. Then classify it: the OWASP Top 10:2025 category, the CWE identifier, and whether the flaw is in the code, the configuration, or the design. State why it existed, not only what it was; "the query concatenated user input" is what, "no data-access layer existed, so every page built its own queries" is why.

5.3 What analysis could not determine

The questions this investigation cannot answer, and for each one, the missing record or capability that makes it unanswerable. This section is mandatory, and an empty version of it is not credible. Each entry here should reappear in §9 as a corrective action.

6Response actions

6.1 Containment

What was done to stop ongoing harm, when, by whom, and per which runbook step. Label every stopgap as a mitigation, not a remediation, and say what it does not protect against. A finding covered only by a stopgap stays open.

6.2 Eradication: the remediation

Three parts, in order, per TC-IR-001 §6.2. First, the remediation identified: what the fix is, traced to the determination in §5.2. Second, the pseudocode: what moves, what changes, what fails closed; this is the decision that gets reviewed. Third, the code, from the change record, with the second-person review noted. Include the credential and session consequences: repairing the flaw does not un-take copies already made.

6.3 Recovery

How service was restored, the monitoring applied afterward and for how long, and what would count as recurrence.

7Confirmation of remediation, annotated

One entry per verification check. Each records what was performed, what resulted, and an annotation stating what the check proves and what it does not. Include at least one check that would still pass with every mitigation removed, and one that exercises the application end to end. A confirmation section without annotations is a list of claims; see TC-IR-001 §7 for the standard.

8Notification determination

Who decided whether notification is required, on what basis, and the outcome. If regulated data categories are involved, counsel makes this call, not the technical team. Record the carrier’s involvement; no public statement is made without its written consent.

9Post-incident actions

Every corrective action with a named owner, a target date, and a status. Pull from §5.3 and §5.1 as well as the root cause; the gaps that slowed the investigation are findings too. Close with the lesson recorded at the blameless review, written so someone who was not there understands what condition, not which person, permitted the incident.

2Executive summary

In the early morning of Saturday, August 22, an unauthenticated actor downloaded the customer portal’s complete database, staff accounts and all, directly from the web server. No software flaw was exploited and no credential was stolen: the files sat inside the directory the web server publishes, and the server did what it is built to do and served them to anyone who asked for their address. The root cause is a design decision, not a coding error, and it is classified that way in §5 (OWASP Top 10:2025 A06, Insecure Design). The incident was contained the morning of discovery with a deny rule in front of the data directory, eradicated two days later by relocating the data outside the published tree and rotating every stored credential, and verified as recorded in §7. Because the customer table includes tax identification numbers, privacy counsel determined notification was required, and every customer in the database has been notified. The portal stayed online throughout.

5Detection and analysis

5.1 How the incident was found

Not by a scanner, an alert, or a monitoring product; none exists on this system. The developer, working on an unrelated change, noticed that an unauthenticated request for a data-directory address returned the file, and reported it within the hour. The senior security analyst was engaged the same day and established the activity summarized in §4, including that the exposure had already been used two days before it was found. The gap between how this should have been detected and how it was detected is corrective action CA-4 in §9.

5.2 The vulnerability identified

The analyst’s determination, restated. The application’s data files, the database and its seed script, live inside the web server’s published document root, and no rule excluded them. Any unauthenticated request naming their path received the file with HTTP 200. Authentication protected the application’s pages; nothing protected the data those pages exist to guard.

5.2 The vulnerability identified. Columns: Classification, Reference.
ClassificationReference
OWASP Top 10:2025A06, Insecure Design. The flaw is where the data was placed, not how any line of code behaved.
CWE (primary)CWE-219: Storage of File with Sensitive Data Under Web Root
CWE (related)CWE-552: Files or Directories Accessible to External Parties
Flaw locationDesign. The code and the server both behaved exactly as written

Why it existed. The directory layout was chosen on the first day of the project, before anyone asked which paths the server may publish, and no review ever asked afterward. The trust boundary between the web server and the filesystem was drawn in the wrong place at design time, which is why no later line of code could have been the fix. The failed sign-in attempts in §4 show the actor tried credentials first; the open directory made credentials unnecessary.

5.3 What analysis could not determine

Working from the sparse records this system keeps, the analyst could not establish the following. Each gap maps to a corrective action in §9: Whether the same files were accessed before the period the analyst could reconstruct. The earliest established activity in §1 is the earliest that could be established, which is not the same claim. (CA-4) Whether the downloaded data has been further distributed. Nothing inside TechCorp can answer this; counsel’s notification decision assumed distribution. (§8) Whether any record was modified rather than read. Database contents matched the most recent backup, which bounds the question without closing it. (CA-4, CA-5)

6Response actions

6.1 Containment

At 11:40 on August 24, following runbook steps C-1 through C-4 (then improvised, since written down): a deny rule was placed in front of the portal so any request whose path begins with the data directory is refused with HTTP 403 and recorded; every active session was invalidated; and every rep credential in the database was rotated, since a copy of the database itself had left the system. The IC decided to keep the portal online behind the rule, and informed the owner.

iNote

MITIGATION, NOT REMEDIATION The deny rule bought time and nothing else. The files were still on disk inside the published tree, and the rule’s protection depended on one configuration line persisting through every future deployment. It was recorded as a mitigation, and the finding stayed open until the relocation below was verified.

6.2 Eradication: the TC-IR-001 remediation

Every remediation in this incident file is recorded in three parts, in order: the remediation identified against the determination, the pseudocode that records the decision, and then the code. A fix whose code cannot be traced back through the pseudocode to the determination is a different fix from the one that was approved. This order is the standard for every report that follows this one. The remediation, identified. The determination in §5.2 says the flaw is where the data lives, so the remediation moves it: the data directory is relocated outside the published tree, the two code paths that open its files are updated, and the containment deny rule is kept so that any missed reference fails closed. Credentials and sessions were already rotated at containment; relocation without that rotation would have left the stolen copies valid. The pseudocode. Written and reviewed before any code (runbook E-2), because what moves, what changes, and what fails closed is the decision that must survive review: BEFORE (vulnerable layout) webroot/ index.php, login.php, profile.php, ... the application data/portal.sqlite served to anyone who asks data/seed.sql served to anyone who asks

REMEDIATION 1. Move the data directory outside the published tree. move webroot/data -> app-root/storage The server can only publish what lives under webroot; what is not under webroot cannot be served, under any future configuration.

  1. Update the two code paths that open data files. in db.php: connect("sqlite:" + APP_ROOT + "/storage/portal.sqlite") in db.php: read(APP_ROOT + "/storage/seed.sql")
  2. Keep the containment deny rule, so any missed reference fails closed instead of open. if request.path starts with "/data": record the attempt return 403
  3. Credentials and sessions were already rotated at containment. Relocating the files does not un-take the copies made on August 22; rotation is what makes those copies worthless.

The code, from the change record. The deployed change, reviewed by a second person before deployment. It is three lines and a move, which is the point: the expensive part of this incident was never the fix. shell: mv webroot/data webroot/../storage

db.php: - $file = __DIR__ . '/data/portal.sqlite'; + $file = __DIR__ . '/../storage/portal.sqlite';

  • $pdo->exec(file_get_contents(__DIR__ . '/data/seed.sql'));
  • $pdo->exec(file_get_contents(__DIR__ . '/../storage/seed.sql'));

auth.php: - $pdo = new PDO('sqlite:' . __DIR__ . '/data/portal.sqlite'); + $pdo = new PDO('sqlite:' . __DIR__ . '/../storage/portal.sqlite');

router.php (containment deny rule): unchanged, kept as depth. README.md and DESIGN.md were removed from the web root in the same change. They are not sensitive in themselves; they were the map that made the data trivial to find.

6.3 Recovery

Service was never interrupted, so no restoration sequence was required. Heightened attention runs through September 25 (runbook R-2): the deny rule’s refusals are reviewed daily, and no recurrence or related activity has been seen as of this version of the report.

7Confirmation of remediation, annotated

Per runbook E-4, each check records what was performed, what resulted, and, in the annotation, what the check proves and what it does not. The annotations are the reasoning a reviewer needs in order to trust this section without re-running it. Check 1. The published addresses, in production Performed: An unauthenticated request was made to each of the three formerly exposed addresses on WEB01. Result: All three return HTTP 403 from the deny rule. Before containment they returned HTTP 200. Annotation. This proves only that the stopgap works. The 403 comes from the deny rule, which is configuration; it says nothing about whether the files are still reachable behind it. On its own, this check is the mitigation wearing the remediation’s clothes, which is exactly why it is not the only check. Check 2. The same addresses, with the stopgap removed Performed: In a second checkout of the application configured identically to production, the deny rule was disabled and the same three requests were repeated. Result: All three return HTTP 404: the server has no file at those paths to serve. Annotation. This is the check that proves the remediation rather than the mitigation. With the rule out of the way, the files are not there. The deny rule is now defense in depth rather than the defense, and a configuration regression no longer re-creates the incident. Check 3. The filesystem, not the URL space Performed: The published tree on WEB01 was listed recursively and compared against the application’s source manifest. Result: No data file, database file, or documentation file exists anywhere under the web root. Annotation. Checks 1 and 2 prove what the server does today when asked; this check proves there is nothing left for any future change to expose. URL tests exercise the front door. This one confirms the room behind it is empty. Check 4. The application still works Performed: A regression pass was run: rep sign-in, the customer list, individual records, and every page that reads the database. Result: All functions behave as before the incident. Annotation. The remediation changed both code paths the application uses to open its data. A fix that breaks the application is a fix the next person on call reverts at 2 a.m., taking the security with it. Proving function is part of proving the fix will last. Check 5. The stolen credentials are worthless Performed: Sign-in was attempted with a known pre-incident password for each rep account, and the rotated credentials were compared against the pre-change copy in the incident folder. Result: Every pre-incident credential is refused; every account carries new credentials; no active session predates the rotation. Annotation. Relocating the files does not un-take the copies downloaded on August 22. The copy of the database in the actor’s hands is only harmless if everything in it has stopped being true. This check closes the half of the incident that lives outside TechCorp’s systems. Check 6. The scan, weighted honestly Performed: The scan used in the ongoing security review was re-run against the remediated portal. Result: No alert for the exposed directory is raised. Annotation. The weakest check here, and recorded as such: the scan did not find this flaw before the incident, because nothing in the application links to the data files and a crawler follows links. Its silence now is therefore weak evidence. It is included because the carrier requires scan output in the incident file, not because it carries the confirmation.

8Notification determination

Privacy counsel, engaged through the carrier’s Breach Response Unit, reviewed the exfiltrated data on August 31. Because the customer table includes tax identification numbers, the incident meets the notification threshold, and counsel directed that distribution be assumed rather than argued. Every customer in the database was notified through the carrier’s panel vendor, with credit monitoring offered. Per the playbook, no statement beyond the counsel-approved notice has been made, and none will be without the carrier’s written consent.
