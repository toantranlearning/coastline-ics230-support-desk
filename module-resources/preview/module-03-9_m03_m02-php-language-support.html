An equipment reservation has an identifier and an owner. A program can look up the reservation correctly and still give it to the wrong person. The PHP might contain no syntax error; the missing part is the rule deciding which owner may read which reservation.

This companion helps you read the queries, policy methods, file operations, and routing conditions in the M02 security lecture. The lecture teaches threat modeling and secure design. These examples explain the language used to express those decisions, without supplying a completed portal claim register or runbook review.

★A library call implements one operation

A parameterized query keeps supplied values separate from SQL syntax. It does not decide which records a person may read. Read the query's selection rule as well as the function calls, because safe syntax and correct permission are different requirements.

1Read shared code and application helper contracts

The lecture begins some fragments with require 'auth.php';. require evaluates a PHP file so the current execution can use its definitions and behavior. The filename is resolved according to PHP's inclusion rules. require_once adds the rule that the same file is not included again in that execution.

PHP
<?php
require __DIR__ . '/auth.php';
$currentUser = require_login();

This is an application fragment, not a standalone exercise: it requires that file and the helper it defines. __DIR__ is the current file's directory, and . joins strings to form the path. require_login is an application function rather than a PHP built-in. In the lecture example, its stated contract is to refuse an unauthenticated request or return the signed-in user.

$currentUser = require_login(); stores that returned user. Calling require_login(); without assignment can still enforce sign-in, but it does not create a $currentUser variable for later ownership checks.

!A helper name is not evidence of its behavior

Read the function definition when a claim depends on what it returns or refuses, because require_login in one application may have a different contract from a similarly named helper elsewhere. Sign-in alone does not prove permission for a selected record.

Source: PHP require (opens in a new tab) describes required inclusion; PHP return (opens in a new tab) describes returning a value to the caller.

2Select a value from a user record

An associative array stores entries by named keys. The following local data represents a user and a reservation; it does not perform a real sign-in or database lookup.

PHP
<?php
$currentUser = ['id' => 7, 'role' => 'customer'];
$reservation = ['id' => 201, 'owner_id' => 7];
echo $currentUser['role'] . "\n";
var_dump($reservation['owner_id'] === $currentUser['id']);
Output
customer
bool(true)

=> associates a key with a value. Square brackets select the named entry. === compares both type and value, so the two integer owner identifiers match. This local example illustrates an ownership relationship. Production code needs a clear type contract for values returned by storage, because a database driver may represent a numeric value as text.

A request value such as $_GET['id'] is different from the user identifier established through server-side session handling. The caller selects the requested resource; the authenticated server state identifies the requester. Assigning both from the request would let the caller claim an identity as well as choose a resource.

Source: PHP arrays (opens in a new tab) explains keyed entries; PHP comparison operators (opens in a new tab) explains strict identity.

3Recognize objects, methods, and constants

An object is an instance of a class, which defines the object's behavior and data. A method is a function associated with that object. The arrow -> selects an object's method or property.

In $pdo->prepare($sql), $pdo is a database connection object, prepare is its method, and $sql supplies an argument. The returned statement is another object. $statement->execute(...) asks that statement to execute with the supplied values.

PDO::FETCH_ASSOC uses ::, the scope-resolution operator, to select a named constant from the PDO class. It tells fetch to return a row as an associative array indexed by column names.

◆Connection, statement, and row

The connection communicates with the database. A statement represents a query to execute. A row is a record returned by that query. These are separate values: a successful connection is not proof that a statement returned a matching row.

Source: PHP objects (opens in a new tab) introduces object instances; PHP scope resolution (opens in a new tab) explains ::.

4Run a small parameterized lookup

The next example creates a temporary, in-memory SQLite database for practice. It does not modify the portal. It requires the PDO SQLite driver supplied by the course environment.

PHP
<?php
$pdo = new PDO('sqlite::memory:');
$pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
$pdo->exec('CREATE TABLE reservations (id INTEGER, owner_id INTEGER, label TEXT)');
$pdo->exec("INSERT INTO reservations VALUES (201, 7, 'Loan kit')");
$statement = $pdo->prepare('SELECT label FROM reservations WHERE id = :id');
$statement->execute(['id' => 201]);
$row = $statement->fetch(PDO::FETCH_ASSOC);
echo $row['label'] . "\n";
Output
Loan kit

new PDO(...) constructs a connection. 'sqlite::memory:' selects an SQLite database that exists in memory for this connection. setAttribute sets exception-based error handling. exec executes the fixed setup statements; these contain developer-written literals, not concatenated requester data.

prepare creates a statement from a template. :id is a named parameter marker representing a data value. The execute array supplies integer 201 for that marker. fetch retrieves the next matching row, and ['label'] selects its text.

Parameters represent complete data values. They do not stand for a table name, a column name, or an arbitrary piece of SQL. The database needs those structural parts in the query template.

Source: PHP PDO::prepare (opens in a new tab) describes templates and marker limits; PHP PDOStatement::execute (opens in a new tab) documents the values array.

5Add a record-selection rule and trace a nonmatch

The earlier lookup selects by resource identifier alone. The next example makes ownership part of the query. The two identifiers remain different arguments.

✓PHPSecure
<?php
// WHY: Matching both the reservation and owner prevents this lookup from selecting another owner's row.
$pdo = new PDO('sqlite::memory:');
$pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
$pdo->exec('CREATE TABLE reservations (id INTEGER, owner_id INTEGER, label TEXT)');
$pdo->exec("INSERT INTO reservations VALUES (201, 7, 'Loan kit')");
$statement = $pdo->prepare(
    'SELECT label FROM reservations WHERE id = :id AND owner_id = :owner'
);
$statement->execute(['id' => 201, 'owner' => 8]);
$row = $statement->fetch(PDO::FETCH_ASSOC);
if ($row === false) {
    echo "No matching reservation.\n";
} else {
    echo $row['label'] . "\n";
}

Secure. Why: Matching both the reservation and owner prevents this lookup from selecting another owner's row.

Output
No matching reservation.

SQL's AND requires both predicates to match. Reservation 201 exists, but its owner is 7. The query supplies owner 8, so no row matches. With this successful query, fetch returns false when there is no next row. The PHP comparison selects the nonmatch branch before code tries to access a field.

Changing the supplied owner to 7 produces Loan kit. That allowed case matters: a rule that refuses everyone would also stop unauthorized reads while breaking the feature.

▸Three outcomes to keep separate

A row can match, a successful query can have no matching row, or a database operation can fail. Exception mode makes an operation failure throw an exception. Do not describe every absent result as the same condition, because failure and legitimate nonmatch can require different operational handling.

Source: PHP PDOStatement::fetch (opens in a new tab) describes returned rows and false; PHP PDO error handling (opens in a new tab) explains exceptions.

6Read a policy object's method and nullable return

The lecture's policy example declares methods returning ?bool. The question mark means the return may be Boolean or null. Null means “no decision” in this example's stated contract.

PHP
<?php
class PracticePolicy
{
    public function allows(string $user, string $action, int $resource): ?bool
    {
        return null;
    }
}
$policy = new PracticePolicy();
$decision = $policy->allows('avery', 'read', 201);
var_dump($decision);
var_dump(!$decision);
Output
NULL
bool(true)

class defines the type. public makes the method callable from outside the class. The parameters declare a string user, a string action, and an integer resource. Those declarations describe types, not a permission rule. The method here returns null deliberately so you can trace a failed lookup.

!$decision converts the value to a Boolean and negates it. Null is false-like, so negating it produces true. This is why a gate that refuses when !allows(...) is true refuses a null decision under this contract.

Source: PHP class basics (opens in a new tab) explains classes and methods; PHP type declarations (opens in a new tab) explains nullable types.

7Require an explicit grant

The following practice compares two gates with the same null decision. The messages make each branch visible without sending a real file.

✕PHPVulnerable
<?php
// WHY: A null denial decision is false-like, so a deny-only gate falls through to the action.
$denied = null;
if ($denied) {
    echo "Operation refused.\n";
} else {
    echo "Operation performed.\n";
}

Vulnerable. Why: A null denial decision is false-like, so a deny-only gate falls through to the action.

Output
Operation performed.
✓PHPSecure
<?php
// WHY: Only Boolean true grants the operation; false, null, and unexpected values take the refusal path.
$allowed = null;
if ($allowed !== true) {
    echo "Operation refused.\n";
} else {
    echo "Operation performed.\n";
}

Secure. Why: Only Boolean true grants the operation; false, null, and unexpected values take the refusal path.

Output
Operation refused.

!== true means “not exactly Boolean true.” It explicitly requires a grant. The lecture's !$policy->allows(...) uses Boolean conversion and is appropriate to its Boolean-or-null return contract. If a different helper returns strings or other types, inspect that contract rather than assuming the same expression is equivalent.

✕Returning null and throwing are different behavior

A null return continues ordinary execution. An uncaught exception stops that ordinary path; it does not fall through to the next statement. A catch block can resume processing, so its behavior must also preserve refusal. Trace the actual failure path because the word “failure” does not specify what PHP executes next.

Source: PHP Boolean conversion (opens in a new tab) explains false-like values; PHP exceptions (opens in a new tab) describes thrown and caught failures.

8Read a file-response fragment

The lecture uses a protected PHP route to deliver a file stored outside the published folder. The following fragment explains the output calls after the application has already performed the required authorization and selected a trusted stored filename.

PHP
<?php
header('Content-Type: application/pdf');
readfile(__DIR__ . '/../private-files/reservation-201.pdf');

This is a web-handler fragment requiring the named file. header adds an HTTP response header. The media type tells the browser the body is PDF data. readfile reads the file and writes its bytes to the output. It does not check who requested it. It returns the number of bytes read, or false on failure, and can emit a warning.

.. in the path means the parent directory. The source directory and deployment configuration determine where this path points. A relative path spelling alone does not prove the file is outside the actual web server's published root.

!Output functions do not enforce the preceding policy

Check permission before writing the file because bytes already sent cannot be taken back by a later refusal. Do not accept a requester-controlled filename as a trusted storage path, because that would create a separate path-selection risk.

Source: PHP header (opens in a new tab) explains response headers; PHP readfile (opens in a new tab) documents output and failure behavior.

9Extract a path before a prefix decision

A request URI may contain a path and query string. The lecture's temporary deny rule extracts the path with parse_url and asks whether it begins with a particular folder prefix.

PHP
<?php
$requestUri = '/files/reservation-201.pdf?download=1';
$path = parse_url($requestUri, PHP_URL_PATH) ?: '/';
echo $path . "\n";
var_dump(str_starts_with($path, '/files/'));
Output
/files/reservation-201.pdf
bool(true)

PHP_URL_PATH selects the path component. ?: is the short ternary form: it uses the left result when truthy and otherwise uses the right value. Here, the fallback is /. Unlike ??, this form also replaces other false-like values. str_starts_with returns a Boolean and performs a case-sensitive prefix test.

This is a string decision, not proof that every server path representation is blocked. A containment rule must be assessed against the actual route handling and deployed server. The assignment asks you to inspect and evaluate the portal, rather than treat this practice string as environmental evidence.

Source: PHP parse_url (opens in a new tab) explains components and its parsing limits; PHP str_starts_with (opens in a new tab) documents prefix matching.

10Distinguish response output from logging

echo writes the response body. error_log sends a message to the configured logging destination. They serve different readers. Where logs go depends on the environment; a call alone does not prove a durable or monitored audit trail.

PHP
<?php
$path = '/files/example.pdf';
$message = 'deny rule: ' . $path;
echo $message . "\n";
Output
deny rule: /files/example.pdf

This standalone example displays the constructed message so you can read it. The actual logging call would be error_log($message);. That does not make the text part of the HTTP response body. The runbook review needs actual evidence of what gets recorded and where it can be found.

iCode is an input to a readiness claim

A runbook step saying “inspect the logs” depends on the configured destination, the events recorded, and the responder's access. Reading a function name establishes none of those by itself. Record the verified behavior and any gap because another responder needs an executable instruction.

Source: PHP error_log (opens in a new tab) explains the configured logging destination.
