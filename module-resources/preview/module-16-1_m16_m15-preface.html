What this module is for

The earlier modules taught weaknesses one at a time. This module looks at how they combine. A breach is usually a chain of ordinary weaknesses, each survivable on its own. The analysis method here takes an incident apart: proximate cause and root cause, verified fact and inference, a timeline, and a control for each condition.

The module then turns to code you did not write. Most of a PHP application is the runtime, packages, and files loaded from a CDN. A flaw in any of it is a flaw in your application. You learn to pin a version, verify the bytes the browser runs, and decide whether a published advisory applies to your own call sites.

Application security has sent the portal team an advisory against the date-picker library the page shell loads from a public CDN. Nothing has been prepared for you. The reachability determination, the remediation decision, and the change are yours. You make the change the way the lecture teaches a security refactor, with a characterization test and a negative test around it.

The question this module answers

How do ordinary weaknesses combine into an incident? And how do you change code that is already running without losing the evidence that it is safe?

What you will be able to do

After Module 15 you can:

  1. Separate verified facts from inference in an incident, and find the root cause behind the proximate bug.
  2. Map each contributing condition to a control and name the control's function: preventive, detective, limiting, or recovery.
  3. Pin a CDN dependency to one version and add a Subresource Integrity hash with crossorigin="anonymous" to the script and the stylesheet.
  4. Decide whether an advisory against a library applies to an application, from its call sites, and cite the file and line.
  5. Review code with no package name or version, including generated code, as code of unknown origin.
  6. Refactor insecure code with a characterization test and a negative test, and state the evidence a finding closes on.

Before you start

  • Reread Module 01 lecture section 5 for source, sink, and flow. This module names those four parts for a library call.
  • Reread Module 02 lecture sections 9 and 10 for residual risk, the blameless review, and the root cause. The analysis method here builds on those definitions.
  • Reread Module 03 lecture section 4 on allow-lists. The refactor in the assignment is one.
  • Sign in to your course environment and open notes.php?customer_id=1. Click into the Since field and watch the picker open. That picker is the subject of the advisory.

Materials

  • The lecture page, which teaches everything the quiz, the forum, and the assignment need.
  • OWASP Top 10:2025 A03 Software Supply Chain Failures, the OWASP Vulnerable Dependency Management Cheat Sheet, and the CLARK dependency-management slides, the three required readings.
  • The dependency advisory application security sent the portal team.
  • layout.php, the page shell that loads the flatpickr stylesheet and script from the CDN, and notes.php, the page that calls the picker, in your course environment.
  • The TC-IR-01 Form and Worked Example page and the Requests and Developer Tools page in the Course Orientation module.

Where you may run this

You change code this module, in your own course environment. The only requests are ones you type at your own portal, and the only files you download are the library files you pin. Read about the advisory if you want the background, and do not download or run proof-of-concept exploit code from anyone. Your own environment is the only target you are authorized to test.

When you are done

Module 15 is complete when you have posted and replied in the forum, submitted the quiz, and submitted the incident report for TC-IR-013. The report is the completed TC-IR-01 form with the reachability determination in section 5. With it come both flatpickr tags in layout.php pinned and carrying an integrity hash, and the date filter in notes.php refactored behind a characterization test and a negative test. Section 7 shows the verified files loading, a wrong hash refused, and a markup payload never reaching the picker while a real date still filters the notes.
