What this module is for

Module 01 gave you the session cookie as the credential the browser attaches on its own. Module 06 showed that a valid session proves the caller signed in, and nothing more. This module adds the decision those pages left open: may this caller perform this action on this object? You make that decision on real code, in your own course environment.

Authentication and authorization are different questions. Authentication asks who the caller is. Authorization asks what that caller may do, to which object, under which conditions. Getting the first right does nothing for the second. When the second is missing, nothing errors: the feature works for whoever uses it.

The incident, TC-IR-007, has two halves. A rep's role travels in a browser cookie the client can edit, so setting it to admin opens admin.php. And customer.php returns any account whose id is in the URL, with no check that the account is assigned to the requesting rep. In both halves the server lets the client say what it may do. You close both.

The midterm examination is also in this module, in two parts. The timed practical runs in Canvas under the conditions the instructor states, without assistance. The written companion is a take-home analysis of one documented breach, on its own assignment page here. The design project also starts this module, with its kickoff page.

The question this module answers

How does the server decide, on every request, whether an authenticated caller may act on a specific object?

What you will be able to do

After Module 08 you can:

  1. State the difference between authentication and authorization, and name the four parts of an authorization decision.
  2. Reproduce both halves of the incident in your course environment: reaching admin.php by editing the role cookie, and reading another rep's customer by changing the id in the URL.
  3. Carry the role in the server-side session, set at sign-in, and read it there on every protected request.
  4. Bind the owner into the lookup so a row that is not the caller's never leaves the database, and answer a forbidden record the same way as a missing one.
  5. Explain deny by default, one central policy check, and where RBAC, ABAC, and a framework's policy layer fit.
  6. Read an HTTP request and response, name the status codes an API uses, and describe how a program authenticates with an API key.
  7. Write and run an authorization matrix, including the rows people forget.
  8. Judge a public breach response on detection, containment speed, and disclosure.

Where you may run this

You change code this module, in your own course environment, using its own demo accounts. The only testing is editing a cookie in your own browser and changing an id in your own address bar. Your own environment is the only target you are authorized to test. The midterm practical states its own conditions.
