What this module is for

Module 04 said injection is one weakness at many sinks, and that one of the sinks is echo into a page. This module is that sink. The interpreter is the browser, the command language is HTML and JavaScript, and the trace from source to sink works the same way it did for the database.

One thing is new. In SQL injection the attacker's input ran against your database. In cross-site scripting it runs in another person's browser, under that person's session. Your server is not breached; it stores a string and later writes the string into a page without encoding it. That is why the fix sits at the moment of output.

QA filed a ticket against the Sprint 15 account-notes release, notes.php. A rep opened a customer's call notes and a note ran as code in the rep's browser instead of displaying as text. The rep had typed nothing unusual; they only opened the account.

The question this module answers

How does untrusted data become code that runs in someone else's browser, and what keeps it data at each place it can land?

What you will be able to do

After Module 05 you can:

  1. Tell reflected, stored, and DOM-based XSS apart by where the value travels and who it runs for.
  2. Explain why a stored payload fires for every viewer, and why the server itself is not breached.
  3. Name the context a value lands in on a page, and choose the encoding or safe API that context needs, or recognize that none exists.
  4. Say why a javascript: URL survives HTML encoding, and what to check first.
  5. Write a browser-side value with textContent and say why innerHTML is the wrong tool.
  6. Explain what a Content Security Policy adds after the sink is encoded, and why it is not the primary fix.
  7. Prove a stored payload is inert for a second signed-in viewer while an ordinary note still reads as typed.

Before you start

  • Reread Module 01 lecture sections 5 and 6 if source, sink, and the session cookie are not yet automatic. The victim's session is what the attacker's script holds.
  • Reread Module 03 lecture sections 6 and 7: htmlspecialchars with its flags, and how to find every sink on a page. This module reuses both without re-teaching them.
  • Sign in to your course environment as rmarsh, open a customer account, and follow its Call notes for this account link to notes.php?customer_id=1. You will watch a stored note reach the page before you change anything.

Materials

  • OWASP Top 10:2025 A05 Injection and the OWASP Cross Site Scripting Prevention Cheat Sheet, the two required readings.
  • notes.php, the call-notes page in your course environment: it lists a customer's notes and saves a new one.
  • The TC-IR-01 Form and Worked Example page in the Course Orientation module.

Where you may run this

You change code this module, in your own course environment, which is the only target you are authorized to test. The only test payloads you use are the harmless ones the lecture names: markup such as <b>stored</b>, and <img src=x onerror=alert(1)>. Nothing you type reads a cookie or contacts another host. There is no scanning.
