The security lecture asks whether a state-changing request carries evidence from a form your application served. This page explains the PHP statements that store, submit, and compare that evidence. The examples use an equipment-preference form rather than the assignment's call-notes handler.

Session authentication, authorization, input validation, and a CSRF token check are separate controls. Understanding the PHP statements helps you explain where each control runs; it does not add a separate graded language exercise.

1Read the request method and request arrays

$_SERVER, $_POST, and $_SESSION are different arrays. PHP creates request information in the first two. The session mechanism makes server-side session values available through the third after a session starts.

1. Read the request method and request arrays. Columns: Expression, What it reads.
ExpressionWhat it reads
$_SERVER['REQUEST_METHOD']The HTTP method, such as 'GET' or 'POST'
$_POST['equipment_color']A submitted form field named equipment_color
$_POST['csrf_token'] ?? nullThe submitted token, or null if missing or null
$_SESSION['csrf_token'] ?? nullThe expected server-side token, or null if unavailable

These array keys are names chosen by the application or PHP request environment. Reading a field does not make it trustworthy. A form control's name determines its submitted field name.

The method comparison in this web-handler fragment uses ===, which compares type and value.

PHP
<?php
if (($_SERVER['REQUEST_METHOD'] ?? '') === 'POST') {
    echo 'Entered the state-change branch.';
} else {
    echo 'Entered the display branch.';
}

For a POST request, it writes Entered the state-change branch. For a GET request, it writes Entered the display branch. This is a branch demonstration, not a complete secure handler: no authentication, token check, or write occurs here.

!A POST branch is a location for controls, not proof of intent

Place the required checks before the write, because changing the method from GET to POST does not establish that the user meant to submit the request.

Source: PHP predefined variables (opens in a new tab) describes these superglobal arrays.

2Read session startup and cookie configuration

session_start() creates or resumes a session and populates $_SESSION. The browser commonly sends a session identifier in a cookie; the application keeps the token in server-side session storage. The CSRF token is a separate value from the session identifier.

This web fragment illustrates startup order. It assumes the deployment actually uses HTTPS.

✓PHPSecure
<?php
// WHY: Cookie settings are configured before session startup so the issued session cookie receives them.
session_set_cookie_params([
    'httponly' => true,
    'secure' => true,
    'samesite' => 'Lax',
    'path' => '/',
]);
session_start();

Secure. Why: Cookie settings are configured before session startup so the issued session cookie receives them.

Square brackets construct an array of named options. => associates a key with its value. true is a Boolean value, not the string 'true'. HttpOnly restricts script access to the cookie. Secure restricts cookie transport to secure connections. SameSite affects cross-site cookie sending; it is not a replacement for the form-token control.

The exact session id varies, so the cookie value is not a fixed expected output. Inspect the attributes rather than copying an example's identifier. A local plain-HTTP environment and an HTTPS deployment need settings appropriate to their actual transport; indiscriminately copying HTTPS assumptions can prevent a local session from behaving as intended.

iStartup must happen before output

Configure and start the session before writing response output, because cookie headers cannot reliably be changed after output has committed the headers. The course's environment and authentication files define the existing startup location; avoid starting an unrelated second session mechanism.

Source: PHP session_start (opens in a new tab) and PHP session cookie parameters (opens in a new tab) describe these operations.

3Read token creation without expecting a fixed secret

A random-byte generator returns binary bytes. Hexadecimal encoding represents each byte with two printable characters. This standalone program demonstrates the length and format without printing the generated token.

✓PHPSecure
<?php
// WHY: A cryptographically secure generator supplies unpredictable bytes rather than a predictable timestamp.
$token = bin2hex(random_bytes(32));
echo strlen($token) . "\n";
echo (preg_match('/\A[0-9a-f]{64}\z/', $token) === 1 ? 'Hexadecimal' : 'Unexpected format') . "\n";

Secure. Why: A cryptographically secure generator supplies unpredictable bytes rather than a predictable timestamp.

Output
64
Hexadecimal

random_bytes(32) produces 32 bytes. bin2hex produces 64 hexadecimal characters from them. strlen counts bytes in the resulting ASCII string. preg_match returns 1 when the entire string matches the shown pattern. \A and \z anchor the start and end; [0-9a-f] describes the permitted characters; {64} requires exactly 64 of them.

The actual value differs each time. Neither the format nor the length alone establishes unpredictability: a timestamp padded to 64 characters could match the format but remain predictable.

The lecture stores the generated token only when the session entry does not already exist. isset($_SESSION['csrf_token']) is true when that entry exists and is not null. !isset(...) means the opposite. Reusing an established token within the session allows forms already displayed to continue to submit under the chosen design.

Source: PHP random_bytes (opens in a new tab) documents secure random bytes; PHP bin2hex (opens in a new tab) documents their printable representation.

4Follow a comparison function

This standalone function demonstrates type checks and comparison without needing an HTTP request or a session. The fixed strings are learning fixtures, not secure generated tokens.

✓PHPSecure
<?php
// WHY: Type checks stop missing or array-shaped values before the string comparison is called.
function tokenMatches(mixed $expected, mixed $submitted): bool
{
    return is_string($expected)
        && is_string($submitted)
        && hash_equals($expected, $submitted);
}

$expected = 'classroom-example';
echo tokenMatches($expected, 'classroom-example') ? "Match\n" : "Reject\n";
echo tokenMatches($expected, 'different') ? "Match\n" : "Reject\n";
echo tokenMatches($expected, null) ? "Match\n" : "Reject\n";
echo tokenMatches($expected, ['classroom-example']) ? "Match\n" : "Reject\n";

Secure. Why: Type checks stop missing or array-shaped values before the string comparison is called.

Output
Match
Reject
Reject
Reject

mixed allows the function to receive different PHP value types so it can reject them deliberately. : bool declares a Boolean return value. && means both conditions must be true. PHP short-circuits this expression: once a condition is false, the remaining calls are skipped. An array therefore never reaches hash_equals.

The comparison's first argument is the known expected string and the second is the submitted string. It compares their contents without numeric-string conversion. Its comparison avoids stopping at the first mismatching character, but a length mismatch returns false immediately; it does not conceal the known string's length.

The conditional expression condition ? "Match\n" : "Reject\n" selects one string, which echo writes. return ends the function and gives its result to the caller; it does not stop the caller's script.

Source: PHP hash_equals (opens in a new tab) specifies argument order, string inputs, and the length caveat.

5Read rejection before the write

The following fragment needs a running web request and an initialized session. It assumes the function from section 4 is available. It demonstrates control order without implementing the assignment's storage operation.

✓PHPSecure
<?php
// WHY: Rejection stops the handler before a later state-changing operation can run.
$submitted = $_POST['csrf_token'] ?? null;
$expected = $_SESSION['csrf_token'] ?? null;
if (!tokenMatches($expected, $submitted)) {
    http_response_code(403);
    exit('Request denied');
}
// Authentication, object authorization, and field validation must also succeed before a write.

Secure. Why: Rejection stops the handler before a later state-changing operation can run.

For a missing token, the intended response is status 403 and body Request denied. The status-setting function does not terminate the script; exit does. If the check passes, execution continues and the other required controls still apply.

A function declared : void returns no value for the caller to use. A course helper that enforces a token can return normally on success and terminate on failure. That differs from tokenMatches, which always returns a Boolean for its caller to handle. Read the helper's contract so you know which behavior it provides.

Source: PHP exit (opens in a new tab) explains termination; PHP return type declarations (opens in a new tab) defines void, Boolean, and nullable returns.

6Read a hidden field in a template

A hidden field submits a named value without displaying an ordinary input box. Being hidden does not make it secret from the browser user.

✓PHPSecure
<?php
// WHY: The value is represented for a quoted HTML attribute at the point it is written.
$token = 'example-token';
?>
<input type="hidden" name="csrf_token" value="<?= htmlspecialchars($token, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') ?>">

Secure. Why: The value is represented for a quoted HTML attribute at the point it is written.

Output
<input type="hidden" name="csrf_token" value="example-token">

<?= ... ?> writes the PHP expression into the surrounding HTML. The field's name causes the submitted value to appear under $_POST['csrf_token'] in a form-urlencoded POST. htmlspecialchars represents the value safely inside that quoted attribute; it does not establish that the submitted token matches the expected one.

Source: PHP htmlspecialchars (opens in a new tab) describes HTML representation and encoding flags.

7Read origin comparison and parsed URL components

An HTTP origin consists of scheme, host, and port. The lecture's helper reads $_SERVER['HTTP_ORIGIN'] and may parse the Referer as a fallback. parse_url separates components, but parsing does not approve the origin. A result may be false, and a component may be missing.

This standalone example demonstrates exact comparison using local values.

✓PHPSecure
<?php
// WHY: Whole-value comparison rejects a look-alike host that merely contains the expected host text.
$expected = 'https://equipment.example';
$origins = [
    'https://equipment.example',
    'https://equipment.example.evil.test',
    'null',
];
foreach ($origins as $origin) {
    echo ($origin === $expected ? 'Accept' : 'Reject') . "\n";
}

Secure. Why: Whole-value comparison rejects a look-alike host that merely contains the expected host text.

Output
Accept
Reject
Reject

foreach repeats the block for each array entry. === compares the whole string. The string 'null' is an actual header value distinct from PHP's null, which represents no value. A substring search would wrongly accept the look-alike host.

A production origin policy must account deliberately for expected ports and normalization. Header absence provides no evidence of the expected origin. Origin checking supports the design; it does not replace authentication, object authorization, or the chosen token policy.

Source: PHP parse_url (opens in a new tab) documents component extraction and parser limitations.

9Check your reading

9. Check your reading. Columns: Question, Answer and explanation.
QuestionAnswer and explanation
Does POST identify the user's intent?No. It identifies the method. The handler still needs the relevant intent control.
What must run before session values are available?The application's session initialization, commonly session_start.
Why are cookie parameters configured first?The session cookie is issued as part of session startup.
How long is bin2hex(random_bytes(32))?64 ASCII characters, because each byte becomes two hexadecimal characters.
Does isset validate token quality?No. It checks whether the entry exists and is non-null.
Why does an array not reach hash_equals in the example?A preceding string check is false and && short-circuits.
Does hash_equals hash its arguments?No. It compares the supplied strings.
Does setting 403 stop the script?No. exit stops it in the rejection branch.
Is a void-returning enforcement helper the same as a Boolean comparison?No. The enforcement helper controls rejection itself; a comparison leaves the decision to its caller.
Does a hidden input prevent requester changes?No. The server must compare the submitted value against its own expected token.
Why reject a look-alike host?Its complete origin differs even though its text contains the expected host.
Does a passing token check establish object permission?No. Authorization remains a separate control before the write.
