A colleague reports that an account still opens after its owner signs out. The password check works, and the browser looks signed out. What did the application actually revoke? Authentication and session management must protect both the moment of sign-in and the access that continues afterward.

★Follow the account's entire access lifecycle

A strong password check cannot compensate for a reusable stolen session, a weak reset, or a second-factor bypass. Ask what evidence grants access, how long it remains valid, and which event revokes it.

The PHP examples make these controls concrete. Use the M09 PHP Companion lecture for function calls, session arrays, and control-flow syntax. Your main task here is to choose and verify security controls, rather than memorize PHP syntax.

!Apply Rules Of Engagement before testing

Use only your authorized course copy and the permitted manual methods, because authentication tests can lock accounts, change credentials, and expose private session data. The Orientation Rules Of Engagement and Lab Guide define your testing boundaries.

2What a sign-in proves

A sign-in answers one question: does this request come from the account it claims to come from? When the answer can be guessed, replayed, or accepted for the wrong account, the weakness is improper authentication (CWE-287).

★A sign-in proves who is asking, and nothing more

A correct password shows that the person typing holds the password. It does not decide what that person may see or change. When the proof is weak, an attacker acts as a real user, and every later control that trusts the identity inherits the mistake.

◆Authentication, credential, factor

Authentication is the process of checking that a request belongs to the identity it claims. A credential is the evidence offered, most often a password. A factor is a category of evidence: something you know, something you have, or something you are.

iAuthentication is not authorization

Module 08 section 2 drew the line: authentication asks who the caller is, and authorization asks what that caller may do. They fail on their own. A correct sign-in with a missing ownership check still leaks another user's record. A careful permission model is worth nothing if an attacker can sign in as that user.

A sign-in is not one check. It is a chain of stages, and each stage can be attacked on its own.

The weakest stage sets the strength of the whole chain. An attacker who cannot beat the password check may not need to. A reset flow that accepts a guessable answer hands over the account. A session that survives sign-out stays open for anyone who copied it.

This module's incident has that shape. An account was reached by someone who guessed a password the owner had reused on a site that was breached. The guessing run met no limit. When a guess finally worked, the session identifier the attacker already held was still valid after the sign-in. Two stages failed, and neither was the password check itself.

The A07 entry in section 1 lists the same stages as weaknesses: automated attacks that are not slowed, weak or breached passwords, weak recovery, weak hashes, no MFA, and session identifiers that are reused after sign-in or never ended.

3Storing passwords: a hash that is slow on purpose

Passwords are verified, never read back. The server never needs the password itself. It needs a way to check a submitted one. So it stores a one-way value computed from the password, and at sign-in it recomputes that value and compares.

Here is the shape that turns a stolen table into a list of passwords. The example is a staff directory tool, and it stores a SHA-1 digest of each password.

✕PHPVulnerable
<?php
// WHY: A fast unsalted digest makes offline password guesses inexpensive and exposes password reuse across accounts.
// Stored when the password was set:   sha1($password)
$row = q_one('SELECT id, password_sha1 FROM staff WHERE email = ?', [$email]);

if ($row !== null && $row['password_sha1'] === sha1($password)) {
    $signedIn = true;
}

Vulnerable. Why: A fast unsalted digest makes offline password guesses inexpensive and exposes password reuse across accounts.

Computing sha1('password') twice produces the same digest. Deterministic hashing alone is not the defect: the password store also lacks a unique salt and uses a function designed to make guesses inexpensive.

Output
5baa61e4c9b93f3f0682250b6cf8331b7ee68fd8
5baa61e4c9b93f3f0682250b6cf8331b7ee68fd8

◆Fast hash, adaptive hash, salt, work factor

A fast hash such as MD5, SHA-1, or SHA-256 is built for speed: it turns any input into a fixed digest in a tiny fraction of a second, with no key and no way back. An adaptive hash such as bcrypt or Argon2 is built to be slow and tunable. Its work factor is a cost setting you raise as hardware gets faster, so each guess stays expensive. A salt is a random value mixed into each password before hashing, so two users with the same password get different stored values. The salt is stored next to the hash and is not a secret.

An attacker who copies the table does not guess through your sign-in form. They guess on their own hardware, offline, where nothing slows them. Fast hashes permit very high offline guessing rates; hardware and algorithm determine the exact rate. GPU implementations can reach billions of MD5 guesses per second. Adaptive password hashes deliberately increase the work for each guess. With no salt, two accounts that share a password show the same digest, and a lookup table built in advance maps common digests straight back to their passwords.

Storing a password under a fast hash is a named weakness: use of a password hash with insufficient computational effort (CWE-916). The repair is a function that handles the salt, the work factor, and the algorithm choice for you.

✓PHPSecure
<?php
// WHY: An adaptive salted hash increases the cost of offline guesses while allowing verification without recovering the password.
// Set or change a password: store the whole string password_hash returns.
$stored = password_hash($password, PASSWORD_DEFAULT);

// Sign in: compare the submitted password with the stored hash.
if (password_verify($password, $stored)) {
    $signedIn = true;
}

Secure. Why: An adaptive salted hash increases the cost of offline guesses while allowing verification without recovering the password.

Output
$2y$12$QWB1XxEsOY7z4JDGBcV2YeqLyfyjZ2PLpQnXM9ngaCr/wmbfji1dm

That string is 60 characters, and it describes itself. $2y$ names the algorithm, bcrypt. 12 is the work factor, so each guess costs 2 to the power of 12 rounds. The next 22 characters are the salt, and the rest is the digest. Because the salt and the cost are inside the string, password_verify needs nothing else to check a password.

▸What happens at sign-in

  1. The user types the same password originally used to create the stored hash. The code reads that stored string.
  2. password_verify reads the algorithm, the cost, and the salt out of the stored string.
  3. It hashes the typed password with that same salt and cost. That takes a measurable fraction of a second.
  4. It compares the result with the stored digest in constant time and returns true.
  5. A password with one changed letter returns false, because it no longer matches the password used to create the hash.

iThe default cost changed in PHP 8.4

PASSWORD_DEFAULT means bcrypt today, and the manual says the constant is designed to change as stronger algorithms arrive. The default cost rose from 10 to 12 in PHP 8.4. Store the hash in a column that can hold at least 255 characters, so a longer format never gets cut off.

!bcrypt reads only the first 72 bytes

With PASSWORD_BCRYPT, the password is cut to 72 bytes before hashing. A passphrase longer than that still verifies, but only its first 72 bytes count. If bcrypt is used, enforce and explain its byte limit on the server, because silently truncating makes different long passwords equivalent. A 64-character Unicode password can exceed 72 bytes. For a policy accepting long Unicode passphrases, use a supported algorithm such as Argon2id with suitable settings rather than silently truncating input.

✕A faster hash with a salt still looks fixed

Swapping SHA-1 for SHA-256 and adding a salt passes every functional test: sign-in still works, and the digests now differ. The offline guessing rate barely drops, because each guess still costs almost nothing. The defect is invisible from the sign-in screen. Slow on purpose is the property that protects a stolen table, and a fast hash cannot provide it.

Your portal's lib/passwords.php wraps the three functions at the current defaults, so a caller never picks an algorithm or a cost. pw_hash returns the hash or throws, never false. pw_verify compares in constant time and returns false for any mismatch, including a malformed hash. pw_needs_rehash is the subject of the next section.

PHP Manual: password_hash (opens in a new tab) documents PASSWORD_DEFAULT, the automatic salt, the cost change in 8.4, and the 72-byte limit. PHP Manual: password_verify (opens in a new tab) confirms that the function is safe against timing attacks and that the stored string carries everything it needs. OWASP Password Storage Cheat Sheet (opens in a new tab) gives the current algorithm and work-factor guidance, including a bcrypt work factor of at least 10.

4Verify, then rehash

A hash made under old settings still verifies years later, because the settings travel inside the string. That is also how you move old accounts to stronger settings without asking anyone to reset. The one moment the server holds the real password is a successful sign-in. Use it.

★A sign-in is the one chance to upgrade a stored hash

password_needs_rehash reads the algorithm and cost out of a stored hash and says whether they match the current defaults. When it returns true after a successful verify, hash the password again with the current settings and write the new value back. Each account upgrades itself the next time its owner signs in.

✓PHPSecure
<?php
// WHY: Verify before rehashing so an incorrect submitted password never replaces the stored credential.
require_once __DIR__ . '/lib/passwords.php';
require_once __DIR__ . '/lib/query.php';

$row = q_one('SELECT id, password_hash FROM accounts WHERE email = ?', [$email]);

if ($row === null || !pw_verify($password, $row['password_hash'])) {
    sign_in_failed();           // one message for every failure; section 6
    return;
}

if (pw_needs_rehash($row['password_hash'])) {
    q('UPDATE accounts SET password_hash = ? WHERE id = ?', [pw_hash($password), $row['id']]);
}

sign_in_succeeded($row['id']);

Secure. Why: Verify before rehashing so an incorrect submitted password never replaces the stored credential.

▸A hash made at cost 10 meets a server at cost 12

  1. The stored value begins $2y$10$. The user signs in with the right password, so pw_verify returns true.
  2. pw_needs_rehash compares the 10 in the string with the current default of 12 and returns true.
  3. pw_hash makes a new string that begins $2y$12$, and the UPDATE stores it.
  4. At the next sign-in, pw_needs_rehash returns false, and the branch is skipped.

The same shape moves an account off a fast hash. An account that still holds an old digest verifies against it once, and on success the code writes a password_hash value and clears the old column. No fast hash is ever written again.

✓PHPSecure
<?php
// WHY: Upgrade a verified legacy credential and remove its fast digest so future database leaks do not expose the old weak representation.
if ($row['password_hash'] === null) {
    // Legacy row: an old SHA-1 digest. Verify against it one last time.
    if (!hash_equals($row['password_sha1'], sha1($password))) {
        sign_in_failed();
        return;
    }
    q(
        'UPDATE accounts SET password_hash = ?, password_sha1 = NULL WHERE id = ?',
        [pw_hash($password), $row['id']]
    );
} elseif (!pw_verify($password, $row['password_hash'])) {
    sign_in_failed();
    return;
}

Secure. Why: Upgrade a verified legacy credential and remove its fast digest so future database leaks do not expose the old weak representation.

✓The pattern to copy

Hash with pw_hash, verify with pw_verify, and after a successful verify call pw_needs_rehash and re-hash when it returns true. For a row that still holds a fast digest, verify against the digest once with hash_equals, write a pw_hash value in its place, and clear the old column. Accounts that never sign in again keep the old digest, so OWASP also suggests expiring those and forcing a reset.

PHP Manual: password_needs_rehash (opens in a new tab) shows the verify-then-rehash example this section is built on. The Password Storage Cheat Sheet linked in section 3 covers upgrading legacy hashes at the next sign-in, and the option of expiring hashes for inactive users.

5Password rules and rotation

The rules that decide which passwords ever reach the store come from NIST SP 800-63B, revision 4, published in July 2025. Its rules run against several old habits.

5. Password rules and rotation. Columns: Rule, What NIST says.
RuleWhat NIST says
Minimum length15 characters when the password is the only factor; 8 when MFA is also required
Maximum lengthallow at least 64 characters, so passphrases fit
Compositionno required mix of character types
Breached passwordscompare every new password against a list of common and breached passwords, as a whole
Scheduled changedo not require users to change passwords on a schedule
Known exposureforce a change when there is evidence the password was compromised
Security questionsdo not use them

◆Credential stuffing

Credential stuffing is trying username and password pairs taken from another site's breach against your sign-in. It works because people reuse passwords. A breach list check at password-setting time and MFA at sign-in are the two defenses OWASP names first.

✓PHPSecure
<?php
// WHY: Length and a whole-password blocklist reject common guesses without imposing predictable composition patterns; this is a policy illustration, not a complete password-setting handler.
function password_is_acceptable(string $password, array $breachedList): bool
{
    $length = mb_strlen($password, 'UTF-8');
    if ($length < 15 || $length > 64) {
        return false;                       // length is the one rule about shape
    }
    return !in_array($password, $breachedList, true);   // the whole value, strictly
}

Secure. Why: Length and a whole-password blocklist reject common guesses without imposing predictable composition patterns; this is a policy illustration, not a complete password-setting handler.

!Composition requirements can produce predictable choices

A rule such as "one capital, one digit, one symbol" pushes people toward Summer2026! and toward adding one to it after each forced change. Attackers know those shapes and try them first. Length and a breach list stop the passwords attackers really try. The shape rule does not.

Rotation follows the same logic. A password that was exposed in a breach, a log, or a shared screen is changed at once, because an attacker may already hold it. A password that was never exposed gains nothing from a change on a calendar. The change on a calendar produces predictable passwords, and NIST now says not to require it.

✓The pattern to copy

Require length, not shape. Check each new password against a breach list. Rotate a password after a known exposure, and never on a schedule. Offer MFA so a reused password alone does not open the account.

NIST SP 800-63B rev. 4, section 3.1.1 (opens in a new tab) is the source for every row in the table, including the change forced after evidence of compromise. OWASP Credential Stuffing Prevention Cheat Sheet (opens in a new tab) defines the attack and lists the defenses. The Authentication Cheat Sheet in section 1 states the same length and composition rules.

6One answer for every failed sign-in

Two failures, a wrong password on a real account and any password on an account that does not exist, must look the same from outside. If they differ, the sign-in page tells an attacker which usernames are real. That list is the input to every guessing run that follows.

◆Account enumeration

Account enumeration is any observable difference that tells an attacker whether an account exists: a different message, a different status code, a different page length, or a measurably different response time.

Your portal already gives one message on both paths. Send a wrong password for a real account, then any password for an unknown account, and compare.

Response
HTTP/1.1 200 OK
<p class="error">That username and password did not match.</p>

The seeded portal uses that message for both paths; verify the actual response from your copy. The OWASP cheat sheet gives Login failed; Invalid user ID or password. as its example of a correct message, and names Login failed, invalid user ID. as a wrong one.

Timing is the channel people forget. If the code skips the password check when the account is missing, that path returns faster, and the difference can be measured. The fix is to do the same work on both paths.

✓PHPSecure
<?php
// WHY: Run password verification for missing accounts too, reducing an account-existence signal in response timing.
// A real hash of a random value, made once and kept as a constant.
const DUMMY_HASH = '$2y$12$QWB1XxEsOY7z4JDGBcV2YeqLyfyjZ2PLpQnXM9ngaCr/wmbfji1dm';

$row    = q_one('SELECT id, password_hash FROM accounts WHERE email = ?', [$email]);
$stored = $row['password_hash'] ?? DUMMY_HASH;     // same cost whether or not the row exists

$matched = pw_verify($password, $stored) && $row !== null;

if (!$matched) {
    http_response_code(401);
    exit('The username or password was incorrect.');
}

Secure. Why: Run password verification for missing accounts too, reducing an account-existence signal in response timing.

▸Reduce the timing signal on a missing account

  1. The account exists. pw_verify runs bcrypt at cost 12 against the real hash.
  2. The account does not exist. pw_verify runs bcrypt at cost 12 against the dummy hash. The expensive hash verification runs on both paths, reducing the obvious timing difference. Database work, different stored hash costs, and network noise can still differ; this is not a promise of identical elapsed time.
  3. In case 2 the verify could only match the dummy value, and $row !== null is false anyway, so the result is a failure.
  4. The message, the status code, and the body are identical on both paths. The server log can still record which case it was.

iStrict comparison, from Module 03

Module 03 section 8 showed why a secret is never compared with ==. pw_verify and hash_equals compare as strings, with no conversion, in constant time. Every comparison that decides a sign-in uses one of them.

The Authentication Cheat Sheet in section 1 gives the correct and incorrect messages and the timing guidance. PHP Manual: hash_equals (opens in a new tab) documents the constant-time comparison, and says to pass the user's value as the second argument.

7Counting failures: the lockout pattern

One uniform message still lets an attacker try password after password. Failing to slow repeated attempts is improper restriction of excessive authentication attempts (CWE-307), and it is the core of this module's incident.

★An unlimited sign-in is guessing at machine speed

When every attempt gets the same answer and nothing counts the failures, an automated run works through candidate passwords as fast as the network allows. A weak or reused password falls in seconds. Counting failures and refusing past a threshold limits the rate of online guesses. Detection also requires monitoring the recorded failures; the counter alone does not raise an alarm.

The limit lives on the server. A limit in page script or in the browser is not a limit, because the requester controls the client. Your portal's data/seed.sql already has the table for it. Sprint 20 added login_failures after a run of lockout complaints nobody could reconstruct, and the file notes that nothing writes to it or reads it yet.

SQL
CREATE TABLE login_failures (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    username  TEXT    NOT NULL,
    source    TEXT    NOT NULL,
    failed_at TEXT    NOT NULL
);

The pattern has four moves: record a failure, count recent failures, refuse at a threshold, and clear on success. Recovery is built in, because a count over a window drops on its own when the window passes.

The helpers use q and q_one from lib/query.php, with ? placeholders, the way Module 04 section 6 showed. The timestamps are text in Y-m-d H:i:s form, the same form lib/tokens.php writes, so a string comparison in SQL orders them correctly.

✓PHPSecure
<?php
// WHY: Server-side timestamped failures let the application enforce and audit a bounded guessing window.
require_once __DIR__ . '/lib/query.php';

function record_failure(string $username, string $source): void
{
    q(
        'INSERT INTO login_failures (username, source, failed_at) VALUES (?, ?, ?)',
        [$username, $source, date('Y-m-d H:i:s')]
    );
}

function account_failures(string $username, int $windowSeconds): int
{
    $since = date('Y-m-d H:i:s', time() - $windowSeconds);
    $row   = q_one(
        'SELECT COUNT(*) AS n FROM login_failures WHERE username = ? AND failed_at > ?',
        [$username, $since]
    );
    return (int) $row['n'];
}

function source_failures(string $source, int $windowSeconds): int
{
    $since = date('Y-m-d H:i:s', time() - $windowSeconds);
    $row   = q_one(
        'SELECT COUNT(*) AS n FROM login_failures WHERE source = ? AND failed_at > ?',
        [$source, $since]
    );
    return (int) $row['n'];
}

function clear_failures(string $username): void
{
    q('DELETE FROM login_failures WHERE username = ?', [$username]);
}

Secure. Why: Server-side timestamped failures let the application enforce and audit a bounded guessing window.

After five failures for rmarsh from one address, plus one failure an hour old, q_one returns the count inside the window.

Output
array(1) {
  ["n"]=>
  int(5)
}

The hour-old row is still in the table, and it is not counted, because its failed_at is earlier than $since. That is the recovery: rows age out of the window with no cleanup job. After clear_failures('rmarsh'), the same query returns 0.

The sign-in handler checks both keys before it verifies the password, and records or clears afterward.

✓PHPSecure
<?php
// WHY: Checking account and source counters before verification slows targeted and noisy guessing; it does not eliminate deliberate account lockout.
$window = 15 * 60;                                  // 15 minutes
$source = $_SERVER['REMOTE_ADDR'] ?? 'unknown';

if (account_failures($username, $window) >= 5 || source_failures($source, $window) >= 20) {
    http_response_code(429);                        // Too Many Requests
    header('Retry-After: ' . $window);
    exit('Too many failed sign-ins. Try again in 15 minutes.');
}

if (!$matched) {
    record_failure($username, $source);
    http_response_code(401);
    exit('The username or password was incorrect.');
}

clear_failures($username);                          // success: the count starts over

Secure. Why: Checking account and source counters before verification slows targeted and noisy guessing; it does not eliminate deliberate account lockout.

Response
HTTP/1.1 429 Too Many Requests
Retry-After: 900

Too many failed sign-ins. Try again in 15 minutes.

▸One guessing run against the handler

  1. Attempts one through five fail. Each one inserts a row with the username, the source address, and the time.
  2. Attempt six arrives. account_failures returns 5, the threshold, so the handler answers 429 with Retry-After: 900 and never looks at the password.
  3. The right password arrives at attempt seven, inside the window. It is refused too. The account is closed to everyone for the rest of the window.
  4. Fifteen minutes after the first failure, that row leaves the window. The count drops to 4, and the next attempt is checked again.
  5. A correct password at that point signs the user in and deletes the account's rows, so the count is 0.

Two keys are counted because each one misses something.

7. Counting failures: the lockout pattern. Columns: Key, What it limits, What it misses.
KeyWhat it limitsWhat it misses
Per accounta targeted run at one userlets an attacker lock a victim out on purpose
Per source addressone noisy clienta run spread across many addresses

!A per-account lockout alone is a weapon

Lock one account after five failures and anyone can lock any user out by failing on that account on purpose. That is a denial of service handed to the attacker. Count the source as well, keep the window short so a locked-out user gets back in on their own, and leave the password reset reachable while the account is locked.

The thresholds are choices. NIST sets an upper bound of 100 failed attempts in a row before an authenticator is disabled, and says lower limits are allowed. The course example uses five failures and a fifteen-minute observation window. OWASP's testing guide describes testing candidate thresholds and recovery behavior; these values are a teaching policy, not universal requirements. Pick numbers, write them down, and test them.

MDN: 429 Too Many Requests (opens in a new tab) defines the status code and its use for rate limiting. MDN: Retry-After (opens in a new tab) documents the header and the delay-in-seconds form. The Authentication Cheat Sheet in section 1 carries the lockout and denial-of-service guidance, and NIST SP 800-63B in section 5 carries the rate-limit requirement.

8The session identifier is a bearer credential

HTTP does not remember anyone between requests. After a successful sign-in, the server issues a session identifier, stores it in a cookie, and from then on identity travels as that string. Module 01 section 6 named it a bearer credential: whoever presents it is treated as the user. Nothing about a later request re-proves who sent it.

That sets two requirements. The identifier must be unguessable, and it must be handled so it does not leak.

◆Session identifier, CSPRNG

A session identifier is the random value that stands in for a signed-in user on every request after sign-in. A CSPRNG, a cryptographically secure pseudo-random number generator, produces values an observer cannot predict even after seeing many earlier ones. A session identifier must come from a CSPRNG.

PHP's session layer makes the identifier for you when you call session_start(). Do not build your own from a counter, a timestamp, a username, or md5(uniqid()). A predictable identifier lets an attacker guess an active session and skip the sign-in. OWASP asks for at least 64 bits of entropy and says to use the identifier your framework issues.

The cookie that carries it needs its attributes set before the session starts.

✓PHPSecure
<?php
// WHY: Configure cookie protections before starting the session so the issued cookie limits transport and script exposure.
ini_set('session.use_strict_mode', '1');   // reject any identifier the server did not issue

session_set_cookie_params([
    'lifetime' => 0,        // session cookie; browser session restoration may retain it
    'path'     => '/',
    'secure'   => true,     // sent over HTTPS only
    'httponly' => true,     // not readable by page script
    'samesite' => 'Lax',    // Module 06 section 7 covers the cross-site trade-off
]);

session_start();

Secure. Why: Configure cookie protections before starting the session so the issued cookie limits transport and script exposure.

▸What each attribute does

  1. lifetime of 0 tells the browser not to keep the cookie in permanent storage. The manual says most applications should use 0.
  2. secure means the browser sends the cookie only on https: requests. Browsers treat localhost specially, but client behavior and preview hosting differ. Verify cookie behavior on the actual HTTPS preview; do not assume a browser exception describes every command-line client.
  3. httponly keeps page script from reading the cookie through document.cookie. That removes the most direct path a cross-site scripting payload would use to steal it.
  4. samesite of Lax keeps the cookie off most cross-site requests. It is one layer; the token from Module 06 is still required.
  5. session.use_strict_mode makes PHP reject an identifier it did not create. The manual calls it mandatory for secure sessions, and it is off by default.

Your portal's first visit to login.php answers with Set-Cookie: PHPSESSID=...; path=/ and nothing more. No HttpOnly, no Secure, no SameSite. The identifier itself is fine, because PHP made it. The cookie around it is not.

!Cookie attributes set after session_start() do nothing

session_set_cookie_params() only affects the current script, and only if it runs before session_start(). A cookie already sent to the browser cannot be re-flagged on the same response. Keep the identifier out of URLs and out of logs as well: a value in a query string lands in browser history, server logs, and the Referer header sent to other sites.

The httponly flag does not stop network capture, a malicious browser extension, or same-origin script acting as the user. Treat it as one layer, not the answer.

OWASP Session Management Cheat Sheet (opens in a new tab) is the source for the entropy requirement, the three cookie attributes, and keeping the identifier out of URLs. PHP Manual: Securing Session INI Settings (opens in a new tab) explains each setting the way the runtime applies it, including use_strict_mode. PHP Manual: session_set_cookie_params (opens in a new tab) documents the array form and the rule that it runs before session_start(). MDN: Set-Cookie (opens in a new tab) describes HttpOnly, Secure, and SameSite from the browser's side. W3Schools: PHP Sessions (opens in a new tab) has runnable examples of session_start and $_SESSION.

9Session fixation and a new identifier at sign-in

The dangerous moment is the one where a visitor becomes a signed-in user and the identifier does not change. If the string that identified the browser before sign-in still identifies it afterward, anyone who knew the earlier value now holds a signed-in session.

✕PHPVulnerable
<?php
// WHY: Keeping the pre-login identifier attaches authenticated access to a value an attacker may already know.
session_start();   // the visitor already had an identifier when they reached this page

if ($matched) {
    $_SESSION['account_id'] = $row['id'];   // stored under the identifier the visitor arrived with
}

Vulnerable. Why: Keeping the pre-login identifier attaches authenticated access to a value an attacker may already know.

The password check is correct. The defect is that the identifier never changed, so the signed-in state is attached to a value that existed before the sign-in. That is session fixation (CWE-384).

◆Session fixation

Session fixation is an attack in which the attacker first gets the victim's browser to use a session identifier the attacker already knows, then waits for the victim to sign in under it. Because the identifier does not change at sign-in, the attacker's copy becomes a signed-in session the moment the victim signs in.

▸Walking the attack through the vulnerable code

  1. The attacker visits the site, is issued the identifier S1, and reads it from their own cookie.
  2. The attacker gets the victim's browser to use S1, for example through a crafted link on a site that accepts identifiers in the URL.
  3. The victim reaches the sign-in page carrying S1 and enters a correct password.
  4. The code stores account_id against the current session, which is still S1. No new identifier is issued.
  5. The attacker sends a request with S1. The server finds a signed-in session and serves the victim's account. The attacker never needed the password.

The fix is to issue a fresh identifier at the instant the sign-in succeeds, before any signed-in state is stored, and to remove the old record so the planted value is dead.

✓PHPSecure
<?php
// WHY: Issue a new identifier before authenticated state is stored so the known pre-login identifier cannot inherit access.
session_start();

if ($matched) {
    session_regenerate_id(true);            // new identifier now; delete the old record
    $_SESSION['account_id']   = $row['id'];
    $_SESSION['signed_in_at'] = time();
    $_SESSION['last_seen']    = time();
}

Secure. Why: Issue a new identifier before authenticated state is stored so the known pre-login identifier cannot inherit access.

✓Regenerate the identifier at every privilege boundary

Call session_regenerate_id(true) the moment a sign-in succeeds, before you store the signed-in state, and again on any step up such as entering an administrative area. The manual says the identifier must be regenerated when privileges are elevated, and that only the new session may carry the signed-in flag.

iWhat the true argument does, and what the manual adds

Without true, the old session record stays on the server, and the manual warns that an obsolete signed-in session may remain in use. With true, the old record is deleted. The manual also notes that on an unstable network, deleting at once can lose a session mid-request, and it describes keeping the old record for a few seconds with a destroyed timestamp instead. For your portal, true is the pattern. Whichever you choose, the planted identifier must stop working.

PHP Manual: session_regenerate_id (opens in a new tab) documents the function and the delete_old_session argument. PHP Manual: Session Management Basics (opens in a new tab) is the source for regenerating at privilege elevation, regenerating before storing the signed-in state, and the destroyed-timestamp alternative. OWASP WSTG: Testing for Session Fixation (opens in a new tab) is the test: compare the cookie before and after sign-in, and the site is vulnerable if it does not change.

10Timeouts and sign-out

A session is a standing grant of access, so it needs an end. A session that outlives its use is insufficient session expiration (CWE-613). Use two limits together. An idle timeout ends a session that has gone quiet, which protects an unattended browser. An absolute lifetime ends a session after a fixed span no matter what, which bounds how long a stolen identifier is worth anything.

Both limits are checked against server-side values. A cookie's own expiry is a request to the browser, and an attacker replaying a captured identifier is not using your browser.

✓PHPSecure
<?php
// WHY: Enforce idle and absolute limits on the server because a client can keep presenting a captured cookie.
session_start();

$now           = time();
$idleLimit     = 15 * 60;       // 15 minutes without a request
$absoluteLimit = 8 * 60 * 60;   // 8 hours from sign-in, active or not

$idle    = isset($_SESSION['last_seen'])    && $now - $_SESSION['last_seen']    > $idleLimit;
$expired = isset($_SESSION['signed_in_at']) && $now - $_SESSION['signed_in_at'] > $absoluteLimit;

if ($idle || $expired) {
    end_session();              // the sign-out below
    header('Location: /login.php');
    exit;
}

$_SESSION['last_seen'] = $now;

Secure. Why: Enforce idle and absolute limits on the server because a client can keep presenting a captured cookie.

Sign-out is where the module's third quiet defect lives. The browser can only show you one half of it.

✓PHPSecure
<?php
// WHY: Remove session data, expire the browser cookie, and invalidate the server record so a copied identifier cannot retain access.
function end_session(): void
{
    $_SESSION = [];                                     // drop the data

    // Expire the browser's copy of the cookie.
    $params = session_get_cookie_params();
    setcookie(session_name(), '', time() - 3600, $params['path'], $params['domain'],
              $params['secure'], $params['httponly']);

    session_destroy();                                  // remove the server-side record
}

Secure. Why: Remove session data, expire the browser cookie, and invalidate the server record so a copied identifier cannot retain access.

✕Clearing the cookie is not sign-out

A sign-out that only expires the cookie leaves the server-side record alive. Anyone who captured the identifier earlier keeps presenting it and stays signed in, while the honest user sees a signed-out screen and believes the session is over. There is no error and nothing visible in the browser, which is why this defect ships and survives review. Destroy the server-side record, or the sign-out is decoration.

The manual says session_destroy() removes the session data and nothing else: it does not clear $_SESSION and it does not remove the cookie. That is why the function above does all three. For accounts that hold sensitive data, also end every other session after a password change.

PHP Manual: session_destroy (opens in a new tab) is the source for the three-step sign-out, including the setcookie call with a time in the past. The Session Management Cheat Sheet in section 8 requires both an idle timeout and an absolute timeout, enforced on the server, and says sign-out must invalidate the session on the server side.

11Multi-factor authentication and TOTP

A password can be guessed, phished, or lifted from another site's breach. Relying on it alone is use of single-factor authentication (CWE-308). Multi-factor authentication answers that directly: a correct password is not enough, because a second factor from a different category is also required.

★A second factor makes a stolen password insufficient

With MFA in place, an attacker who holds the password still cannot sign in, because they do not hold the second factor. The reused credential and the lucky guess both stop at the second factor. That is the gap this module's incident fell through.

◆Factor independence

Two factors are independent when compromising one does not yield the other. A password is something you know. A phone or a security key is something you have. A fingerprint is something you are. A password plus a PIN is not MFA, and OWASP says it offers minimal added security, because both are things you know.

The second factor for this course is a time-based one-time password, or TOTP: the six-digit code an authenticator app shows and replaces every thirty seconds. RFC 6238 defines it as an HMAC over a shared secret and a time step.

▸How a TOTP code proves possession

  1. At enrollment, the server generates a secret K and shows it to the app once, usually as a QR code. Both sides store it.
  2. Each side computes the time step: the seconds since 1970, divided by 30. When the example was run, that was 59715893.
  3. Each side computes HMAC(K, time step) and reduces the result to six digits. Both get the same digits, because both hold K and the same clock.
  4. The user reads the digits from the app and types them. The server compares in constant time.
  5. An attacker with only the password does not hold K and cannot produce the digits. The code demonstrates knowledge of the shared secret for an accepted time step; a stolen secret or relayed code can also produce a successful response.
✓PHPSecure
<?php
// WHY: Check the code type and format before constant-time comparison; a complete verifier also limits attempts and prevents code replay.
// $expected is the six-digit code a TOTP library computed for the current step.
$typed = $_POST['code'] ?? '';

if (!is_string($typed) || !preg_match('/\A[0-9]{6}\z/', $typed) || !hash_equals($expected, $typed)) {
    second_factor_failed();
    return;
}

Secure. Why: Check the code type and format before constant-time comparison; a complete verifier also limits attempts and prevents code replay.

RFC 6238 recommends allowing at most one time step for transmission delay. A vetted library handles the algorithm and permitted clock window. Rate-limit failed codes and record successful use so the same code cannot be accepted again during its validity window. The comparison below illustrates only the final check, not a complete MFA verifier.

Not every second factor resists the same attacks. A code the user reads and types can be relayed to a fake site in real time. A phishing kit forwards the code to the real site inside the thirty-second window. OWASP lists TOTP as susceptible to phishing, though short-lived, and prefers FIDO2 and WebAuthn authenticators, whose response is bound to the site's origin.

✓Treat enrollment and recovery as the attack surface

Require a fresh sign-in with an existing factor before a factor can be added, removed, or changed, because the active session may be a stolen one. Give the user single-use recovery codes at enrollment, store them hashed, and show them once. Recovery must never become a way around MFA.

↗Why origin binding changes the picture

The Guide to Web Authentication (opens in a new tab) explains that a WebAuthn key pair is tied to one origin, so a key registered at the real site cannot be used at a look-alike. That is what a typed code cannot do.

RFC 6238: TOTP (opens in a new tab) defines the algorithm, the 30-second default step, and the one-step allowance for delay. OWASP Multifactor Authentication Cheat Sheet (opens in a new tab) is the source for factor categories, the password-plus-PIN rule, the phishing note on TOTP, and the reauthentication rule for factor changes.

12Account recovery

A password reset is a second door into the same account. If it is easier to force than the sign-in, attackers use it instead. A reset that can be beaten without the password is a weak password recovery mechanism (CWE-640).

Your portal's reset-password.php asks a security question and compares the typed answer with the stored one. The seeded answers are the office each person works in, and the question is the same for every account. NIST says not to prompt for knowledge-based answers at all, and OWASP says a security question must never be the only gate on a reset.

A sound reset has these parts, and each closes a specific hole.

  • One response to the request, whether or not the account exists, so the reset does not confirm addresses.
  • A token that is random, single-use, short-lived, and bound to one account.
  • Delivery to a channel verified earlier, never one supplied in the request.
  • A rate limit on requesting a reset and on redeeming a token.
  • Only the hash of the token in storage, never the token itself.
  • Every other session of the account ended once the reset completes, and a notice sent to the owner.

Your portal's lib/tokens.php already builds the token. token_issue draws 32 random bytes, stores only the SHA-256 of the token in reset_tokens with an expiry, and returns the token once. token_check returns the username only while the token is unexpired and unused. token_burn marks it used.

✓PHPSecure
<?php
// WHY: A consistent reset response limits account enumeration and sends the token only to a previously verified address.
require_once __DIR__ . '/lib/tokens.php';
require_once __DIR__ . '/lib/passwords.php';

// Step 1: the request. One answer whether or not the account exists.
$account = q_one('SELECT username, email FROM accounts WHERE username = ?', [$username]);
if ($account !== null) {
    $token = token_issue($account['username'], 15 * 60);       // valid 15 minutes
    send_reset_link($account['email'], '/reset.php?t=' . $token);
}
echo 'If that account exists, a reset link is on its way.';

Secure. Why: A consistent reset response limits account enumeration and sends the token only to a previously verified address.

✓PHPSecure
<?php
// WHY: Validate the token before changing a credential; production redemption must atomically consume it with the password update.
// Step 2: redeem. The link carries the token; the table holds only its hash.
$token    = $_GET['t'] ?? '';
$username = is_string($token) ? token_check($token) : null;

if ($username === null) {
    http_response_code(400);
    exit('That link is not valid.');
}

q('UPDATE accounts SET password_hash = ? WHERE username = ?', [pw_hash($newPassword), $username]);
token_burn($token);

Secure. Why: Validate the token before changing a credential; production redemption must atomically consume it with the password update.

iReset redemption needs an atomic operation

The two snippets illustrate issuance and checking. In a production implementation, validate the new password policy and perform token consumption and password update in one atomic transaction or equivalent operation, because two simultaneous requests must not redeem the same token. The course helper checks and burns separately and does not itself guarantee atomic single use.

A reset token can be stored under a fast hash, unlike a password. The token is generated from 256 bits of CSPRNG output, so exhaustive guessing is computationally infeasible when secure randomness and adequate length are preserved. A human password has little randomness, which is why its store needs a slow hash. A full-entropy token does not need password-style stretching, but still needs expiry, single-use enforcement, and protected delivery.

!A security question is not a factor

A first school, a first car, or a home office is discoverable, guessable, or shared across every site that asks the same question. Treat it as a usability extra at most, and never as the only gate on a reset.

OWASP Forgot Password Cheat Sheet (opens in a new tab) is the source for the consistent response, the token requirements, the rate limits, the session invalidation, and the rule on security questions. PHP Manual: random_bytes (opens in a new tab) documents the CSPRNG behind token_issue. NIST SP 800-63B in section 5 carries the rule against knowledge-based authentication.

14Common misconceptions

  • ✕"Passwords should be encrypted."

    Encryption can be reversed, which is the property you do not want. If the system can recover the password, so can an attacker who takes the key. Passwords are stored as a slow, salted hash and verified.

  • ✕"A salt is a secret."

    A salt is unique per password and stored right beside the hash. Its job is to defeat lookup tables, not to stay hidden.

  • ✕"SHA-256 with a salt is a safe password store."

    It is a fast hash. The offline guessing rate barely drops. A password store needs a hash that is slow on purpose, with a work factor you can raise.

  • ✕"Forcing a password change every 90 days is a control."

    NIST says not to require scheduled changes. They produce predictable passwords. Change a password after a known exposure.

  • ✕"Locking the account after five failures solves guessing."

    It also lets anyone lock any user out on purpose. Count the source as well, keep the window short, and let the count age out.

  • ✕"Two sign-in steps are multi-factor authentication."

    A password and a PIN are both things you know. MFA needs factors from different categories.

  • ✕"Closing the browser signs you out."

    The server-side session may still be valid, and an attacker replaying the identifier is not using your browser. Sign-out destroys the record on the server.

  • ✕"HttpOnly prevents session theft."

    It blocks page script from reading the cookie. It does nothing about network capture, a malicious extension, or same-origin script acting as the user.

15Check your understanding

Work these before you look at the answers.

  1. What question does authentication answer, and how is that different from what authorization answers?
  2. Why is a fast hash such as SHA-1 the wrong way to store a password, even with a salt added?
  3. What is a salt, is it a secret, and what does it defeat?
  4. What does password_needs_rehash check, and when in the sign-in is the only moment you can act on its answer?
  5. A rule requires a capital letter, a digit, and a symbol, and a change every 90 days. Which NIST rules does it break, and when should a password be changed?
  6. Why must a wrong password and an unknown account return the same message, status, and timing?
  7. A lockout counts failures per account only. What attack does that enable, and what second key fixes it?
  8. Why is the session identifier described as a bearer credential, and what does that require of how it is generated?
  9. What does the true argument to session_regenerate_id change, and why is a sign-in that skips the call still vulnerable even with a correct password check?
  10. A sign-out expires the cookie and nothing else. What does the user see, and what has not happened?
  11. What makes two factors independent, and why is a password plus a PIN not MFA?
  12. Why can a reset token be stored under a fast hash when a password cannot?

Answers: (1) authentication asks who the caller is; authorization asks what that caller may do; they fail independently. (2) a fast hash lets an attacker who stole the table try billions of guesses a second offline; a salt stops lookup tables but does not slow the guessing. (3) a random value mixed into each password before hashing, stored next to the hash, not secret; it makes equal passwords hash differently and defeats precomputed tables. (4) whether the hash's algorithm and cost match the current defaults; right after a successful verify, because that is when the server holds the password. (5) composition rules and scheduled rotation, both of which NIST says not to require; change a password after a known exposure. (6) any difference tells an attacker which usernames exist, and that list feeds a guessing run. (7) anyone can lock a victim out on purpose; count failures per source address as well, and let the count age out of a short window. (8) possession is identity and nothing later re-proves the sender, so it must come from a CSPRNG, which PHP's session layer provides. (9) true deletes the old server-side record; without a new identifier, a value planted before sign-in becomes a signed-in session at sign-in. (10) a signed-out screen; the server-side record is still alive, so a copied identifier still works. (11) compromising one does not yield the other; a password and a PIN are both things you know. (12) the token is 256 random bits with nothing to guess, while a password has little randomness and needs a slow hash to make guessing expensive.
