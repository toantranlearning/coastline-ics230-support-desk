A PHP application calls an HTTPS service and receives an error. One proposed change turns off certificate verification. Another repairs the trust configuration. Both may make a request complete, but they establish different guarantees about who received the data.

This companion helps you read the PHP in the M11 secure-communication lecture. The lecture explains TLS, certificates, and browser policies. Here, you trace options, return values, headers, and cookie settings. Network examples are environment-dependent fragments; no external call is required for the standalone practice.

★A configuration option changes a guarantee

Identify what each option verifies before changing it because a request that completes after disabling a check has not proved that the peer's identity is trustworthy.

1Read a cURL handle and its options

PHP's cURL extension provides functions for transfers. curl_init creates a handle representing a transfer. curl_setopt configures one option; curl_setopt_array configures several options from an array.

✓PHPSecure
<?php
// WHY: Certificate-chain and host-name checks preserve the intended server identity checks.
$ch = curl_init('https://inventory.example.com/status');
curl_setopt_array($ch, [
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_SSL_VERIFYPEER => true,
    CURLOPT_SSL_VERIFYHOST => 2,
    CURLOPT_CONNECTTIMEOUT => 5,
    CURLOPT_TIMEOUT => 10,
]);

Secure. Why: Certificate-chain and host-name checks preserve the intended server identity checks.

This fragment configures a handle but does not execute a network request. It requires the cURL extension. => associates each named option constant with its value. These constants are identifiers supplied by the extension, rather than quoted array-key text written by the developer.

CURLOPT_RETURNTRANSFER requests that successful body content be returned to PHP instead of directly written to output. CURLOPT_SSL_VERIFYPEER enables certificate-chain verification. CURLOPT_SSL_VERIFYHOST value 2 requires the certificate name to match the requested host. The timeout options bound connection setup and overall transfer time in seconds.

!The two certificate checks are different

Keep both checks enabled because a chain trusted by a certificate authority does not itself establish that the certificate identifies the requested host. Fix the trust store or endpoint configuration when verification fails; disabling the checks changes the security property.

Source: PHP curl_setopt (opens in a new tab) documents option values; libcurl CURLOPT_SSL_VERIFYHOST (opens in a new tab) defines host-name verification.

2Distinguish transfer failure from an HTTP response

curl_exec performs the configured transfer. With return-transfer enabled, a successful transfer normally returns response-body text. It returns false when the transfer fails. A body can be empty, so compare specifically with false rather than testing whether the result is truthy.

PHP
<?php
$sampleBodies = ['', 'Status available', false];
foreach ($sampleBodies as $body) {
    if ($body === false) {
        echo "Transfer failed.\n";
    } else {
        echo 'Transfer returned ' . strlen($body) . " bytes.\n";
    }
}
Output
Transfer returned 0 bytes.
Transfer returned 16 bytes.
Transfer failed.

This local example supplies practice return values without making requests. foreach examines each value, === false identifies failure, and strlen measures the returned body's bytes. An empty successful body stays separate from failure.

In a real handler, the next fragment must follow a configured handle. It is not standalone and has no predetermined output.

PHP
<?php
$response = curl_exec($ch);
if ($response === false) {
    error_log('Outbound request failed: ' . curl_error($ch));
} else {
    $status = curl_getinfo($ch, CURLINFO_HTTP_CODE);
}

curl_error retrieves the most recent error text. curl_getinfo reads transfer information. The HTTP status is a separate result: with the usual options, a server returning 404 is not itself a curl_exec transfer failure. A completed TLS connection also does not prove that the application operation succeeded.

Source: PHP curl_exec (opens in a new tab) explains returned content and HTTP error statuses; PHP curl_getinfo (opens in a new tab) documents transfer information.

3Read client-certificate configuration

Mutual TLS adds a client identity check. PHP configures the certificate and private key presented by its outbound client.

PHP
<?php
$clientIdentity = [
    'certificate' => '/etc/course-service/client.crt.pem',
    'private_key' => '/etc/course-service/client.key.pem',
];
echo basename($clientIdentity['certificate']) . "\n";
echo basename($clientIdentity['private_key']) . "\n";
Output
client.crt.pem
client.key.pem

This practice array holds paths; it does not open the files or prove that they exist. basename returns the final component of a path. In a cURL configuration, CURLOPT_SSLCERT identifies the client certificate file and CURLOPT_SSLKEY its private key file. They do not replace verification of the server's certificate.

✕A path to a private key remains sensitive configuration

Protect the file and its access permissions because possession of the private key can permit impersonation of the client. Recording a filename for a configuration review is different from copying key contents into a report or repository.

The lecture's example uses PEM files. Their names alone do not establish format, validity dates, matching keys, or acceptance by the partner service. Those require verification in the authorized deployment.

Source: libcurl CURLOPT_SSLCERT (opens in a new tab) and libcurl CURLOPT_SSLKEY (opens in a new tab) describe the client identity options.

4Read a nested stream context

PHP can also make HTTPS requests through stream functions. A context stores options grouped by wrapper or transport name. Creating the context does not make the request.

✓PHPSecure
<?php
// WHY: Peer and name verification remain enabled while an explicit CA file supplies the trust configuration.
$options = ['ssl' => [
    'verify_peer' => true,
    'verify_peer_name' => true,
    'cafile' => '/etc/course-service/internal-ca.pem',
]];
$context = stream_context_create($options);
$stored = stream_context_get_options($context);
var_dump($stored['ssl']['verify_peer']);
var_dump($stored['ssl']['verify_peer_name']);

Secure. Why: Peer and name verification remain enabled while an explicit CA file supplies the trust configuration.

Output
bool(true)
bool(true)

The outer array has an ssl key. Its value is another array containing verification and trust-file settings. stream_context_create creates the context resource, and stream_context_get_options retrieves its configured options. This practice reads configuration only; it does not verify that the CA file exists or trusts a real server.

The lecture's file_get_contents($url, false, $context) passes that context as the third argument. The second argument controls use of the include path, not certificate verification. The request requires applicable PHP stream-wrapper support and deployment configuration. Failure can return false and emit a warning, so its result needs explicit handling.

Source: PHP SSL context options (opens in a new tab) defines peer, name, and CA settings; PHP file_get_contents (opens in a new tab) explains its arguments and return value.

5Inspect server variables without confusing two connections

$_SERVER contains values supplied by PHP's request environment. isset tests whether a value exists and is not null. empty also treats values such as an empty string, zero, false, and a missing entry as empty.

PHP
<?php
$environment = ['HTTPS' => 'on'];
var_dump(isset($environment['HTTPS']));
var_dump(empty($environment['HTTPS']));
var_dump(isset($environment['UNKNOWN']));
Output
bool(true)
bool(false)
bool(false)

This local array demonstrates the language tests. The actual value of $_SERVER['HTTPS'] depends on the server and deployment. Behind a TLS-terminating proxy, the browser's HTTPS connection and PHP's connection from the proxy can differ. A missing PHP variable alone does not prove that the browser used plaintext.

A deployment may use a trusted proxy configuration to establish the external scheme. Request headers that any caller can supply do not automatically qualify as trusted proxy evidence. The main lecture explains the course environment's division of responsibility.

iName the connection your evidence describes

Identify browser-to-proxy and proxy-to-application observations separately because a variable seen by PHP describes its environment rather than every segment of the request path.

Source: PHP $_SERVER (opens in a new tab) documents server-dependent entries; PHP isset (opens in a new tab) explains existence checks.

6Read a redirect and the stopping statement

A Location header identifies a response destination. The lecture uses a fixed canonical hostname instead of constructing a destination from an untrusted Host header.

PHP
<?php
$canonicalHost = 'portal.example.com';
$path = '/equipment.php';
$destination = 'https://' . $canonicalHost . $path;
echo $destination . "\n";
Output
https://portal.example.com/equipment.php

This practice constructs text only. A web fragment could then call header('Location: ' . $destination, true, 301); and exit;. The second argument requests replacement of an existing same-type header, and the third sets status 301. exit stops later application code from executing. The header-setting call alone does not stop execution.

The full redirect logic must be evaluated with actual path handling and proxy configuration. A fixed host prevents a requester-supplied host from choosing the destination; it does not establish every other routing guarantee.

Source: PHP header (opens in a new tab) explains headers and status arguments; PHP exit (opens in a new tab) describes termination.

7Read browser response policies as headers

The main lecture uses header for HSTS and cache policy. Their names are HTTP field names, not PHP functions. PHP writes the fields; the browser or another recipient interprets them.

PHP
<?php
$policyHeaders = [
    'Strict-Transport-Security: max-age=86400',
    'Cache-Control: no-store',
];
foreach ($policyHeaders as $policyHeader) {
    echo $policyHeader . "\n";
}
Output
Strict-Transport-Security: max-age=86400
Cache-Control: no-store

This standalone example prints the intended header text. It does not send HTTP headers. In a web response, header($policyHeader) would set the field before response output has committed headers. HSTS is accepted through HTTPS under the browser's rules. max-age is a duration in seconds.

!Displayed text is not a transmitted response header

Inspect the actual response fields when verifying a deployment because echoing a header-shaped string writes body content rather than configuring browser policy. The same distinction applies to a predicted header in a report.

Source: MDN Strict-Transport-Security (opens in a new tab) explains HSTS delivery and duration; MDN Cache-Control (opens in a new tab) defines no-store.

8Configure session cookies before session start

session_set_cookie_params configures parameters for session cookies in the current execution. Call it before session_start, which opens or resumes the session and may send its cookie.

✓PHPSecure
<?php
// WHY: Applying attributes before session initialization lets the session cookie use the intended delivery policy.
session_set_cookie_params([
    'lifetime' => 0,
    'path' => '/',
    'secure' => true,
    'httponly' => true,
    'samesite' => 'Lax',
]);
session_start();

Secure. Why: Applying attributes before session initialization lets the session cookie use the intended delivery policy.

This is an HTTP bootstrap fragment, not a command-line proof of browser behavior. Secure restricts cookie delivery to HTTPS. HttpOnly prevents access through ordinary browser JavaScript cookie APIs, while the cookie can still accompany requests. SameSite Lax limits cross-site delivery under its rules; it is not a complete replacement for request-intent defenses.

A zero lifetime creates a nonpersistent session cookie. Browser session restoration can preserve such cookies, so “always erased when the window closes” is too strong. The path setting determines where the cookie applies; it is not an authorization boundary for the application.

Source: PHP session_set_cookie_params (opens in a new tab) documents supported options; MDN Set-Cookie (opens in a new tab) explains delivery and browser-session caveats.

9Read an expiry calculation for a separate cookie

setcookie sends a cookie independently of PHP's session mechanism. Its option names include expires, an absolute Unix timestamp, whereas the session parameter uses lifetime, a duration.

PHP
<?php
$secondsPerDay = 60 * 60 * 24;
$duration = $secondsPerDay * 30;
echo $duration . "\n";
Output
2592000

time() + $duration calculates an expiry relative to the current time. The lecture's device cookie uses that expression with Secure, HttpOnly, and SameSite options. Setting a cookie does not validate its future contents or create a secure device-token design by itself. The token must be generated, stored, checked, expired, and revoked according to the application policy.

↗Read the function's option names

Compare session-cookie parameters and setcookie options in their PHP Manual pages because similar-looking configuration arrays can use different names and units.

Source: PHP setcookie (opens in a new tab) describes options and timestamp expiry.
