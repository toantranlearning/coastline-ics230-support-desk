For the rest of the term, alongside your incident reports, your team designs one thing together and each of you builds it. The project is a REST API: a way for TechCorp's business partners to reach the support portal's data through code instead of the web pages you have been repairing. Your team writes the design. Then each member writes the running code for it in their own portal copy. It starts now, at Module 08, and finishes at Module 16.

Plan about an hour for the kickoff: read the memo, assign the sections, and write the first design notes.

What the design project is

Your team designs a partner REST API for the TechCorp support portal. You design it together, deciding what it does, where each safeguard sits, and why. Then each member builds it as running code, in an api/ folder inside their own portal copy, and tests it with curl commands typed by hand at localhost:8080.

The split is deliberate. The design is a group decision, so the whole team reasons about it together. The build is individual, so each of you shows you can turn that design into code that runs. The design document is graded as a team. Your build and one written defense of a decision you made are graded per student.

★Shared design, individual implementation

The team agrees on how the API should work. Each student builds the required core and records results from their own application. Sharing design decisions is collaboration; a teammate's successful request is not evidence that your build works.

Start the project in one meeting

  1. Read the business memo together and identify which data belongs to each partner because that ownership rule shapes the API.
  2. Assign a lead and reviewer for each design section because overlapping decisions need a responsible owner.
  3. Record the required core and chosen electives because the implementation and verification plan must match the agreed scope.
  4. Write down unresolved questions because a visible disagreement can be reviewed before it becomes conflicting code.

Your team

Your instructor assigns teams of three at this module, once the roster is stable.

You do not propose an application. The subject is given: the partner API described in the requirements document below. That removes the concept-approval step and lets every team start on the same target, which is fairer to grade.

Each member leads one section of the shared design. All members review the decisions, and each member implements the complete required core in their own lab copy. The sections and their owners are assigned at kickoff and recorded in an attribution table the team keeps current.

The requirements document

Here is the memo your TechCorp team lead sent. It says what the business wants the partner API to do. Read it the way you would read a real brief: it lists features and never mentions security. Deciding what each feature needs to be safe, and building that in, is your work.

iNote

From Dana Okafor, Partner Platform Lead, to the design team.

Leadership approved a partner API for the support portal this quarter. Our larger customers keep asking to connect their own systems to us instead of signing into the portal by hand. Here is what the business needs it to do. Give me a design that says how each of these works, then stand up the endpoints so I can see it run.

  1. Partners connect their own systems to the portal through the API. Each partner's system has to identify itself when it connects, so we know which partner is calling.
  2. Some partners run a third-party dashboard. A support rep should be able to let that dashboard read their ticket queue for them, without handing the dashboard their portal password.
  3. A partner can look up the customers that belong to them. Partner A must never see Partner B's customers.
  4. A partner can pull a full export of its own customer list for its records. A few partners will pull it often.
  5. When a ticket a partner cares about changes status, we notify them by calling a callback URL the partner registers with us.
  6. Every change to a billing record has to be traceable afterward. Partners dispute charges, and we need to show who changed what, and when.

The feature menu

This is a menu of features you can build. Each entry names the feature, the control it uses and the lecture that teaches it, a few lines of reminder pseudocode where the lecture has not yet shown the code, and the lib/ helper that supports it. The pseudocode shows the shape, not code to paste; you write the real code against your own portal.

The required core is mandatory. Every project builds all five, so every design meets the exercise and the rubric has common ground. The electives sit on top; choose the ones your design needs. Your team may also design a feature that is not on this menu. The design document is where you defend what you chose, what you left out, and the threat each choice answers.

Required core (build all five)

API-key authentication. Taught in the M08 lecture, section 10, which shows the complete pattern on the portal's api_clients table: the key read from the X-API-Key header, the client found by the key's hash with q_one from lib/query.php, and the compare with hash_equals. It answers feature 1: a partner identifies itself. There is no pseudocode here because the lecture already shows the code.

A key exchanged for a short-lived bearer token with a scope. Taught in the M12 lecture, section 8, and built in Module 12 after that section. Supported by hmac_sign and hmac_verify from lib/hmac.php, which the M10 lecture, section 9, teaches; they sign the token so a client cannot forge it. This is a simplified classroom token model, not an implementation of OAuth or proof of user consent. The design section must distinguish a partner key exchange from genuine user-delegated authorization and explain what a production dashboard would require.

Trade a valid API key for a short-lived, scoped token:
    on POST /api/token:
        verify the API key (as in the core)
        payload = partner_id + "|" + "queue:read" + "|" + (now + 900)
        token   = hmac_sign(payload)     # signed, so the client cannot alter it
        respond 200 with {"token": token, "expires_in": 900}

On later requests:
    payload = hmac_verify(bearer)        # null means altered or forged
    if payload is null or its expiry has passed or its scope is wrong:
        respond 401 or 403

A per-object ownership check. Taught in the M08 lecture, section 5, and applied to the API in the M12 lecture, section 9. Supported by q_one and q_all from lib/query.php. It answers feature 3: a partner sees only its own customers.

Put the owner rule inside the query, so the wrong row never comes back:
    row = q_one("SELECT id, name FROM customers
                 WHERE id = ? AND partner_id = ?",
                [requested_id, caller_partner_id])
    if row is null:
        respond 404      # do not confirm the row exists to someone who does not own it

Input validation. Taught in the M03 lecture, section 4, and for an API body in the M12 lecture, section 10. The validated value reaches the database only through lib/query.php placeholders; the allow-list itself is a few lines you write. It keeps a caller from setting fields you never offered.

Accept only the fields you named, and reject the rest:
    allowed = ["display_name", "timezone"]
    unknown = keys(body) that are not in allowed
    if unknown is not empty:
        respond 400

Check type, length, and range before you use a value.
Pass every request value to the database through q(...) placeholders,
never by building the SQL string yourself.

Errors that leak nothing. Taught in the M12 lecture, section 11, and in the M14 lecture, section 4. This is a pattern you write, not a helper: catch at the top, log the detail, return a short message. It keeps stack traces, SQL messages, and file paths out of the response.

Wrap the whole request in one handler:
    try:
        ... run the endpoint ...
    catch any error:
        id = short random correlation id
        log(id, the real error)          # detail goes to the log, not the caller
        respond 500 with {"error":"server_error","correlation_id": id}

Electives (add what your design needs)

Rate limiting. Taught in the M12 lecture, section 13. Supported by lib/query.php to count a caller's recent requests in the api_calls table. It answers the often-pulled export in feature 4.

Count this caller's recent requests, refuse past the cap:
    count = q_one("SELECT COUNT(*) AS c FROM api_calls
                   WHERE partner_id = ? AND made_at > ?",
                  [caller_partner_id, now - 60]).c
    if count >= 100:
        respond 429 with header "Retry-After: 60"
    else:
        q("INSERT INTO api_calls (partner_id, made_at) VALUES (?, ?)",
          [caller_partner_id, now])

HMAC-signed requests. Taught in the M10 lecture, section 9. Supported by hmac_sign and hmac_verify from lib/hmac.php. The partner signs the request; you verify before trusting it.

The partner sends "body.signature"; you verify before acting:
    payload = hmac_verify(signed_value)   # returns the body, or null
    if payload is null:
        respond 401                        # the signature did not match

An audit log. Taught in the M14 lecture, section 5. Supported by q from lib/query.php to append a row to the audit_log table. It answers feature 6: every billing change is traceable.

Append one row for every change to a billing record:
    q("INSERT INTO audit_log (partner_id, action, target, at)
       VALUES (?, ?, ?, ?)",
      [caller_partner_id, "update_charge", charge_id, now])

Write the row after the change succeeds, and let no caller edit it.

A CORS policy. Taught in the M12 lecture, section 12. This is response headers you set, not a helper. It tells a browser which origins may read the response.

Name the origins a browser app may read from:
    allowed = ["https://partner-dashboard.example"]
    origin  = header "Origin"
    if origin is in allowed:
        send header "Access-Control-Allow-Origin: " + origin
    never send "*" together with credentials, and compare the whole origin.

Pagination caps. Taught in the M12 lecture, section 13. Supported by q_all from lib/query.php with a bound limit. It keeps the export in feature 4 from returning an unbounded result.

Clamp the page size the caller asks for, then bind it:
    limit  = min(requested_limit, 50)     # never unbounded
    offset = max(requested_offset, 0)
    rows   = q_all("SELECT id, name FROM customers
                    WHERE partner_id = ? LIMIT ? OFFSET ?",
                   [caller_partner_id, limit, offset])

iThe callback URL is a trap worth naming

Feature 5 asks the API to call a URL the partner gives you. That is server-side request forgery: a caller who registers http://127.0.0.1:8080/admin.php makes your server reach an address the caller could not reach on its own. If your design includes the callback, the operations section has to say how you keep it in bounds. The control is an allow-list of destinations you decide in advance, taught in the M12 lecture, section 14.

The design document

Your team writes one design document. It has three sections, a threat model, and a verification plan. Each part names its author, and the attribution table keeps that current.

  • Authentication. Who is calling. API-key authentication for partner systems, and the token exchange for the dashboard. Say where the key is read, how it is stored, how it is compared, and what the token carries and for how long.
  • Authorization and data. What a caller may reach, and the data the API holds. The per-object ownership check so a partner sees only its own customers, input validation on every request body, and what each endpoint returns and stores.
  • Operations. How the API behaves under load and when things go wrong. Rate limits and pagination caps, the audit log, errors that leak nothing, a CORS policy if a browser app calls it, the callback URL's destination allow-list if you build feature 5, and serving the whole API over TLS.
  • The threat model. The actors (a partner, a stolen key, a partner reaching for another partner's data, a third-party dashboard), what each may do, and the risks the design must answer. It names an owner.
  • The verification plan. For each safeguard, the hand-typed curl request that shows it works: the owner gets 200, a non-owner gets 403 or 404, a request with no key gets 401, and malformed JSON gets 400 with no stack trace. It names an owner.

Every section, the threat model, and the verification plan name their author in a table the team keeps current. The individual grade rests on this table, so no member should author nothing.

The design document is a shared Google Doc. You already have a Google account for Cloud Shell. The team submits it as a PDF export.

The build

Each member builds the API as running code in their own portal copy, so each of you meets the exercise on your own.

  • The code lives in a new api/ folder, one file per resource, reached through the portal's router.php at localhost:8080. The M08 lecture, section 9, explains how the router finds the file.
  • Build the token endpoint and about three resource endpoints. The required core has to work: API-key authentication, the token exchange, the per-object ownership check, input validation, and errors that leak nothing.
  • Build on lib/. Use its documented helper contracts, and each module teaches the one it uses: query.php (Module 04), passwords.php (Module 09), hmac.php and crypto.php (Module 10). You call them.
  • Test every endpoint with curl typed by hand at localhost:8080, as the Requests and Developer Tools page shows. Paste the request and the response, as text, into your build report. That text is your evidence.
  • Your build report is a Markdown file, written as the Writing in Markdown page shows. It holds your endpoints and their evidence, and at the final it holds your decision-under-challenge section.

How it is graded

The design project is one category of your course grade, split three ways: the draft at Module 12, the team design document at Module 16, and your individual build with its decision-under-challenge section, also at Module 16. The Design Project Rubric page in Module 08 carries the weighting and the criteria.

The team design document is graded as a team. Your build and your decision-under-challenge are graded per student. The attribution table is what makes the individual grade fair: a member who authored and built nothing has nothing of their own to be graded on.

AI assistance and accountability

AI may help explain requirements, propose or refactor implementation code, suggest tests, and plan or edit the design and build reports. Record the tool, assistance requested, material used or changed, and checks performed. Each student must understand the code and report results they actually observed. The final individual decision under challenge remains unaided under the syllabus because it assesses the student's own reasoning.
