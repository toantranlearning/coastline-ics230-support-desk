What Cloud Shell is

Google Cloud Shell is a free Linux computer you use through your browser. Your own copy of the TechCorp portal lives on it, and everything you do in this course happens there. There is nothing to install, so a Chromebook, a school computer, or a home laptop all work the same way.

  • It is yours and private. Your copy lives in your Google account. No other student, and nobody who is not signed in as you, can see or reach it.
  • It is free, with no card. You do not need a credit card or a paid trial. If a banner offers "$300 in free credits" or asks for a card, close it. You never need it for this course.
  • It is a Google service, not GitHub. All you need is a Google account.

The screen has three parts: the file list on the left is every file in your copy, the editor in the middle is where you read and change code, and the black terminal across the bottom is where you run commands. Everything you change stays in your own copy.

One command runs everything: start.sh

You have one command to remember. On the first launch, the tutorial helps put it into your terminal. It does not execute the command for you:

Bash
bash scripts/start.sh

Press Enter in the terminal to run the command. Wait for the startup messages before opening Web Preview. If the command was not inserted, type or paste it into the terminal, then press Enter.

start.sh sets up your copy and starts the portal, and it is safe to run every time you open the project. It checks what is already done and does only what is missing, so a single run puts your environment right no matter what state it was in. On each run it:

  • keeps exactly one copy of the project, removing any extra copies a second click on the launch link created,
  • adds the database driver Cloud Shell needs, if it is not already there (the first run takes a few extra seconds for this),
  • frees port 8080 if something was still using it, and
  • starts the portal on port 8080 in the background, so your terminal stays free.

Because it does all of this itself, you almost never troubleshoot the environment by hand. If the portal will not load, a copy looks duplicated, or you see a database or port error, the answer is the same: run bash scripts/start.sh again. It restarts clean.

Two things start.sh cannot do for you, both quick:

  • If the launch link does nothing, you are signed out of Google. Sign in on the page you land on, then click the link again.
  • If the terminal says your folder no longer exists (it can happen right after the cleanup removes a duplicate you were sitting in), run the cd line start.sh prints. That moves you back into the project.

If something is still wrong after a fresh start.sh, or you cannot reach Cloud Shell at all because a locked-down network blocks it, post in the Q&A discussion or message me in the Canvas Inbox. Do not work around a network you do not control; there are other paths, but they take time to arrange.

Getting back in

After the first launch you do not click the launch link again; clicking it makes a second copy that start.sh then has to clean up. Coming back is three steps:

  1. Reopen your Cloud Shell tab, or go to shell.cloud.google.com (opens in a new tab) (opens in a new tab) and sign in with the same Google account. Your copy and every edit you have made are still there, exactly as you left them.
  2. Run bash scripts/start.sh in the terminal to start the portal.
  3. Open the portal: click the Web Preview icon at the top right of the Cloud Shell window and choose Preview on port 8080. Only you can open that tab; it is tied to your Google sign-in.

If the tutorial panel is gone and you want it back, run teachme TUTORIAL.md in the terminal.

Your copy persists

  • Cloud Shell gives you a 5 GB home directory that survives between sessions. An edit you make in week 3 is still there in week 6. You do not re-launch or rebuild each week; you reopen the tab and run start.sh.
  • Your home is wiped only after 120 days with no session at all, which an 8- or 16-week term never reaches. Week to week, your work is safe.
  • The lasting record of finished work is what you submit to Canvas. Cloud Shell holds your working copy; Canvas holds the graded one. If anything ever happened to your copy, the modules you already submitted are safe.

The weekly limit

Cloud Shell is free up to about 50 hours a week. Normal course work rarely comes close. If you ever reach it, the environment is unavailable until the weekly counter resets, and then your work resumes right where it was. Your files are never lost when this happens. Closing the tab when you finish for the day keeps your hours low.

Working with files

  • Create a file: right-click the folder in the file list and choose New File, then type the name with its extension (proof.php, tc-ir-004.md).
  • Delete a file: right-click it in the file list and choose Delete.
  • Make a file of a given size for a test, in the terminal: head -c 6M /dev/zero > big.bin makes a 6 MB file named big.bin; : > empty.txt makes an empty one.
  • See a file's size: ls -l in the terminal, or hover the name in the file list.
  • Search a file for text: grep 'text' file in the terminal prints every matching line; grep -c counts them.
  • Make a file read-only or unwritable for a test: chmod 000 file; restore it with chmod 644 file.
  • Run a PHP file from the terminal: php file.php. Keep such test files in reports/, which the portal never serves.
  • Load a SQL file into the portal's database: sqlite3 data/portal.sqlite < file.sql.
  • Rebuild the database from the seed: delete data/portal.sqlite (or run ./scripts/reset.sh); db.php rebuilds it from data/seed.sql the next time a page loads.
  • The Source Control panel (the branching icon on the left bar) lists every file you have changed. A file named in .gitignore, such as .env, never appears there.

Gemini code assistance

Gemini can help explain a function, draft a focused code change, or propose tests. AI-generated code is permitted on practice work and project builds under the syllabus policy. You are responsible for reviewing, testing, and explaining the code you use.

Choose an available route

In Cloud Shell Editor: if Gemini Code Assist is already configured for your account, open a source file, select the relevant function, and open the Gemini chat control next to the search bar. Paste the learning-coach instructions, then describe the behavior you need. Google documents a project-selection and API-enablement step for this integration. Follow your institution's approved setup if one is supplied; this course does not require you to purchase an AI subscription or enable paid services.

In a separate browser tab: use Gemini web chat (opens in a new tab) if available to your account. Paste the learning-coach instructions at the beginning of a conversation, followed by a small course-code excerpt and your question. Review any proposed change before copying it into Cloud Shell. A saved Gem is optional. The web chat does not automatically see your editor, files, or terminal results. If Gemini is unavailable, continue with the lecture, PHP Manual, and instructor support; paid AI access is not required.

Google's Cloud Shell Code Assist guide (opens in a new tab) describes the editor integration. The Gemini Learning Coach page supplies the course instructions to paste into either route; a saved Gem does not automatically configure the Cloud Shell extension.

Try a focused learning request

Use an example function from the lecture, rather than asking the tool to replace the entire application. Supply the field's actual rules.

I am practicing input validation in PHP. Here is my current function.
The field accepts whole-number quantities from 1 through 25.
Explain the current behavior, propose a small change if needed,
and explain each changed line. Give expected results for missing,
array-shaped, out-of-range, and valid inputs. Do not claim you ran tests.
Ask me to predict one result before revealing its expected value.

Before applying the proposal, explain what you expect to change. Inspect the diff in the Source Control panel, then run a syntax check on the changed file. For example, from the project folder:

Bash
php -l customer.php

The expected syntax-check output is No syntax errors detected in customer.php. A clean syntax check means PHP can parse the file; it does not prove the security fix works. Send the assignment's hostile input and a legitimate input to your own portal, record the actual results, and compare them with your prediction. A proposed test remains a proposal until you run it.

iKeep the record in your submission

Disclose the AI help, describe what you changed, and include your own evidence. Canvas submissions remain the lasting record of finished work.

Disable AI chat and inline suggestions during unaided assessments. Do not share real credentials, personal data, or protected assessment prompts. Ask before running a generated command you cannot explain, especially one that deletes files, installs tools, or tests another system. The lab's no-scanner rule still applies.

Rules Of Engagement

Read the dedicated Rules Of Engagement page before your first hands-on exercise. These are the rules to keep beside you while working:

  • Test only your own portal copy. Your course environment is the only system authorized for these exercises. Do not direct tests, payloads, or tools at another student's environment or another system.
  • Do not run scanners or attack tools in Cloud Shell, including against your own copy. Google's Cloud Shell terms prohibit network scanning. In Module 07, you analyze the supplied testing evidence packet.
  • Test fixes by hand. Send requests to your own portal through the browser or with curl, as shown on the Requests and Developer Tools page.
  • Follow the assignment's scope. Read its rules before testing. The Course Materials, Software & Technology Requirements page provides the course's lab-safety and authorized-use requirements.
