What this module is for

Since Module 08 your team has been designing a partner REST API for the TechCorp support portal. Each of you has been building it under api/ in your own portal copy. This module finishes both. The team brings the three sections of the design document, authentication, authorization and data, and operations, into one design that agrees with itself. Each of you finishes the running code and defends one decision you made.

The lecture does not add a new vulnerability class. It teaches how the controls you already know fit together in one request handler, and where the gaps between two working controls hide. It also shows how to write a safeguard, a verification plan, and a defense that another engineer can check.

The question this module answers

Can your team present one secure design whose sections agree, with each safeguard tied to the threat it answers and the request that proves it? And can you build the API it describes and defend a decision you made?

What you will be able to do

After Module 16 you can:

  1. Follow one API request through every control in order, and name the fact each control hands to the next.
  2. Find the seam between two controls that each work, and repair it.
  3. Tell a primary control from a supporting one, and say which is authoritative in the design document.
  4. Write a safeguard in four parts: the control, the point it is enforced, the threat it prevents, and the verification that shows it works.
  5. Write the verification plan: the hand-typed curl request for each safeguard and the result it should return.
  6. Reconcile a control that two sections of the design both describe, so one section owns it and the other points to it.
  7. Ground the threat model in the requirements memo and the term's incidents.
  8. State the risk that remains, and defend or concede one design decision against its strongest objection.

Before you start

  • Reread Module 02 lecture sections 3, 8, and 9 for the four questions of threat modeling, the secure-design principles, and residual risk. The design document opens with the first and closes with the third.
  • Reread Module 08 lecture section 5 on object-level access control. Reread Module 12 lecture sections 7, 9, and 11 on the API key, authorization on every endpoint, and errors that leak nothing. The lecture builds one handler from these.
  • Reread Module 14 lecture section 4 on safe error handling at one boundary; the forced-failure evidence depends on it.
  • Bring your team's design draft from Module 12 and the feedback you received on it. Bring your attribution table, and your own api/ build with the curl evidence you have so far.

Materials

  • The lecture page, which the quiz and the final assignment are written from.
  • OWASP Top 10:2025 and the OWASP Secure Product Design Cheat Sheet, the two required readings, linked in lecture section 1.
  • The Design Project Kickoff page in Module 08: the requirements memo, the feature menu, and the shape of the design document.
  • The Design Project Expectations page in Module 08: the weight split, the five criteria, and the evidence table.
  • The Requests and Developer Tools page in the Course Orientation module, for curl with and without a JSON body.
  • The Writing in Markdown page in the same module, for the build report.

Where you may run this

You build and test in your own portal copy in Cloud Shell, with curl typed at localhost:8080. There is no scanning. Your own environment is the only target you are authorized to test, and your evidence has to come from your own copy, not a teammate's.

When you are done

Module 16 is complete when you have submitted the quiz and your team has submitted the final design document: the threat model, three reconciled sections, four-part safeguards, the verification plan, and the attribution table. You also submit your own build report: your api/ endpoints with their curl evidence, and your decision under challenge on a safeguard you authored.
