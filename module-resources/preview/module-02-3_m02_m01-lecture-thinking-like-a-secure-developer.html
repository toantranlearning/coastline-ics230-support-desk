A customer orders two items, and the checkout calculates the right price. Another request sends a negative quantity, and the same checkout calculates a negative bill. Both requests run without an error. What rule did the developer leave out?

Secure development starts by deciding what the application must refuse. A working feature needs rules about who may use it, which values it accepts, and what happens when a dependency fails. This module introduces the concepts you use to explain those decisions: security objectives, trust boundaries, data flow, and secure design principles.

★The question behind a security review

What can a caller change, and which server rule prevents that change from causing harm? Behavior for a cooperating user establishes expected use; security review also examines misuse and failure.

2Why software security matters

When software fails at security, the failure is concrete. Someone reads a record they were never allowed to see. Someone changes a value they were never allowed to change. Someone takes a service offline that other people were counting on. A single sign-in query written without care can hand over an entire customer table. A credential left in a repository can open systems that repository never touched. The consequences can reach customers, staff, and others whose information the application holds.

It is tempting to assume that software which passes its tests is safe. Functional testing asks one question: does valid input produce the expected output? That question is necessary. It is not enough. Security asks the adversarial version of it. What happens with input that is hostile, oversized, repeated out of order, or sent by someone with no authorization to send it?

Here is a checkout step written exactly as its specification asked. The specification said: multiply the quantity by the price.

✕PHPVulnerable
<?php
// WHY: Casting to an integer does not enforce a positive quantity, so the calculation accepts values the business rule must refuse.
$price    = 49.99;
$quantity = (int)($_POST['quantity'] ?? 0);
$total    = $quantity * $price;

printf("Total due: %.2f\n", $total);

Vulnerable. Why: Casting to an integer does not enforce a positive quantity, so the calculation accepts values the business rule must refuse.

A cooperating user sends quantity=2. A hostile user sends quantity=-5. The code handles both the same way.

Output
Total due: 99.98
Total due: -249.95

▸Read the second line

The first request produces the right total, and the functional test passes. The second request produces a negative total, which could become an unauthorized credit if the application used this total to settle the order. The code did nothing wrong by its own specification. The specification never said the quantity must be positive. So the code is correct, and it is still not secure.

The word "correct" is more slippery than it looks. Correctness is measured against a specification. If the specification never described what the software must refuse to do for a hostile user, then the code can be completely correct and still be exploited. Nobody wrote down the rule it is breaking.

★Correct and secure are measured against different things

Correct means the implementation matches its specification. Secure means it holds up against someone actively trying to abuse it. When a specification leaves out hostile use, a correct program can still be an insecure one, and functional testing will report success the whole time.

The repair is to write the missing rule down and enforce it.

✓PHPSecure
<?php
// WHY: The server rejects missing, invalid, and out-of-range quantities before calculating a bill.
$price    = 49.99;
$quantity = filter_input(INPUT_POST, 'quantity', FILTER_VALIDATE_INT);

if ($quantity === false || $quantity === null || $quantity < 1 || $quantity > 25) {
    http_response_code(400);
    exit('Quantity must be a whole number from 1 to 25');
}

$total = $quantity * $price;
printf("Total due: %.2f\n", $total);

Secure. Why: The server rejects missing, invalid, and out-of-range quantities before calculating a bill.

!Passing every functional test does not mean the code is safe

Functional tests confirm that a feature works for a cooperating user. They say nothing about the hostile request, the oversized value, or the caller who was never meant to reach the feature at all. This is the check that gets skipped, and the gap it leaves is where incidents come from.

Security requirements are rarely present by default. They appear when someone deliberately sets out to write them. OWASP's Top 10 entry on insecure design says a secure design can still have implementation defects, and an insecure design cannot be fixed by a perfect implementation. Both halves matter: the rule has to exist, and the code has to enforce it.

OWASP Top 10:2025 A06 Insecure Design (opens in a new tab) is the source for the design-versus-implementation point above. PHP Manual: filter_input (opens in a new tab) documents the function in the repair, which returns false when the value fails the filter and null when the field is missing.

3The three security objectives

Security protects three properties of the data an application holds. Learn them by what happens when each one fails, because that is how you will recognize a failure in the wild.

★Confidentiality, integrity, and availability are what security protects

Every security control in this course exists to keep one of three promises. Only authorized people can read the data. It changes only through authorized actions. It is there when authorized people need it. These three are called the security objectives. The term appears in threat modeling and in every risk document.

◆Confidentiality, integrity, availability

Confidentiality is the requirement that information be readable only by authorized subjects. Integrity is the requirement that data and behavior change only through authorized actions. Availability is the requirement that authorized users can reach the service and the data when they need them. United States law (44 U.S.C. 3542, quoted by NIST) defines the three the same way: preserving authorized restrictions on access, guarding against improper modification, and ensuring timely and reliable access.

Confidentiality fails when someone reads what they had no authorization to read: another customer's record, a private profile, a session identifier, or a password hash. The controls that hold it up are authentication, authorization, encryption, and secret management. A fifth is the cheapest and the most often forgotten: before you store a value, ask whether the application needs it at all. Data you never collected cannot be stolen from you.

Integrity fails when data changes through an action nobody authorized. A payment amount is altered in transit, a balance is edited by the wrong person, or a dependency is swapped for a malicious copy. The controls are authorization, input validation, integrity checks, audit logs, and a deployment path that cannot be modified from outside it.

Integrity failures are usually found last. Picture a scale that has drifted out of calibration. It does not throw an error or refuse to weigh anything. It keeps working and returns a confident, wrong number, and everyone downstream treats that number as fact. An integrity failure behaves the same way. The application keeps running, so nothing prompts anyone to look.

Availability fails through resource exhaustion, a destructive change, an unhandled error in the wrong place, or a dependency outage that spreads. The controls are rate limits, capacity planning, timeouts, safe error handling, backups, and a recovery procedure that has been rehearsed. A recovery plan you have never rehearsed is a document, and a plan is something you have run.

The three are not separate boxes. Each one is load-bearing on its own: an application with excellent encryption and broken authorization is not partially secure. It is insecure. They also fail together. One query that pastes user input into SQL can be turned into each of these:

SQL
-- confidentiality: read every row
SELECT * FROM customers WHERE id = 7 OR 1=1;
-- integrity: change a value nobody authorized
UPDATE customers SET balance = 0 WHERE id = 7;
-- availability: remove the data
DROP TABLE customers;

Classify a finding as only an availability problem and you will tick that box and never report the other two.

iWhere the words come from

The three objectives are defined in federal law and used by NIST in every standard it publishes. When a risk document says "impact on confidentiality," it means this definition, and a CWE entry's "Common Consequences" table names which of the three a weakness breaks.

NIST glossary: confidentiality (opens in a new tab), NIST glossary: integrity (opens in a new tab), and NIST glossary: availability (opens in a new tab) give the statutory definitions quoted in the DEFINE block, each attributed to FIPS 200 and 44 U.S.C. 3542.

4Trust boundaries and untrusted input

A developer asks what a feature should do. A secure developer keeps going, and the extra questions are the substance of the discipline:

  • What can the user control?
  • What am I assuming, and what enforces that assumption?
  • Where does data cross from an area I do not control into one I do?
  • What is the worst request that still looks valid?
  • What happens after a control fails?

The third question locates most vulnerabilities, so it gets a name.

◆Trust boundary

A trust boundary is any point where data or control passes between areas with different levels of trust. The browser-to-server boundary is the first one that matters. Hidden form fields, cookies, headers, URL parameters, and every check that runs in the browser all sit on the far side of it, in territory you do not control.

▸A hidden price still crosses the boundary

Suppose a form contains a hidden field with a price of 49.99. A caller can replace that value before sending the request. The server must obtain the price from its own authorized product data, because hiding a field changes its presentation rather than who controls it.

Everything the browser sends to the server is composed by the client, and it arrives as structured text. Here is the request your browser sends when you sign in to your portal copy:

POST /login.php HTTP/1.1
Host: localhost:8080
Content-Type: application/x-www-form-urlencoded
Content-Length: 33

username=rmarsh&password=password

Four parts carry meaning: the method (POST), the path (/login.php), the headers, and the body. Every one of them was written by whoever sent the request. There is no hidden channel alongside this text. Nothing proves the request came from your page, your form, or your browser at all. If you want the server to know something, it has to be in that text, and anything in that text can be forged. A program such as curl sends a request like this without loading any page first; the Orientation page Requests and Developer Tools shows how.

That is why the place code runs decides what it can enforce. Server-side code, which is PHP in this course, runs on the server rather than in the caller's browser. Under normal operation, the caller cannot edit that server code through a form. Client-side code, the HTML and JavaScript you send, runs in the user's browser, on the user's machine, under the user's control. They can read it, edit it, disable it, or skip your page entirely and compose the request by hand.

Here is a form that limits a display name to eighty characters, and a server that believes the form.

✕PHPVulnerable
<?php
// WHY: The caller can bypass the form, so trusting its length check leaves the server rule unenforced.
// The form said: <input name="display_name" maxlength="80" required>
// so the server assumes the value is short and present.
$displayName = $_POST['display_name'];
save_display_name($displayName);

Vulnerable. Why: The caller can bypass the form, so trusting its length check leaves the server rule unenforced.

A request typed by hand never saw the maxlength attribute. $_POST['display_name'] can hold ten thousand characters, or an array, or nothing at all. The server has to check again, on its own side of the boundary.

✓PHPSecure
<?php
// WHY: The server checks presence, type, and character length because browser restrictions can be bypassed.
$displayName = $_POST['display_name'] ?? null;

if (!is_string($displayName) || $displayName === '' || mb_strlen($displayName, 'UTF-8') > 80) {
    http_response_code(400);
    exit('Display name is required and must be 80 characters or fewer');
}

save_display_name($displayName);

Secure. Why: The server checks presence, type, and character length because browser restrictions can be bypassed.

A check written in JavaScript guides a cooperating user and stops no attacker, because it runs on the attacker's computer. Client-side checks guide users. Server-side checks stop attackers. MDN says it the same way: never trust data passed to your server from the client, because a malicious user can alter the network request.

!The most common version of this mistake

Enforcing a rule where the user controls it, and then trusting the result on the server. A disabled button, a maxlength attribute, a hidden price field, a cookie that names the user's role, and a JavaScript pattern check are the same mistake wearing different clothes. The rule has to be enforced again on the server, where the user cannot reach it. MITRE catalogs the mistake as client-side enforcement of server-side security (CWE-602).

MDN: An overview of HTTP (opens in a new tab) names the parts of a request (method, path, headers, body) and says HTTP is stateless, which section 6 builds on. MDN: Client-side form validation (opens in a new tab) carries the warning quoted above. CWE-602: Client-Side Enforcement of Server-Side Security (opens in a new tab) is the formal entry. PHP Manual: mb_strlen (opens in a new tab) counts characters rather than bytes, which is why the secure example uses it.

5Source, sink, and flow

Your application is not the last stop for the data it receives. It passes that data onward to other interpreters. The database expects SQL. The browser expects HTML and JavaScript. Sometimes a shell expects a command, or a filesystem expects a path. Each of those is a separate language with its own parser, and each expects to receive a command. Suppose your code builds that command by pasting user input into a string. The parser on the far end cannot tell which characters came from you and which came from an attacker. It parses what it was handed.

◆Source, sink, flow

A source is where untrusted data enters, such as $_GET, $_POST, $_COOKIE, a header, or an uploaded filename. A sink is the operation that hands the data to an interpreter, such as a database query, an echo into a page, or a shell call. The flow is the path from the source to the sink, which is what you follow in a code review and what a taint analyzer automates.

Receiving input is not itself an injection vulnerability. The question is how the program uses that input at a sink. In code review, follow the value through assignments and function calls to find the control that keeps data separate from instructions.

★Injection is data reaching an interpreter that expects a command

Untrusted data flows into a sink with nothing enforcing the boundary. The interpreter on the far side reads part of that data as instructions rather than as a value. That is injection (CWE-74). MITRE's title for the entry says the same thing in its own words: improper neutralization of special elements in output used by a downstream component. The interpreter changes from one case to the next. The shape does not.

Here is the shape at its smallest, writing a name into a page:

✕PHPVulnerable
<?php
// WHY: Writing caller-controlled text directly into HTML allows the browser to interpret markup as page instructions.
$displayName = $_POST['display_name'] ?? '';
echo 'Welcome, ' . $displayName;

Vulnerable. Why: Writing caller-controlled text directly into HTML allows the browser to interpret markup as page instructions.

Submitted with Avery, this behaves correctly, which is the difficulty: it works, so nothing prompts a second look. Consider the illustrative input <script>steal(document.cookie)</script> in the same field. Here, steal is a hypothetical function, not a working test supplied by the course. The page sends this back:

Output
Welcome, <script>steal(document.cookie)</script>

▸Read what the browser sees, not what you meant

The source is $_POST['display_name']. The sink is the echo, which places the value straight into the page's HTML. The flow is the concatenation on the last line, and nothing guards it. The browser receives the response and parses it as HTML, the way it parses every page. It has no record of which characters you wrote and which the user supplied, so it reads <script>...</script> as a real script element and runs it. The value was never meant to be code. The browser treated it as code because it arrived in a place where code is allowed.

The repair is to decide what you accept, and then make the value inert for the place it is going.

✓PHPSecure
<?php
// WHY: Validation constrains the field and HTML encoding keeps accepted text from becoming markup at this output.
$displayName = $_POST['display_name'] ?? '';

if (!is_string($displayName) || mb_strlen($displayName, 'UTF-8') > 80) {
    http_response_code(400);
    exit('Invalid name');
}

echo 'Welcome, ' . htmlspecialchars($displayName, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');

Secure. Why: Validation constrains the field and HTML encoding keeps accepted text from becoming markup at this output.

Output
Welcome, &lt;script&gt;steal(document.cookie)&lt;/script&gt;

✓Validate the input, then encode it for its destination

Validation decides what you accept: here the value must be a string no longer than eighty characters, and anything else is refused. Encoding makes the accepted value safe for the interpreter that receives it. htmlspecialchars turns < into &lt;, > into &gt;, & into &amp;, and with ENT_QUOTES both quote characters into entities, so the browser shows those characters as text instead of reading them as a tag. This call is appropriate for HTML text and quoted ordinary HTML attributes. It is not a universal defense for JavaScript, SQL, or shell commands. Each destination needs its own safe mechanism, such as bound parameters for SQL. Validation and the destination control solve separate problems.

CWE-74: Injection (opens in a new tab) is the general weakness class, and its entry lists the specific kinds beneath it. PHP Manual: htmlspecialchars (opens in a new tab) documents each character the function converts and the flags. W3Schools: PHP htmlspecialchars() Function (opens in a new tab) has a live editor for trying the call. MDN: Website security (opens in a new tab) states the rule behind this section in one line: never trust data from the browser.

6Sessions, ambient authority, and the bearer credential

HTTP is stateless. RFC 9110 defines it that way: each request can be understood on its own, with no link to the request before it. PHP makes this concrete. A request arrives, the server runs your script from the top, builds the response, and discards everything in memory when the script ends. The next request starts from nothing.

A session supplies application state across requests. When you log in, the server generates an unguessable session identifier and stores your data under it. It hands the identifier to your browser in a Set-Cookie header. The browser sends the cookie on later requests that match its scope and delivery rules, and the server uses the identifier to retrieve the session. Domain, path, expiration, Secure, and SameSite settings affect when the cookie is sent.

You can watch this in your own portal copy. A request for the profile page with no cookie is turned away:

GET /profile.php HTTP/1.1
Host: localhost:8080
Response
HTTP/1.1 302 Found
Host: localhost:8080
Date: Thu, 08 Oct 2026 16:17:44 GMT
Connection: close
X-Powered-By: PHP/8.5.8
Set-Cookie: PHPSESSID=12518a0ed33bd8e99529499c4abcc7fe; path=/
Expires: Thu, 19 Nov 1981 08:52:00 GMT
Cache-Control: no-store, no-cache, must-revalidate
Pragma: no-cache
Location: login.php
Content-type: text/html; charset=UTF-8

The same request, carrying the PHPSESSID cookie that a successful sign-in produced, is answered with the page:

GET /profile.php HTTP/1.1
Host: localhost:8080
Cookie: PHPSESSID=3bfd7c12681bdf3a5f08d9dd1d5d9f6c
Response
HTTP/1.1 200 OK
Host: localhost:8080
Date: Thu, 08 Oct 2026 16:17:44 GMT
Connection: close
X-Powered-By: PHP/8.5.8
Expires: Thu, 19 Nov 1981 08:52:00 GMT
Cache-Control: no-store, no-cache, must-revalidate
Pragma: no-cache
Content-type: text/html; charset=UTF-8

▸What the two responses show

  1. The first request carried no cookie, so session_start() in the portal's auth.php began a fresh, empty session and sent its identifier back in Set-Cookie. The page found no signed-in user in that session and answered 302 Found with Location: login.php, which tells the browser to go to the sign-in page instead.
  2. The second request carried an identifier that a sign-in had already filled in. The server looked it up, found the user, and answered 200 OK with the profile. Nothing else about the two requests differed. The cookie was the whole difference.

That is the point to hold onto. An accepted active session identifier lets the server retrieve the signed-in identity. It does not replace permission checks for each operation, and it does not establish that the user intended that operation.

◆Bearer credential

A bearer credential is a credential that works for whoever presents it. RFC 6750 defines a bearer token this way: any party in possession of the token can use it in any way that any other party in possession of it can. The bearer proves nothing else. A session identifier is a bearer credential: the server checks possession, not the presenter. A stolen active identifier can let another caller impersonate the user until the session expires, is revoked, or another control prevents its use. Protecting that identifier is part of protecting the account.

The OWASP Session Management Cheat Sheet says the session identifier is temporarily equivalent to the strongest authentication method the application uses. Whoever captures it can fully impersonate the user.

◆Ambient authority

Ambient authority is authority that travels automatically with a request rather than being presented deliberately. The session cookie is the clearest example. When the cookie's rules permit delivery, the browser attaches it automatically. Delivery does not establish that the user deliberately requested the action.

A request that arrives carrying your valid session cookie is not proof that you intended it. The cookie can accompany a request when its delivery rules permit it. That includes a request triggered by another site's page, an image tag, or a form submitted by a script you never saw. The credential is valid. The intent behind the request is a separate question, and the cookie answers only the first one.

iThe attack that ambient authority makes possible

Cross-site request forgery (CWE-352) is ambient authority turned against the user. An attacker's page causes your browser to send a request to a site you are signed in to. If the cookie's delivery rules permit it, the browser attaches the cookie automatically. A server that treats a valid credential as proof of intent performs the action as you. MITRE's description of the weakness is that the application does not sufficiently verify whether a request was intentionally provided by the user who sent it.

✕A session identifier in a URL or a log is a credential in plain sight

Anyone who can read the identifier can present it, and the server will treat them as you. An identifier in a URL ends up in browser history, in bookmarks, and potentially in referrer information, depending on the referrer policy. An identifier written to a log file is readable by everyone who can read logs. Nothing fails and nothing warns. Keep the identifier in the cookie, and keep it out of anything you write down.

RFC 6750, section 1.2 (opens in a new tab) is the definition of a bearer token quoted above. OWASP Session Management Cheat Sheet (opens in a new tab) is the source for the equivalence between the identifier and the login. 7Principles of the secure developer

A handful of principles cover most secure-coding decisions. None of them is a rule you apply once. Each is a habit you carry into every feature.

  • Never trust input. Treat outside values as untrusted and check them before security-sensitive use, because their apparent source does not prove that they satisfy your rules.
  • Validate and encode. Validation decides what you accept. Encoding makes an accepted value safe for the interpreter that receives it. They answer different questions, and you need both.
  • Least privilege. Give each account and component the minimum access it needs. When something is compromised, its privileges are the ceiling on the damage.
  • Defense in depth. Assume any single control can fail, and place another one behind it. The second layer is what stands when the first is bypassed.
  • Secure defaults. The setting a system starts with should be the safe one. A user who changes nothing should get the protected behavior.
  • Fail securely. When something goes wrong, deny the action and reveal nothing useful, rather than falling open and letting the request through.
  • Keep secrets out of code. Passwords, API keys, and tokens do not belong in source files or anything you commit to a repository.
  • Security is a property of the whole system. Configuration, dependencies, identity, data storage, and deployment all decide whether a feature is safe. The function alone does not.

The last principle is why a flawless function can sit inside a vulnerable feature.

Two of these principles have a code shape that people get backwards. The first is failing securely. Here the role lookup returns null when the database is unreachable, and the test was written for the role being refused instead of the role being granted. Run with a stub lookup_role that returns null and a stub show_admin_page that prints one line, the two versions print what the Output blocks show.

✕PHPVulnerable
<?php
// WHY: A missing role differs from customer, so a negative role test can grant access during a lookup failure.
$role = lookup_role($userId);      // returns null when the database is down

if ($role !== 'customer') {
    show_admin_page();             // null is not 'customer', so the outage opens the door
}

Vulnerable. Why: A missing role differs from customer, so a negative role test can grant access during a lookup failure.

Output
admin page shown
✓PHPSecure
<?php
// WHY: Only an explicit admin role grants this operation; errors and unexpected values take the refusal path.
$role = lookup_role($userId);      // returns null when the database is down

if ($role === 'admin') {
    show_admin_page();
} else {
    http_response_code(403);
    exit('Forbidden');             // an outage denies access; it never grants it
}

Secure. Why: Only an explicit admin role grants this operation; errors and unexpected values take the refusal path.

Output
403 Forbidden

▸Trace the outage through both versions

  1. The database is down, so lookup_role returns null in both versions.
  2. In the vulnerable version, null !== 'customer' is true. The admin page is shown to everyone, with no error and no log line.
  3. In the secure version, null === 'admin' is false. The request is refused with 403 Forbidden. The outage still has to be fixed, and until it is, nobody gets in. MITRE names the vulnerable shape as not failing securely, or failing open (CWE-636).

The second is keeping secrets out of code. A credential typed into a source file runs fine and passes every test.

✕PHPVulnerable
<?php
// WHY: A credential in source can be exposed through repository access and history without a runtime error.
$apiKey = 'EXAMPLE_KEY_DO_NOT_USE';   // shipped in the repository forever

Vulnerable. Why: A credential in source can be exposed through repository access and history without a runtime error.

✓PHPSecure
<?php
// WHY: Loading configuration at runtime separates the secret from source; a missing key stops the operation rather than selecting an unsafe fallback.
$apiKey = getenv('TECHCORP_API_KEY');   // read from the environment at run time

if ($apiKey === false || $apiKey === '') {
    http_response_code(500);
    exit('Server configuration error');  // refuse to run without it; never fall back to a default key
}

Secure. Why: Loading configuration at runtime separates the secret from source; a missing key stops the operation rather than selecting an unsafe fallback.

✕A hardcoded secret produces no error and passes every test

A credential written into source code may produce no runtime warning. Anyone who can read the repository or its history may obtain it, including after the current file is changed. There is no failure to notice, which is why this one gets missed, and it can outlive every other control you put in place. MITRE's entry is use of hard-coded credentials (CWE-798). Read secrets from the environment or from a secrets manager at run time, never from the code itself.

The OWASP Secrets Management Cheat Sheet prefers a dedicated secrets manager and says environment variables are the fallback when a manager is not available. In this course's environment there is no secrets manager, so the portal's helpers read their keys from the environment, and the file that sets them never ships with the code.

✓The habit to carry

Write the test for the permission you are granting, and treat every other result, including an error, as a refusal. Read every secret from configuration at run time, and refuse to start without it. Give each component the least access it needs, and choose independent layers for important risks, because repeating the same assumption in two places leaves both exposed to the same failure.

PHP Manual: getenv (opens in a new tab) confirms the function returns false when the variable does not exist.

8How the profession names weaknesses

Security work has a shared vocabulary, and two references supply most of it. Learning to read them now means a scanner finding or an advisory is legible to you from the first module.

The OWASP Top 10 is an awareness and prioritization document. It ranks the risks that break web applications most often and gives each a shared name, so a team can talk about "broken access control" and mean the same thing. The 2025 edition runs from A01, Broken Access Control, through A05, Injection, to A10, Mishandling of Exceptional Conditions. It is a map of where to look. It is not a checklist that proves an application is secure, and addressing all ten categories does not establish that anything is safe.

◆CWE

The Common Weakness Enumeration is a community-developed list of common software and hardware weaknesses, maintained by MITRE, that gives each kind of weakness a number. Scanners, security advisories, and bug reports cite the number rather than spelling out the weakness, so reading the number lets you follow a finding straight to its definition.

The numbers form a family. The general injection class is CWE-74. Beneath it sit the specific kinds. SQL injection is CWE-89, improper neutralization of special elements used in an SQL command. Cross-site scripting is CWE-79, improper neutralization of input during web page generation. Here is an illustrative scanner finding, not a result from your portal:

[High] CWE-79 Cross-site Scripting (reflected)
  File: search.php, line 42
  Parameter: q
  Evidence: <script>alert(1)</script> returned unencoded in the response body

▸Reading the finding

The CWE number names the weakness, so you know what it means before you read another word. The file and line locate the sink. The parameter names the source. The evidence records the reported test and response. Raw markup alone does not prove that script executed; context and browser defenses matter. Whether this is a real vulnerability still has to be confirmed using the permitted methods, which section 9 takes up.

iThe two references do different jobs

A Top 10 category groups many weaknesses under one risk, so it tells you which kind of problem you are looking at. A CWE number names one weakness exactly, so it tells you what the finding is. A report that cites both has told you where it sits on the map and what it is.

CWE: About (opens in a new tab) is MITRE's own definition of the list. CWE-89: SQL Injection (opens in a new tab) and CWE-79: Cross-site Scripting (opens in a new tab) are the two entries named above. CWE Top 25 (opens in a new tab) lists the most common and impactful weaknesses as the profession currently ranks them, a companion to the Top 10 in section 1.

9The words you use to describe risk

A useful report distinguishes what was observed, what could happen, and what control is missing. These terms let another person evaluate that reasoning.

  • Asset: something worth protecting.
  • Threat: an actor or circumstance that can cause harm.
  • Vulnerability: a weakness that can be used to cause harm.
  • Exploit: a method that uses a vulnerability.
  • Control: a safeguard that prevents, detects, or limits harm.
  • Risk: likelihood combined with impact.
  • Attack surface: every reachable way to interact with the system.

Those terms connect into one chain. Every secure-coding decision links four things: an asset that has value, a threat actor with a goal, a weakness that creates a path to the asset, and a control that blocks or limits that path. Code appears nowhere in that chain by itself, which is the point of the last principle in section 7.

Here is the same observation written twice.

Loose:   "The search page is insecure."
Precise: "The search page (asset: customer records) reflects the q parameter
          unencoded (vulnerability, CWE-79). Anyone who can send a link
          (threat) can run script in a signed-in rep's browser (impact).
          Encoding the value at the sink (control) removes the path."

The second version names the asset, the weakness, who can use it, what they get, and what closes it. Someone can act on that. Nobody can act on the first.

Two of these terms are worth separating carefully. A vulnerability is a confirmed weakness. A scanner alert is a claim that one might exist, and it needs to be checked before you act on it. The OWASP Testing Guide says the same thing about tool output: review the findings carefully and weed out the false positives. In the same way, "we fixed it" is not "we verified it." The strongest evidence that a coding defense works is to re-run the original attack and watch it fail safely, where it used to succeed. A fix you have not re-tested is a claim about the code, and the re-run attack is the evidence for it.

!Reporting an alert as a vulnerability

A finding is a question that needs validation. A vulnerability is a confirmed weakness that can be used. Reporting the first as the second wastes the reader's time and your credibility, and it buries the real findings in a report full of noise.

✓Permission comes before a test

Follow the Orientation Rules Of Engagement before sending a security test. Course work is limited to your own authorized environment and permitted manual methods, because permission defines both the target and the activity. Written permission for an unrelated system does not expand the scope of a course assignment.

iUse the evidence in your incident report

Record the request, the actual response, the missing rule, and the result after a repair. Explain unknowns rather than filling them with guesses, because a reviewer must be able to distinguish an observed weakness from a suspected incident. The Orientation Incident Reporting Guide explains the course form and its relationship to industry guidance.

NIST glossary: vulnerability (opens in a new tab), NIST glossary: threat (opens in a new tab), NIST glossary: risk (opens in a new tab), and NIST glossary: attack surface (opens in a new tab) give the standard definitions; the risk entry says risk is a function of adverse impact and likelihood. OWASP Web Security Testing Guide: Introduction (opens in a new tab) is the source for the false-positive rule.

▸Separate potential impact from established harm

A changed identifier returning a protected record establishes unauthorized access in the test. It does not establish that an outside attacker accessed that record before your test. State the demonstrated failure and the available evidence separately, because response decisions depend on both.

10Common misconceptions

  • ✕"It runs on localhost, so the code is safe."

    Localhost limits who can reach the code today. It repairs nothing. Move the same code to a server and the weakness travels with it, unchanged.

  • ✕"The user cannot change a hidden field."

    Any value the client holds can be edited, or submitted without your page ever loading. The browser is the attacker's computer, and a hidden field is only hidden from a cooperating user.

  • ✕"Security means encryption."

    Encryption addresses specific confidentiality and integrity problems. Authorization, validation, safe configuration, logging, and availability controls are all still required. Encryption protects data; it does not decide who is allowed to ask for it.

  • ✕"If it passes its tests, it is secure."

    Functional tests confirm the feature works for a cooperating user. Correctness is measured against a specification, and a specification that never described hostile use cannot catch its abuse.

  • ✕"A valid session cookie proves the user meant to send the request."

    A browser can attach a cookie automatically when its delivery rules permit it. An accepted cookie establishes a session, not the user's intent to perform a particular action.

  • ✕"The OWASP Top 10 is a checklist that proves an application is secure."

    It is an awareness and prioritization document. Working through all ten categories tells you that you looked in the common places, not that nothing is wrong.

  • ✕"A scanner finding means there is a vulnerability."

    A finding is a claim that needs validation. A vulnerability is a confirmed weakness that can be used. Reporting the first as the second wastes the reader's time and your credibility.

!A repair needs an ordinary-use test too

Re-run the permitted reproduction and a valid request after changing a control. Refusing every request can stop the demonstration while breaking the feature, so verification must show that authorized work still succeeds.

11Check your understanding

Work these before you read the answers. The quiz draws on the same ideas.

  1. A page returns another customer's record after the id in the URL is changed. Which security objective is most directly broken, and what check was missing?
  2. Why is a value from a form untrusted even when the form used a dropdown that offered only three choices?
  3. HTTP is stateless, so how does the server know that this request came from someone who signed in a minute ago?
  4. What does it mean to call a session identifier a bearer credential?
  5. Your browser attaches the session cookie to a request that a different site's page caused you to send. Why does the browser do that, and what attack does it enable?
  6. What is the difference between a vulnerability and a scanner alert?
  7. Name the four parts of the chain that connects a secure-coding decision to the asset it protects.
  8. State the general definition of injection, and name one interpreter it can reach.
  9. Why is a check written in JavaScript not a security control?
  10. A role lookup returns null because the database is down. Write the one-line test that fails closed.
  11. What is the strongest evidence that a fix works?
  12. Where, in this course, may you run a test or an exploit?

Answers: (1) confidentiality, with a missing authorization check that confirms this user may read this record. (2) the request can be altered or built by hand and sent without your page, so the dropdown constrains nothing on the server. (3) the browser sends back a session cookie the server issued earlier, and the server looks the user up by that identifier, so an accepted active identifier retrieves the signed-in identity. (4) it works for whoever presents it; the server checks possession, not the presenter, so a stolen active identifier can allow impersonation. (5) the browser sends eligible cookies automatically. That ambient authority can enable cross-site request forgery when the server lacks an appropriate request-intent control; SameSite and other cookie rules affect delivery. (6) a vulnerability is a confirmed weakness that can be used; an alert is a claim that needs validation. (7) an asset with value, a threat actor with a goal, a weakness that creates a path, and a control that blocks or limits it. (8) injection is untrusted data reaching an interpreter that reads part of it as a command instead of a value; it can reach the database, the browser, or a shell. (9) it runs in the browser, on the user's machine, where the user can edit, disable, or bypass it. (10) if ($role === 'admin'), so that null and every other value are refused. (11) re-running the original attack and watching it fail safely where it used to succeed. (12) your own authorized course environment, using the methods permitted by the course Rules Of Engagement.
