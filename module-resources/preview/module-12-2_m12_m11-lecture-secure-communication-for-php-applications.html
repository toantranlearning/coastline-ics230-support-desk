A partner sends an API key to a service. The application may validate the key perfectly, but the connection also needs to protect the key and identify the intended server. This module explains TLS and the deployment decisions that surround it.

2What TLS protects, and what it does not

Module 10 protected data at rest, in the database. This module protects data in transit, while it moves between the browser and the server. The hard part of the module is knowing where that protection stops. OWASP files this family of failures under A04 Cryptographic Failures: data that should have been protected in transit or at rest was not, or the protection was weak enough to defeat.

HTTP is a plain protocol. MDN describes HTTP messages as readable by humans, and the request and the response travel as text over a TCP connection. Anyone who can see that connection can read a password or a session cookie exactly as it was typed. Sending sensitive data that way is cleartext transmission of sensitive information (CWE-319).

◆TLS and HTTPS

Transport Layer Security (TLS) is a protocol that wraps a connection so that the two ends can talk privately across a network they do not trust. HTTPS is HTTP carried inside a TLS connection. The HTTP request and response do not change. They travel encrypted.

Module 01 section 3 gave you the three security objectives. TLS gives you all three for the bytes on the wire, and only for those bytes. RFC 8446, the TLS 1.3 standard, states them this way.

  • Confidentiality. Data sent over the channel is visible only to the two endpoints.
  • Integrity. Data sent over the channel cannot be changed by an attacker without the change being detected.
  • Authentication. The server side of the channel is always authenticated. The client side is optionally authenticated.

★TLS protects the channel, not the endpoints

TLS makes the connection private and tamper-evident, and it proves the server's identity to the client. It says nothing about whether the data inside the connection is safe, and nothing about what the server does after it decrypts the request. The moment the request is decrypted, the headers, cookies, and body are ordinary input again, and every weakness from the earlier modules still applies.

Read each of these as a boundary. TLS does not do the following.

  • It does not decide whether a user may reach a record. That is authorization, from Module 08.
  • It does not validate input or encode output, so it stops neither SQL injection nor cross-site scripting.
  • It does not protect data after the server decrypts it, or data written to disk, which was Module 10.
  • It does not make a secret in a URL acceptable. A URL lands in browser history and server logs no matter how the request travelled.

iThe transport ends where your code begins

Module 01 section 4 drew the trust boundary at the edge of your application: the request's headers, cookies, and body are attacker-controlled input. TLS does not move that boundary. It protects those bytes while they travel and hands them to PHP unchanged, still untrusted. Server authentication is also not user authentication. TLS proves the server's identity to the browser. Proving the user's identity is your application's job, from Module 09.

RFC 8446, section 1 (opens in a new tab) states the three properties quoted above and says the server is always authenticated while the client is optional. MDN: Overview of HTTP (opens in a new tab) describes HTTP as a human-readable protocol sent over TCP, or over a TLS-encrypted TCP connection.

3SSL, TLS, and the versions you will meet

You will hear "SSL certificate," "SSL/TLS," and "TLS" used for the same thing. The names come from the protocol's history.

◆SSL and TLS

Secure Sockets Layer (SSL) was the original protocol that encrypted HTTP traffic. Its last version, SSL 3.0, was published by engineers at Netscape in November 1996. TLS is the name the IETF gave to the standardized successor. TLS 1.0 appeared in January 1999, and its RFC says the differences from SSL 3.0 "are not dramatic," though the two do not interoperate. Every version since has been TLS. SSL is the old name for the same job, and no version of SSL is safe to use.

Here is the line of versions, with the documents that introduced or retired each one.

Why the old versions were retired matters for reading an advisory. RFC 8996 explains that TLS 1.0 and 1.1 protect the handshake with a running SHA-1 hash, and neither version lets the two sides pick a stronger hash. The only fix was a newer version. RFC 7568 points to the long series of attacks on SSL 3.0 since 1996 and requires that it not be used.

★Use the maintained defaults, and turn the old versions off

The OWASP cheat sheet says web applications must default to TLS 1.3 and may support TLS 1.2 for compatibility, and that SSLv2, SSLv3, TLS 1.0, and TLS 1.1 must be disabled. Current web servers, proxies, and libraries ship with those defaults. A cipher list copied from an old article is how an application ends up running advice that expired years ago.

A phrase like "SSL certificate" is still common. The certificate is the same certificate TLS uses; the name is a leftover. When you read "SSL" in a product name or a log line, read it as TLS unless the context names a version.

RFC 6101 (opens in a new tab) is the historical record of SSL 3.0, dated November 18, 1996, written by Netscape engineers. RFC 2246 (opens in a new tab) is TLS 1.0, January 1999, and holds the "not dramatic" sentence. RFC 5246 (opens in a new tab) is TLS 1.2, August 2008. RFC 7568 (opens in a new tab) retires SSL 3.0 and RFC 8996 (opens in a new tab) retires TLS 1.0 and 1.1, with the SHA-1 reasoning. MDN: TLS glossary entry (opens in a new tab) says TLS was formerly known as SSL and that major browsers removed TLS 1.0 and 1.1 in early 2020.

4The TLS handshake

You will not write a handshake. You will read error messages and logs about it for the rest of your career, so learn its shape.

★The handshake builds one authenticated, encrypted channel before any HTTP moves

Before the first byte of HTTP is sent, the client and server agree on a version and a cipher suite, the server proves its identity with a certificate, and both sides derive the same secret keys. After that, every HTTP header and body travels encrypted and integrity-checked under those keys.

RFC 8446 describes the TLS 1.3 handshake in three phases. Read it as a sequence of messages.

  1. Key exchange. The client sends ClientHello: the versions and cipher suites it supports, and its share of the key agreement. The server answers with ServerHello: the choices it made and its own share. From this point both sides can compute the same keys, and every later handshake message is encrypted.
  2. Server parameters. The server sends the settings for the rest of the connection and, if it wants the client to prove its identity too, a CertificateRequest. On the web it almost never does, which section 7 picks up.
  3. Authentication. The server sends Certificate (its certificate chain), CertificateVerify (a signature over the whole handshake so far, made with the private key that matches the certificate), and Finished (a message authentication code over the handshake). The client checks all three, then sends its own Finished.

Then application data, your HTTP request, flows under the agreed keys.

▸What a browser does before it shows the page

  1. A user opens https://portal.example.com. The browser sends ClientHello offering TLS 1.3 and its cipher suites.
  2. The server answers ServerHello, picks a suite, and both sides compute the keys. The rest of the handshake is encrypted.
  3. The server sends its certificate for portal.example.com, the chain up to a certificate authority, and CertificateVerify.
  4. The browser checks the chain, the name, and the dates (section 5), and checks the signature against the public key in the certificate. If any check fails, the browser stops here and shows an error instead of the page.
  5. Both sides send Finished. Only now does the browser send GET / and it travels encrypted.

◆Session keys and forward secrecy

Session keys are the secret keys derived for one connection and discarded when it ends. They are not the server's long-term private key. Forward secrecy means that recording today's traffic and stealing the server's private key later does not let the attacker read the recording, because the session keys were never derived from that private key. RFC 8446 removed the key exchanges that lacked this property, so every TLS 1.3 connection has it.

You can read the result of a real handshake with curl. The -v flag prints what the client negotiated and what certificate it checked. Here is a trimmed run against Let's Encrypt's own site.

Bash
curl -sv -o /dev/null https://letsencrypt.org/ 2>&1 | grep -E "SSL connection|subject:|start date|expire date|issuer:"
Output
* SSL connection using TLSv1.3 / AEAD-CHACHA20-POLY1305-SHA256 / [blank] / UNDEF
*  subject: CN=letsencrypt.org
*  start date: Sep  4 14:34:32 2026 GMT
*  expire date: Dec  3 14:34:31 2026 GMT
*  issuer: C=US; O=Let's Encrypt; CN=YE2

The first line is the version and cipher suite the two sides agreed on. The next four are the certificate the client validated: the name it covers, the dates it is valid for, and who issued it. Those are the facts the next two sections are about.

RFC 8446, section 2 (opens in a new tab) is the protocol overview this section follows: the three phases, ClientHello and ServerHello, the optional CertificateRequest, and the Certificate, CertificateVerify, and Finished messages. Its section 1.2 says all handshake messages after ServerHello are encrypted and that static RSA and Diffie-Hellman suites were removed so every key exchange provides forward secrecy. MDN: Transport Layer Security (opens in a new tab) gives the same handshake in four plain steps and names encryption, integrity, and authentication as what TLS provides.

5Certificates and the chain of trust

The handshake proves the server holds the private key for the certificate it sent. The certificate is what ties that key to a name.

◆Certificate, certificate authority, chain of trust

A certificate is a signed data file that binds a public key to a name, such as portal.example.com, together with the dates it is valid for. A certificate authority (CA) is an organization that signs certificates, asserting that the key and the name belong together. Browsers and operating systems ship with a list of trusted root certificates. The chain of trust is the series of signatures from the server's certificate, through one or more intermediate certificates, up to one of those roots.

★A certificate is an identity claim, and the client checks the claim

The server can send any certificate it likes. The client decides whether to believe it, by following the signatures to a root it already trusts, by comparing the name in the certificate to the hostname it asked for, and by checking the dates. The security value is in those checks, not in the certificate's existence.

The client checks these things before it trusts the connection.

  • The chain. Each certificate is signed by the one above it, and the top one is in the client's trusted root list. Let's Encrypt describes the goal from the CA's side: the browser must be able to validate the signatures all the way up to a root it trusts. CAs keep the root's key offline and sign day-to-day certificates with intermediates, which is why there is a middle link at all.
  • The name. The certificate must cover the exact hostname the client requested. A mismatch is improper validation of certificate with host mismatch (CWE-297).
  • The dates. The current time must fall inside the validity period. Skipping this is improper validation of certificate expiration (CWE-298).
  • The signature. CertificateVerify from section 4 must check out against the public key in the certificate, which proves the server holds the matching private key.

The name check carries the most weight. Without it, a valid certificate for any domain at all would satisfy the connection, and an attacker holding a real certificate for their own site could stand in for yours. Here is what each failure looks like from curl, against test hosts that fail on purpose.

Bash
curl https://wrong.host.badssl.com/
Output
curl: (60) SSL: no alternative certificate subject name matches target host name 'wrong.host.badssl.com'
Bash
curl https://expired.badssl.com/
Output
curl: (60) SSL certificate problem: certificate has expired
Bash
curl https://self-signed.badssl.com/
Output
curl: (60) SSL certificate problem: self signed certificate

Each message is a check doing its job. The first certificate was real and trusted, and it was issued for a different name. The second was real and its dates had passed. The third was signed by nobody the client trusts.

◆Self-signed certificate

A self-signed certificate is one the server signed with its own key, so no certificate authority vouched for it. It encrypts the connection, and it establishes no identity a browser can verify, because a browser cannot tell it apart from an impostor's. It can support an isolated development demonstration after you configure your own machine to trust it. It is never an answer for a public host.

!A certificate warning in production is a signal, not an obstacle

A browser certificate warning reports that one of the checks above failed. In production that is a real failure to investigate: the wrong name, an expired certificate, a broken chain, or an attacker. Clicking through discards server authentication, which is the one property that stops interception. The correct response is to fail safely and find out which check failed.

MDN: Digital certificate (opens in a new tab) defines a certificate as a data file that binds a public key to an organization, most often signed by a certificate authority. MDN: Certificate authority (opens in a new tab) defines the CA and says browsers come preloaded with a list of root certificates that a site's certificate must chain back to. Let's Encrypt: Chains of Trust (opens in a new tab) shows a real root, intermediates, and end-entity certificates and says the root key is kept offline. CWE-297 (opens in a new tab) and CWE-298 (opens in a new tab) are the name and expiry checks as the profession names them.

6Certificate lifetime and automated renewal

Every certificate has a start date and an end date. The end date is not a formality. Section 5 showed that a client refuses an expired certificate, and it refuses it for everyone at once.

★Expiry is a control that fails closed, so renewal has to be automatic

A certificate that passed its end date is treated exactly like a forged one. Browsers show an error, API clients abort, and nothing on the server has to be broken for the whole service to be unreachable. The only reliable defense is renewal that runs by itself, well before the date, with monitoring that notices when it did not.

Let's Encrypt, the nonprofit CA that MDN names as widely used, issues certificates that are valid for 90 days by default, and it recommends renewing them at about the 60-day mark. Its integration guide puts the rule generally: renew when a third of the lifetime is left, which for 90 days means 30 days before expiry. The CA explains the short lifetime two ways: it limits the damage from a stolen key or a wrongly issued certificate, and it forces operators to automate, because nobody renews by hand every two months for long.

◆ACME

ACME is the protocol an ACME client on your server uses to talk to a certificate authority with no human in the loop. Let's Encrypt describes the two steps. First the client proves to the CA that the server controls the domain, by placing a file at a well-known URL on the site or by adding a DNS record the CA names. Then the client can request, renew, and revoke certificates for that domain. Certbot is the client Let's Encrypt recommends starting with.

The flow for a renewal is short.

  1. A timer on the server runs the ACME client, Let's Encrypt asks that it run at a random time of day.
  2. The client checks whether the certificate is inside its renewal window, a third of the lifetime remaining.
  3. If it is, the client proves control of the domain again, receives a new certificate, installs it, and reloads the web server.
  4. Monitoring checks the expiry date the server actually presents, the expire date line from section 4, and alerts a person when it is closer than the renewal window allows.

Step 4 is the one teams skip. An expired certificate is not detected by the renewal job that failed to run. It is detected by the first customer who cannot connect.

!Every certificate in the chain has a date

The intermediate certificates from section 5 expire too, on their own schedule. A client validating the chain checks every link, so an expired intermediate fails the connection even when the server's own certificate is current. Let's Encrypt publishes its intermediates and says they are likely to change, and tells ACME clients to fetch the current one with each certificate rather than hardcoding it. A long-lived device or service that ships with a fixed chain and no renewal path has a date on which it stops working.

✓The pattern to copy

Use short-lived certificates from a CA that supports ACME. Run the ACME client from a timer and let it renew when a third of the lifetime remains. Let the client fetch the current intermediate with each issuance. Monitor the expiry date the server presents, and alert on the whole chain, not only the leaf. Treat a manual renewal as a defect to automate.

Let's Encrypt: FAQ (opens in a new tab) states the 90-day default, the six-day option, the 60-day renewal recommendation, and the Certbot recommendation. Let's Encrypt: Integration Guide (opens in a new tab) gives the rule of renewing when a third of the lifetime remains, the randomized schedule, and the advice to fetch intermediates rather than hardcode them. Let's Encrypt: Why ninety-day lifetimes for certificates? (opens in a new tab) gives the two reasons. Let's Encrypt: How It Works (opens in a new tab) describes the ACME domain-control step and the two challenge types. The OWASP cheat sheet in section 1 says to consider ACME so systems request and update their own certificates.

7Client certificates and mutual TLS

Section 2 said the server is always authenticated and the client is optionally authenticated. This section is the option.

◆Client certificate and mutual TLS

A client certificate is a certificate the client presents so the server can verify the client's identity, the mirror of what the server does for the browser. Mutual TLS (mTLS) is a TLS connection in which both sides present a certificate and both sides verify the one they receive.

In the handshake from section 4, the server turns this on by sending CertificateRequest in the server-parameters phase. RFC 8446 says a server that authenticates with a certificate may optionally request a certificate from the client, and the client must then send its own Certificate and CertificateVerify. The server checks the client's chain against the CA it trusts for clients, which is usually a private CA the organization runs, not a public one.

★Mutual TLS authenticates a machine, not a person

A client certificate proves that whoever is connecting holds a particular private key. That suits one service calling another, or a partner's server calling your API, where the caller is a machine with a key file. It does not suit a human at a browser. MDN says client authentication is rare on the web outside specialized applications, and the OWASP cheat sheet says client certificates are rarely used in public systems and should be considered for high-value applications or APIs.

Your PHP code meets client certificates from the client side: when PHP calls another service that requires one. With curl, two options name the certificate and its key.

✓PHPSecure
<?php
// WHY: TLS peer and hostname verification bind the encrypted connection to the expected server identity.

$ch = curl_init('https://partner-api.example.com/orders');
curl_setopt_array($ch, [
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_SSLCERT        => '/etc/techcorp/client.crt.pem',   // our certificate, PEM format
    CURLOPT_SSLKEY         => '/etc/techcorp/client.key.pem',   // its private key
]);

$response = curl_exec($ch);
if ($response === false) {
    error_log('Partner API call failed: ' . curl_error($ch));
}

Secure. Why: TLS peer and hostname verification bind the encrypted connection to the expected server identity.

With PHP's stream functions the same two files go in the SSL context as local_cert and local_pk. In both cases peer verification stays on; presenting your own certificate never replaces checking the server's.

The private key file is a credential. It goes outside the web root, readable only by the account that runs PHP, and it is rotated like the keys in Module 10 section 12.

RFC 8446, section 4.3.2 (opens in a new tab) says a server authenticating with a certificate may optionally request a certificate from the client, and section 4.4.2 says the client must send its Certificate if and only if the server asked. PHP Manual: cURL constants (opens in a new tab) documents CURLOPT_SSLCERT as a PEM certificate file and CURLOPT_SSLKEY as its private key, beside the two verification options the next section uses. PHP Manual: SSL context options (opens in a new tab) documents local_cert and local_pk for stream clients.

8Certificate validation in outbound PHP calls

Your application is a TLS client whenever PHP calls another HTTPS service: a payment gateway, a partner API, a webhook receiver. The checks the browser runs in section 5 have to run in your code too. Skipping them is improper certificate validation (CWE-295).

★Encryption without identity is not security

A client that skips certificate validation still encrypts the traffic, so the code looks like it works. What it threw away is authentication, which means it can no longer tell the real server from a machine sitting in the middle of the path.

The temptation, when a certificate error blocks development, is to turn the check off. It appears in real codebases for exactly that reason.

✕PHPVulnerable
<?php
// WHY: Disabling certificate checks accepts an encrypted connection without authenticating the intended server.

$ch = curl_init('https://payments.example.com/charge');
curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);

// These two lines keep the encryption and throw away the identity check.
curl_setopt($ch, CURLOPT_SSL_VERIFYPEER, false);
curl_setopt($ch, CURLOPT_SSL_VERIFYHOST, 0);

$response = curl_exec($ch);

Vulnerable. Why: Disabling certificate checks accepts an encrypted connection without authenticating the intended server.

✕Disabling peer verification fails silently and defeats itself

Setting CURLOPT_SSL_VERIFYPEER to false, or verify_peer to false on a stream, produces no error and no warning. The call succeeds, the traffic is encrypted, and the code ships. From then on, anyone who can place themselves on the network path presents any certificate at all, and your client accepts it. The data is encrypted to the attacker.

▸How a skipped check becomes a machine in the middle

  1. Your PHP client opens a connection to what it believes is payments.example.com.
  2. An attacker on the path answers instead, with a certificate for a name they own, or a self-signed one.
  3. With verification on, the client compares the name, sees the mismatch, and aborts with the curl: (60) error from section 5.
  4. With verification off, the client accepts the certificate, derives keys with the attacker, and sends the card data encrypted to the attacker.
  5. The attacker decrypts it, reads it, and forwards the request to the real gateway, so nothing downstream looks wrong.

The repair is to leave both checks on. The manual says CURLOPT_SSL_VERIFYPEER defaults to true and CURLOPT_SSL_VERIFYHOST defaults to 2, so the safest version sets nothing extra. Writing them out makes the intent visible to the next reader.

✓PHPSecure
<?php
// WHY: Keeping certificate and hostname checks enabled rejects a peer that cannot establish the expected identity.

$ch = curl_init('https://payments.example.com/charge');
curl_setopt_array($ch, [
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_SSL_VERIFYPEER => true,   // the chain must lead to a trusted root
    CURLOPT_SSL_VERIFYHOST => 2,      // the name in the certificate must match the host
]);

$response = curl_exec($ch);
if ($response === false) {
    // A verification failure is the check working. Fix the trust store; do not bypass the check.
    error_log('Outbound TLS failed: ' . curl_error($ch));
}

Secure. Why: Keeping certificate and hostname checks enabled rejects a peer that cannot establish the expected identity.

!CURLOPT_SSL_VERIFYHOST is not a boolean

The manual lists its values: 2 checks that the certificate's name matches the hostname, 0 skips the check, and 1 "should not be used," with support for it removed in cURL 7.28.1. Passing true is the value 1. Use 2, or leave the default alone.

The stream functions, file_get_contents with an https:// URL and the like, have the same two switches with the same safe defaults: verify_peer and verify_peer_name are both true. If you must trust a private CA, point cafile at its certificate bundle instead of turning verification off.

✓PHPSecure
<?php
// WHY: Stream-context verification options preserve both trust-chain and hostname checks for the TLS peer.

$context = stream_context_create(['ssl' => [
    'verify_peer'      => true,
    'verify_peer_name' => true,
    'cafile'           => '/etc/techcorp/internal-ca.pem',   // trust our CA, keep the checks on
]]);

$body = file_get_contents('https://inventory.internal.example/stock', false, $context);

Secure. Why: Stream-context verification options preserve both trust-chain and hostname checks for the TLS peer.

✓The pattern to copy

Leave peer and hostname verification on for every outbound call, in curl and in streams. When a certificate fails, the fix is the trust store or the certificate, never the switch that turns the check off. To trust a private authority, add its CA certificate with CURLOPT_CAINFO or cafile. Log a verification failure and stop; do not retry with the check disabled.

PHP Manual: cURL constants (opens in a new tab) documents CURLOPT_SSL_VERIFYPEER (default true) and the three values of CURLOPT_SSL_VERIFYHOST. PHP Manual: SSL context options (opens in a new tab) documents verify_peer, verify_peer_name, allow_self_signed, and cafile, with their defaults. CWE-295: Improper Certificate Validation (opens in a new tab) is the weakness by name.

9What TLS means in your course environment

Everything above describes a server that terminates TLS itself. Your portal does not, and you need to know exactly what you can and cannot show from it.

scripts/start.sh starts the portal with php -S 0.0.0.0:8080 router.php. That is PHP's built-in web server, and it speaks plain HTTP. The PHP manual says the built-in server is meant to aid development, is not intended for production, and should not be used on a public network. Nothing in its documentation offers TLS.

You open the portal through Cloud Shell's Web Preview, at an address of the form https://8080-<your host>. Google's documentation says the preview works through a series of HTTP proxies, and that the ports are available only to the secure Cloud Shell proxy service, which restricts access over HTTPS to your user account only. The proxy holds the certificate and runs the handshake with your browser. It then forwards the request to your php -S process as plain HTTP.

★TLS ends at the proxy, so your code sees plain HTTP

Your browser's connection is HTTPS, to Google's proxy, with Google's certificate. The hop from the proxy to your PHP process is HTTP. The lock icon in your browser describes the first hop only. Your code can set the headers and cookie attributes that an HTTPS site must send, and your browser will honor them because the connection it sees is HTTPS. Your code cannot show you a handshake, a certificate, or a protocol version, because none of those happen in your process.

You can see the second hop directly. From the Cloud Shell terminal, a request to http://localhost:8080 goes to your process without the proxy, and PHP reports no HTTPS at all.

PHP
<?php
// https.php: what the PHP process knows about its own connection
var_dump(isset($_SERVER['HTTPS']));
Bash
curl http://localhost:8080/https.php
Output
bool(false)

The manual says $_SERVER['HTTPS'] is set to a non-empty value when the script was queried through HTTPS. Under php -S it is never set, whether the request came from the terminal or through the preview.

iWhat you can and cannot evidence from your portal

You can show the response headers your code sends, with curl -i in the terminal or in the browser's Network panel, and the attributes on the cookies your code sets, in the Application panel. The Orientation page Requests and Developer Tools shows both. You can show that your browser, on the HTTPS preview, sends a Secure cookie back. You cannot show a certificate your code presented, a TLS version your server negotiated, or an HTTP-to-HTTPS redirect at your server, because the proxy owns all three. Say so in your evidence rather than claiming them.

When TLS ends at a proxy, the application learns the original scheme from a request header such as X-Forwarded-Proto, which MDN describes as the de-facto standard header for the protocol a client used to reach a proxy or load balancer. In PHP it arrives as $_SERVER['HTTP_X_FORWARDED_PROTO']. It is a request header, and Module 01 section 4 settled what request headers are: client-controlled input. Trust it only when the only path to your process is through the proxy that sets it, and never when the process is reachable directly.

PHP Manual: $_SERVER (opens in a new tab) documents HTTPS and says the HTTP_* entries are built from request headers. MDN: X-Forwarded-Proto (opens in a new tab) documents the header.

10HTTPS for the whole application: redirects and HSTS

Protecting the sign-in page is not protecting the application. Module 01 section 6 named the session identifier a bearer credential, and the browser sends it on every request after sign-in. If any one of those requests travels over plain HTTP, the credential is in the clear, and the encrypted sign-in page did not help. The OWASP cheat sheet says it directly: TLS should be used for all pages, not only the sensitive ones such as the login page.

Redirect plain HTTP to HTTPS

On a server that terminates TLS itself, the first job is to send every plain request to the HTTPS address. There is a wrong way to build that redirect.

✕PHPVulnerable
<?php
// WHY: An omitted or misplaced response policy leaves the downstream browser behavior unrestricted.
// redirect.php: the destination host comes from a header the client sent.
$host = $_SERVER['HTTP_HOST'];
header('Location: https://' . $host . $_SERVER['REQUEST_URI'], true, 301);
exit;

Vulnerable. Why: An omitted or misplaced response policy leaves the downstream browser behavior unrestricted.

HTTP_HOST is the request's Host header, and a client can put anything in it.

Bash
curl -i -H 'Host: evil.example' http://localhost:8080/redirect.php
Response
HTTP/1.1 301 Moved Permanently
Location: https://evil.example/redirect.php

Your own server wrote a redirect to the attacker's site. Fix the hostname in code instead.

✓PHPSecure
<?php
// WHY: The explicitly selected response policy must be applied before headers are committed.
// redirect.php: the destination host is a constant, never read from the request.
$canonicalHost = 'portal.example.com';

if (empty($_SERVER['HTTPS'])) {
    header('Location: https://' . $canonicalHost . $_SERVER['REQUEST_URI'], true, 301);
    exit;
}

Secure. Why: The explicitly selected response policy must be applied before headers are committed.

Do not accept a sensitive request body over HTTP and then redirect. The body was already sent in the clear before your redirect ran.

HSTS

A redirect helps only after the first plain request has already gone out. HSTS closes that gap for every visit after the first.

◆HTTP Strict Transport Security (HSTS)

HSTS is a response header, Strict-Transport-Security, that tells the browser two things about this hostname for a stated number of seconds: reach it only over HTTPS, upgrading any http:// address before the request leaves the browser, and do not let the user click through a certificate error. MDN adds that HSTS identifies a host by its domain name only.

✓PHPSecure
<?php
// WHY: The explicitly selected response policy must be applied before headers are committed.
// Sent on every HTTPS response, before any output. Start with a short max-age.
header('Strict-Transport-Security: max-age=86400');

Secure. Why: The explicitly selected response policy must be applied before headers are committed.

Response
HTTP/1.1 200 OK
Strict-Transport-Security: max-age=86400
Content-type: text/html; charset=UTF-8

Three facts about the header decide how you deploy it.

  • It is learned over HTTPS only. MDN says browsers ignore the header when it arrives over plain HTTP, so that an attacker on the path cannot plant or expire a policy. That also means the very first visit, before the browser has seen the header, is not protected.
  • It is a commitment the browser keeps. For max-age seconds, the browser refuses plain HTTP to that host and refuses to let the user bypass a certificate error. You cannot recall it from a browser that already stored it. If HTTPS breaks during that time, the site is unreachable for those users.
  • includeSubDomains extends the rule to every host under the name. Add includeSubDomains only when every host under the domain, including the ones you forgot, serves HTTPS; until then, leave it out. A legacy status page or a vendor-hosted portal on a subdomain becomes unreachable for the full max-age otherwise.

Deploy it in stages. Make HTTPS correct and complete for the host. Publish a short max-age, a day, and watch for breakage. Raise it toward a year once you are confident. Consider the preload list last.

!The preload list is close to permanent

Browsers ship a built-in list of HSTS hosts so that even the first visit is protected. To be accepted, hstspreload.org requires max-age of at least 31536000 seconds (one year), includeSubDomains, the preload directive, and a redirect from HTTP to HTTPS. Its own page says removal takes months to reach users and tends to be slow and painful. Do not send preload as an experiment.

▸What the browser does with the header

  1. The user opens https://portal.example.com and signs in. The response carries Strict-Transport-Security: max-age=86400. The browser stores the rule for that hostname for one day.
  2. An hour later the user types portal.example.com into the address bar. The browser would normally try http:// first. It checks its HSTS store, finds the rule, and changes the address to https:// before sending anything. No plain request ever leaves the machine.
  3. On an airport network, an attacker presents a wrong certificate for the host. The browser refuses the connection and offers no button to proceed.
  4. After a day with no further visit, the rule expires, and the next visit behaves like a first one until the header is seen again.

In your course environment the preview hostname is a real HTTPS host to your browser, so a header you send through it is a real commitment for that hostname. Keep max-age short while you test.

MDN: Strict-Transport-Security (opens in a new tab) is the source for the header's meaning, the three directives, the rule that browsers ignore it over HTTP, the no-click-through behavior, and the first-visit weakness. OWASP HTTP Strict Transport Security Cheat Sheet (opens in a new tab) lists the threats the header addresses and warns that preload can have permanent consequences. HSTS Preload List Submission (opens in a new tab) states the four requirements and the slow removal. PHP Manual: header (opens in a new tab) says the function must be called before any output is sent.

11Cookie attributes that keep the session on HTTPS

HSTS tells the browser how to reach the host. The cookie's own attributes tell the browser how to handle the credential. Module 05 section 9 introduced Secure, HttpOnly, and SameSite, and Module 06 section 7 taught SameSite in full. This section is about Secure, the attribute that belongs to transport, and about where PHP's session cookie gets its attributes.

Here is where the portal stands. auth.php starts the session with session_start() and sets nothing about the session cookie, so the cookie carries PHP's defaults. The sign-in page's real response shows what that means.

Bash
curl -i http://localhost:8080/login.php
Response
HTTP/1.1 200 OK
Set-Cookie: PHPSESSID=28e223ae2afcd4e28730106a08e800d2; path=/
Cache-Control: no-store, no-cache, must-revalidate

No Secure, no HttpOnly, no SameSite. A session cookie that can travel over plain HTTP is a sensitive cookie in an HTTPS session without the Secure attribute (CWE-614). One that page script can read is a sensitive cookie without the HttpOnly flag (CWE-1004). auth.php also sets a second cookie by hand, setcookie('role', $account['role'], 0, '/'), with no attributes at all; the deeper problem with that cookie, a role the client can edit, was Module 08's.

PHP's session cookie is not created by a setcookie call you can find. session_start() creates it, and its attributes come from session_set_cookie_params(), which must run first. Here is a shared bootstrap for a different application, with all three attributes set.

✓PHPSecure
<?php
// WHY: Session cookie settings must be selected before session startup so the session cookie uses the intended policy.

// bootstrap.php: every page includes this before it does anything else.
session_set_cookie_params([
    'lifetime' => 0,        // a browser-session cookie; restoration may preserve it
    'path'     => '/',
    'secure'   => true,     // sent only over https:
    'httponly' => true,     // not readable by page script
    'samesite' => 'Lax',    // withheld on cross-site POST, Module 06 section 7
]);

session_start();

Secure. Why: Session cookie settings must be selected before session startup so the session cookie uses the intended policy.

Response
HTTP/1.1 200 OK
Set-Cookie: PHPSESSID=16a9034d8472e7e404caf385f48e5e1c; path=/; secure; HttpOnly; SameSite=Lax

◆The Secure attribute

Secure tells the browser to send the cookie only on requests made with the https: scheme. MDN adds one exception: the requirement is ignored on localhost, so development on your own machine still works. A Secure cookie never rides on a plain http:// request to the host, so even a request the browser was tricked into making over HTTP carries no session.

▸Reading the Set-Cookie line

  1. PHPSESSID=16a9... is the name PHP gives its session cookie and the identifier it generated.
  2. path=/ means the browser sends it for every path on the host.
  3. secure means the browser attaches it to https: requests only.
  4. HttpOnly means document.cookie cannot read it, so an injected script cannot copy it out, as Module 05 section 9 explained.
  5. SameSite=Lax means a cross-site POST does not carry it, as Module 06 section 7 explained.
  6. There is no Expires, so lifetime was 0: the cookie lasts for the browser session.

!The attributes must be set before the session starts

session_set_cookie_params() changes the next Set-Cookie PHP writes, and PHP writes it inside session_start(). Call the function after session_start() and nothing happens, with no error. Put the call in the one file every page includes first, so no page can start a session without it.

For a cookie you set yourself, setcookie() takes the same attributes as an options array, and the manual says the same thing about secure: it is on the programmer to send such a cookie only on a secure connection, and the samesite value None requires secure too.

✓PHPSecure
<?php
// WHY: Explicit cookie options restrict delivery and script access for this particular cookie.

// A "remember this device" cookie set by hand, for a different application.
setcookie('device_token', $token, [
    'expires'  => time() + 60 * 60 * 24 * 30,
    'path'     => '/',
    'secure'   => true,
    'httponly' => true,
    'samesite' => 'Lax',
]);

Secure. Why: Explicit cookie options restrict delivery and script access for this particular cookie.

iWhat Secure does in your course environment

Your browser reaches the portal over the HTTPS preview, so a Secure cookie is sent back on every request, and the portal keeps working. curl against http://localhost:8080 still receives the Set-Cookie line, because Secure is an instruction to the browser about when to send the cookie back, not a condition on setting it. The browser's Application panel shows the attributes on the stored cookie, which is the evidence that the flag is in place.

✓The pattern to copy

Set Secure, HttpOnly, and SameSite on every session cookie with session_set_cookie_params(), in the one file every page includes before session_start(). Set the same three on any cookie you create with setcookie(). Secure keeps the value off plain HTTP, HttpOnly keeps it from page script, and SameSite keeps it off cross-site requests. The three together keep the credential on the transport you intended.

PHP Manual: session_set_cookie_params (opens in a new tab) documents the options array with secure, httponly, and samesite, and says the function must be called before session_start(). PHP Manual: setcookie (opens in a new tab) documents the same keys for a hand-set cookie and the None requires secure rule. W3Schools: PHP setcookie() Function (opens in a new tab) is an independent walk-through of the secure and httponly parameters. MDN: Set-Cookie (opens in a new tab) defines Secure with its localhost exception, HttpOnly, and the SameSite values. CWE-614 (opens in a new tab) and CWE-1004 (opens in a new tab) are the two missing-attribute weaknesses by name.

12What HTTPS does not cover

A valid certificate and a Secure cookie do not make a page safe on their own. Three gaps survive them, and each leaks data the transport was supposed to protect.

Mixed content

An HTTPS page that loads a script, a stylesheet, an image, or a frame over plain HTTP has an unprotected part.

HTML
<!-- An HTTPS page loading its script over plain HTTP. -->
<script src="http://cdn.example.com/app.js"></script>

◆Mixed content

Mixed content is a page loaded over HTTPS that fetches some resource over HTTP. MDN divides it in two. Upgradable content, images, audio, and video set through src, is rewritten by the browser from http to https before the request is sent. Blockable content, everything else including scripts, stylesheets, frames, fonts, and fetch() calls, is refused outright.

A script delivered over HTTP could be replaced by anyone on the path, and it would then run with the page's full authority. That is why browsers block it, which usually turns the mistake into a broken feature rather than a breach. Load every resource over HTTPS and the question never comes up.

HTML
<script src="https://cdn.example.com/app.js"></script>

Caches

TLS protects data while it moves. It does not protect a copy saved afterwards in a browser cache or a shared proxy cache. Mark a sensitive response so no cache keeps it. MDN says no-store tells caches of any kind, private or shared, not to store the response.

✓PHPSecure
<?php
// WHY: The explicitly selected response policy must be applied before headers are committed.
header('Cache-Control: no-store');

Secure. Why: The explicitly selected response policy must be applied before headers are committed.

PHP's session layer already sends Cache-Control: no-store, no-cache, must-revalidate on pages that start a session, which is the line you saw in section 11's responses.

Secrets in URLs

A secret placed in a URL leaks in ways the transport cannot reach. The OWASP Session Management Cheat Sheet says a session identifier in a URL can be disclosed through web links, logs, browser history and bookmarks, the Referer header, and search engines. The same is true of a reset token or an API key. Keep secrets in the request body or in a header, never in the path or the query string.

MDN: Mixed content (opens in a new tab) defines the term, the upgradable and blockable categories, and current browser behavior. MDN: Cache-Control (opens in a new tab) defines no-store. OWASP Session Management Cheat Sheet (opens in a new tab) lists the places a URL-carried identifier leaks and states the three cookie attributes as requirements.

14Common misconceptions

  • ✕"The lock icon means the application is secure."

    It speaks to the transport and the server's identity. Every application flaw in this course works over a valid HTTPS connection.

  • ✕"SSL and TLS are different technologies."

    TLS is the standardized successor to SSL and does the same job. Every current version is TLS; every version of SSL is retired.

  • ✕"Encrypt the sign-in page and you are done."

    The session cookie travels on every request after sign-in, so every page has to be HTTPS, and the cookie has to carry Secure.

  • ✕"A self-signed certificate means there is no encryption."

    It encrypts. What it lacks is a chain to a trusted root, so it establishes no identity a browser can verify.

  • ✕"A certificate that was valid when we shipped stays valid."

    Every certificate in the chain has an end date, and a client refuses an expired one as firmly as a forged one.

  • ✕"Users can click through a certificate warning if they know the site."

    Clicking through discards server authentication, which is the property that stops interception.

  • ✕"Disabling certificate verification is fine for an internal service."

    It removes authentication on the internal network, where a machine in the middle is still possible. Point the client at the internal CA instead.

  • ✕"HSTS will fix our broken HTTPS."

    HSTS commits browsers to HTTPS. If HTTPS does not work, it commits them to an outage.

  • ✕"Our portal runs under HTTPS, so our code handled TLS."

    The proxy handled TLS. The code set the headers and cookie attributes an HTTPS site needs, which is a different and real contribution.

  10. Why is includeSubDomains in an HSTS header a decision that is hard to undo?
  11. In your course environment, which three things about TLS can you not evidence from your own portal, and why?
  12. An HTTPS page loads a script over HTTP. Why is that unsafe, and what do current browsers do about it?

Answers: (1) confidentiality, integrity, and server authentication; it does not authorize a user, does not validate input or encode output, and does not protect data after decryption or at rest. (2) TLS is the IETF's standardized successor to Netscape's SSL and does the same job; default to TLS 1.3, allow 1.2 for compatibility, and disable SSL 2, SSL 3, TLS 1.0, and TLS 1.1. (3) Certificate carries the server's certificate chain, CertificateVerify proves the server holds the private key for it by signing the handshake, and Finished proves the whole handshake arrived unchanged. (4) without it any valid certificate for any domain would satisfy the connection, so an attacker with a certificate for a site they own could impersonate yours. (5) automated renewal when a third of the lifetime remains should have prevented it, and monitoring of the expiry date the server presents should have detected the renewal that did not happen. (6) it provides no chain to a trusted root and so no verifiable identity, so a browser cannot tell it from an impostor's certificate. (7) one machine calling another, such as a partner server calling an API, where the caller holds a key file; not people at browsers, where client certificates are rare. (8) authentication is lost while encryption remains, so an attacker on the path presents any certificate, the client accepts it, and the attacker decrypts, reads, and forwards the traffic. (9) the browser sends the cookie only on https: requests, so it never travels in the clear; for PHP's session cookie set it in session_set_cookie_params() before session_start(). (10) it binds every subdomain, including forgotten ones, and browsers keep the stored policy for the full max-age, which you cannot recall. (11) the certificate, the negotiated TLS version, and an HTTP-to-HTTPS redirect at the server, because Cloud Shell's proxy terminates TLS and php -S speaks plain HTTP. (12) a script over HTTP could be replaced on the path and would run with the page's full authority, so browsers block it as blockable mixed content.
