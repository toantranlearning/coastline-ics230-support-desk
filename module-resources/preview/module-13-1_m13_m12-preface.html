What this module is for

Module 08 gave you HTTP, REST, and the API-key pattern, and your team has been designing and building the partner API since the kickoff. This module puts the whole API together: how a request reaches an endpoint through router.php, how a JSON body is read without trusting it, how a key is traded for a short-lived token with a scope, and how every endpoint decides which rows a caller may touch.

Authentication, scope, and ownership are three different questions. A key says which partner is calling. A scope says which class of action the token may perform. The ownership rule in the query says which rows belong to this caller. An endpoint asks all three, in that order, on every request.

There is no incident this module. The graded work is the design project's draft: your team assembles the design it has grown since the kickoff, with each member's build so far and its curl evidence, into one document.

The question this module answers

What does an endpoint have to check, in what order, before it does any work, and how do you show each check holds?

What you will be able to do

After Module 12 you can:

  1. Send a request with a JSON body using curl and read the status line that comes back.
  2. Explain how router.php turns /api/customers/7 into a script and a PATH_INFO.
  3. Read an untrusted JSON body with a content-type check, a size limit, a depth cap, and a thrown parse error.
  4. Authenticate a partner by the hash of its API key, and trade the key for a signed token that carries a partner id, a scope, and an expiry.
  5. Apply the three gates, authentication, scope, and ownership, and answer 404 for a row the caller does not own.
  6. Refuse fields a caller may not set, and explain mass assignment.
  7. State what CORS decides and what it does not, what a rate limit and a pagination cap protect, and why a destination allow-list beats a block-list.
  8. Assemble your team's design increments and each member's build in progress into one draft, and name what is still owed.

Before you start

  • Reread Module 08 lecture sections 9 and 10 if the request, the response, the status codes, or the API-key pattern are not yet automatic. This module builds on both.
  • Reread Module 10 lecture section 9 for what hmac_sign and hmac_verify do. The token in this module is signed with them.
  • Start your portal in Cloud Shell and keep it running while you read. Every curl command on the lecture page is one you type yourself.
  • Have your team's design increments since the kickoff and each member's api/ work at hand before the assignment.

Where you may run this

You write code and send requests this module, in your own portal copy in Cloud Shell. Every request is a curl command you type by hand at localhost:8080. The seeded key demo-key is the only credential you use. Your own environment is the only target you are authorized to test; the Working in Google Cloud Shell page states the rule on scanners.
