What this module is for

Module 01 gave you the words session cookie, bearer credential, and ambient authority. The browser attaches your session cookie to every request bound for the portal, whether or not you meant to send it. This module is where that habit becomes an attack, and where you build the control that stops it, on real code: the add-note form in your own course environment.

A valid session proves the sender, not the intent. Authentication answers who is signed in. Authorization answers whether that account may act on the object. Cross-site request forgery is the request that passes both checks and was never intended by the person whose browser sent it. The control is a value another page cannot read or set, checked on the server before anything changes.

QA filed one ticket against the call-notes feature. A note appeared on a customer account that no rep remembers writing, filed under a rep's own display name. The add-note form on notes.php carries nothing that proves the request came from the portal's own page. Any request that carries the rep's session is accepted. You reproduce that on your own environment, then make the form carry a proof another page cannot supply.

The question this module answers

Why can a browser send an authenticated request the user never intended, and how does the server require proof of intent?

What you will be able to do

After Module 06 you can:

  1. Explain why the browser attaches the session cookie by destination, and why that makes a forged request authentic to the server.
  2. Say which of the three questions (who, may they, did they mean to) a session cookie does not answer.
  3. Keep every state change off GET, and say why changing GET to POST is a prerequisite and not the fix.
  4. Implement a synchronizer token as one shared check that every POST handler calls, verified with hash_equals before any database work.
  5. Set SameSite and HttpOnly on the session cookie, and state what each covers and does not cover.
  6. Say why an origin check supplements the token, and why cross-site scripting defeats every CSRF defense.
  7. Prove a token-less request is refused while the portal's own form still works.

Before you start

  • Reread Module 01 lecture section 6 on sessions, ambient authority, and the bearer credential. This module assumes all three.
  • Reread Module 03 lecture section 6 on encoding a value for an HTML attribute, and section 8 on why == is the wrong comparison. The token lands in a hidden field and is compared on the server.
  • Reread Module 05 lecture section 9 on cookie attributes. This module sets two of them.
  • Sign in to your course environment as rmarsh, open a customer account, and follow Call notes for this account to notes.php. You will watch the browser send an authenticated request nobody intended before you write anything.

Materials

Where you may run this

You change code this module, in your own course environment. The only requests you send are typed by hand at your own portal, with curl in the Cloud Shell terminal and with the portal's own form in the browser. You build no page on another site and host nothing. Your own environment is the only target you are authorized to test; the Working in Google Cloud Shell page states the rule.
