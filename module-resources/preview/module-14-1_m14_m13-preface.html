What this module is for

Module 01 gave you the stance: do not trust what the client sends, and limit what the client can do. This module applies both halves at deployment time, on real code: the document upload and the page shell in your own course environment.

A response header is a second layer. Upload handling is a fix. A header takes a decision the browser was going to make on its own, such as whether to run a script or allow a frame, and makes it for the browser. It shrinks what a mistake in a page can do; it does not repair the mistake. An uploaded file is different. Its bytes were chosen by the sender, and if they land in a folder the server runs code from, the sink is your own server. The controls that close that sink are the fix.

A rep attached a .php file to a customer record by mistake and the server ran it. You own that incident, and the headers no page of the portal sends.

The question this module answers

How do response headers constrain what the browser does with your page, and how do you keep an uploaded file from becoming code on your server?

What you will be able to do

After Module 13 you can:

  1. Read a response and say which security headers are missing, and why the response is the only evidence.
  2. Write a Content Security Policy from an inventory of what a page loads, stage it in report-only mode, and name which directives do not fall back.
  3. Send frame-ancestors, X-Frame-Options, nosniff, a Referrer-Policy, and Strict-Transport-Security with the values the lecture gives, from one function, before any output.
  4. Trace an upload as source, trust boundary, sink, and interpreter, and name the three claims a client makes about a file.
  5. Validate an upload by its bytes against an allow-list map, cap its size, generate its stored name, store it outside the web root, and serve it through a handler that authorizes every request.
  6. Prove that a .php upload is refused while a real PDF still attaches, and that the headers are present.

Before you start

  • Reread Module 01 lecture section 5 if source, sink, and interpreter are not yet automatic. The upload trace uses all three.
  • Reread Module 03 lecture section 4 on allow-lists, and Module 05 lecture section 8, where the policy and the nonce were introduced. This module teaches the rest of the header.
  • Sign in to your course environment as rmarsh, open a customer record, and open its documents on upload.php. You will attach a file before you change anything.

Materials

  • The lecture page, which teaches everything the quiz and the assignment need.
  • OWASP A02 Security Misconfiguration, the OWASP File Upload Cheat Sheet, the OWASP HTTP Headers Cheat Sheet, and the CLARK Deployment-time Defenses slides, the four required readings.
  • upload.php, the document upload from Sprint 17, and layout.php, whose page_header() opens every page, in your course environment.
  • The TC-IR-01 Form and Worked Example page in the Course Orientation module.

Where you may run this

You change code this module, in your own course environment. The only hostile input you create is the one-line proof file the assignment specifies, attached through the portal's own form, and only there. Do not write anything that takes a parameter, runs a command, reads a file, or opens a connection. Your own environment is the only target you are authorized to test.
